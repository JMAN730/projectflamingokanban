## Original body

While testing VIctory’s graphics on my RTX 5090, I found two texture layouts where the calculation in `crates/victory-gpu/src/resource.rs` disagrees with Windows Direct3D 12. I tested main at `d2a4bae` on Windows 11 build 26300.9974, NVIDIA driver 621.24.

| Input | VIctory calculation | Native D3D12 |
| --- | --- | --- |
| 10×6 texture, mip 1 (5×3), DXGI 68 or 69 | 5 texels in the footprint, 10 bytes per row | 6 texels in the footprint, 12 bytes per row. These formats store two texels per four-byte word. |
| 10×6 RGBA8, first two mips, base offset 1 | Offsets 512 and 2048, total 2579 bytes | Offsets 1 and 1537, total 2068 bytes. At base zero the offsets are 0 and 1536, and the total stays 2068. |

Across 576 queries, the original calculation differed from native D3D12 in 402 cases. The revised calculation matched all 576. These were layout queries. I didn’t submit an unaligned GPU copy.

**To reproduce**, download the complete folder, extract the graphics-test ZIP inside, and run `pwsh -NoProfile -File .\footprints\Verify-Footprints.ps1` in 64-bit PowerShell 7 on Windows. The recorded output is in `footprints/results.txt`. The ZIP includes the proposed patch and Rust regression tests.

The complete folder also contains the separate RTX 5090 and AMD Radeon pixel tests from PR #89. All 17 standalone programs passed locally. The patches applied to the tested main revision and PR #89 at `081afbd`. I haven’t compiled the patched VIctory crate or tested GTA VI gameplay.

So the base-offset change is confirmed on a second host, and the 68/69 change matches the table but needs your Windows/pwsh result (or a Windows D3D12 host) for the host-side confirmation. No other test changes were needed.
