### Comment 5 — @rouges78 — 2026-11-24T08:55:22Z

Code-reading data point, with two defects reproduced on hardware. No title run behind any of this (I have no dump on this machine yet), so I can't say it changes the device loss.

Setup: RTX 4080, Windows 11, main at 6af0fae.

**1. The indirect budget wraps (reproduced).** In `indirect.rs` every record adds its cost to the list's budget word with a plain 32-bit `InterlockedAdd`, rejected records included. 64 garbage draw records of 2^26 bring the word back to zero and work is let in again. Running the clamp alone over 128 all-ones draw records (kind 0, stride 16) and reading the buffer back: 4 records stay live and the budget word reads 0; the design says 2 and 2^27.

**2. A compare-exchange reservation is not the fix (also reproduced).** I first replaced the add with a saturating `InterlockedCompareExchange` loop, still 64 threads per group. It passes the garbage cases, but with 65,536 records of one vertex instance each (all fit) the retries grow with the record count and the device was removed three runs out of three, with three nvlddmkm event 153 entries. Noting it so nobody else takes that route. What works here is one thread walking the records in order with a saturating count: about 27 ms for 65,536 records, 0.4 s for 2^20, so it needs a cap on records per execution (or a count-buffer-aware clamp).

**3. A failed dynamic table still runs its draw.** In `draw.rs`, when `host.dynamic(n)` returns `None`, `tables()` continues and `bind()` passes the title's own table offset, which on a capped heap is past the host's. Exhaustion warns once, but `n > DYNAMIC` returns `None` with no warning at all (`descriptor/host.rs`, top of `dynamic()`), so a log without "no free dynamic descriptor slots" does not show the fallback was not taken. That may matter for the runs above where the warning was gone and the device was still lost. A root view the title did not set is skipped the same way and the command still runs.

**Update:** main has since fixed the dynamic-slot part of this (3c81420: a table that gets no dynamic slots, for either reason, now drops its draw). The root view case is unchanged on main.

**4. The loop limit does not bound nested loops.** On a conditional back edge the limit is folded into the branch condition, so a capped lane leaves by the loop's ordinary exit and keeps running, and the counter restarts at each entry. Two nested loops can still do 2^20 x 2^20 iterations per lane. The comment on `LOOP_LIMIT` says the lane leaves the program, which is only true for an unconditional back edge.

Branch with three commits: https://github.com/rouges78/VIctory/tree/fix/597-bounded-indirect-and-bindings (the serial clamp with tests that run on the real device, where the wrap test fails on the current shader; dropping draws and dispatches whose table or root view cannot be bound; the comment fix). The second one drops commands that run today on an unset binding, and I have not run the menus with it. Happy to open PRs for whichever of these is wanted, the budget fix first since it stands on its own.

**Edit:** the budget fix alone, on current main (one commit, CI commands pass locally): https://github.com/rouges78/VIctory/tree/fix/indirect-budget-wrap. Opening a PR is refused for my account right now, so it stays a branch until that changes. #583 and #242 fix the same wrap with a compare-exchange loop and also read the count buffer, which this does not; I tested my own loop, not theirs, and the test `records_within_the_budget_all_run` on that branch is the case to run against them.

### Comment 7 — @rouges78 — 2026-11-24T11:33:37Z

@rpmaster2 your "page fault ... inside freed texture" runs match a lifetime gap I found reading current `main` (ffe310e). It is untested against the title (I have no dump here), so I would be glad if you could A/B it with your 480 s procedure.

**What I think happens.** Translated shaders index the host descriptor heaps directly, and lists hold only the textures they transition, so a texture read only through a heap slot is kept alive by that slot alone (`HostHeap::kept`). `Host::execute` waits for the GPU holding only its own lock; meanwhile other title threads keep recording, and `mirror` nulls the slot of a released texture (or remakes a changed one) and drops its last reference. The running submission may already have read the old descriptor, so it reads freed memory. The `a title texture was released while a list not yet reset names its host copy` line is the protected case (a list holds the copy), not the fault itself.

A second, related gap: the title's descriptor heap owns its host heap outright, and lists keep only the `ID3D12DescriptorHeap`. If the title releases a heap before submitting a list that binds it, the references its slots held go with it.

**Branch:** https://github.com/rouges78/VIctory/tree/fix/heap-slot-lifetime (two commits on ffe310e, CI commands pass locally, a test for each on an RTX 4080):
1. a slot's previous resource lives until the next submission starts;
2. lists hold the host heaps they bind until reset.

To try it:

```
git fetch https://github.com/rouges78/VIctory fix/heap-slot-lifetime
git switch --detach FETCH_HEAD
cargo build --profile diag -p victory --features diagnostics
```

**What would settle it:** 5 runs of `main` and 5 of the branch, diag build, `VICTORY_D3D12_DRED=1`. Diagnostics builds of the branch log two counters:
- `a heap slot let go of a resource while a submission ran` (fix 1's case);
- `a descriptor heap was released while a list not yet reset names it` (fix 2's case).

If the removals stop and the first counter grows, this was it. If the counters stay at zero and the removals stay, this rules the idea out.

Not covered: rewriting a descriptor that a running submission may read is still outside D3D12's rules (this only keeps the memory valid), and aliasing and UAV barriers still name resources without holding them.

On the fault with no freed node, one thing about how to read the line. `shadow::near` prints the closest title memory copy starting *below* the address and never checks that the address is inside it. So "offset 0x670000" means inside only if it is smaller than the `+len` printed just before it. If the line has no `inside [...]` list either, the address is in no live allocation and no recently freed one, which is what a read past the end of that copy looks like.

There is a path in `main` that can produce that. `root_view` in `draw.rs` binds root CBVs and SRVs by address alone: it finds the copy holding the first byte and passes its host address to `Set*RootShaderResourceView` / `Set*RootConstantBufferView`. D3D12 does no bounds check on root descriptors, so a shader that indexes beyond the end of the copy reads unmapped host memory. On the console the same read lands in whatever title memory follows, so it would be harmless there. I have not confirmed this is what happens; it is a reading of the code.

The log can settle it without another run, if you still have the removal line of fix run 3 (or main run 2):
1. the full `nearest title memory copy below it: START+LEN at host GPU, offset 0x670000` part, with the `nearest above` part and any `inside [...]` list;
2. for the stopped draw or dispatch, the `rootN=ADDR host (GPU, LEFT)` entries.

If the fault address is one of those `GPU` values plus something at or beyond its `LEFT`, it is a root view read past the end of its copy. If the offset is below `LEN`, the address is inside a live copy and this idea is wrong too.
