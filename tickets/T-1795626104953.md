</html>## Problem

On upstream `ffe310e`, a draw or dispatch requiring multiple fresh descriptor tables can successfully allocate some tables before another allocation fails.

Although `State::bind()` subsequently rejects the operation, the successful allocations remain in `fresh_tables` and `dynamic` until the command list is reset or released.

These reservations are not necessarily permanent waste because subsequent operations may reuse them. However, under descriptor pressure, unrecovered reservations may contribute to further allocation failures and amplify heap exhaustion.

## Technical analysis

Affected file: `crates/victory-gpu/src/draw.rs`.

- [[State::bind — operation rejection](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs#L459-L473)](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs#L459-L473)
- [[State::tables — descriptor reservation and retention](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs#L726-L737)](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs#L726-L737)

The current allocation path allows partial reservations to survive an unsuccessful bind.

### Synthetic example

Consider an eight-slot dynamic heap with two occupied slots:

1. A draw requests two fresh tables requiring four and three slots.
2. The first allocation succeeds.
3. The second allocation fails.
4. The draw is rejected, but four newly reserved slots remain occupied.
5. A subsequent operation requiring six contiguous slots cannot allocate them.

With transactional reservation, the unsuccessful operation would leave the original six free slots available.

This is a synthetic allocator-level example, not a measured in-game workload.

## Proposed investigation

Before changing allocator behavior, I developed an opt-in diagnostic patch to quantify:

- New descriptor reservations.
- Reservations originating in rejected binds.
- Reservations subsequently recovered through accepted cache hits.
- Outstanding unrecovered reservations.
- Peak unrecovered reservations within a command list recording.
- Allocation failures occurring while earlier unrecovered reservations exist.
- Failed allocation size distributions.

The diagnostic patch preserves existing allocation behavior, cache semantics, descriptor lifetimes and bind return values.

Enable it using:

`VICTORY_DESCRIPTOR_ADMISSION=1`

If unrecovered reservations represent a significant fraction of descriptor demand, transactional reservation could complement existing allocator and reclamation improvements.

## CPU-side validation

The reservation-policy model was evaluated across 194,074 exhaustive small-heap scenarios.

| Metric | Current model | Transactional model |
|---|---:|---:|
| Rejected operations retaining new reservations | 86,354 | 0 |

The diagnostic accounting model was independently validated across:

- 40,000 completed bind snapshots.
- 180,093 allocation and cache events.
- Zero discrepancies against a history-recomputing reference model.

All 12 Python tests across both models passed.

These results establish the modeled behavior and accounting invariants. They do not establish the frequency or performance impact of this mechanism in the title.

## Relationship to existing work

This investigation complements:

- #251 — descriptor allocation across the search cursor.
- #562 — immutable descriptor table reuse.
- #688 — reclamation of descriptor slots from completed command lists.
- #840 — avoiding unnecessary dynamic allocations for aligned CBVs.
- #887 — descriptor heap capacity pressure.

Unlike those approaches, this investigation specifically measures descriptor reservations originating in unsuccessful binds and their subsequent reuse.

## Validation requested

The attached package includes:

- A diagnostics-only Rust patch targeting `ffe310e`.
- Native Rust regression tests.
- Python accounting tests.
- Build instructions and counter definitions.

Native Rust compilation, D3D12/WARP testing and hardware measurements remain pending.

The immediate objective is to determine whether this mechanism contributes significantly to descriptor pressure before proposing a production allocator change.

Independent validation and feedback would be appreciated.

**Reading it:**
- The mechanism is real in the title: almost nothing reserved by a rejected bind is reused (102 of 110,180 slots), so those slots stay held until the recording is reset.
- But it is small against the shortage. At most 849 slots are pending in any one recording, about 1.3 % of the 65,536 dynamic slots, while the failed requests asked for 2.38 million slots in the same time, many of them 65-256 wide. Even with every pending slot returned, most of those requests would still fail.
- So on this card the failures are capacity first, which the 2^18 reserve of #747 removes (zero failures on `integration/testers` here, above). Transactional reservation would trim the pending slots, but by itself it would not stop the drops; it could matter later if demand grows past 2^18.
