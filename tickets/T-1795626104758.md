## Original body

## Summary

Windows 10's in-box D3D12 runtime tops out at shader model 6.5, so `Host::new` returns `Err` and the seven `emit::valu_tests` panic on `assert!(ran > 0)`. Nothing is wrong with the hardware — an RTX 3080 supports the feature set — the OS runtime simply does not expose it. The Agility SDK fixes it without touching a single shader:

```
before   62 passed; 7 failed
after    69 passed; 0 failed
```

The seven tests now execute on the GPU and check RDNA2 semantics (`v_med3` with NaN, `v_fract` near 1.0, `v_sin`/`v_cos` turn reduction, `bfe`) against real hardware output.

## Environment

| | |
|---|---|
| OS | Windows 10 Pro 22H2, build 19045.0 |
| GPU | NVIDIA RTX 3080 10 GB, driver 32.0.16.1742 |
| Compiler | MSVC 14.44.35207, Windows SDK 10.0.26100.0 |
| Rust | 1.98.1, `x86_64-pc-windows-msvc` |
| Commit | `d2a4bae` |
| Agility SDK | NuGet `Microsoft.Direct3D.D3D12` 1.610.5 (`D3D12_SDK_VERSION` 610) |

## Before

```
no SM 6.6 hardware device; skipped
no SM 6.6 warp device; skipped
panicked at crates\victory-shader\src\emit\valu_tests.rs:203:
neither hardware nor WARP SM 6.6 device available
```

`Host::new` (`emit/host.rs:82-96`) asks `D3D12_FEATURE_SHADER_MODEL` for `>= 6.6`; the in-box runtime on this build answers 6.5 for both the hardware adapter and WARP.

## The patch

Three files, about thirty lines. `crates/victory-shader/src/lib.rs` gets one line, and the module is
`#[cfg(test)]` because the front end needs its own copy — two definitions in one binary would
collide at link time.

```rust
// crates/victory-shader/src/lib.rs
+ #[cfg(test)]
+ pub mod agility;

// apps/victory/src/main.rs
+ mod agility;
```

```rust
// crates/victory-shader/src/agility.rs  (new; apps/victory/src/agility.rs is identical)
#[allow(dead_code)]
#[unsafe(no_mangle)]
pub static D3D12SDKVersion: u32 = 610;

/// A `const char*`, not a char array: the loader dereferences this symbol.
#[allow(dead_code)]
#[unsafe(no_mangle)]
pub static D3D12SDKPath: &[u8; 9] = b".\\D3D12\\\0";
```

```rust
// build.rs, in both crates
if std::env::var("CARGO_CFG_TARGET_OS").as_deref() == Ok("windows") {
    println!("cargo:rustc-link-arg=/EXPORT:D3D12SDKVersion,DATA");
    println!("cargo:rustc-link-arg=/EXPORT:D3D12SDKPath,DATA");
}
```

Then `D3D12Core.dll` ships next to the executable under `D3D12\`. `/EXPORT:` is used rather than a
`.def` file because `.def` is not on the asset-policy allowlist; `cargo xtask policy` reports
`155 files ok` with this change.

```
test result: ok. 69 passed; 0 failed
```

## Four things that cost time

- **`D3D12SDKPath` must be a pointer.** Exported as a byte array (`[u8; 9]`), the loader reads the
  first eight bytes as an address and the process dies in `DllMain` with `0xC0000142`
  (STATUS_DLL_INIT_FAILED), before `main` runs.
- **`D3D12SDKVersion` must match the DLL exactly.** With 610 in the code and 620 on disk, the
  loader silently falls back to the in-box runtime — no warning, and the seven tests fail again.
- **Once the exports exist, the DLL is mandatory.** Without it `D3D12CreateDevice` returns
  `0x887e0003` instead of falling back.
- **WARP stays below 6.6** even with the Agility runtime (`no SM 6.6 warp device; skipped`), so the
  software-adapter half of these tests is still skipped. Only hardware coverage improves.

## Unrelated, same machine: `victory-hle`

`net::tests::only_loopback_is_reachable` panics with `winhttp.dll lacks
WinHttpGetProxySettingsEx`. `dumpbin /exports C:\Windows\System32\winhttp.dll` on 19045 (file
version 10.0.19041.3636) lists `WinHttpGetProxyForUrlEx`, `WinHttpReadProxySettings` and
`WinHttpGetProxySettingsVersion` but not `WinHttpGetProxySettingsEx`, so the "every override names
a real export" assertion cannot hold on Windows 10. It means `cargo test --workspace` can never be
green there, even with everything else passing.

## Questions

1. Would you take a PR for this? Where should `D3D12Core.dll` live — checked in under
   `apps/victory/D3D12/`, fetched by a build script, or left to the packaging step? Distribution
   terms are in the SDK's `distributable files.txt`.
2. Is Windows 10 meant to be supported? If yes, the requirements line could say "shader model 6.6,
   which on Windows 10 needs the Agility SDK"; if not, saying "Windows 11" outright would save
   people the dead end.
3. Should the capability check skip rather than fail when 6.6 is absent? A Win10 contributor
   currently sees a red suite even though every test that can run passes.

Happy to verify any variant on this machine.
