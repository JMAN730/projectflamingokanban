### Comment 2 — @mercuryVM — 2026-11-24T05:03:17Z

Static look at `+0x2237178` in the 1.0.2.1 executable (same SHA-256 as yours). I did not run the title, so this is what the code does, not what failed on your machine.

**It is the title's own assert at the end of its package mount setup, not a GPU, feature-level or licensing check.**

- The function is `0x2236e00..0x22371bd` (.pdata). It decodes two obfuscated string literals on the stack, `packroot:/` and `packcache:/config`, and sets up the engine's mounts with them.
- Several steps can fail: the first lookup at the top, `[rsi]` already set, the `packcache:/config` mount (`call +0x2237480`) and others. Each failure jumps straight to `+0x223716c`.
- There the title calls `+0x6170`, which is only `return ecx != 0`, on the dword at `[rsi+0xC]`, and executes `int3` when it is zero. Your registers fit that: `rcx 0`, `rax 0`.
- So the breakpoint means "a mount step failed and left no result", and it happens before any window.
- This function does not call into `rpcrt4` directly. I did not follow its callees, so the refused `rpcrt4.dll` is not ruled out.

**What would tell us which step fails,** if it still happens on current main with a diagnostics build:

```
set VICTORY_LOG=victory_hle::modules::files=debug,victory_hle::modules::storage=debug,victory_hle::modules::xpackage=debug,info
target\diag\victory.exe run <game>\game_scarlett_master.exe --execute
```

The last path calls before the breakpoint should show which one is refused. Look for the package root (G:) or the cache/persistent-storage drive, and for a missing folder or a write that is denied under your data folder.

Counts and structure only; nothing of the title beyond those two mount names.
