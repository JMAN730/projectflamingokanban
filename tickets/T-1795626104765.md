## Original body

**Build:** `pr336` head on `d2a4bae` (also merged with `pr458`); RX 9070 XT, 9800X3D, Windows 11 26300, driver 32.0.32029.2010. Follow-up to #304: with #336 the dynamic-slot warning is gone entirely and the world runs longer, but it still dies the same family of way.

**Symptom.** 30-180 s into the world (six runs: 34, 47, 59, 79, 127, plus one 21 s), `DXGI_ERROR_DEVICE_HUNG` with DRED:

```
page fault at 0x3a5f76000; inside freed ["texture 1024x1024 f98 flags 0x0 (type 34)"]
```

Always the same victim class — a freed 1024x1024 texture (once: freed title-memory copies) — and the stopped command is always an `ExecuteIndirect` kind 10 (mesh) list, a different mesh pipeline each run. The breadcrumb tail ends `0/156`: the faulting list had not finished its first command.

**Theory.** The title streams: it releases a texture as soon as the CPU is done, while indirect commands already submitted may still read it through whatever value a shader-visible-heap slot held at record time — the console keeps the backing memory alive until it is reused, so that is legal. On VIctory the host copy can be released the moment the last *named* user drops, and lists only hold textures they could name: indirect arguments are written by compute on the GPU, so nobody holds these.

**Experiment.** A small patch parking host textures (and slot-replacement resources) in a late-keep queue drained by `HostList::reset` (which runs only after submissions were waited for) instead of releasing on the CPU drop:

```rust
impl Drop for HostTexture {
    fn drop(&mut self) { crate::descriptor::host::late_keep(&self.texture); }
}
```

Survival grew (47 s -> 59-127 s across three runs) but the same fault still lands, so the lifetime gap looks real yet wider than what the lists name — the drain point may still be too early for multi-list frames, or more free paths bypass named holds than this covers. Sharing the data in case it saves a round-trip; happy to test variants on RDNA4.

### Comment 1 — @Len1k — 2026-11-24T04:57:38Z

The experiment's result points somewhere useful: the drain point is probably fine, but `Drop for HostTexture` is one of at least three free paths, and it is not the one that a mesh `ExecuteIndirect` list can reach.

**Why `HostList::reset` is a sound drain point.** `Host::execute` (`crates/victory-gpu/src/host.rs:492`) signals the queue's fence and calls `WaitForSingleObject(self.event, INFINITE)` per group before returning, and `reset` is the title reusing a list (`crates/victory-gpu/src/list.rs:254`, "Every submission of the list has run (submissions are waited for)"). So anything drained there is provably past GPU use. Two caveats on top of that: the drain only runs when the *title* resets the list, so a list the title abandons never drains (that leaks, it does not fault), and `allocator_reset` is a no-op stub.

**Free paths `Drop for HostTexture` does not cover.**

1. `HostHeap::keep` (`crates/victory-gpu/src/descriptor/host.rs:279`):

   ```rust
   fn keep(&self, index: u32, resource: Option<ID3D12Resource>) {
       let mut kept = self.kept.lock().unwrap_or_else(|e| e.into_inner());
       if let Some(slot) = kept.get_mut(index as usize) {
           *slot = resource;      // the previous ID3D12Resource is released here
       }
   }
   ```

   Rewriting a slot (`make_at`, `make_null`, `mirror` at line 353, `constant_at` at line 289) drops the resource the slot held *inline on the CPU*, during recording. That is not `HostTexture::drop`, so a late-keep installed there never sees it. `HostHeap`'s own comment (`descriptor/host.rs:25-29`) says the slot holds the resource precisely because "a slot the title has not rewritten since it released the resource may still be read" — the mirror image of that case is a slot the title *rewrote* while a queued list still reads the old contents through an index it takes from GPU memory.

2. `shadow::unregister` (`crates/victory-gpu/src/shadow.rs:391`):

   ```rust
   /// The title released it; lists that still hold its copy keep it alive.
   pub(crate) fn unregister(resource: usize, start: u64) {
       buffers().remove(&(start, resource));
   }
   ```

   The `Arc<Shadow>` goes away here, and with it `Shadow::buffer` (`ID3D12Resource`). "Lists that still hold its copy" is true only for a copy a list *named* — vertex and index binds (`draw::prepare_for`, `draw.rs:335`) hold one. A mesh `ExecuteIndirect` does not: the arguments are written by compute into a shadow buffer and never read back on the CPU, so the host cannot know which title address the list will read. That is the exact shape of your fault — stopped command is always an `ExecuteIndirect` kind 10, victim always a freed texture.

3. `make_null` / `keep(index, None)` release the slot's resource the same way, and `HostList::reset` clears `states`/`pipelines` (`host.rs:880`) — that one is safe by the wait above.

**What that suggests for the patch.** Move the late-keep out of `Drop for HostTexture` and into the two places that actually release: the `*slot = resource` assignment in `HostHeap::keep`, and `shadow::unregister`. A single global `late_keep(ID3D12Resource)` drained at the fence wait in `Host::execute` after `WaitForSingleObject` is strictly safer than draining at `reset`, because the wait is the proof and it fires for every submission. Note that `shadow::loose` (`shadow.rs:448`) already never frees its windows — the `shortcut` at line 441 — so loose-memory shadows cannot be the victim; only `BUFFERS` entries can.

Two things I cannot check from here: whether DRED's `type 34` resolves to one of these paths or to a pooled snapshot `Vec<u8>`, and whether `Deferred` already holds every `Arc<Shadow>` a list took (if it does, path 2 needs a different explanation than the one above and I would drop it). I have the source but no Rust toolchain and no title files on this machine, so I cannot build or run anything — read this as code-level only, nothing tested.

Happy to write it as a PR if it is useful, with the build and test done by someone who has the toolchain.

### Comment 3 — @Amit89-beep — 2026-11-24T04:59:16Z

Draining the deferred queue in HostList::reset only waits for that single command list to finish. Because ExecuteIndirect mesh draws (kind 10) read textures through indices already written into shader-visible descriptor heaps or GPU argument buffers, another command list or queue in flight across multi-list frames can still execute after an individual list resets.

2. Dangling GPU virtual addresses in shader-visible descriptor slots
Even when the ID3D12Resource is kept alive longer, freeing/reclaiming its slot in the shader-visible CBV_SRV_UAV heap without overwriting the descriptor leaves a stale GPU VA pointer. If a delayed indirect draw still indexes that slot, the GPU faults on the unmapped page (0x3a5f76000).

3. Missed transient copy buffers
As noted in the DRED log ("once: freed title-memory copies"), transient upload/alias buffers backing title-memory texture copies also need the same deferred lifetime as HostTexture.

Proposed Fix:

Global Queue-Fence Graveyard: Tag every dropped ID3D12Resource (both HostTexture and title-memory copy buffers) with the latest submitted command-queue fence value (last_submitted_fence), and only release them once queue_fence.GetCompletedValue() >= drop_fence (with a 2–3 frame safety margin across all active queues).

Null-SRV Overwrite on Slot Free: When a texture's SRV slot is freed, immediately overwrite that shader-visible heap descriptor with a valid null SRV (or 1x1 dummy black SRV) before recycling the slot index, so any stale ExecuteIndirect read samples black instead of hitting a freed GPU VA.

### Comment 4 — @Len1k — 2026-11-24T05:18:13Z

Thanks — three points, one of which is a misunderstanding worth clearing up, and one of which I have now covered.

**1. The drain is not in `HostList::reset`.** It is in `Host::execute` (`crates/victory-gpu/src/host.rs`), immediately after `Signal` + `SetEventOnCompletion` + `WaitForSingleObject(self.event, INFINITE)`. The module's own `shortcut` note says it: "every submission is waited for, so CPU and GPU never overlap". So the drain cannot land between two in-flight lists — no command list, on any list of a multi-list frame, can still execute when it runs. `HostList::reset` is only where the *title* reusing a list would have been a drain point, and that is exactly why I did not put it there.

**2. Stale GPU VAs in shader-visible slots.** In this code the descriptor is never left pointing at an unmapped resource: `HostHeap::keep` (`descriptor/host.rs:279`) always writes a replacement descriptor *and* stores the resource in `kept` (`Option<ID3D12Resource>` per slot), so the slot is either rewritten to a new descriptor or left holding a resource that is still alive. The bug is the third case: `keep` assigned the new resource over the old one, dropping the previous `ID3D12Resource` **while that slot's old contents could still be read** through an index taken from GPU-written arguments. Nothing was overwriting the descriptor to null — the resource behind a live descriptor was being freed.

**3. Transient copies.** Agreed, and that is the second path: `shadow::unregister` (`shadow.rs:391`) dropped the `Arc<Shadow>` and with it `Shadow::buffer`. Pooled snapshot memory (`Vec<u8>` in `POOL`) is host memory, not an `ID3D12Resource`, so it cannot be the page fault; `shadow::loose` never frees its windows at all (`shortcut` at `shadow.rs:441`).

I opened #575 for the two paths (`HostHeap::keep` and `shadow::unregister`) with the `execute`-time drain, `cargo test -p victory-gpu` 43 passed / 0 failed. It is deliberately narrow: it removes frees nothing can justify, and does not claim to fix the fault on its own — a fence-tagged graveyard with a frame margin is a bigger change than the evidence I have supports, since submissions here are already fully serialised.
