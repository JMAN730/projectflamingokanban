## Original body

### What happens

On Windows 10 the in-box D3D12 runtime reports shader model 6.5 at most. VIctory requires 6.6 (`crates/victory-shader/src/emit/host.rs:91`, `crates/victory-gpu/src/host.rs:375`), so even on a GPU that supports 6.6 (an RTX 4080 here):

- `victory translate <shaders> --validate --pipelines` stops with `Error: the device supports SM 0x65 only`.
- The README lists Windows 10 as supported.

### What fixes it here

The D3D12 Agility SDK. I exported its two symbols from `victory.exe` and put Microsoft's `D3D12Core.dll` beside it:

```rust
// apps/victory/src/main.rs
// D3D12 Agility SDK: Windows 10's in-box runtime stops at shader model 6.5.
#[unsafe(no_mangle)]
pub static D3D12SDKVersion: u32 = 620;

#[repr(transparent)]
pub struct SdkPath(*const std::ffi::c_char);
// SAFETY: points at a static, immutable C string.
unsafe impl Sync for SdkPath {}

#[unsafe(no_mangle)]
pub static D3D12SDKPath: SdkPath = SdkPath(c".\\D3D12\\".as_ptr());
```

```rust
// apps/victory/build.rs
fn main() {
    println!("cargo:rustc-link-arg-bins=/EXPORT:D3D12SDKVersion,DATA");
    println!("cargo:rustc-link-arg-bins=/EXPORT:D3D12SDKPath,DATA");
}
```

I also copied `D3D12Core.dll` (and `d3d12SDKLayers.dll`, for the debug layer) from the `Microsoft.Direct3D.D3D12` 1.620.2 NuGet package into `target\<profile>\D3D12\`. `dumpbin /exports` then lists both symbols.

With that:

- `translate --validate --pipelines` on a 40-shader sample creates 40/40 pipelines on the 4080. Without the SDK the run stops at the error above.
- The title boots on Windows 10, using #28 for the loader: account prompt, intro with sound, legal notices, start screen and the story loading screens at about 30 fps.

### Environment

Windows 10 22H2 19045.6456, i5-13600K, RTX 4080 (driver 621.01), main `97c78d1`. AI-assisted (Claude); I ran everything above myself.

The DLL can't be committed under the asset policy, so shipping it needs a fetch step or a README note. If you want that route, I can open a PR with the exports and an `xtask` that downloads the pinned NuGet package and checks its hash.

### Comment 4 — @Zilumz1 — 2026-11-24T08:40:10Z

## Windows 10 + pre-RDNA AMD (Polaris): what the Agility runtime does and doesn't fix

**Machine:** Windows 10 Pro, **AMD Radeon RX 580 2048SP (Polaris / GCN4)**, Adrenalin driver 31.0.21925.1001. `main` at `ba7d873`, Rust 1.98.1, MSVC 14.44. `D3D12Core.dll` from NuGet `Microsoft.Direct3D.D3D12` 1.620.2. All results are from real runs on this machine using synthetic shaders and no title data. The probes were temporary tests in `emit/valu_tests.rs`, not committed.

### 1. Device caps, in-box runtime vs. Agility 1.620.2

| `CheckFeatureSupport` | In-box | Agility 1.620.2 |
|---|---|---|
| Highest shader model | **6.5** | **6.6** |
| Resource binding tier | 3 | 3 |
| Wave lanes (min..max) | 64..64 | **64..64** |
| Int64 shader ops | yes | yes |
| 64-bit atomics: typed / groupshared / descriptor heap | (query refused) | yes / yes / yes |
| Mesh shader tier | not supported | **not supported** |
| Raytracing tier | not supported | not supported |

So the Agility runtime gives Polaris SM 6.6 with full 64-bit atomics. It doesn't give mesh shaders, and the card only runs 64-lane waves.

### 2. Heap-indexing flags: the Agility runtime is required, and a retry without the flags doesn't help

I lowered a real GFX10 compute shader through `build_valu_cs` (`cs_6_6`, `createHandleFromHeap`) and created its PSO directly on the hardware device:

| Runtime | With `*_HEAP_DIRECTLY_INDEXED` | Without the flags |
|---|---|---|
| In-box | root signature refused (`0x80070057`, "Unsupported bit-flag set (root signature flags 601)") | root signature OK, **PSO refused** `0x80070057` |
| Agility 1.620.2 | **root signature + PSO OK** | root signature OK, **PSO refused** `0x80070057` |

A fallback that drops the flags (as #623 currently does) only moves the failure from root-signature serialization to PSO creation. The working fix is #175 / #463 for `victory.exe` and #486 for the test binaries. I posted details on #623.

### 3. `WaveSize(32)` compute shaders are refused on 64-lane-only hardware

`lower.rs:395-398` declares `WaveSize` equal to the console program's width when a compute shader uses cross-lane operations (`v_mbcnt`, DPP, `ds_swizzle`, permutes, readlane/writelane, or masks read as data), or when it's a single wave with LDS. The console title mixes wave32 and wave64 programs, and RDNA2 runs both.

On this card with the Agility runtime:
- A synthetic wave32 compute shader containing `v_mbcnt_lo_u32_b32` declares `WaveSize(32)`. `dxil.dll` validates it, but `CreateComputePipelineState` refuses it with `0x80070057`.
- The same harness without cross-lane operations (no `WaveSize`) creates its PSO fine.

So on Polaris (and older GCN, 64 lanes only), **every wave32 compute program with cross-lane operations will be refused**. NVIDIA and Intel hosts (32 lanes) have the mirror problem with the wave64 programs the README already mentions ("some compute programs need a GPU with 64-lane waves"). Only RDNA hosts, which accept both widths, avoid both cases.

Suggestions:
- Log the host's `WaveLaneCountMin..Max` once at device creation, next to the existing `host mesh shader support` line. Then a "pipeline refused" report shows straight away whether this is the cause.
- Longer term, emulating a 32-lane console wave inside a 64-lane host wave (masking the upper half and remapping the lane ID) would cover GCN. Emulating 64 on 32 is harder. Possibly related: #593 (lane-indexed reads on a 64-lane host wave).

### 4. Mesh shaders: Polaris can't reach the world

The mesh shader tier stays "not supported" even with SM 6.6, and the world uses mesh pipelines (README: "mesh shaders for the world"). On GCN 4 and older, VIctory can at best reach the menus. Unless the README already intends that, its "a Direct3D 12 GPU with shader model 6.6 (and mesh shaders for the world)" line could say this explicitly for Windows 10 users.

### 5. Test suite on this machine

- `cargo test --workspace` on `main`: everything passes except the 8 GPU `valu_tests` (`neither hardware nor WARP SM 6.6 device available`).
- With #486 + Agility 1.620.2: **69/69** `victory-shader` tests on `6179b10`. They run on hardware; WARP stays below 6.6.

Glad to run further probes on this card on request.
