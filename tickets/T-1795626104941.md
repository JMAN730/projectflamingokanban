## Original body

## Setup

- VIctory `ffe310e` (main, 2026-11-24), diagnostics build (`--profile diag --features diagnostics`)
- Windows 11, NVIDIA GeForce RTX 4070, Windows Graphics Tools installed (D3D12 debug layer)
- Retail GTA VI package 1.0.2.1, default console (Series X)
- Menus, intro video and world load all work as described in the README. In the world the screen stays dark and the host device is removed after roughly 1–3 minutes.

## Symptom

`host GPU device removed ... (0x887A0006)`. With `VICTORY_D3D12_DEBUG=1` the debug layer reports `DXGI_ERROR_DEVICE_HUNG ... TDR`. Before the removal, single host lists take 2.3–5.3 s (`slow host list ms=2304 / 2872 / 3381 / 5331`), above the 2 s Windows TDR.

## Measurements

All runs with `VICTORY_D3D12_DEBUG=1 VICTORY_D3D12_DRED=1 VICTORY_GPU_TIMING=1`.

### 1. Indirect dispatches whose argument block is never written

`slow list command` totals per pipeline for one run (default settings):

| ms total | count | command |
|---:|---:|---|
| 2345 | 16 | `indirect kind 2 max 1 at 0xdc799b440 [compute 8bbcbda6008eaa37]` |
| 345 | 6 | `indirect kind 2 max 1 at 0xdc799b660 [compute 87df99711607dd60]` |
| 341 | 11 | `indirect kind 2 max 1 at 0xdc799b640 [compute 776d835da5ffa646]` |
| 255 | 9 | `indirect kind 2 max 1 at 0xdc799b600 [compute 84eafa50504bc9ef]` |
| 226 | 13 | `indirect kind 2 max 1 at 0xdc799b400 [compute c7feccae4e01e454]` |

Each of these single-record dispatches takes 100–270 ms. All read their arguments from the same small block (`0xdc799b400..0xdc799b660`), and their outputs `u4`/`u5` are mostly null descriptors (`[heap 330472: null]`, `[heap 330576: null]`). Also in the family: `8a7b68076089f7a8`, `915ed81ea580a276`, `bc6ca78d5425c179`.

Skipping two of them only moved the time onto the others in the same block. Skipping all eight (`VICTORY_SKIP_PIPELINES`) removed every slow list above ~50 ms.

**Lowering the clamp in `indirect.rs` did not help:** `GROUPS` 1<<20 → 1<<14 and `BUDGET` 1<<27 → 1<<25 still left `8bbcbda6008eaa37` at ~100 ms per dispatch (3,986 ms over 40). The cost is per thread, not in the group count. That points to the shader running against null descriptors / uninitialised data rather than to an oversized dispatch.

### 2. Mesh draws with null descriptors (slow, then a real hang)

- With default settings, single-group `mesh 1` / `mesh 3` draws took 100–300 ms each, about 2.2 s per list (for example `mesh 04b9be3756e8f41c / pixel 1af4a50c7fb40c97`, `mesh a26422c01dcf5612 / pixel 6a3a8d3fe52b4eab`, `mesh c5ffa556ab926155 / pixel c4a269f4eeba3cac`). `VICTORY_SHADER_LOOP_LIMIT=4096` brought this down to ~0.26 s total, so these are loops that run to the limit.
- With the compute family skipped and the loop limit on, the run lasted about 3 min. It then hung for real: DRED reports `a list stopped at command 287 of 404 (op 42)`, which is a DispatchMesh with no marker. The list held `mesh c962201cddbdd7dd / pixel e5e9af2bbd2c006a` with `u8`/`u9` null.
- After also skipping `c962201cddbdd7dd`, the next run hung earlier (1 min 40) the same way: `a list stopped at command 346 of 375 (op 42)`. That list held `mesh 51ff151f75cd5759 / pixel 7fe75645c406cac6`, also with `u8 = [heap 327680: null]`.

DispatchMesh commands carry no marker (`command 287 (op 42): no marker`), so the hanging draw itself cannot be named from DRED today. A marker per mesh dispatch would let users narrow it down.

### 3. Other observations

- Debug layer: `ResourceBarrier: Before state (UNORDERED_ACCESS) ... does not match with the current resource state (VERTEX_AND_CONSTANT_BUFFER) (assumed at first use)` on `title buffer 0x16870000+0xae00000`.
- `--console series-s`: the title stays on a black screen at 11 draws/frame and never progresses.

## Summary / suggestions

1. The `0xdc799b4xx` indirect-argument block is never filled with valid data in the world, so the whole compute family runs on garbage arguments against null outputs. Its producer is probably among the compute shaders that "do not translate" or whose host pipeline is refused.
2. Shaders that read null descriptors (the `[heap N: null]` slots) can loop until the loop limit or hang the GPU. Skipping a draw whose bound descriptors are null, or binding a safe zero resource instead, may avoid the TDRs.
3. A marker for each DispatchMesh would make DRED reports name the hanging mesh draw.

Best combination found so far (about 3 min in the world, no slow lists):

```
VICTORY_SHADER_LOOP_LIMIT=4096
VICTORY_SKIP_PIPELINES=8bbcbda6008eaa37,776d835da5ffa646,c7feccae4e01e454,87df99711607dd60,84eafa50504bc9ef,8a7b68076089f7a8,915ed81ea580a276,bc6ca78d5425c179,c962201cddbdd7dd
```

Full logs are available on request. They are kept local because they contain title addresses.

### Comment 1 — @MichaelSmithAI — 2026-11-24T13:51:15Z

On ffe310e the direct mesh path already records a marker immediately before DispatchMesh. A command explicitly printed with `no marker` means the formatter could not associate it with a preceding marker. Knowing which other pipelines appeared on that list is insufficient to name the shader at command 287 or 346.

There is also a separate truncation case. When more than twelve commands fall between barriers, the report can omit the progress command altogether. A [follow-up to #669](https://github.com/iurysf/VIctory/pull/1) keeps the excerpt near the breadcrumb counter. A synthetic 40-entry history now prints the known marker for mesh command 29 under Wine. An explicitly unmarked command still prints as such.

The eight-pipeline skip result narrows the slow-list workload. The per-command timings span consecutive marker timestamps, so setup for the next command, including its argument clamp, can contribute to the preceding interval. Likewise, `uN [heap …: null]` comes from interpreting a user-data value as a heap index. It can describe a literal or the original table when a draw bound a freshly copied table. To distinguish these cases in a completed frame, the useful evidence is the shader’s actual bound table and slot, together with the indirect argument values and the last write covering that record.


### Comment 2 — @BastienRodz — 2026-11-24T13:52:00Z

1. The null slots (`u4`/`u5` `[heap N: null]`, `u8 = [heap 327680: null]`) are what #568 changes. On `main`, any host slot without a title view is a null Texture2D SRV, whatever the shader reads or writes there (a UAV, a raw or structured buffer); a null descriptor of the wrong kind is undefined behaviour in D3D12. With #568, slots the shader annotates get a null of the matching kind, so reads return zero and writes are dropped (dynamically indexed slots keep the old null). Whether that ends the slow loops and the TDR is unknown; nobody has tried it on NVIDIA yet.

   Branch: https://github.com/BastienRodz/VIctory/tree/gpu/typed-null-descriptors (`22e6676`, rebased on `main` `ffe310e`). Most useful runs: default settings, then your "best combination" without `VICTORY_SKIP_PIPELINES`. Report whether the `slow list command` totals for the `0xdc799b4xx` family and the mesh draws change.

2. On `DispatchMesh` markers: diagnostics builds already set a marker right before each `DispatchMesh` (`crates/victory-gpu/src/draw.rs:598`, `note_op` with `"mesh {x}"`), as for dispatches and draws. So `no marker` on `op 42` means the report's matching failed, not that the marker is missing; it pairs the k-th `SetMarker` in the breadcrumb history with the k-th note. Could you paste the full `commands a..b between its barriers:` part of that device-removed line (title addresses removed if you like)? Then we can see whether the other commands got their text and fix the matching.
