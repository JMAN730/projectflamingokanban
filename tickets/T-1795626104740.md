## Original body

## Environment

- GPU: NVIDIA GeForce RTX 4090 (24 GB), driver 621.24
- CPU: Intel Core i7-12700K
- OS: Windows 11 [build from `winver`, optional]
- VIctory: commit d2a4bae, built with `cargo build --profile diag -p victory --features diagnostics`
- Run on the real GPU (`VICTORY_D3D12_WARP` not set), with `VICTORY_D3D12_DRED=1`
- Command: `victory.exe run <exe> --execute`

## What happens

Boot and the menu run at 30 fps, and so does the loading screen. When the game goes into the opening cutscene, the framerate drops to about 1 fps. It stays there for roughly a minute and then crashes, and the display driver resets. [Add whether the picture was black or showed anything.]

`crashes.log` gets a host GPU failure entry each time. Across 7 runs, the device-removed reason was `0x887A0005` (device suspended) in the first two and `0x887A0006` in the rest. The latest run was the first with DRED enabled, and its debug layer message reports `DXGI_ERROR_DEVICE_HUNG` (TDR triggered).

## DRED output (latest run)

- Breadcrumbs: 435 command lists tracked. 405 completed, and list #405 stopped at command 514 of 1304 (op 5). DRED reports `no marker` for that command, so it doesn't say what it was.
- The 29 lists after it had 0 commands done (not started).
- In-flight commands include compute dispatches (e.g. pipeline `eccf008b413ba7b1`, 32x32x6) and several mesh draws, including indirect ones. One indirect mesh draw uses mesh shader `b7a81f5b96f4ca93` and pixel shader `ee78da6862364ddd`.

I can't tell from the log which in-flight command caused the hang. Two things in it stood out, and either could be unrelated:

- That indirect mesh draw reads a buffer view of 182,452,224 elements.
- Several of its descriptor slots (u8, u9, u10) are logged as `null`.

The trimmed log is attached (`crashes-trimmed.log`). The long breadcrumb array and repeated detail lines were removed and nothing else was edited.

## Notes

- The README says the world stage fails on a real GPU and that this has only been tested on an AMD RX 6700 XT. This may be the NVIDIA version of that failure, so I'm reporting it with the extra detail.
- Related: #11 (an RTX 4060 hang, though at the first-boot screens rather than the world).
- The same run also logs many `shader does not translate` warnings, e.g. "a select on an untracked mask is not supported" and "a structured buffer of unknown stride is not supported". Those look like the known compute-shader gaps rather than part of this hang, but I can post the list if it helps.
- The CPU got past the loader on this machine (12th-gen Intel), in case that's useful alongside #6 and #7.

Happy to run extra diagnostics (`VICTORY_D3D12_DEBUG`, `VICTORY_CAPTURE`, etc.) if useful.

### Comment 4 — @YorangSama — 2026-11-24T04:20:10Z

Same failure on an RTX 4070 (driver 32.0.16.2114), Windows 11 build 26300, VIctory d2a4bae, cargo build --profile diag -p victory --features diagnostics, Series X profile, real GPU (VICTORY_D3D12_WARP not set). Posting because I could get numbers your report does not have, and two of them look like they explain the NVIDIA-specific half.

What it looks like

Boot and the menus run at 30 fps, 3–10 draws/frame.
The intro card renders at 1 fps 916.7 ms/frame 1302 draws/frame — the picture is there (a captured frame is the loading key art, correct at 1920×1080), but the scene behind it stays black.
Then a single submission of 32 lists (mesh+pixel pairs) takes 12.9 s and the device is removed with 0x887A0006. Windows logs LiveKernelEvent P1=141 (VIDEO_ENGINE_TIMEOUT_DETECTED) and writes a WATCHDOG-<date>.dmp. No black screen here only because the display is not on this adapter.
--console series-s behaves differently: black from the first frame, 2828 draws/frame, and the hang moves to a 6-list compute-led submission at 13.16 s.
Two things that seem NVIDIA-specific

With VICTORY_D3D12_DEBUG=1, 22 compute programs are refused at creation in a single 7-minute run:

代码块


ID3D12Device::CreateComputeShader: Shader wants wave lane count of 64 but maximum wave lane count for
device is 32. ... id=622 severity=1
WARN victory_gpu::pipeline::host: host pipeline refused error=…(0x80070057) shaders=[compute …]
Each takes its dispatch with it (a dispatch without a host pipeline dropped). The README's Shaders row already says some compute programs need 64-lane waves; this is what that looks like on Ada. Might be worth collecting: on an RDNA3 iGPU in the same machine, the same run has 0 of these refusals.

With VICTORY_D3D12_GBV=1 on top of the debug layer:

代码块


Draw, SRV resource dimensions differs: Expected D3D12_SRV_DIMENSION_TEXTURE2D,
In Descriptor D3D12_SRV_DIMENSION_TEXTURE1D     (7×, e.g. [mesh d4111a6e6ea49d91, pixel c0a7fe77b1862e10])
Dispatch, UAV resource dimensions differs: Expected D3D12_UAV_DIMENSION_TEXTURE3D,
In Descriptor D3D12_UAV_DIMENSION_TEXTURE2D     (1×, heap index 372683, dispatch 4)
Those are consistent with your note that several descriptor slots are logged as null: resources are being bound with the wrong view kind (or not bound at all), and the driver seems to tolerate it until it does not.

VICTORY_SHADER_LOOP_LIMIT is worth trying on your 4090

VICTORY_SHADER_LOOP_LIMIT=1000 changes the submission that ends the run on my iGPU from 20,518 ms to 444–498 ms (same scene, same cache) and the run reaches 787 draws/frame. It did not stop the hang there — that run then hit an unbound-UAV page fault, which I filed separately — but it does mean the 12.9 s / 13.16 s submissions are loops running to the 2^20 default, not an inevitably slow pass. If your cutscene submission also collapses from 13 s to under a second, the watchdog stops being the thing that ends the run, and what is left should be much easier to name.

Other things I checked, in case they save you a run

The title's own crash.log at the moment of death shows the intro mission genuinely running (fbk_stry000_FBK_STRY000_INTRO, Prestream, building/vehicle/ped pools populated, player 130/130), so the CPU side is not what fails.
VICTORY_D3D12_WARP=1 survives 167 s with no watchdog event and no GPU fault (it ends on 0x887A0004, i.e. WARP lacking something), which supports the hang being in the D3D12 path rather than the title.
Skipping pipeline hashes one at a time moves the hang (the first skip changed a 12.9 s submission to 527 ms and let 1098 draws through) but never removes it, so I stopped bisecting after six rounds.
