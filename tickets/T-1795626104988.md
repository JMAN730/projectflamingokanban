## Original body

Thanks for VIctory and for merging so fast. I measured where pull requests wait, using the GitHub API on 24 Nov ~15:00 UTC. A few repository settings could raise the merge rate without extra review work.

## Numbers

- 672 PRs since 23 Nov 22:37 UTC: 499 open, 89 merged, 84 closed. Peak 36 merges/hour, median 3.3 h from open to merge.
- In a random sample of 150 open PRs, **125 (83%) have no CI run on their head commit**.
  - **372 workflow runs are in `action_required`**: they wait for a manual "Approve and run".
  - `ci.yml` landed on 24 Nov 08:55 UTC, so older PRs without a later push never got a run.
- Same sample: 22 (15%) have merge conflicts; 38 have failing or pending checks.

## Suggestions, by expected effect

1. **Settings → Actions → General → "Approval for running fork pull request workflows from contributors"**: switch to *Require approval for first-time contributors who are new to GitHub*. CI then runs on most PRs without a click. The workflow already has `permissions: contents: read`.
2. **Auto-merge or a merge queue** on `main` with CI as the required check. Add `merge_group:` to the `on:` triggers of `ci.yml` for the queue.
3. **A stale bot** (e.g. `actions/stale`) that labels PRs with conflicts or red CI and closes them after a few days without a push. Contributors then rebase before you look.
4. **Group duplicates**: several PRs address the same thing (e.g. PR templates in #9, #113, #543).

This is complementary to #763, which proposes an external review tool; these are built-in GitHub settings. Happy to send a PR for the `merge_group:` trigger or a stale workflow if useful.
