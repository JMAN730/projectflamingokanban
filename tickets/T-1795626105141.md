## What

On `main` (d9548c0c), the translator does not know which SGPRs a pixel program receives after its user data:

- `native.rs` does not read `SPI_SHADER_PGM_RSRC2_PS` from the pixel stage data.
- `io::raise` sets `initialized_sgprs` only for compute programs, and gives pixel programs no input for the primitive mask SGPR or the POPS collision wave id SGPR.

So when a pixel program uses one of these registers as a value, it reaches `Val::Missing("a hardware SGPR input")` in `emit/lower.rs`. A program that uses POPS also reads `src_pops_exiting_wave_id` (operand 239), which `resource::inline` does not handle. A related case: pixel programs that load descriptors through the heap's base address (user-data dwords 2 and 3) are refused because the `ResourceHeap` and `SamplerHeap` parameters only own one dword each.

## Evidence and limits

This comes from reading the code. The 751 programs I dumped locally from my own copy contain **no** program that fails for this reason, so I can't give a count from my machine. Other reports in this tracker quote the "a hardware SGPR input" refusal on other sets. I have not checked that those have the same cause.

## Setup

`main` d9548c0c, Linux. Nothing here depends on the GPU. Not tested on NVIDIA hardware.
