## Original body

# Windows 10 + RTX 4070 SUPER: three verified fixes get the title past Game Init into the render loop

**AI-assisted:** yes
**Kind:** verified local fixes + a reproduction note, not a PR yet. No game data.

## Environment

- OS: Windows 10 Pro 22H2 (build 19045)
- CPU: Ryzen 7 7800X3D
- GPU: RTX 4070 SUPER 12 GB, driver 591.74
- VIctory: `main` @ `d2a4bae`, release profile, real GPU
- Title: Xbox Series 1.0.2.1, 120,181,760-byte exe

## Symptom before the fixes

Identical to the closed #348: `XUserAddAsync` completes and the title immediately faults:

```
unhandled exception 0xc0000005 at victory-image-...dll+0xb5a5f8 (read 0x68)
  rax 0x0 ... r15 0x651e95c4d06fbfb1
  #0 +0xb5a5f8  #1 +0x5bb7cce  #2 +0x1dbdc0b ...
```

`token and signature: offline` never appeared in the log, so the token path was not reached;
the fault is between `XUserAddAsync` and any token call.

## Fix 1 (decisive): implement XUser maximum-users slot 0x30

`crates/victory-hle/src/modules/xuser.rs` had `missing::<6>` at slot 0x30 (maximum users).
The title calls it during account init, gets `E_NOTIMPL` with no output written, and
dereferences the result regardless.

```rust
extern "system" fn get_max_users(_: This, _: Handle, out: *mut u32) -> HRESULT {
    put(out, 1)
}
```

VTABLE slot 0x30 points at `get_max_users`. Result: the title gets past Game Init and into
the render loop — `frame presented` runs continuously (64 frames in the first ~2 s, 96 draws
submitted).

## Fix 2: report offline token as success

`token_async` returned `FAILED_TO_GET_TOKEN` for every request. Changed to complete with
`S_OK` and the existing one-byte `TOKEN` result buffer (same shape as `resolve_privilege_async`).
This path was not reached in our run, so it is untested here; it is included because #348
flagged it as the same class of failure.

## Fix 3: fall back when Windows 10 d3d12core rejects the 1.1 heap-indexing flags

`crates/victory-gpu/src/pipeline/host.rs` always set
`CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED | SAMPLER_HEAP_DIRECTLY_INDEXED` (0xc00) on a 1.1 root
signature. Windows 10's d3d12core refuses the whole signature with
`Unsupported bit-flag set (root signature flags c01)`, which dropped every draw.

The build now retries serialization without those two flags when the first attempt fails:

```
root signature: Unsupported bit-flag set (root signature flags c01).
root signature: retried without the 1.1 heap-indexing flags and it serialized
```

The retry succeeds and the signature is created. (On this host the draw is still dropped by
the next step — see below — so this fix removes one of the two stacked failures.)

## What remains on this host

After fix 1, `frame presented` continues but `drawn=0`:

```
frame=64 draws=96 drawn=0 dispatches=0 dispatched=0
WARN host pipeline refused error=0x80070057 shaders=[vertex …, pixel …]
WARN host pipeline refused error=0x80070057 shaders=[compute …]
```

Both graphics and compute PSOs are refused even with the root-signature fallback. The compute
refusals match #468 (wave64 compute programs, 32-wide subgroup device). The graphics refusals
on an RTX 4070 SUPER likely overlap #199. The D3D12 debug layer was not installed on this host,
so no `D3D12 ERROR` detail was available.

## Why this is useful

Fix 1 turns "crashes at Game Init on every NVIDIA/Windows 10 box" into "reaches the render
loop". It is the missing piece that #348 proposed but which is still absent from `main`
(`missing::<6>` at slot 0x30 as of `d2a4bae`). The other two are small and each removes a
documented failure class.

# Agility SDK plan for Windows 10 hosts (SM 6.6 without OS upgrade) — path verified, one Rust linking gap remains

Follow-up to the reproduction in this issue. Everything below was measured on this host
(Windows 10 19045, RTX 4070 SUPER); the concept is proven, the last mechanical step needs
a repo owner's hand.

## Why: the PSO refusals on Windows 10 are an OS boundary

With the root-signature fallback in place, every remaining `0x80070057` PSO refusal traces to
one fact: the title's shaders are emitted as **SM 6.6 with `ResourceDescriptorHeap[]`**, and
Windows 10 19045's `d3d12core` (`10.0.19041.1806`) refuses the 1.1 heap-indexing root-signature
flags. On Windows 11 the same binary's menus draw (issue #348 follow-up). This is not a shader
bug and not a driver bug — verified by running on WARP, where the refusals are identical.

## The fix that works without upgrading Windows: Agility SDK

Ship `D3D12Core.dll` (Agility SDK **1.620.2**, stable) beside `victory.exe` and export the two
activation symbols. The OS `d3d12.dll` then routes all D3D12 through the new core.

Measured on this host:

1. Copying `build/native/bin/x64/D3D12Core.dll` from the
   `Microsoft.Direct3D.D3D12` NuGet package (1.620.2, 4.6 MB) next to the exe.
2. The two exports are **mandatory**: `D3D12GetInterface` (function) and `D3D12SDKVersion`
   (data). With only the function exported, the OS does not activate the core and the
   refusals stay. With both exported, the old `flags c01` refusal disappears from the log
   entirely.
3. **Trap 1 — never LoadLibraryW inside the forwarder.** The OS calls `D3D12GetInterface`
   while the loader lock is held. A `LoadLibraryW("D3D12Core.dll")` forwarder deadlocks:
   the process shows 0 threads / 0 CPU immediately after `CreateProcess` and never reaches
   main. This is exactly why the SDK wants the import linked statically.

## What I could not finish on this host: the Rust import

The forwarder must be a static import so `D3D12Core.dll` is loaded as a normal PE dependency
(before the loader-lock call). The repo does not ship `D3D12Core.lib`, so I generated one
with `lib /def:D3D12Core.def /machine:x64 /out:D3D12Core.lib` (the DLL exports exactly
`D3D12GetInterface` and `D3D12SDKVersion`).

The blocker is mechanical: in the current Rust setup neither
`#[link(name = "D3D12Core")]` on the `unsafe extern` block nor a full-path
`cargo:rustc-link-arg=...D3D12Core.lib` produced an `D3D12Core.dll` row in the PE import
table (`dumpbin /imports` shows only `d3d12.dll`), and a `#[used]` static holding the import
did not keep it alive under `/OPT:REF,ICF`. The command line that *should* work is:

```
/EXPORT:D3D12GetInterface /EXPORT:D3D12SDKVersion,DATA <path>\D3D12Core.lib
```

with the forwarder body being a plain call to the imported `D3D12GetInterface`. A repo owner
who knows this toolchain's linking idioms will close this in minutes; the runtime behaviour
on this host is already measured on both sides of the gap.

Working diff (the forwarder + exports, minus the linking plumbing) is on the PR branch
`bittertea0323:fix/win10-init-and-rootsig` (PR #623); it intentionally does **not** include
the Agility bits yet.

## Outcome expected once linked

With the core active, the `flags c01` refusal and the compute `E_INVALIDARG` class tied to
the OS runtime should clear on Windows 10; what remains is the wave64 compute set that
genuinely needs 64-lane waves (issue #468), which is a hardware property, not an OS one.


### Comment 3 — @bittertea0323 — 2026-11-24T06:43:57Z

Follow-up to the Agility plan comment: **measured result on this host — the activation shape is now exactly the official one, and this Windows 10 install still refuses it.**

## What the final shape is (all verified by dumpbin)

```
imports   d3d12.dll!D3D12GetInterface   (system, NOT the core)
exports   D3D12GetInterface             (jmp [__imp_D3D12GetInterface])
          D3D12SDKVersion               (DATA, matches the core's 610/620)
beside    D3D12Core.dll                 (present, NOT in the import table)
```

This is the documented Agility layout: forwarder to the SYSTEM d3d12.dll, core loaded
by the OS at D3D12CreateDevice time. The earlier hang (0 threads) is gone.

## What this host does with it

With the exports present, the process fails at startup with
**`0xC0000142` (STATUS_DLL_INIT_FAILED)** — with the core present *and* with the core
absent, and with both Agility 1.620.2 and 1.610.5. Without the exports the same binary
boots normally. So on this install the presence of the two exports alone is fatal.

## Why

The system d3d12.dll here is **10.0.19041.1266** (July 2021), on Windows 10 22H2 UBR 2006.
Cumulative updates do not advance this d3d12.dll on this install (it has not moved past
1266 while UBR went to 2006), so the Agility forwarding mechanism — which newer
d3d12.dll builds implement — is not available; the old shell reacts to the exports by
attempting activation and failing the process.

## The boundary, stated plainly

- Agility SDK activation on Windows 10 requires a newer D3D12 system shell than
  19041.1266 (a Store-updated D3D12Core or a servicing update that advances d3d12.dll).
- On such a host the two exports are a liability: they kill every launch.
- Practical consequence for the repo: if this lands, gate the two exports behind a
  feature flag (default OFF) so Windows 10 hosts with old d3d12 shells keep booting.

The WIP code for the activation is on branch `bittertea0323:fix/agility-win10-wip`
(do-not-merge, as committed). The measured boundary is this comment.
