## Original body

## What's wrong

Microsoft's [GameInput keyboard and mouse documentation](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/input/advanced/input-keyboard-mouse#reading-key-state) specifies the order of the array returned by `IGameInputReading::GetKeyState`:

> "New keys are added at the end of the array, and when a key is released, everything shifts down to fill in the gap."

In `crates/victory-hle/src/modules/gameinput.rs:1158-1163`, `host::Host::keys` rebuilds the held-key list on every poll by scanning virtual-key codes in ascending numerical order:

```rust
let held: Vec<u8> = (0x08..=0xFE_u8)
    .filter(|vk| !(0x10..=0x12).contains(vk) && !down.contains(vk))
    // SAFETY: plain queries.
    .filter(|&vk| unsafe { GetAsyncKeyState(i32::from(vk)) } < 0)
    .collect();
down.extend(held);
```

`key_state` (`crates/victory-hle/src/modules/gameinput.rs:1003-1014`) copies that list directly into the caller's `GameInputKeyState` buffer. If the player holds `Z` (`0x5A`) and then also presses `A` (`0x41`), GameInput documents `[Z, A]`, while VIctory reports `[A, Z]`.

## Impact

Key-binding screens and any title code that identifies the most recently pressed key from the end of the `GetKeyState` array read the wrong key whenever a newly pressed key has a lower virtual-key code than a key already held (for example, binding `Z` when the player pressed `A`).

## Fix

Track the previous poll's held virtual keys on `host::Host` and compute the next ordered list with a small pure `press_order(previous, down)` helper: keep keys from `previous` that are still in `down` in their existing order, then append keys in `down` that were not in `previous`. Because PR #656 also edits `Host::keys`, the helper lives outside `keys` and the change inside `keys` is limited to applying `press_order` and iterating `self.held_keys`, leaving key scanning, filtering, and `KeyState` construction untouched.

The fix is ready on a branch of my fork, since PR creation is limited to collaborators: https://github.com/BastienRodz/VIctory/commits/hle/held-keys-in-press-order (one commit on `main` `ffe310e`, `gameinput.rs` +37/-1).

## Tests

`held_keys_keep_their_press_order` exercises `press_order` with these sequences:
- Z held, then A pressed: `[Z, A]`. Today's scan gives `[A, Z]`.
- B added: `[Z, A, B]`.
- Z released: `[A]`.
- Z pressed again: it goes to the end, `[A, Z]`.

On GitHub's `windows-latest`, with the upstream CI's commands (clippy `-D warnings` with and without `--all-features`, then `cargo test --workspace --locked`), everything passes: `victory-hle` 95 passed, 0 failed (https://github.com/BastienRodz/VIctory/actions/runs/45399104790).

**Not tested:** a title's key-binding screen.

No game data used. AI-assisted: found with GPT-6.2 Astra, written with Gemini 4 Neon, reviewed and verified with Claude Code.

### Comment 1 — @MichaelSmithAI — 2026-11-24T13:20:28Z

The guest GetKeyState check confirms the fix on Win64 under Wine. With Z held on one poll and A added on the next, ffe310e returns [A, Z] and 4ce99c1 returns [Z, A]. Release/repress, a two-key caller buffer, and reading older retained snapshots after later polls all passed. The keyboard states were injected at the host query boundary. The test is in [BastienRodz/VIctory#2](https://github.com/BastienRodz/VIctory/pull/2).

For anyone combining this with #656, both branches edit Host::keys. Building the character state from the current held set and emitting the reading in remembered press order preserves both behaviors. All 11 GameInput tests passed with the new fixture on that merge, including the character and modifier tests.
