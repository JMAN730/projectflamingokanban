## Original body

`LoadLibraryExW(L"comctl32.dll", NULL, LOAD_LIBRARY_AS_DATAFILE)` returns NULL with `ERROR_MOD_NOT_FOUND` (126) on `ffe310e`, while Windows returns a data-file handle. The same happens for any DLL outside `HostPolicy` loaded with `DONT_RESOLVE_DLL_REFERENCES`, `LOAD_LIBRARY_AS_DATAFILE(_EXCLUSIVE)` or `LOAD_LIBRARY_AS_IMAGE_RESOURCE`.

`LoadLibraryExA/W` already computes `runs_code(flags)` and passes it to `find_module` as `load`, but `find_module` still applies the HostPolicy refusal at the end:

```rust
if host_dll {
    return None;
}
refuse(&file);
host::set_last_error(ERROR_MOD_NOT_FOUND);
Some(std::ptr::null_mut())
```

That contradicts the comment above `runs_code`: a load that runs no code can go to the host. The existing test at `kernel.rs:680` only asserts the result is not the title's mapped base, so NULL also passes it.

## Fix on a fork

- **Branch:** https://github.com/davutsimsekk/VIctory/tree/fix/loadlibrary-datafile-host
- **Commit:** `343aa42` on `main` `ffe310e`, one file (`crates/victory-hle/src/modules/kernel.rs`).
- The load's `runs_code` value is passed into `find_module`; when it is false and the name is not one of our pseudo modules or an already mapped image, `find_module` returns `None` so the host loader maps the file as data. Code loads, `GetModuleHandle`, pseudo-module resolution and the HostPolicy checks are unchanged.

### Comment 1 — @pushkarreddyy — 2026-11-24T12:07:15Z

Claiming this issue.

In `crates/victory-hle/src/modules/kernel.rs`, `LoadLibraryExW` computes `runs_code(flags)` where flags like `LOAD_LIBRARY_AS_DATAFILE`, `LOAD_LIBRARY_AS_DATAFILE_EXCLUSIVE`, and `DONT_RESOLVE_DLL_REFERENCES` evaluate to `false`.

When `runs_code` is false, the DLL is mapped strictly as a passive data/resource file and will not execute any DllMain or code. However, `find_module` currently enforces `HostPolicy` refusal unconditionally, causing data-file loads of standard Windows libraries (e.g. `comctl32.dll` for UI icons/resources) to fail with `ERROR_MOD_NOT_FOUND` (126).

Passing `runs_code` into `find_module` so passive data-file mappings are permitted to fall through to the host loader cleanly fixes this without weakening code-execution sandboxing.

Preparing a clean branch with regression tests on fork.

- Introduced `LoadKind { Query, Code, Data }` to clearly distinguish between querying loaded module handles (`GetModuleHandle`), executable library loads (`LoadLibrary` / `runs_code == true`), and passive data-file mappings (`LOAD_LIBRARY_AS_DATAFILE`, `DONT_RESOLVE_DLL_REFERENCES` / `runs_code == false`).
- When `LoadKind::Data` is passed, `find_module` returns `None` for DLLs outside `HostPolicy`, allowing the host loader to map the DLL strictly as passive data/resources without running code or executing `DllMain`.
- Retains existing sandboxing and refusal for code-execution loads and module queries.
