### Comment 2 — @KingKaom — 2026-11-24T13:54:40Z

**Per-command frame-cost attribution on RDNA4 (`VICTORY_GPU_TIMING`).** Diagnostics build on a stack of the open shader-coverage/lifetime PRs (incl. #180) atop a recent main; `VICTORY_D3D12_DRED=1` so commands are named. Caveat: the timing knob serializes each submission's lists while measuring, so absolute frame totals differ from uninstrumented frames — the split is the signal. Same stack without the knob: ~0.3 fps, 3.4 s/frame, 2.6–2.9 s of it "on the GPU".

Measured across 86 world frames (serialized, median 1.1 s/frame, ~0.4 s GPU-busy), of ~128 s total slow-list time:

- **Two compute pipelines behind `ExecuteIndirect` = 68% of slow time**: `8bbcbda6008eaa37` (35%) and `776d835da5ffa646` (33%) — 3–4 indirect dispatches per frame each at 100–250 ms apiece; in the median serialized frame these two take ~0.3 s + ~0.5 s between them. No single compute command anywhere exceeded 250 ms, so the multi-second GPU frame is many repeats of these, not one monolith.
- **Mesh-shader draws ≈ 25%** (most commonly a 1-mesh draw at ~200–250 ms; per-draw observed cap 245 ms).
- **One pathological mesh-pipeline pair** (`mesh 04b9be3756e8f41c` + `pixel 1af4a50c7fb40c97`): single commands timed at 1032 / 508 / 389 / 372 / **3392 ms**. The 3.4 s command dominates the worst frame (4.7 s, 4.1 s on the GPU) and recurs in the final frame before device removal.

All three hot pipelines translate and execute (they are cost, not drops), and `VICTORY_SKIP_PIPELINES` cannot A/B them — it filters direct dispatches while these run inside `ExecuteIndirect`. The equal fps across vendors here, #748 and this thread despite 2–3x hardware spread fits the same picture: the bulk of world frame time is a handful of repeated indirect compute/mesh command families, not geometry throughput.


### Comment 3 — @JFIREonFIRE — 2026-11-24T14:14:59Z

On crash 1, `0xc0000005` at `+0x23cf683 (write 0x0)`: it's the title's own hang watchdog, not a null pointer.

- `+0x23cf683` is `mov dword [0], 0x4d8bd421`, a write to the literal address 0. It comes right after the title hands its fatal-error path the string "GPU Loc Sig".
- The caller, `+0x2215a60` (frame #1), is a watchdog thread. It sleeps 1 s per tick, compares a table of heartbeat timestamps against a 300 s limit, and after a 30-tick countdown calls that fatal callback. `+0x2215c35` is its fallback `int3` in case the callback returns.
- So the title stalled long enough for its hang check to fire. The ~1 fps world and the GPU hang in your second run fit that.

The same site is mapped in #630. Open PR #454 adds an opt-in `VICTORY_NO_WATCHDOG`, which lets a run continue past it and see what actually stalls. On NVIDIA one stall is the GPU hang in #71/#578: wave64 compute `eeed82b877b44b5f` hangs 32-lane cards. A rerun with `VICTORY_D3D12_DRED=1` would show whether that's what you hit.

### Comment 5 — @KingKaom — 2026-11-24T16:28:52Z

**Two answers from an RDNA4 host** (for the "which of 2–4 have been measured" ask) — plus a note on the earlier `VICTORY_SKIP_PIPELINES` claim in this thread: correction accepted, the indirect check is real on the current head.

Item 3 measured as a same-binary A/B (diag build, open shader-coverage/lifetime PR stack, `VICTORY_SKIP_PIPELINES` = `8bbcbda6008eaa37,776d835da5ffa646,04b9be3756e8f41c,1af4a50c7fb40c97`, world steady state):

- Without skip: ~1.1 fps, 933 ms/frame = ~660 ms preparing (title-copy refresh ~550 ms, ~453 MB/frame) + ~160 ms on the GPU + ~95 ms copying back.
- With skip: ~1.2 fps, 850 ms/frame = ~655 ms preparing (copies ~535 ms, ~388 MB/frame) + **~62 ms on the GPU** + ~100 ms copying back.

So skipping all four removes ~60% of the measured GPU-side frame work (~100 ms) and moves fps 1.1 → 1.2: on this box the world frame is CPU-prepare-bound (title-copy refresh), not indirect-command-bound. The cold-cache 98%-CPU / 4–22%-GPU observation in the issue body fits the same picture on NVIDIA.

Item 4 (`VICTORY_DUMP_TARGETS` on in-world frames, same stack): the world **is drawn** — two 2560×1440 render targets on the presented frame hold full scene content (terrain, vegetation, structures) — while the **presented** backbuffer of that same frame is pure black apart from the HUD hint overlay. On RDNA4 the black frame is therefore the final present/post step failing, not world geometry never drawing (and not only untranslated world shaders). No Series X mode and no sub-16 GB card tested here.
