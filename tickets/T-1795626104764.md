Environment: Windows [version], NVIDIA RTX 3070 Ti (driver [version]), 32 GB RAM, commit [git rev-parse --short HEAD], diag build. README says it was tested on AMD only; NVIDIA waves are 32 lanes.

1) Hang on the real GPU
Boot, menus and world loading work. In the world: 0.8-1.6 fps, ~1,400 of ~5,800 draws/frame dropped (untranslated shaders), then the device is removed (0x887A0006 / 0x887A0004, DXGI_ERROR_DEVICE_HUNG). Slow submissions of 5-6 s. VICTORY_SHADER_LOOP_LIMIT=64 did not avoid it.

2) Debug layer (VICTORY_D3D12_DEBUG=1), repeated ERROR id=538
DrawIndexedInstanced / IASetVertexBuffers on 'title buffer 0x159f0000+0xae00000' (182,452,224 bytes): state UNORDERED_ACCESS, expected VERTEX_AND_CONSTANT_BUFFER. Six lists in one run. Also with VICTORY_GPU_TIMING=1 (one list per ExecuteCommandLists), so it is not a batching artifact.

Code observation (hypothesis, not verified): these buffers come from Host::shared_buffer (COMMON, ALLOW_UNORDERED_ACCESS). shadow.rs tracks no resource state and I found no explicit buffer barrier in victory-gpu; draw.rs:373 binds shadow.gpu(...) as a vertex buffer without a transition. I could not confirm that fixing this avoids the hang.

3) DRED
Breadcrumbs stop at op 6 inside a list (command 111 of 429, commands 16..254 between barriers; an earlier run: 143 of 354). With GPU timing, a list took 6364 ms but its six slowest completed commands took <= 0.7 ms each, so some command never completes.

4) Perf
The 174 MiB buffer is refreshed ~90x/frame (~16 GB/frame); "preparing" is ~60% of frame time.

5) With VICTORY_D3D12_WARP=1 + DEBUG + GBV + DRED
It did not reach the world (3-12 draws/frame, ~1.2 fps), so item 2 did not reproduce there. Found:
- GBV id=940: pixel stage of [vertex 089d6271be6650ef, pixel 0d1575a396dfe513] expects TEXTURE2D, descriptor (heap index 0) is TEXTURE1D.

- Title access violation (write 0x0) at victory-image-b99f876b74d4a77f.dll+0x23cf683 on a worker thread, shortly after the second refusal (the first refusal 18 s earlier did not crash; no causal link established).
- Pipeline library ids 970/972 ("desc does not match", "already exists") for the same names (e.g. b621eaede8c436ee056a37d8442094fd): possibly an incomplete cache key (perf only).

### Comment 1 — @Len1k — 2026-11-24T04:52:32Z

The code observation holds, and the gap is narrower than it looks: `ensure_state` cannot cover buffers at all today.

- `draw::readable` (`crates/victory-gpu/src/draw.rs:1074`) handles a buffer view through `descriptor::host::buffer_range`: it calls `shadow.refresh` and, for a UAV, `shadow.gpu_writes`. The two `ensure_state` calls below (`View::Shader` and `View::Unordered`, around lines 1097 and 1114) only match texture views.
- `list::ensure_state` (`list.rs:391`) goes through `HostList::transition` (`host.rs:905`), which resolves `host_copy` — a `HostTexture`. A shadow buffer has none, so `transition` returns `None` and no barrier is ever recorded for it.
- Vertex and index binding (`draw.rs:335` `prepare_for`, `IASetVertexBuffers` at line 373 and `IASetIndexBuffer` after it; the mesh path binds at line 888) use `shadow.gpu(address)` directly.
- Shadow buffers come from `host::shared_buffer` (`host.rs:1759`): `D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS`, created in `D3D12_RESOURCE_STATE_COMMON` (line 1789). D3D12 promotes COMMON to UNORDERED_ACCESS implicitly on the first UAV use, and that promoted state holds for the rest of the command list. So a compute pass that skins into the 174 MiB heap leaves the buffer in UAV; the mesh draw that reads the same heap as vertex data in that list is exactly the debug-layer 538 you see. The promoted state is not a per-list artifact either — the same mismatch on a driver that does not report it is a candidate for the hang, though that part is unproven.
- Even if the states matched, the write→read pair needs a UAV barrier; `readable` writes no barrier between `gpu_writes` and the vertex bind. (`indirect.rs` has a `uav_barrier()` helper already.)

Shape of a fix, for what it is worth:

1. Give `HostList` a buffer-state record keyed by the `ID3D12Resource` pointer of `Shadow::buffer`, mirroring the texture record that keys on the copy pointer (`host.rs:905`).
2. Record UNORDERED_ACCESS in `readable`'s UAV arm for shadow buffers, and record (at least) VERTEX_AND_CONSTANT_BUFFER / INDEX_BUFFER / GENERIC_READ at the bind sites.
3. When leaving UAV for a read in the same list, emit a UAV barrier and the transition (`host::transition` at `host.rs:1874` already builds the barrier struct).
4. If the driver does not decay promoted state at list end, carry the real state across lists in `prelude()` (`host.rs:929`) the way textures do; otherwise the per-list record is enough.

I can write that as a PR with `cargo test -p victory-gpu` (no title here — RDNA1, no mesh shaders), but I did not want to touch the state path without a word from you first. Whether it also stops the `DEVICE_HUNG` is a separate question from whether the debug-layer error is real; this report is the only place I have seen the mismatch named.

### Comment 2 — @wwwwwwww3333333 — 2026-11-24T05:07:13Z

@Len1k before you start on that: #334 (realhenners, open, clean against `d2a4bae`) already implements the shape you describe. It adds a per-list `BufferStates` record for host copies (`GENERIC_READ` for vertex/index/constant/SRV/indirect reads, `UNORDERED_ACCESS` for shader writes) with transitions where the use changes. The prelude moves each buffer from `COMMON` to its first state and `close` moves it back. It also replaces `indirect.rs`'s fixed `UAV ↔ INDIRECT_ARGUMENT` barriers, which on `main` leave the shared heap explicitly in `UNORDERED_ACCESS` after every indirect draw.

I ran #334 (`af2aecf`) on Windows 11 / Rust 1.98.1 MSVC / RX 6750 XT (RDNA2). `cargo test -p victory-gpu` passes (45 passed, 1 ignored). That includes `debug_layer_accepts_buffers_written_then_read_as_vertices`, which ran with the D3D12 debug layer (not skipped) and reported no errors. Clippy `-D warnings` is clean apart from the pre-existing `host.rs:267` lint that #355 fixes.

So this report looks like #199/#264 on another NVIDIA card. Testing #334 on the RTX 3070 Ti would show whether id 538 and the hang go away. Not runtime-tested with game files.

### Comment 3 — @LAKSHYA-cmd-tech — 2026-11-24T05:14:20Z

PR #588 addresses this exact issue:

1. \Shadow\ now tracks the D3D12 resource state of each host buffer copy via an \AtomicU32\.
2. \Shadow::ensure_state\ emits an explicit \ResourceBarrier\ transition whenever a buffer moves between states (such as from \UNORDERED_ACCESS\ to \VERTEX_AND_CONSTANT_BUFFER\).
3. In \prepare_for\, vertex buffers and index buffer are transitioned to \VERTEX_AND_CONSTANT_BUFFER\ and \INDEX_BUFFER\ respectively before calling \IASetVertexBuffers\ and \IASetIndexBuffer\, clearing debug layer ERROR id=538.
4. In \eadable\, buffers accessed via UAV transition to \UNORDERED_ACCESS\.

### Comment 4 — @Len1k — 2026-11-24T05:18:15Z

Good catch, and it settles it: #334 already implements the shape I sketched, so my four-step plan is redundant — I would rather not duplicate realhenners' work.

For the record on the two differences, in case they matter for the RTX 3070 Ti test: my sketch wanted the state record keyed by the `ID3D12Resource` pointer of `Shadow::buffer`, and the UAV barrier between `shadow.gpu_writes` and the vertex bind. #588 proposes a second implementation of the same thing (`Shadow::ensure_state` with an `AtomicU32`). Whichever lands, the `debug_layer_accepts_buffers_written_then_read_as_vertices` test #334 adds is the part worth keeping — the shape is otherwise unverifiable without the title.
