## Original body

Same family as #131/#125, one level up: for `MaskData::Host` (pixel/vertex programs, no `WaveSize`, so the host wave can be 64 lanes = two console waves), the lane-indexed ops either refuse or read the wrong wave.

`crates/victory-shader/src/emit/lower.rs`, `valu_op`:

- `v_readlane_b32` with a **constant** lane takes `cross_lane(false)` → `a cross-lane operation outside compute` → the whole program is refused. On a wave32 program under a 64-lane host wave, console lane `k` of the lane's own wave is host lane `k | (lane & 32)` — expressible, no refusal needed. The same refusal hits **wave64** programs, where a constant lane is already a valid host lane and should just work.
- `v_writelane_b32` calls `cross_lane(false)` unconditionally → refused on every pixel/vertex program, computed lane or not. On host lanes, `me == lane` is already the correct host-space test for a computed lane; a constant lane needs the same `| (lane & 32)` base.
- `v_readfirstlane_b32` emits `waveReadLaneFirst` → the host wave's first active lane — wave A's lane 0 — for lanes 32-63, whose console wave's first lane is a lane of the ballot's high half + 32.

Repro (synthetic wave32 pixel program, `v_readlane v4, v2, 5`): the write is dropped (`a cross-lane operation outside compute`), the register reads back its input `0`, and the op list shows no `waveReadLaneAt`.

Found while continuing #131: mask-as-number reads were fixed there; these are the lane-index uses the same host-wave model needs.
