### Comment 1 — @EduBertozzi — 2026-11-24T09:21:10Z

I've started a prototype of this on a fork: [`EduBertozzi/VIctory` @ `proto/mesh-compute-fallback`](https://github.com/EduBertozzi/VIctory/tree/proto/mesh-compute-fallback). It's an experiment and not a PR. I'm posting it here to ask whether the approach is wanted, and for help testing it on the real title, since I don't have a PC dump.

## How it works

The mesh program is lowered by the same `Lower` as today. Only the four mesh output ops change: they become raw-buffer stores, and the program is emitted as `cs_6_6` with the same thread group:

| mesh op | compute form |
|---|---|
| `setMeshOutputCounts` | dropped (counts are the declared maxima, as today) |
| `storeVertexOutput` | `u0`: vertex `g * max_vertices + v`, 4 dwords per output element |
| `emitIndices` | `u1`: 3 indices per primitive, with the group's first vertex added. Culled or unexported ones are `0, 0, 0` (no area) |
| `storePrimitiveOutput` | `u2`: per-primitive records |

All three are in a new `MESH_OUT_SPACE` (space 2). A generated vertex shader reads record `SV_VertexID` from `t0` and writes it out with the mesh program's own output signature, so the title's pixel shader links unchanged. `DispatchMesh(x)` becomes:

1. `Dispatch(x)`;
2. a transition barrier;
3. `DrawIndexedInstanced(3 * max_primitives * x)`.

In `victory-gpu`:

- The fallback is used when the host has no mesh shaders, or everywhere with `VICTORY_MESH_FALLBACK=1` for comparing.
- The mesh stage's root parameters become visible to all stages, and its graphics root arguments are set on the compute bindings. For that, `bind` is split into "which title roots to read" and "which host bindings to set".
- Each fallback draw gets its own default-heap buffer in the list.

## What's verified

- On a synthetic mesh program (hand-assembled GFX10), both forms pass `dxil.dll` validation (`emit/mesh_compute_tests.rs`).
- On a GTX 1060 (Pascal, no mesh shaders, Windows 10 with the Agility SDK runtime), the compute form writes the expected vertices and indices.
- Drawing the triangle both ways gives the same image:
  - WARP 1.0.22's mesh shader and its fallback match within 1e-6;
  - the GTX 1060's fallback has the same coverage as WARP's mesh shader, and values within 1e-3.
- `cargo test --workspace`, clippy (with and without `diagnostics`) and `cargo xtask policy` are clean.

## What isn't

- **Never run against the title.** The `victory-gpu` side is checked only by compiling and review.
- Mesh programs with per-primitive outputs are refused, because a vertex shader cannot pass them on. Using a GS or `SV_PrimitiveID` would be the next step.
- Indirect mesh dispatches are dropped.
- The compute translation isn't in the shader cache yet.
- One buffer per draw, sized for the declared maxima. Expect it to be slow and memory-hungry.

## How to test it

You need the title and a GPU without mesh shaders (RX 5700 XT / RDNA1, GTX 10xx), or any GPU with `VICTORY_MESH_FALLBACK=1`.

- The branch carries the #719 test fix and #486 so the GPU tests run on Windows 10. On Windows 10, the app itself still needs the Agility SDK runtime (#175/#463).
- In the log, look for:
  - `mesh programs run as compute`;
  - `host mesh pipeline, run as compute`;
  - refusals: `the mesh shader does not translate as compute`, `per-primitive mesh outputs are not drawn without mesh shaders`, `the mesh program binds otherwise when run as compute`.
- With `VICTORY_MESH_FALLBACK=1` on a mesh-capable GPU, a `VICTORY_CAPTURE` of the same frame with and without the fallback would show whether the two paths match.

Counts are the most useful result: how many mesh pipelines take the fallback, and how many are refused and why. Screenshots of what renders help too.

### Comment 2 — @EduBertozzi — 2026-11-24T09:46:43Z

Update on the fallback branch ([`proto/mesh-compute-fallback`](https://github.com/EduBertozzi/VIctory/tree/proto/mesh-compute-fallback)). The two gaps from my last comment are closed:

- **Per-primitive outputs** (`351895b`). These programs were refused before. Now they are drawn unindexed, three vertices per primitive. The vertex shader reads the corner's index from `t1` and the primitive's record from `t2`, and writes that record as constant-interpolated outputs after the vertex rows. The pixel shader links by semantic, so the title's PS is unchanged.
  - Tested with a synthetic program whose per-primitive `COLOR0` is read by the PS. WARP's mesh shader and the fallback give the same image (1e-6). The GTX 1060's fallback has the same coverage, with values within 1e-3.
- **Indirect mesh dispatches** (`a4d1797`). These were dropped before. Now, after the argument clamp, an HLSL pass (compiled like the clamp) walks the records and their count. For each record it writes:
  - a compute command: `u0`-`u2` root UAV addresses, placed after the previous records' groups, then the dispatch;
  - a draw command: a `t0` root SRV address, then a draw starting at the record's first index or vertex.

  Two `ExecuteIndirect` calls follow, with command signatures made under the fallback pipeline's root signature.
  - The pass is tested on the GPU: records of 2, 0 and 5 groups, indexed and expanded, with and without a count.
  - The two `ExecuteIndirect` calls have no test, because they need victory-gpu's host device.
  - Each execution writes at most 32 MiB; records past that run empty.

Still untested against the title. Of the cases my first comment listed as refused, only the shader-cache entry for the compute form is still missing. Performance is the open question: one buffer per draw, and a single-thread argument pass.

### Comment 7 — @EduBertozzi — 2026-11-24T13:57:29Z

I measured what the fallback costs per frame on a GPU without mesh shaders. The result: **it isn't the shaders, it's how the draws are recorded.**

The benchmark is [`2704a57`](https://github.com/EduBertozzi/VIctory/commit/2704a570560b91e5d33ef74b7bb325518f642c1e) on `pr/mesh-compute-fallback`, an ignored test with no game data:

```
cargo test -p victory-shader --lib fallback_frame_cost -- --ignored --nocapture
```

It draws a synthetic mesh program (32-lane groups, so 4 of them per 128-thread group of the title's; position plus one attribute; triangles under a pixel, so the raster costs little) in frames of 1,000 to 7,000 draws. Each frame is recorded three ways and timed with GPU timestamps (median of 7). GTX 1060 6 GB, Windows 10, Agility SDK 1.620.2:

| frame | per draw (today) | computes batched | draws only |
|---|---:|---:|---:|
| 1,000 draws × 32 groups (1.0M triangles) | 7.13 ms | 1.60 ms | 0.47 ms |
| 2,000 draws × 16 groups (1.0M triangles) | 12.05 ms | 1.42 ms | 0.41 ms |
| 7,000 draws × 4 groups (0.9M triangles) | 32.86 ms | 1.87 ms | 0.35 ms |
| 7,000 draws × 16 groups (3.6M triangles) | 34.82 ms | 4.40 ms | 1.27 ms |

- **Per draw** is what `victory-gpu` records today: compute pass, transition to read, draw, transition back.
- **Batched** puts every draw's compute pass first, then one transition, then every draw.
- **Draws only** is the same draws from buffers already written: what drawing these triangles with a vertex shader costs.

So the per-draw cost is about 4.5 µs whatever the draw holds. At the ~7,000 draws per frame reported in #841, that's ~33 ms before anything else is drawn.

**It isn't the barriers.** I also timed (and didn't keep, because it races) the same per-draw recording with the compute writing to a buffer nobody reads and no transitions: 29.06 ms instead of 31.10 ms for 7,000 × 4. What costs is switching between compute and graphics work on every draw, which Pascal pays with a drain each time.

**What would fix it, and why I haven't done it.** The compute passes would have to run ahead of the draws, in batches: for example, recorded into a list that runs before the draws' list, the way `HostList`'s prelude already runs before it. That is only correct when nothing earlier in the same list writes what the mesh program reads: a compute pass or copy that fills a buffer it reads, or a render target it samples later in the frame. I can't tell how often the title does that without a capture. A conservative rule would be to batch only until the list's first dispatch, copy or UAV-writing draw, and record per draw after that.

@permadiego (Vega 7) and anyone else with a GPU that has no mesh shaders (Pascal, Polaris, Vega): numbers from that test on your hardware would show whether this is Pascal alone or every pre-mesh GPU. Before I build the batching, I'd like a maintainer's view on whether the ordering rule above is the right one.
