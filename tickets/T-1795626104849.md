## Original body

`crates/victory-core/src/policy.rs` (`ensure_outside_repo` / `resolve`) has two path-normalization bugs for non-existing paths containing `..` or `.`:

1. **Trailing `..` / `.` fails with `PolicyError::Io`**: `resolve()` peels segments with `Path::file_name()`, which returns `None` for `..` and trailing `.`. As a result, `<repo>/not-yet-created/..` returns `PolicyError::Io` instead of `PolicyError::InsideRepo`, and valid external paths like `<tmp>/not-yet-created/..` fail instead of returning `Ok(())`.
2. **Windows `\\?\` verbatim prefix skips `..` folding**: `std::fs::canonicalize()` returns a `\\?\` verbatim path on Windows, where `Path::components()` parses `..` as `Component::Normal(..)` rather than `Component::ParentDir`. Pushing `..` onto the canonical prefix and running `normalize(&out)` therefore leaves `..` uncollapsed — allowing `<outside>/not-yet-created/../<repo>/cache` to slip past both `starts_with(&root)` and the `.victory-root` ancestor walk on Windows.

### Comment 4 — @studiostephe — 2026-11-24T12:48:04Z

Independent fix for both reported bugs, with the Windows `\\?\\` folding handled in the same pass.

## What changes

`resolve()` peeled non-existing segments with `Path::file_name()`, which is `None` for `..` and a trailing `.` — so bug 1 (trailing `..`/`.` → `PolicyError::Io` instead of the resolved result). The peeled tail was then re-appended *as raw names* and passed through `normalize()`, which only folds `Component::ParentDir` — but under a Windows `\\?\\` verbatim prefix (which `canonicalize` returns), `..` parses as `Component::Normal(..)`, never `ParentDir`. So bug 2 (`<outside>/not-yet-created/../<repo>` slipping past both checks) is fixed by folding the tail **by component**, treating `Normal("..")` as a parent too.

One semantic note: a `..` that would pop past the canonical prefix is now dropped (the old code's `normalize` did the same via `out.pop()` on an empty path). The prefix is canonical, so it cannot contain a `..` for the pop to undo — the result is the prefix itself, which is the only sane resolution.

### Comment 5 — @pushkarreddyy — 2026-11-24T13:01:19Z

Thanks @studiostephe for the investigation and macOS verification!

Your component-based peeling in `existing.components().next_back()` matches the implementation on my fork branch [`fix/policy-resolve-dotdot`](https://github.com/pushkarreddyy/VIctory/tree/fix/policy-resolve-dotdot) (commit [`b05bc7c`](https://github.com/pushkarreddyy/VIctory/commit/b05bc7c)).

One critical Windows edge case to note:
Under Windows `\\?\` verbatim prefixes returned by `std::fs::canonicalize`, `std::path::Component` treats `..` strictly as `Component::Normal(OsStr(".."))`, **never** as `Component::ParentDir`.

In your snippet:
```rust
match component {
    Component::CurDir => {}
    Component::ParentDir => {
        out.pop();
    }
    c => out.push(c),
}
```
Because `component` is `Component::Normal("..")`, it falls through to `c => out.push(c)` and appends the literal `..` component without popping the parent prefix!

In commit `b05bc7c` on my fork, we explicitly match both variants:
```rust
match component {
    Component::CurDir => {}
    Component::ParentDir => {
        out.pop();
    }
    Component::Normal(s) if s == ".." => {
        out.pop();
    }
    c => out.push(c),
}
```
This ensures consistent lexical folding across both standard POSIX paths and Windows `\\?\` verbatim paths. Verified on Windows with unit tests covering trailing `..` and `.`.


### Comment 6 — @DaniiL35 — 2026-11-24T13:58:31Z

Verified the path resolution analysis across both branches (`8a0ac65` and `b05bc7c`):

### 1. Windows Verbatim Prefix (`\\?\`) & Component Semantics
`@pushkarreddyy`'s observation is correct: `std::fs::canonicalize()` on Windows produces a verbatim `\\?\` prefix. In `std::path::Component`, verbatim components do not classify `.` or `..` as special directory navigation tokens—they are returned as `Component::Normal(OsStr(".."))` and `Component::Normal(OsStr("."))`. Folding those in the loop:
```rust
Component::Normal(n) if *n == ".." => { out.pop(); }
Component::Normal(n) if *n == "." => {}
```
correctly ensures that non-existing tails appended to canonicalized Windows prefixes fold lexically.

### 2. Critical CI Warning Catch for `b05bc7c` (`-D dead-code`)
In commit `b05bc7c`:
By inlining the folding loop into the canonical prefix loop and returning `return Ok(out);` directly, the helper function `fn normalize(path: &Path) -> PathBuf` (at line 107) is left with zero call sites.
Because `.github/workflows/ci.yml` strictly enforces:
```sh

```
`rustc` will reject the compilation with `error: function normalize is never used [-D dead-code]`.
**Action needed in `b05bc7c`**: Delete the unused `fn normalize` helper function (or gate/remove it) to keep CI green.

Tested on macOS (APFS):

Component-based peeling via `existing.components().next_back()` correctly separates the existing canonicalized prefix from non-existing trailing components, avoiding the spurious `PolicyError::Io` previously triggered by `file_name()` returning `None` on trailing `..`.
