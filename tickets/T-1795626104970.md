## Original body

### What renders
On an NVIDIA RTX 5080 (32-lane waves only), the world's mesh shaders now draw world geometry into the G-buffer. The presented image is still black.

From `VICTORY_DUMP_TARGETS=1`:
- **Frame 1550, two 2560×1440 targets (formats 28 and 87):** full of hard-edged world meshes across the letterboxed view, including large surfaces, a framed structure and foliage-like clumps. The colours are packed data shown raw, so they're false colour, but the shapes are clearly geometry.
- **Frames 1500 and 1600, a 480×270 target (format 24):** a tree-line skyline over open ground or water. It's identical in both frames from a fixed camera, so it's stable content, not noise.
- **Without mesh shaders (run 17), the same 2560×1440 targets are uniform.**

Images stay local (rule #1). Counts, hashes and frame numbers only here.

### The new change
`Shaders: wave64 mesh code counts lanes the host's way on 32-lane hosts`
- Branch: https://github.com/Peppacodes/VIctory/tree/exp/mesh-host-lanes
- Commit: `ed9afc0`. It is one small change in `lane_index()` in `emit/lower.rs`, on top of #189.

Mesh shaders can't declare `WaveSize`, so on a 32-lane host a wave64 mesh program runs as two 32-lane waves:
- Its lane masks come from host ballots, which hold no bits for console lanes 32–63.
- `lane_index()` numbered mesh lanes by console lane (`flattenedThreadIdInGroup & 63`).
- So `v_mbcnt` and lane picks on console lanes 32–63 read an empty half.

When #189's mode isn't `Native`, the change numbers wave64 mesh lanes by the host lane (`WaveGetLaneIndex`), so masks and lane numbers agree within each 32-lane half. Mesh code reads no other lanes (the existing comment there, and @ByMateos's census in #778), so each half acts as a narrower console wave.

It doesn't cover the 115 programs with explicit lane reads. @alfycs's `feat/wave64-mesh-emulation` (LDS emulation) is the fuller fix for those. This is a much smaller alternative for the rest.

### Comment 1 — @EduBertozzi — 2026-11-24T14:24:11Z

One note for whoever carries `ed9afc0` forward: the compute fallback for GPUs without mesh shaders (#3, `pr/mesh-compute-fallback` on my fork) lowers mesh programs through the same `lane_index()`. `s.mesh` stays set when `mesh_as_compute` is on, so the compute form also numbers lanes as `flattenedThreadIdInGroup & 63`.

On a 32-lane GPU without mesh shaders (Pascal, or Intel iGPUs before Arc running 32-wide), a wave64 mesh program run as compute therefore has the same mismatch you describe: host-ballot masks covering 32 lanes, numbered by console lane. The change should cover that path as written. Its condition is on #189's mode, not on the shader stage. If it lands, I'll add a case to the fallback's synthetic tests: a 128-thread wave64 program using `v_mbcnt`, run as compute on a GTX 1060.

## Ported `ed9afc0` to an RTX 5060 tree — the world still presents black

Tried your mesh-host-lane change on a minimal local tree (upstream `ffe310e` + #876 typeless + #902 heap fallback + the `#728` waterfall/lane fork). That tree has no `Wave64Mode` / `host_lane_index()` (no #189), so I reproduced the semantics inline in `lane_index()`:

```rust
if self.s.mesh.is_some() {
    if self.x.native.wave64 {
        self.s.flags |= flags::WAVE_OPS;
        return self.s.op(self.s.entry, "waveGetLaneIndex", Attr::ReadOnly, self.s.t.i32, 111, &[]);
    }
    ...
}
```

Compiles clean, runs through the same boot path. **Result: presented image unchanged** — `500 draws/frame`, 1.0 fps (1080 ms/frame), uniform dark purple, same as before the patch. No device removal, no `no host texture`, heap still capped at 1,000,000 for 1,245,184.
