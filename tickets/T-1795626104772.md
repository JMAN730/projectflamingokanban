## Original body

Counts and container-format facts only: no shader hashes, disassembly or other game data.

## What happens

`XboxBvhBuilder.dll` holds 52 compute programs. In a release run into the first mission, the title uses 35 of
them, and all 35 fail at pipeline creation, so their dispatches are dropped. In that run, 4 of the 7 programs
dropping the most dispatches per frame are builder programs: about 690 dropped dispatches per frame together.
Whatever reads the structures they should build then reads nothing.

## How the builder's programs get their arguments

Read from the containers as `crates/victory-shader/src/native.rs` documents them:

- Each container has an `RTS0` root signature (version 2, flags 0x3000000: directly indexed heaps) made only of
  root views (UAV, SRV) and root constants (1 to 19 dwords); no descriptor tables.
- Each compute record has a root layout table (3 to 9 entries) whose first parameter starts at user-data dword 16,
  while `COMPUTE_PGM_RSRC2` asks for 4 user SGPRs. The program reads its arguments through the table `s[0:1]`
  points to (the high dword masked to a 40-bit address): dword `16 + k` of the user data is at byte `4 * k`.

That is the spill-table case #302 handles. With #302 merged, the 35 programs the title uses still fail, for these
reasons:

| programs | reason |
|---|---|
| 10 | a root UAV or typed root view is not supported (most builder buffers are root UAVs) |
| 8 | an address from a root parameter that is no address (addresses passed as two root constants) |
| 12 | an address not from a root parameter (not looked at yet) |
| 4 | console wave64 lanes on a host without 64-lane waves |
| 1 | an address in an SGPR that is no root parameter |

## What it needs

1. Root UAVs end to end (#294 adds them).
2. Addresses held in a pair of root constants, treated like a root view's address (translator and the GPU side).
3. A look at the 12 programs whose addresses come from neither.

Note: `victory translate` does not apply #302's spill rewrite (`apps/victory/src/translate.rs` calls `ir::build`),
so on the command line all 52 still fail with "an address in an SGPR that is no root parameter". Comment on #302.

Related: #274 (the builder's containers use the same native format as the title's), #302, #294.

Checked on: `main` (d2a4bae) with #175, #89, #302, #489, #307, #320, #550, #483, #452, #587 and 162 other open PRs
merged locally, release build, Windows 10 19045, RTX 5060 Ti (driver 621.14). Not checked on AMD.

AI use: Claude Code, Claude Opus 5.5.

Where the `an address from a root parameter that is no address` programs go next, measured in the title's opening cutscene. Counts only.

**The case.** On plain `main` these programs stop earlier, at `no root parameter`. With #302 and #489, 8 compute programs in the cutscene stop here, all with the address passed as two root constants. 7 of the 8 first use that address in a `global_load`, and none stores or does atomics through it.

**The prototype.** I prototyped the read-only route locally:
- the tracker recognises the constant pair, at any dword, across two parameters, and with an added offset;

To help debug this, I built a verification harness that provides a bit-exact golden model for FidelityFX CAS: [github.com/Cobrall/ffx-kit](https://github.com/Cobrall/ffx-kit)
Why it helps: Naive 'mathematically correct' CPU references often disagree with AMD's intended fast-math paths (like APrxLoRcpF1) by up to ~8.5%, causing false failures when validating a shader translator. This kit provides the exact expected output (including D3D saturate(NaN)=0 semantics), so you can definitively prove whether a translated shader is correct or if the bug lies elsewhere (e.g., descriptors, memory, or wave64 emulation).

### Comment 4 — @nineforge0 — 2026-11-24T08:12:40Z

We extracted the root parameter layouts of all 9,282 mesh shader programs and 2,647 compute shaders from the retail pipeline cache using [forge9](https://github.com/nineforge0/forge9). Here are the findings that may help with the rootless mesh shader translation:

**All mesh shaders follow a uniform 7-parameter binding model:**

| Slot | Type | SGPR count | Contents |
|------|------|-----------|----------|
| s8 | Table | 1 | Main descriptor table (72-261 entries) |
| s9 | Table | 1 | Secondary table (4-13 entries) |
| s10 | Table | 1 | Single-entry table |
| s11 | Descriptor | 2 | Root CBV/SRV (reg 0-9) |
| s13 | Constants | 1 | 1-2 dwords at b500/b501 |
| s15 | ResourceHeap | 1 | Bindless resource heap |
| s16 | SamplerHeap | 1 | Bindless sampler heap (87% of shaders) |

**Key findings:**
- Tables take **1 dword** in root memory, Descriptors take **2 dwords**.
- CascadeShadow shaders (522 programs) use a 5-param variant: no SamplerHeap, 1dw constants, Descriptor at s10 instead of s11.
- Compute shaders start at s4 (not s8), consistent with the 32-SGPR compute user-data window.
- The 64 RT trace/BVH compute shaders use only Tables + ResourceHeap + SamplerHeap in their FSSM root layouts. No root UAVs or root-constant address pairs appear in FSSM metadata.

**Full docs:** https://github.com/nineforge0/forge9/blob/main/docs/mesh_shader_binding_model.md

**To reproduce:** `forge9 fssm shaders.rpf 0 --roots` dumps the complete root parameter map for all 25,194 programs.

Hope this helps with the rootless shader translation path.
