## Original body

PR creation is limited to collaborators, so this is a branch ready to merge: [permadiego/VIctory@shader/mask-dword-joins](https://github.com/permadiego/VIctory/tree/shader/mask-dword-joins) (one commit, 7ab94ab, on top of ffe310e). Happy to open it as a PR if access opens up.

## What changed

Outside compute shaders a lane mask has no numeric form. Two patterns made programs fail with "a lane mask read as data" even though neither one reads a lane mask as a number.

**A mask dword at a data join.** The compiler reuses registers once a mask is dead. In the ped and fire mesh programs, for example, `s[8:9]` gets `s_cselect_b64 s[8:9], exec, 0` on one path, and `s9` gets `s_buffer_load_dword s9, ...` on the other. The data phi for `s9` then has a mask dword on one edge and failed. It now takes `undef` on the mask's edge. This is the same shortcut #180 uses for descriptor dwords at joins: it assumes the program reads the joined value only on paths coming from the data edge.

**`s_bcnt1` of a mask, used only for SCC.** For example:
```
s_xor_b64 s[12:13], vcc, exec
s_bcnt1_i32_b64 s12, s[12:13]      ; the count is overwritten right after
s_cbranch_scc1 ...
```
The lane pass now treats that SCC ("some lane is set") per lane, as it already does for the mask operations themselves (`r.scc` in `sop`). The count itself still has no numeric form, so a program that reads it still fails as before.

### Comment 9 — @r4tedx — 2026-11-24T17:23:38Z

A counterexample to the `fill_phis` arm in `7ab94ab`, run on main and on your branch.

The arm hands out `undef` for every incoming edge of a data phi whose value is a tracked lane-mask dword. It sits before the `read_phis` → `Retry` arms and has no check that the phi is never read after that edge. I wrote the same rule on another branch, and a review there found the problem with my own test, so I reverted it. The same program applies to yours:

```
v_cmp_eq_u32   vcc, 0, v0
s_mov_b64      s[8:9], vcc        ; mask in s[8:9]
s_cbranch_vccz join               ; taken only when VCC == 0, so s9 == 0 on this edge
s_movk_i32     s9, 0x1234         ; data on the other edge
join:
s_and_b32      s0, s9, 0xff       ; the joined s9 is read on both paths
v_mov_b32      v1, s0
exp            pos0 v1, v1, v1, v1 done
s_endpgm
```

As a wave64 vertex program (`0x7D840080, 0xBE88046A, 0xBF860001, 0xB0091234, 0x8700FF09, 0x000000FF, 0x7E020200, 0xF80008CF, 0x01010101, 0xBF810000`, `SV_Position` in OSG1), lowered with `emit` in a unit test:

- main `ffe310e`: refused, `a lane mask read as data` at offset 28.
- `7ab94ab`: translates. On the mask edge the console exports 0 (VCC's high dword when VCC is 0); the translation exports `undef`.

Validation cannot see this, so validated counts don't measure it. This doesn't say the programs the rule unlocks are wrong: NuraadGit's run above shows draws gained, and those may all be register reuse with dead mask edges. It says the rule can't tell them apart from a program like this one. The rule is still worth having: the programs it unlocks look like register reuse, where the joined value is only read after a data edge. But it needs that proven per program. The review suggested three things:
- hand out `undef` only where every block that reads the phi is reached only after a data edge (the structurisation's `reach` conditions);
- keep the `Retry` in the console flow and for the instructions allowed to read masks as numbers;
- add a test where the mask edge's value is dead, checking the value read on the GPU, not just that translation succeeds.

The title was not used in this test: it is the hand-assembled program above, compiled into the unit tests of both trees. The test code is below for anyone who wants to run it.
