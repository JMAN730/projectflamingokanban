## Original body

`max_and_min_order_negative_zero_below_positive_zero` in `valu_tests.rs` checks that `v_max_f32`/`v_min_f32`/`v_max3_f32`/`v_min3_f32` order −0 below +0 as RDNA2 requires. The f16 equivalents (`v_max_f16`, `v_min_f16`, `v_max3_f16`, `v_min3_f16`) go through the same `max_min()` helper (fixed by #448) but are never covered by any test.

## Affected instructions

| Instruction | VOP3 opcode | Tested f32 sibling |
|---|---|---|
| `v_max_f16` | 0x111 | `v_max_f32` (0x110) ✓ |
| `v_min_f16` | 0x10E | `v_min_f32` (0x10F) ✓ |
| `v_max3_f16` | 0x354 | `v_max3_f32` (0x154) ✓ |
| `v_min3_f16` | 0x351 | `v_min3_f32` (0x151) ✓ |

## Implementation evidence

`lower.rs`, `max_min()` at line 1377, is the single helper for all float min/max variants. For f16 inputs the caller widens them from f16 to f32 via `half_fsrc()` before entering `max_min()`, so the helper operates on f32-widened values. RDNA2's f16 −0 (`0x8000`) widens to f32 −0 (`0x8000_0000`), so the magnitude AND with `0x7FFF_FFFF` correctly detects the two-zeros case in widened space.

PR #448 explicitly states the fix covers "v_max_f32, v_min_f32, their three-operand and f16 forms". The implementation is correct; the f16 test was never added.

The f16 path in `valu16_op()` (`lower.rs` around line 4344):

```rust
"v_max_f16" => self.max_min(true, a, b),
_ => self.max_min(false, a, b),   // catches v_min_f16
```

And the three-operand f16 forms (`lower.rs` around line 4377):

```rust
"v_max3_f16" => { let t = self.max_min(true, a, b); self.max_min(true, t, acc) }
"v_min3_f16" => { let t = self.max_min(false, a, b); self.max_min(false, t, acc) }
```

## Missing test

`valu_tests.rs` `fn max_and_min_order_negative_zero_below_positive_zero()` (line 311) covers only f32 opcodes (`0x110`, `0x10F`, `0x154`, `0x151`). The f16 opcodes `0x111`, `0x10E`, `0x354`, `0x351` do not appear in the test.

The test helpers for f16 bit patterns are already present in the file (`f16_to_f32`, `is_f16_nan`), and f16 −0 (`0x8000`) is already used in `v_cmp_lg_is_false_for_nan`. Adding the f16 cases requires only a second `ops` array.

## Suggested test addition

Extend `max_and_min_order_negative_zero_below_positive_zero` with an f16 block:

```rust
// f16: -0 = 0x8000, +0 = 0x0000. The low 16 bits of v0 hold the f16 result.
let (pz16, nz16) = (0x0000_u32, 0x8000_u32);
let cases16 = [
    [nz16, pz16, nz16, 0],
    [pz16, nz16, nz16, 0],
    [nz16, pz16, pz16, 0],
    [pz16, nz16, pz16, 0],
];
let ops16 = [
    ("v_max_f16",  0x111, pz16),
    ("v_min_f16",  0x10E, nz16),
    ("v_max3_f16", 0x354, pz16),
    ("v_min3_f16", 0x351, nz16),
];
for (name, op, want) in ops16 {
    let shader = build_valu_cs(&vop3(op, 0, vgpr(1), vgpr(2), vgpr(3)));
    run_cases(&shader, &cases16, |backend, _, inp, got| {
        // compare low 16 bits only (f16 result sits in the low half)
        assert_eq!(got & 0xFFFF, want, "{backend}: {name} {inp:x?}");
    });
}
```

No game data needed; the test skips when no SM 6.6 device is available and runs on WARP.
