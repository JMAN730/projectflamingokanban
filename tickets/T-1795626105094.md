## Original body

## Summary

On an NVIDIA GeForce RTX 4060 the host device is removed during the
first-boot / menu screens, about 60–70 s after start (frames ~1250–2100),
well before loading into the world.

## Environment

- VIctory `main` at 015d45b, `diag` profile with `--features diagnostics`
- Windows 11 Pro 10.0.26200
- NVIDIA GeForce RTX 4060, driver 32.0.16.2124
- Console mode: Series X (default)

## Steps

    cargo build --profile diag -p victory --features diagnostics
    $env:VICTORY_D3D12_DRED = '1'
    target\diag\victory.exe run <game dir>\game_scarlett_master.exe --execute

Let the boot screens play. 4 runs out of 4 failed with exit code 5.

## What happens

    host GPU device removed after a submission of 4 lists; ...
    device removed: ... (0x887A0006)

With `VICTORY_D3D12_DEBUG=1` the debug layer reports no errors before the
removal (only harmless warnings: unbound DSV, resource creation hints), and
the reason is:

    DXGI_ERROR_DEVICE_HUNG: The Device took an unreasonable amount of time
    to execute its commands ... TDR

DRED reports no page fault.

## Where it stops (DRED breadcrumbs)

The hang does not follow one draw:

| Run | Frame | Stopped at |
|-----|-------|------------|
| 1 (DRED) | ~1870 | indexed 30x1, VS a59924ecd59ce5dd / PS a820d0c3bdb59905, next in flight PS 82ba5eae46a856a4 |
| 2 (DRED + debug layer) | ~2090 | one of 12 indexed draws with no marker; the list's last note was PS 872592596b3651f0 |
| 3 (DRED) | ~1224 | indexed 30x1, PS 82ba5eae46a856a4 |
| 4 (DRED, 82ba5eae dropped) | ~1650 | draw 6x1, VS 0602c2384acbb3b2 / PS a78d088fa55aa495 (full-screen pass reading a 3840x2160 SRV) |

The shaders in flight are trivial. I disassembled two of them with
`victory shader-info --disasm`:
- `a820d0c3bdb59905`: interpolates a color and exports it, no resources
- `82ba5eae46a856a4`: samples one 2D texture and exports it, no loops

Run 4 dropped every draw using `82ba5eae46a856a4` and still hung, at a
different draw. One bad shader seems unlikely.

## Pattern

Every hang comes at a screen change. On the GPU runs, "a black frame after a
frame that was not" is logged about every 216 frames (frames 357, 573, 789,
1005, 1222, ...), and each hang comes on one of those changes, when the next
screen first binds new pipelines. On WARP only the frame-1 black frame is
logged.

The window also goes black for a few seconds and comes back several times
before the hang. These are those same black frames.

## Not yet tried

- An Nsight Aftermath GPU crash dump, which would name the shader and
  instruction the GPU was running
- Whether Series S mode or a release build behave the same

Full logs available on request.

### Comment 2 — @DaniloMaglia — 2026-11-23T23:09:57Z

Update: it isn't a hang. It's a use-after-free, and I have a fix.

**What Aftermath shows.** I loaded NVIDIA's Aftermath library in the
diagnostics build and got a GPU crash dump on the next failure. It shows a
page fault, not a timeout:

    "Device state": "Error_DMA_PageFault"
    "Fault Type": "Failed to translate the virtual address."  (Read, pixel shader)
    "Resource": committed 256x1 DXGI_FORMAT_R32G32B32A32_FLOAT, 32 KB,
                "Destroyed": true

The title creates and releases this texture within 2.7 ms around screen
changes, and the host copy was freed about 3 ms before the fault. That's why
DRED and the debug layer pointed at a different trivial draw each time.
NVIDIA faults on this; other hardware may read zeros instead.

**Two gaps let the host texture be freed while it's still referenced:**

1. `Queue::signal` completes the title's fence at once, but a host submission
   from another thread can still be running. The title then releases the
   texture, `Resource`'s `Drop` frees the `ID3D12Resource`, and the running
   submission reads freed memory.
2. Translated shaders index the host descriptor heap directly, and a slot is
   only rebuilt when a draw's table walk visits it. After
   `descriptor::forget`, a slot made from a released texture keeps a live SRV
   to the freed host resource.

**Fix.**
- `host::retire` frees a released resource's host texture at once if no
  submission is running, otherwise after the running one finishes.
- `descriptor::forget` passes the retired view records to every host heap,
  which nulls the slots made from them (a record-to-slots index, so no heap
  scan).

**Result.** With both changes there's no device loss. The run gets through
the setup screens (about 2 minutes) and the opening cinematic starts, with
audio. Then the title itself crashes: the frame counter stays at 2222 for
more than 10 s while mesh pipelines are built, followed by
`0xc0000005 at <title exe>+0x23cf683 (write 0x0)` and the title's crash
reporter. That looks like a deliberate fatal error, probably part of the
known world-performance work rather than this bug.

I don't yet know whether the slot-nulling change is needed on its own; the
page fault was gone only once both changes were in.

Still open from my first post: on the real GPU, single black frames show up
about every 216 frames during the setup screens. They're single frames
between normal ones, not fades.

I can open a PR with the fix. I also added three diagnostics-only switches
that could go in the same PR or be left out:
- `VICTORY_AFTERMATH=<path to GFSDK_Aftermath_Lib.x64.dll>` writes an NVIDIA
  crash dump and its decoded JSON when the device is lost. The DLL is loaded
  at run time; nothing from NVIDIA is linked or shipped.
- `VICTORY_SHADER_DUMP=<dir>` saves each translated shader container.
- `VICTORY_SKIP_SHADERS=<hash>,...` drops the draws of the listed shaders.

### Comment 5 — @DaniloMaglia — 2026-11-23T23:31:34Z

Update: with current `main` plus two fixes from elsewhere, the RTX 4060 runs
without device loss and the menu flicker is gone.

**Device loss: fixed** by the patch in
https://github.com/Marvisak/VIctory/issues/16#issuecomment-7116625315
(thanks @FIocker). My logs had both `no host texture` lines, formats 86
(`B5G5R5A1_UNORM`, UAV) and 115 (`B4G4R4A4_UNORM`, render target), on every
GPU run and never on WARP. With the patch:

    the host's format support lacks uses of this texture; made without them format=86 flags=0x5 dropped=0x4
    the host's format support lacks uses of this texture; made without them format=115 flags=0x1 dropped=0x1

The run then goes through the setup screens and menus, plays the
"Rockstar Games presents" card and loads into the world (game audio plays,
the picture is black, as listed under "Not working yet" in 8c26061).
After about 2 min 20 s there was no device loss and no crash.

The use-after-free I described above is already handled on `main` by
8c26061 (host lists hold the textures they name, heap slots hold the
resource they view), so I'm dropping my fix for it.

**Black flashes in the menus: fixed** by #20. Without it, single black
frames showed up about every 216 frames and in bursts at screen changes
(frames 357, 573, 789, ... in each run). With #20 the only black frames
left are frame 1 and a 4-frame black at frame 759, which looks like an
intended cut (brightness 44 → 0 for four frames → 45), not flicker.

Tested on `main` (8c26061) with the #16 patch and #20 applied:
- NVIDIA GeForce RTX 4060, driver 621.24, Windows 11 Pro 26200
- `cargo test -p victory-gpu`: 36 passed; clippy clean
