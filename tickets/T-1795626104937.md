## Original body

### GPU: Pre-check wave lane constraints for compute pipelines

Fixes #817 (related to #468 / PRs #233, #189, #578).

#### Problem
Titles emitting 64-lane compute shaders cause pipeline creation to fail on host GPUs that only support up to 32 lanes (e.g. NVIDIA or Intel hardware reporting `WaveLaneCountMax = 32`). While logging the error inside `CreateComputePipelineState` failure paths (as explored in diagnostic branches) surfaces the issue, passing an incompatible bytecode directly to the D3D12 runtime triggers driver error queue noise and debug layer breaks.

#### Solution
Instead of failing late inside the driver, this PR adds an upfront capability check:

1. **Device Capability Query (`crates/victory-gpu/src/device.rs`, `host.rs`)**:
   - Queries `D3D12_FEATURE_DATA_D3D12_OPTIONS1` at device creation via `CheckFeatureSupport`.
   - Stores host `wave_lanes: Option<(u32, u32)>` (`WaveLaneCountMin`, `WaveLaneCountMax`).

2. **Wave Size Extraction from DXIL (`crates/victory-shader/src/emit/mod.rs`)**:
   - Implements `HostShader::required_wave_size(&self) -> Option<u32>`.
   - Inspects the DXIL container's `PSV0` runtime info part (bytes 20..28) to read the declared wave size constraint (`WaveSize`).

3. **Compute Pipeline Pre-check (`crates/victory-gpu/src/pipeline/host.rs`)**:
   - In `HostPipeline::create()`, if the compute shader specifies `required_wave > max_wave_lanes`, we emit an informative `tracing::warn!` and skip host pipeline creation cleanly (`return None`) without invoking `CreateComputePipelineState`.

#### Verification
- Unit test `required_wave_size_reads_the_emitted_constraint` covering unconstrained, Wave32, and Wave64 shaders in `victory-shader`.
- Unit test `query_wave_lane_limits_reports_capabilities` in `victory-gpu`.
- `cargo test -p victory-gpu` (51 passed, 0 failed).
- `cargo clippy --all-targets -- -D warnings` and `cargo xtask policy` pass cleanly.

Branch: [`feat/issue-817-wave-lane-check`](https://github.com/Xvania7/VIctory/tree/feat/issue-817-wave-lane-check) (commit `1318357`).

### Comment 2 — @fuzeofficlal — 2026-11-24T13:53:29Z

The upper-bound test above covers Wave64 on a `32..=32` device. I checked the other end on `1318357` with a CPU-only capability fixture. For `[WaveSize(32)]` and a reported range of `64..=64`, the existing max-only check still proceeds toward PSO creation. D3D12 validates a fixed wave size against the full reported range. [Shader Model 6.6 runtime validation](https://microsoft.github.io/DirectX-Specs/d3d/HLSL_SM_6_6_WaveSize.html#runtime-validation)

[Follow-up commit](https://github.com/fuzeofficlal/VIctory/commit/1ca1b018e110d7fbec9069c71634bb680fafd036) checks the inclusive range and reports both limits in the existing warning. The tests cover both out-of-range directions, accepted boundaries, and the path for an absent constraint or unavailable caps.

`victory-gpu --lib` passed 53 tests with one benchmark ignored. Clippy and the staged asset check passed.
