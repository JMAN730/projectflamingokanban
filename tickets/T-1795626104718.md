## Original body

game_scarlett_master.exe crashes ~1.3 s after the first frame with 0xc000001d at victory-image-b99f876b74d4a77f.dll+0x4ecc84a.

Running under Intel SDE shows why:

SDE-ERROR: Executed instruction not valid for specified chip (FUTURE): clzero
Instruction bytes are: 0f 01 fc

CLZERO is AMD-only (Zen), so any Intel CPU raises #UD. (The SDE site differs from the native crash site, so there may be several; I haven't confirmed the native one is also clzero.)

Suggestion: emulate it in a vectored exception handler. On EXCEPTION_ILLEGAL_INSTRUCTION with bytes 0f 01 fc at RIP, zero 64 bytes at RAX & !63, add 3 to RIP, and continue.

Environment: Windows 11, Intel Xeon E5 2680 v4 (X99), RX 580, 16 GB RAM.

If required, log will be attached.

### Comment 2 — @DaviTostes — 2026-11-24T00:38:23Z

This is the same class as #7/#102/#103: the loader's illegal-instruction handler (`crates/victory-loader/src/crash.rs`) emulates the console-CPU instructions an Intel host lacks, and the missing ones are being added in open work.

- **CLZERO**: a single `clzero` is already handled on `main` (`0f 01 fc` → zero the 64-byte line at `rax`).
- **CLZERO loops and `rdpru`**: **#34** (open, `faa0a9a`) rewrites the handler so a compiler's `clzero`/`monitorx`/`mwaitx` loop completes in one exception and adds `rdpu` (`0f 01 fd`). That looks like the missing piece for a title that spins on `clzero`.
- For reference, **#45** (now merged in `7d33c46`) is the CLWB counterpart for Intel CPUs before Ice Lake.

If it still faults with #34 on top, the useful next datum is the crash log line with the exception address and the exact CPU model — the handler matches instruction bytes, so that tells which encoding it did not recognise.
