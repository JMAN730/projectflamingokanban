### Comment 1 — @meeyao — 2026-11-24T20:28:23Z

One concrete set from the Linux/Proton side: fxceless/victory-gta6#28 carries three fixes that were the difference between a black frame and a rendering world on Proton Experimental + vkd3d-proton + RTX 3070.

1. **The argument clamp needs a compiler Wine has.** `indirect::make` uses `D3DCompile`; Wine's `d3dcompiler_47` refuses the source (`InterlockedMax`, stores to a raw buffer), so `bound()` fails and every indirect execution is dropped. The PR falls back to DXC (`dxcompiler.dll` beside the exe) as `cs_6_0`. On Windows the system compiler still wins.
2. **The watchdog hooks are absent from that fork.** Every run there ended at `+0x23cf683` after 6–8 minutes in the world; upstream #454's `VICTORY_NO_WATCHDOG` patches (build hash + exact bytes, jump over the call and NOP the deliberate fault) stop that. Patching the watchdog thread's entry instead stops the kills but the title never draws.
3. **Pipeline workers need more than the default 2 MiB stack.** Large mesh programs overflow it: `thread 'victory-pipelines-2' has overflowed its stack`. The worker dies, the pipeline never appears, and the title waits forever — the log goes silent for ~10 minutes with CPU still busy. `stack_size(32 << 20)` fixes it.

With those: world geometry renders, `frame=4096 draws=28708 drawn=25391`, `3,389 indirect commands bounded`, no stack overflow and no watchdog kill. The remaining wall is speed (0.1–0.5 fps; host-side copies and watches, GPU ~12% busy).

Reproduction notes, environment sets, expected warnings and a stall-skipping supervisor: https://github.com/meeyao/VIctory/tree/linux-findings — no game data, patches only.


### Comment 2 — @Luislariosss — 2026-11-24T20:42:39Z

A review of fxceless/victory-gta6 against current main (`ffe310eb`), in answer to this issue's question. Short version: several pieces look worth taking, one is blocked by licensing, and much of the rest duplicates open PRs. Nothing can be merged wholesale — the repo is standalone (not a GitHub fork), 9 commits ahead, and nearly all of the work sits in one squashed commit (`578d459c`, 68 files), so every piece would need to be split out, rebased and given its own tests and attribution.

What is in it, grouped (memberships from the compare's file list, the fork's README and commit messages; the large GPU/shader diffs were not read line by line):

- **Shader clean-up passes** (`emit/bitcode/opt.rs`, `emit/bitcode/census.rs`, selected by `VICTORY_SHADER_OPT` bits): dead-code removal, folding, reuse, branch facts, block-local loads. The fork's README claims about 43% fewer host instructions and about 20 ms less GPU time per frame, measured on one machine. I found no open PR covering this. New, self-contained, and the most interesting claim — worth splitting out and re-measuring on other GPUs. The bit-mask switch is part of the shader cache key and needs a correctness review there.
- **Ray-tracing emulation** (a CPU reference for `image_bvh(64)_intersect_ray`, DXIL lowering, raw 40-bit title-memory reads, `docs/fork-ray-tracing.md`): overlaps open #1198 (and #702 for a native DXR path); better compared with that author's work than merged on top of it.
- **Wave64-on-wave32 forms** (`emit/wave.rs`, `wave64_tests.rs`, `threading.rs`, behind `VICTORY_WAVE_WIDE=1`): overlaps #189/#1589/#1618.
- **Pipeline waits and prewarm** (ZazaJr24's `d279e69a`): overlaps #254/#275/#1551.
- **GPU and memory work** (in-place card-memory copies of large title buffers, shadow buffers, watch/page-query speedups, late wait and relay thread, descriptor-table exhaustion, pipeline library mapped rather than read, and a fix for the library being replaced while mapped): overlaps the upstream shadow and pipeline-library PRs (#1124 #1502 #1472 #185 #1555, and the #1604 bundle). The "library replaced while mapped" fix may be new — worth hunting for it in the diff.
- **Test and CI robustness** (the software adapter is no longer mistaken for hardware, so card-needing tests skip on hosted runners; a mesh pipeline test fixed for unsupported GPUs): small, cheap to take as a rebase.
- **Console-instruction emulation** (`clzero` and other Zen 2 instructions the title zeroes memory with, `crates/victory-loader/src/console_insn.rs`): genuinely new and valuable for Intel hosts — but **blocked as it stands**: the file states it is ported from XCL (GPL-2.0-only) with the decoder copied unchanged. GPL-2.0-only code cannot be relicensed into this repository's GPL-3.0-or-later. It would need a clean-room rewrite from AMD's published documentation.

The Proton fixes meeyao points at below (the fork's PR #28) are already upstream: the DXC fallback is #178, the watchdog hooks #454, the 32 MiB worker stacks #1257.

Asset policy: I found nothing game-derived in the tree — the largest files are all source, and the only binary is the allowed `bcpack-tables.bin`. The license is GPL-3.0. Two caveats for a maintainer's eye: `lower.rs` there is about 488 KB, near the policy's 512 KiB per-file limit, and `docs/fork-ray-tracing.md` names the title's `XboxBvhBuilder.dll` and counts its compute programs — descriptive prose, but it deserves one read under the "derived from the game" rule.

Facts only; no verdicts on anyone's approach. The fork's own README is honest about its state (one RTX 4070, several off-by-default switches, `shortcut:`-marked paths, "not playable yet").
