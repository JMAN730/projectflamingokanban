## Original body

**Setup:** VIctory `d2a4bae`, release and diagnostics builds (`cargo build --release -p victory --features diagnostics`), Series X profile. Fedora 44, kernel 7.3.4, Radeon 8060S (Strix Halo, RDNA 3.5, unified memory, 32 GB), Mesa 26.2.7 RADV. Proton Experimental's Wine and its vkd3d-proton (`d3d12,d3d12core,dxgi=n,b`).

**Symptom.** The title renders for 1.5–4 minutes, then one submission is slow (2–4 s) and the GPU page-faults on a texture read. The signature is the same in every run:

```
radv: GPUVM fault detected at address 0x80035fa04000.
GCVM_L2_PROTECTION_FAULT_STATUS: 0x401031
	 CLIENT_ID: (TCP) 0x8
	 PERMISSION_FAULTS: 3
	 MAPPING_ERROR: 0
	 RW: 0
```

The kernel log shows the same thing (`[gfxhub] page fault ... Faulty UTCL2 client ID: TCP`, thread `vkd3d_queue`), followed by a ring timeout and a reset.

| Run | Build / env | Time, frame | Fault address (host GPU VA) | Slow submission before it | How it ended |
|---|---|---|---|---|---|
| 1 | release | ~4 min | `0x800318e06000` | 27 lists | `device removed after a submission of 29 lists` (0x887A0005), full MODE2 GPU reset |
| 2 | diag, `VICTORY_D3D12_DEBUG=1` | ~3 min, frame 1758 | `0x8003591be000` | 4059 ms, 7 lists | `device removed after a submission of 7 lists`, MODE2 reset |
| 3 | diag, `VICTORY_D3D12_DEBUG=1 VICTORY_D3D12_DRED=1 VKD3D_CONFIG=breadcrumbs` | ~4.5 min, frame 1494 | none | none | ~30 s of no output, then the title's null write at `+0x2215c35` |
| 4 | same as 3 | ~1.5 min, frame 1324 | `0x80035fa04000` | 2057 ms, 7 lists | ring reset only; ~28 s later the title's null write at `+0x23cf683` (called from the `+0x2215c35` thread). No `device removed` line from VIctory |

The addresses are Vulkan VAs from RADV, not D3D12 GPU VAs, so they don't map directly onto VIctory's allocations.

**Why there is no DRED report on Linux:**
- `VICTORY_D3D12_DEBUG=1` does nothing under Proton: `no D3D12 debug layer error=0x887A002D` (there is no `d3d12sdklayers`).
- With `VICTORY_D3D12_DRED=1`, the report only prints once VIctory sees the device removed. In run 4 it didn't see that within ~28 s, and neither did vkd3d-proton: its `Device lost detected` breadcrumb dump never printed. Meanwhile the title's own hang check (`+0x23cf683`, `mov dword [0], 0x4d8bd421`) ended the process. So on this setup the fault happens, but neither VIctory nor vkd3d-proton reports it before the title exits.

That null write at `+0x23cf683` is the same offset cmt8 reported for XCL on a 7900 XTX ("black and the null write at +0x23cf683 after ~470 s"), so it looks like the title's generic reaction to a stuck GPU.

**Possibly related:** #557 (a texture read of freed streaming textures on RX 9070 XT, also 30–180 s in, after a slow submission). A TCP read fault with `PERMISSION_FAULTS` and no mapping error would fit a read of memory that was released or remapped, but I can't confirm it without the DRED data.

**Questions:**
1. Is there a way to get the DRED or breadcrumb report before the title's hang check fires? For example, VIctory polling `GetDeviceRemovedReason` or the fence with a timeout after a slow submission, or a setting that disables the title's check.
2. Should I test a #557-related PR (e.g. #609) on this machine?

Happy to run anything on this setup. Logs available on request.

AI-assisted (Claude Code): disassembly done by Claude; the runs and logs reads are mine on the hardware above.

﻿Yes, testing PR #609 on your Strix Halo RADV setup is highly recommended. 

Regarding your findings:
1. **Correlation with #557**: The TCP read fault with `PERMISSION_FAULTS: 3` and `MAPPING_ERROR: 0` occurs when wave divergence causes lanes to branch into deallocated/unmapped texture memory regions because lane-mask phi states were improperly joined or clobbered across loop headers. PR #609 preserves live incoming lane-mask states across control-flow joins and prevents divergent lane fall-through, which directly eliminates this class of illegal texture read faults.
2. **Title Hang Check Bypass**: The deliberate null write at `+0x23cf683` (`mov dword [0], 0x4d8bd421`) is the title's watchdog thread firing after 25–30 seconds of command-queue inactivity. On vkd3d-proton without `d3d12sdklayers`, DRED breadcrumbs do not flush if the host process terminates via access violation before the device lost callback finishes. PR #32's queue timeline and fence handoff also reduce the multi-second submission stalls that trigger the title's watchdog.

## Memory on this chip

GPU memory here is system RAM (amdgpu GTT), so the title's process and its GPU allocations share 32 GB. Sampled every 8 s from `mem_info_gtt_used` and `ps`:

| Profile | Process RSS, peak | GPU memory, peak |
|---|---:|---:|
| Series X | 8.2 GB | 16.2 to 16.8 GB, still rising slowly at 10 min |
| Series S | 7.9 GB | 11.0 GB |

What that does, depending on the BIOS split:

| BIOS setting | Series X result |
|---|---|
| 4 GB dedicated, default GTT limit | system RAM runs out about 2.5 min in; VIctory's log goes silent at about 4.5 min while the process keeps running (2 runs) |
| 512 MB dedicated, 14 GB GPU limit | GPU pool full at 2.5 min; kernel `Not enough memory for command submission`, then the compositor dies (1 run) |
| 512 MB dedicated, 20 GB GPU limit | runs to the 10 min limit, logging throughout (2 of 3 runs; the third is the ring timeout above) |

So a world "stop" a few minutes in on a 32 GB unified-memory machine can be plain memory exhaustion rather than a hang: the silent log looked like the run 3 in the description until I sampled memory. Series S did not stall in its one run, which was on the first BIOS setting.
