## Original body

`format_load` pads the 4th channel of a `tbuffer_load_format_*` with `1` / `1.0` when the format has fewer channels. RDNA2 hardware reads 0 there. I measured all 77 GFX10 buffer formats; the full result tables are below.

**Setup.**

- **Hardware:** an AMD Radeon iGPU (Ryzen 7 9800X3D), **gfx1036 / RDNA2**, AMD driver 32.0.21042.62, Windows 11. A HIP kernel (assembled by the driver's amd_comgr) builds a raw V# over 64 rows of 4 dwords and runs `tbuffer_load_format_xyzw … format:N offen` for N = 1..77. The rows hold byte, half and float edge patterns, plus random values.
- **Translator:** the same `MTBUF` words through `build_valu_cs`, on `main` `ffe310e`. The test stores the 4 input dwords to the UAV, loads them back with `format:N` and stores the 4 results. It ran on an RTX 5080 (driver 610.88) and on the same Radeon iGPU (picked with #94's `VICTORY_ADAPTER`). Both hosts give the same results, apart from NaN payloads of the 16-, 11- and 10-bit floats on NVIDIA.

This is RDNA2 desktop silicon, not the console's GPU. No game data was used.

**1. Channels a format doesn't have read 0, including the 4th.** This holds on gfx1036 for every format with fewer than 4 channels and every numeric kind. All 6,208 missing-channel values in the run are 0. `main` gives 1 / 1.0 in the 4th channel, so with these rows the translation differs from the hardware in 64 of 64 rows for each of the 49 formats with 1-3 channels.

The descriptor's `dst_sel` doesn't change this for `tbuffer` loads. In one kernel, with one descriptor, I set the V#'s `dst_sel` to identity, W=ONE, W=ZERO, all ONE, X↔Y, and X=W:

| | `tbuffer_load_format_xyzw format:32_32_32_FLOAT` | `buffer_load_format_xyzw`, V# format `32_32_32_FLOAT` |
|---|---|---|
| identity | `(x, y, z, 0)` | `(x, y, z, x)` |
| `dst_sel_w` = ONE | `(x, y, z, 0)` | `(x, y, z, 1.0)` |
| `dst_sel_w` = ZERO | `(x, y, z, 0)` | `(x, y, z, 0)` |
| X↔Y | `(x, y, z, 0)` | `(y, x, z, x)` |

So the typed (`MTBUF`) form ignores `dst_sel` and reads 0 past the format, which matches the `shortcut:` in `format_load`. The `MUBUF` form applies `dst_sel`. With an identity swizzle the `MUBUF` form reads the format's own channels again in the missing slots: `32_FLOAT` gives `(x, x, x, x)`, `32_32_FLOAT` gives `(x, y, x, y)`, `8_8_UNORM` gives `(x, y, x, y)`. That second column doesn't affect `format_load`. It may matter for the typed-view path of `buffer_load_format_*`, where a D3D typed view reads `(…, 0, 0, 1)`.

**2. UNORM / SNORM: the hardware rounds correctly.** #25's comment already notes that the division is 1 ULP off. For the record, on gfx1036 every UNORM and SNORM value in the run is the correctly rounded `k / (2^n - 1)` (0 exceptions over all 20 norm formats, the 2-, 10- and 11-bit fields included). The host's division is off on these values, identically on AMD and NVIDIA:

| Format | values differing from the hardware (1 ULP) |
|---|---|
| `8_UNORM`, `8_8_UNORM`, `8_8_8_8_UNORM` | 16 of 64, 40 of 128, 80 of 256 |
| `8_8_SNORM`, `8_8_8_8_SNORM` | 4 of 128, 6 of 256 |
| `16_UNORM`, `16_16_UNORM`, `16_16_16_16_UNORM` | 1, 1, 3 |
| `16_SNORM`, `16_16_SNORM`, `16_16_16_16_SNORM` | 1, 2, 3 |
| `10_11_11_UNORM`, `_SNORM` | 1, 6 |
| `11_11_10_UNORM`, `_SNORM` | 1, 4 |
| `10_10_10_2_SNORM` | 6 |
| `2_10_10_10_UNORM`, `_SNORM` | 3, 6 |

For example, byte `0xfe` as `8_UNORM` is `0x3f7efeff` on the hardware and `0x3f7eff00` on the host.

The packed formats from #25 (`10_11_11`, `11_11_10`, `10_10_10_2`) otherwise match the hardware bit for bit, including the `_FLOAT` ones.

**A fix.** On `Lyrnc/VIctory` branch [`fix/tbuffer-hw-channels`](https://github.com/Lyrnc/VIctory/tree/fix/tbuffer-hw-channels) (one commit on `ffe310e`):

- Missing channels read 0, and the doc comment says why.
- The UNORM/SNORM conversion no longer divides. In binary, `k / (2^n - 1)` is the `n` bits of `k` repeating forever. So the f32 is the first 24 bits of that stream after its leading 1, rounded up when the 25th bit is set. A tie can't happen, because the stream never ends. In the lowering, `k` times a repeat constant gives the stream in an i64. `k`'s f32 exponent gives the shift, and a 39-bit right shift gives 24 bits plus the rounding bit. SNORM is the same on `|s|` with `n - 1` bits, then the sign, with the most negative value clamped to -1.
- The `typed loads` diff test zero-pads `snorm16x2` on the PC side. That was the only case with a 2-channel format loaded as 4. I couldn't run the diff tests, since they need the console compiler.
- Two GPU tests in `valu_tests.rs`. One checks for 0 past the format's channels (8 formats). The other checks norm rounding for 15 formats, with every byte in every position and the values from the table above. Expected values come from an f64 division in the test, which is exact here.

Results on that branch:

| Run | RTX 5080 | Radeon gfx1036 | WARP |
|---|---|---|---|
| new tests | pass | pass | pass |
| new tests with `main`'s `lower.rs` | fail (`format 5: [1, 0, 0, 1], want 0 past channel 1`) | — | — |
| all 77 formats × 64 rows against the hardware | 0 differences (NaN payloads aside) | 0 differences | — |

I'll open it as a PR once external pull requests are open again, or a maintainer can take it from the branch.
