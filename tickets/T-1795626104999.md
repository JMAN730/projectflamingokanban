### Comment 1 — @Ingenioeren — 2026-11-24T15:27:29Z

If the `0x887A0004` in this report is on the `no breadcrumbs` line, it is the result of `GetAutoBreadcrumbsOutput`. The separate `device removed` field comes from `GetDeviceRemovedReason` and is where `0x887A0006` identifies the reported hang. On `ffe310e`, these come from [the breadcrumb query](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L653-L660) and [the final failure report](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L95-L104).

I checked both APIs on Windows 11 build 26200 using a synthetic WARP device and `ID3D12Device5::RemoveDevice()`. With auto-breadcrumbs forced off, the breadcrumb query returned `0x887A0004`. With auto-breadcrumbs forced on before device creation, it returned `S_OK`. The removal reason in this synthetic test was `0x887A0005` in both runs. This confirms that the breadcrumb error can change independently of the removal reason. [Microsoft's breadcrumb API documentation](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12deviceremovedextendeddata-getautobreadcrumbsoutput)

For this report, the useful follow-up would be the stopped list and command from a diagnostics build (`cargo build --profile diag -p victory --features diagnostics`) with `VICTORY_D3D12_DRED=1`. The release build's debug flag alone leaves breadcrumb collection off. That would help tie the hang to an in-flight command instead of the last pipeline logged. [VIctory diagnostics options](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/README.md#L106-L124)

_AI-assisted. The synthetic probe used no game files and did not reproduce the cutscene hang._
