## Original body

### **Summary**
On my NVIDIA machine, entering the world ends in a host GPU failure: the device is removed and Windows resets the display driver. Menus, intro video and loading into the world all work fine on the same adapter; only the world reproduction fails. I'm reporting the breadcrumb pattern and a full offline shader-translation report because both repeat across runs.
The README notes the project was tested on AMD RX 6700 XT and warns that entering the world on a real GPU can hang it. I don't have an AMD card to compare, so all data below is from NVIDIA.

### **Environment**

- OS - **Windows 11 x64 (Russian locale, so system strings in the log are localized**
- GPU - **NVIDIA GeForce RTX 4060 Ti (DXIL SM 6.6, wave32)**
- GPU Driver - **Game Ready 562.01 (WHQL)**
- CPU - **Intel Core i5-12400F**
- RAM - **32GB DDR4**
- Build - **The latest as of 24.11.2026**

### **Repro**

    Fresh config from victory.example.toml.
    Run the title: first-boot screens, intro video, menus, start screen — all OK at 30 fps.
    Load a save, wait through the world loading screen (~50 s).
    The world is reached; the screen goes black for a moment (Windows driver reset), and the run ends with a host GPU failure logged to crashes.log.
Reproduces every attempt to enter the world (8 failures over 3 sessions, same day).

### **Offline shader-translation statistics**
Ran victory translate --list --jobs 8 on the title files. Summary:

> containers   26599 (614 duplicates skipped)
> programs     26148 translated of 26148 (40647088 IR instructions)
> structured   26148 of 26148 (32660347 vector instructions, 822675 guarded, 49485 on opaque masks)
> resources    25502 of 26148 tracked (descriptors 250974 loaded, 123322 built, 172440 constant)
> DXIL         12284 emitted of 14013 vertex and pixel programs
>              1693 emitted of 2581 compute programs
>              8191 emitted of 8506 mesh programs

So roughly 12% of V/P programs, 34% of compute programs and 4% of mesh programs fail to emit DXIL. The full per-shader log is attached as shader_errors.txt.

### **Top Shader Translation Failures:**
Here are the most frequent unsupported features found in the game's shaders:

    653 occurrences: emit: a 64-bit image atomic
    573 occurrences: emit: a scalar memory read as data
    298 occurrences: resources: a descriptor neither loaded nor built
    288 occurrences: emit: a select on an untracked mask
    276 occurrences: emit: a lane mask holding lanes elsewhere read as data
    247 occurrences: resources: an address in an SGPR that is no root parameter (Note: 100% of shaders in XboxBvhBuilder.dll fail with this exact error).
    207 occurrences: I/O: an interpolation with computed barycentrics
    117 occurrences: emit: a structured buffer of unknown stride
    29 occurrences: no DXIL part (SM5 or older) (Specifically in amd_fidelityfx_upscaler_xbox.dll)

### **Crash Log Snippet (WARP):**
The crash consistently happens during compute dispatches related to world streaming or BVH building. Example from crashes.log:

...
device removed: (DXGI_ERROR_DEVICE_REMOVED, 0x887A0005)



    Is there a known workaround or stub for the 64-bit image atomic and SGPR root parameter issues to at least allow the game to boot into a (possibly broken) world on NVIDIA hardware?
    Should amd_fidelityfx_upscaler_xbox.dll (SM5 shaders) be bypassed entirely in favor of a different upscaling method for now?
