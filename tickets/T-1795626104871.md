## Original body

# A reusable bench script: one command gives the same five numbers for any build

Chasing individual bugs is the maintainers' job. What is missing on the testing side is a
**comparable scorecard** — right now every report in this tracker states its numbers differently
(different durations, different stages, sometimes no memory figure), so two patches cannot be put
side by side. This is a small script that fixes that for Windows hosts.

## What it produces

One Markdown report per run, with exactly the numbers a patch review needs:

```markdown
| metric | value |
|---|---|
| translation failures | 63 |
| texture creation failures | 4 |
| peak draws/frame | 1894 |
| peak fps | 30 |
| peak RAM | 3.34 GB |
| crash RVA | (none) |

## Failures by reason
  44x  a descriptor read only as data
  11x  a structured buffer of unknown stride
```

plus a 3-second-resolution timeline and an optional `-Baseline <report>` diff table, so
"this patch moved the needle" becomes a two-column comparison instead of a paragraph.

## Safety is built in (this matters on 32 GB hosts)

A title run in Series X mode reaches 13.2 GB RSS and eats the desktop (see #784). The script
therefore stops the run on any of three conditions and says which one fired:

```
process RSS   > 8 GB        (default, -MaxRamGB)
system free   < 3 GB        (default, -MinSysGB)
time budget   expired       (default 180 s, -Seconds)
```

Three-second sampling, because a 5-second window can miss a spike.

## Usage

```powershell
# baseline, memory-lean mode
.\victory-bench.ps1 -Console series-s -Seconds 120 -Label 'main @ ffe310e'

# a patched build, diffed against that baseline
.\victory-bench.ps1 -Exe ..\victory-target\release\victory.exe `
                    -Baseline .\bench\report-<stamp>.md -Label 'with #728'
```

It never writes into the repository, never reports game content, and only records counts,
timings and the faulting RVA.

## First measured baseline on this host (Series S, 90 s, `main` @ `ffe310e` + #729)

```
translation failures   0        (menu stage only)
texture failures       4        (the 86/115 video formats, see #797)
peak draws/frame       8
peak fps              30
peak RAM              3.34 GB
crash                  none
```

That is the honest baseline for "menus only": zero translation failures at the menu, and the four
texture failures are the video path. It also shows why Series S mode is the safe way to test on a
32 GB box — 3.34 GB versus 13.2 GB.

I am happy to keep posting these scorecards for each new `main` if that is useful; the script is
under `E:\gta6-build\bench\victory-bench.ps1` on my side but is small enough to include on request.

### Comment 1 — @bittertea0323 — 2026-11-24T11:36:14Z

Second run with the script, this time **Series X with the 8 GB guard**, confirms why scene-stage
numbers are rare in this tracker:

```
failures=63  texFail=2  peakDraws=11  peakFps=31  peakRAM=8.3GB  crash=none
                                                        ^ stopped by -MaxRamGB 8
```

`peakDraws` is still 11 (menu) when the guard fires: **Series X loading alone reaches 8.3 GB
before the scene appears**, and the scene itself measured 13.2 GB earlier (#784). On a 31.2 GB host
there is no safe window to capture the scene numbers at all.

So the three data points on this machine are:

```
Series S  3.34 GB    runs, 8 draws (menu/UI only)
Series X  8.3 GB     loading, guard-fired before the scene
Series X 13.2 GB     after the scene loads, system already unstable
```

That is the honest reason my copy-cost numbers are menu-stage only, and probably why other testers
report the same gap. Reducing the title process footprint would be worth as much as any shader fix
for testability: with Series X at 13 GB, nobody on a 32 GB box can iterate on the world.
