## Original body

## What's wrong

On RDNA2, `glc` on a buffer or image load means "skip the per-CU (L0) cache". It's how one workgroup sees another workgroup's writes: LLVM's GFX10 memory model (AMDGPUUsage) lowers an agent-scope atomic load to `buffer/global/flat_load glc=1 dlc=1`. Titles use it for cross-workgroup spin waits and look-back scans.

The lowering never marks a handle globally coherent (`IsGloballyCoherent`, props bit `0x4000`, in DXC's `DxilResourceProperties.h`):

- Buffer handles (`crates/victory-shader/src/emit/lower.rs:6075-6076`) and image handles (`:5470-5475`) only set `IsUAV`.
- `glc` is looked at only to decide whether an atomic returns its old value (`:5519`, `:5546`, `:6095`).

So a `glc` load becomes an ordinary, group-coherent UAV load. The host compiler may keep it in a register or a non-coherent cache, or hoist it out of a loop.

## Example

A spin wait such as the one in #452:

```
buffer_load_dword v1, v0, s[8:11], 0 idxen glc     E0306000 80020100   (repeated until v1 changes)
```

- Console: sees the other group's write once it reaches L2.
- Ours: may never see it. #452 measured loops like this running until its iteration cap.

I haven't shown that the missing flag **is** the cause of #452's hangs: it's one plausible cause.

## Suggested fix

OR `0x4000` into a UAV handle's props when the access has `glc` (props are already part of the handle cache key). For that to reach heap descriptors, they first have to be known as UAVs (#724).

**Not tested:** a test asserting the props (as in #724) would show the missing flag. A behavioural test on WARP would depend on timing, so I haven't written one.

## Related

- #452 caps spin loops but doesn't add coherence.
- #190 writes root-UAV metadata with globally coherent set to false.

### Comment 2 — @RID-Games — 2026-11-24T09:45:16Z

Same note as on #724: the [branch](https://github.com/Hiiva/VIctory/tree/hiiva/heap-uav-coherence) marks glc UAV accesses coherently, but a heap descriptor read only by `glc` loads (the spin-wait in this issue's example) is never inferred as a UAV — the pre-pass filter is `store || atomic`, and `resource_flags(false, true)` is 0 — so it still gets a plain SRV handle and no `0x4000`. Marking `glc` accesses in the #724 pre-pass (as the issue prescribes: "store, atomic or glc") is what makes this fix reach heap descriptors. Verified the branch's tests on Linux: 72 passed. AI-assisted.

### Comment 3 — @dpalacios69 — 2026-11-24T10:22:24Z

Prepared a standalone branch on `ffe310e` covering both #724 and #725 (including the `glc`-only heap load spin-wait case noted above): `dpalacios69/VIctory@fix/shader-glc-globally-coherent`.

- Pre-lowering pass in `Lower::new` (`crates/victory-shader/src/emit/lower.rs`) infers resource-heap UAVs keyed by `(param, byte_offset, dynamic)` from `store`, `atomic`, or `glc` loads (excluding `image_sample*` and descriptor loads `s_load_dword*`), and routes `s_buffer_load` on UAVs to raw UAV handles instead of CBV.
- ORs `IsGloballyCoherent` (`0x4000`) into UAV handle properties when `cache.glc` is set on buffer, image, and `s_buffer_load` accesses.
- Tradeoff documented in code: inferring UAV from `glc` loads matches #724/#725 so `glc`-only heap spin-waits get `0x500B`, with the caveat noted by @Hiiva that a `glc` load on a read-only heap SRV would be annotated as a UAV.
- Verified with synthetic tests on Linux only (`cargo test -p victory-shader --locked`: 101 passed, 0 failed, 1 ignored, including 5 new tests; `clippy -D warnings` clean on `lower.rs`; `cargo xtask policy` ok). **DXIL validator (`dxil.dll`) and GPU execution were not run locally.**

AI-assisted; no game data used.
