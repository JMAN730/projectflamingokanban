## Original body

On RDNA2, the VOP3 `op_sel` bits are ignored by the 16-bit compares (`v_cmp_*` and `v_cmpx_*` on `f16`, `u16`, `i16`). Both sources always come from the low 16 bits of the register. VIctory honours the bits and reads the high half instead.

### Example

```
v0 = 0x4000_3C00    high half 2.0, low half 1.0 (f16)
v1 = 0x3C00_3E00    high half 1.0, low half 1.5

v_cmp_lt_f16_e64 vcc, v0, v1 op_sel:[1,0]
```

| | compares | result |
|---|---|---|
| RDNA2 hardware | low(v0) 1.0 < low(v1) 1.5 | true |
| VIctory | high(v0) 2.0 < low(v1) 1.5 | false |

### Where

`compare()` in `crates/victory-shader/src/emit/lower.rs` reads both sources through `half_src` / `half_fsrc`, and `half_src` picks the half from `op_sel`:

```rust
let mut high = v.opsel >> k & 1 != 0;
```

`op_sel` is decoded for VOP3 compares in `gfx10/fields.rs` (`v.opsel = (w0 >> 11 & 0xF) as u8`).

### Possible fix

Ignore `op_sel` for the compares in `half_src`, and keep the SDWA select below it, which does pick the half on hardware:

```rust
// RDNA2 ignores VOP3 op_sel on 16-bit compares (v_cmp_class not measured).
let name = inst.name();
let compare = name.starts_with("v_cmp") && !name.contains("class");
let mut high = !compare && v.opsel >> k & 1 != 0;
```

### Measurement

gfx1036 (RDNA2 iGPU), raw instruction words, wave32 and wave64. I covered VGPR, SGPR, 32-bit literal and inline constant sources, plus `v_cmpx_*_e64`. All 146 rows matched the hardware ignoring `op_sel`. As a control, `v_add_nc_u16` with the same bits set does honour them, so the encoding is right.

### Impact

None for GTA VI right now. `shaders.rpf` has 1,368 16-bit compares, 166 of them VOP3 encoded, and none of them set `op_sel`. Filing it so it's known if another title runs into it.

## What's wrong

On RDNA2 the VOP3 `op_sel` bits are ignored by the 16-bit compares (`v_cmp_*` and `v_cmpx_*` on `f16`, `u16`, `i16`): both sources come from the low 16 bits. #833 measured it on gfx1036 (146 rows, every source kind, wave32 and wave64), with `v_add_nc_u16` as the control that does honour the bits. `half_src` honours `op_sel` for every 16-bit operation:

```rust
let mut high = v.opsel >> k & 1 != 0;
```

So `v_cmp_lt_f16_e64 vcc, v0, v1 op_sel:[1,0]` with v0 = `0x4000_3C00` and v1 = `0x3C00_3E00` compares high(v0) 2.0 < low(v1) 1.5 and gives false, where the hardware compares 1.0 < 1.5 and gives true.

## What the fix does

`half_src`, which `half_fsrc` also goes through, ignores `op_sel` when the instruction is a `v_cmp*` other than `v_cmp_class*` (whose behaviour was not measured, so it stays as it was). The SDWA select below it, which does pick the half on hardware, is unchanged, and so is every non-compare 16-bit operation.

## How it behaves after the fix

16-bit compares read the low halves whatever `op_sel` says, as RDNA2 does. Nothing changes for Grand Theft Auto VI: #833 counted 166 VOP3 16-bit compares in its shaders, none with `op_sel` set.

## Tests

`cmp16_ignores_op_sel_as_rdna2_does` (`valu_tests.rs`, run on the host GPU and WARP):
- `v_cmp_lt_f16`, `v_cmp_lt_u16` and `v_cmp_lt_i16`, each with `op_sel` `0b01`, `0b10` and `0b11`, on values where the high and low halves give opposite answers;
- `v_cmpx_lt_f16_e64` writing EXEC;
- a control: `v_add_nc_u16` with `op_sel:[1,0]` still adds the high half.

On GitHub's `windows-latest`, Rust 1.98.1, with the upstream CI's commands (clippy `-D warnings` with and without `--all-features`, `cargo test --workspace --locked -- --test-threads=1`):
- **This change:** everything passes; `victory-shader` 121 passed, 0 failed (https://github.com/BastienRodz/VIctory/actions/runs/45389398916).
- **The new test alone on `main`:** it fails at the first case, `hardware: v_cmp_lt_f16 opsel=0b1 (0x40003c00, 0x3c003e00) = 0, want 1` (https://github.com/BastienRodz/VIctory/actions/runs/45389413162).

`cargo xtask policy`: ok. Synthetic programs only; no game data.

**Not tested:** `v_cmp_class_*` with `op_sel` (left as it was); a title that sets `op_sel` on a 16-bit compare.
