## 4. `pc_format` has no fallback for three formats this driver refuses as render targets

The world asks for two 2560×1440 targets that the driver rejects with `E_INVALIDARG`:

```
WARN victory_gpu::resource: no host texture error=0x80070057 (E_INVALIDARG)
     desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, mip_levels: 1,
                         format: 86, sample_count: 1, layout: 0, flags: 5 }
WARN victory_gpu::resource: no host texture error=0x80070057
     desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, mip_levels: 1,
                         format: 115, sample_count: 1, layout: 0, flags: 1 }
```

(format 86 = `B5G5R5A1_UNORM`, format 115 = `B4G4R4A4_UNORM`; #778 reports the same two on an RTX 3070.)

`host_texture()` calls `CreateCommittedResource` once and gives up. A stand-in table in `pc_format()` — which both the resource and the views go through — removes every refusal. This is proposed separately as its own pull request, since it is independent of both PRs above.

```rust
pub(crate) fn pc_format(format: u32) -> u32 {
    match format {
        118 => 45,
        119 => 46,
        120 => 47,
        // These are refused as render targets on this driver.
        85 | 86 | 115 => 28,   // B5G6R5 / B5G5R5A1 / B4G4R4A4 -> R8G8B8A8_UNORM
        67 => 10,              // R9G9B9E5_SHAREDEXP -> R16G16B16A16_FLOAT
        other => other,
    }
}
```

Measured effect, same run line:

| | `no host texture` lines | world capture |
|---|---|---|
| unpatched | 2 (formats 86, 115) | black |
| `85\|86\|115 -> 28` | 1 (format 67 @1920×1080) | black |
| `+ 67 -> 10` | **0** | black |

So all three targets now exist, and the world is *still* black — the remaining cause is the dropped wave64 mesh/compute work from #578, not the formats. But the fallback is still worth having: without it these targets silently never exist, which makes every later stage of the frame meaningless.

Colours from the stand-in formats are wrong by construction (16-bit packed and shared-exponent data read as 8-bit/16-float); these are only for looking at frames, not for correctness.

`0x80070057` is `E_INVALIDARG`.

Read together, the three line up as:

| flags | use | result |
|---|---|---|
| `0` | plain texture | creation path accepted; only fails on memory (`E_OUTOFMEMORY`) |
| `4` | unordered access only | `E_INVALIDARG` |
| `5` | render target + unordered access | `E_INVALIDARG` |

So on this driver format 67 as an ordinary texture is fine and as a render target or typed UAV is not. That looks like the unsupported *write usage* you were distinguishing from a creation failure, rather than the format being unusable at all. For completeness, the same pattern holds for the packed formats on this host: format 86 at 1280×720 `flags: 5` and format 115 at 1280×720 `flags: 1` are both refused with `E_INVALIDARG`.

You are right about the 4 → 8 bytes per texel problem, and it applies to the packed formats too (8 bits per channel standing in for 16). A global mapping in `pc_format()` is the wrong shape: it also rewrites textures the title only ever samples. Better three ways, in order of preference:

1. Substitute only when the description's flags include render target or unordered access, so sampled textures keep their format and their uploads and copies stay byte-identical.
2. Keep `pc_format()` pure and retry `CreateCommittedResource` once on failure with the stand-in, so only the resources that actually need it change.
3. If the stand-in must stay global, at least record the substitution per resource so guest uploads and copies can convert (this is the conversion work you described).

The downstream PR #29 integrated the global form of the mapping; it would be worth narrowing it there rather than propagating it.

On my host the same format is refused only for write uses, not in general:

| format 67 (`R9G9B9E5_SHAREDEXP`), 1920×1080 | flags | result |
|---|---|---|
| plain texture | `0` (2560×1440 copy in a low-memory run) | creation accepted, fails only on memory (`0x8007000E`) |

So a global substitution in `pc_format()` also rewrites textures the title only ever samples, and for 67 → 10 that doubles the bytes per texel (4 → 8), for 86/115 → 28 it doubles them again in the other direction (16-bit packed → 32-bit). Any upload or copy path that assumes the console's layout then needs a conversion that this change does not do.

Two narrower shapes that fix the same refusals without touching sampled textures:

1. Key the table on the description's flags — substitute only when render target or unordered access is set.
2. Leave `pc_format()` alone and retry `CreateCommittedResource` with the stand-in only after the first attempt fails, recording the substitution per resource.

Either keeps the "`no host texture` count goes to 0" result while leaving ordinary textures byte-identical to what the title expects.
