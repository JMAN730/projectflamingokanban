## Original body

### Summary

Attempting the world on a Radeon integrated GPU (RDNA3, 64-lane waves) gets further than on the discrete
NVIDIA card in the same machine, and DRED names the fault exactly: a compute dispatch writes two UAVs that
resolve to `None`, whose descriptor heap is null, and the GPU page-faults.

Same machine, same title, same build, two adapters (per-app GPU preference switches between them):

* **RTX 4070** — 22 compute programs are refused at creation (`wave lane count of 64 … maximum … is 32`)
  and their dispatches are dropped; the world submission then removes the device.
* **Radeon iGPU** — 0 wave64 refusals, 0 host-pipeline refusals, but a page fault in a compute dispatch.

With `VICTORY_SHADER_LOOP_LIMIT=1000` the iGPU run's slow submissions drop from **20,518 ms to 444–498 ms**
and it reaches 787 draws/frame, capturing loading frames correctly — so the loop limit works as the README
describes. What remains is not slowness: after that, a submission still removes the device, with DRED
pointing at an unbound UAV write.

### Setup

- CPU: Ryzen with Radeon integrated graphics (RDNA3) **and** RTX 4070, driver 32.0.16.2114
- Windows 11 build 26300, `VICTORY_DXIL` = DXC 1.9.2609.5 `dxil.dll`
- VIctory `d2a4bae`, `cargo build --profile diag -p victory --features diagnostics`
- `victory.exe run <exe> --execute`, Series X profile unless noted

### Data

### Comment 1 — @BastienRodz — 2026-11-24T04:43:54Z

I'm working on this. Reading the code: a descriptor slot the title never wrote a known view into is a null **Texture2D SRV** on the host (`HostHeap::fill_null`, and `make_null` for fresh tables). The translated shaders index the heap directly (SM 6.6), with the kind they expect in each handle's annotation. So the dispatch in your DRED (`Uav s1+8: uav None`, `Uav s1+16: uav None`) writes through SRV descriptors, which a GPU does not have to survive.

Plan: the translator records the resource kind it annotates for each table descriptor it reads (UAV or SRV; buffer, raw, structured or texture dimension). Where the title has no view, the host makes a null descriptor of that kind, so writes are dropped and reads return zero. I'll open a PR when it's tested. No game data used.

### Comment 2 — @wwwwwwww3333333 — 2026-11-24T04:43:57Z

**Source-level analysis; not runtime-tested with game files.**

**Q1 (drop dispatches with `None` UAVs):** I think #135 already covers most of this. It writes a null view of the kind the shader expects into fresh tables (`make_null_kind(index, u.kind, u.dwords)`), and it drops the dispatch when a table can't be made. #336 also drops it.

One path it doesn't change: in `State::table_entry`, which handles tables that are not rebuilt, `mirror()` returns `None` for a slot with no view. The slot then keeps the null **Texture2D SRV** from `fill_null`/`make_null`. A shader that writes that index as a UAV through `ResourceDescriptorHeap[]` hits an SRV, which is a descriptor-type mismatch. That fits the RDNA3 page fault. #413 keeps `make_null` there as well. On top of #135, this could be a one-line follow-up: when `u.kind == ResourceType::Uav` and `index < host.count()`, call `make_null_kind(index, u.kind, u.dwords)`.

I can't tell from the report whether `s1+8`/`s1+16` came from a fresh table or a mirrored one. If you can test #135 on the iGPU with GBV enabled, that would show whether the second path matters.

**Q2 (wave64 on 32-lane hosts):** this is in progress in open PRs: #189, #233 and #223 (plus #54, #192 and #439 for small groups and LDS). The RTX refusals look like #71, #264 and #468.

**Q3 (GBV in diagnostics):** a diagnostics build already enables it with `VICTORY_D3D12_DEBUG=1 VICTORY_D3D12_GBV=1` (`host.rs`), and the first debug-layer error goes into the device-removed report. #205 fixes the Texture2D-vs-3D null UAV mismatch that GBV reports.

### Comment 3 — @LAKSHYA-cmd-tech — 2026-11-24T04:49:29Z

PR #552 addresses this crash:

1. Unbound / \None\ UAV slots in descriptor tables now allocate valid null UAV descriptors (\make_null_uav\) instead of falling back to default \
ull_view\ SRVs, ensuring hardware properly drops UAV writes per D3D12 spec instead of faulting on invalid descriptor types.
2. \
ull_for\ now matches exact UAV dimensions (\Texture3D\, \Texture1D\, \Texture2DArray\, \Buffer\) from descriptor words rather than hardcoding \Texture2D\, eliminating the GBV dimension mismatch error.
3. \placed_texture\ now handles \View::Placed(true, ...)\ so placed UAV textures get mapped to host textures and transition to \UNORDERED_ACCESS\.
4. An opt-in \VICTORY_DROP_UNBOUND_UAV=1\ switch is added if you prefer to drop compute dispatches with unbound UAVs entirely.

One correction to the reading above: the `view heap ...: 0x... past its end (slot N)` lines are not an index the shader read. `near_heaps()` in `descriptor/host.rs` takes the *fault address* and places it against each heap's GPU range, and it prints that for every fault.
