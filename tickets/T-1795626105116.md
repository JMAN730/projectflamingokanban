## Original body

`crates/victory-gpu/src/fence.rs:90-95`. In D3D12, a NULL event means "block until the fence reaches the value". We return `E_NOTIMPL`. The comment's reason ("nothing can reach it while no GPU work runs") no longer holds, because queues and the CPU now signal fences (`fence.rs:99`, `queue.rs:160`).

Proposed patch (formatted with the repo's rustfmt; **not compiled or tested**, since I have no Windows machine). It blocks on a `Condvar` paired with the existing `waiters` mutex, which `signal` already holds, so no wakeup is lost. The patch also updates the unit test to cover the blocking wait.

### Comment 1 — @Yorivel — 2026-11-24T09:43:14Z

Compiled and tested on Windows 11 26300 (MSVC, Rust 1.98.1, `--test-threads=1`): the patch applies to `8e79c80`, its updated test passes 3 of 3 runs, clippy (`-D warnings`) and rustfmt are clean.

One gap: a list's bottom-of-pipe write (`write32`/`write64`, `list.rs`) can store the value straight at the fence's address (`gpu_address`), which moves it without `signal`, so the `Condvar` is never notified. A test that does that (`Written::Value(9).write` to the fence's address while another thread waits with no event) times out after 2 s with the patch as posted.

Branch with the patch plus a fix: https://github.com/Yorivel/VIctory/tree/fix/fence-blocking-wait. The wait uses `wait_timeout` (1 ms) so it also sees a value written without a signal; signals still wake it at once. Both tests pass 3 of 3, `cargo test -p victory-gpu --lib` 51 passed / 1 ignored, clippy clean, `cargo xtask policy` ok. The module comment no longer says only signals move a fence.

Not covered: such a write sets no waiting *events* either (the same path, before this patch); that needs fences findable by address and is left alone here.

Written with Claude Code.

### Comment 3 — @AndyLatimer — 2026-11-24T10:08:29Z

Open PR #32 already fixes this, including the gap @Yorivel describes and the part left out there:

- `SetEventOnCompletion(value, NULL)` blocks on a condition variable instead of returning `E_NOTIMPL` (tests `blocking_wait_returns_at_once_when_reached`, `blocking_wait_blocks_until_signalled`).
- Live fences are registered by their value address, so a list's bottom-of-pipe write (`Written::write`) wakes both a blocking wait and the events waiting on that fence (`bottom_of_pipe_write_releases_blocking_wait`, `bottom_of_pipe_write_sets_waiting_event`).
- A write straight to the fence's memory (CPU or shader) is picked up by a watcher thread that polls only while a wait is pending (`direct_memory_write_sets_waiting_event`).
