## Original body

Black world and host GPU reset (DXGI_ERROR_DEVICE_HUNG) on NVIDIA at the first cutscene; 343 shaders don't translate

## Environment
- VIctory commit: <output of `git rev-parse --short HEAD`>
- Windows: 26H2 Build 26300.9818
- CPU: Ryzen 7 5800X
- GPU: GeForce RTX 2070 SUPER, driver 32.0.16.2124
- Title: GTA VI, Xbox Series package v1.0.2.1 
- Builds: `cargo build --release -p victory`, and the diag profile with `--features diagnostics`

## What happens
The game boots to the menus and the loading screen (music plays, though it sounds wrong). At the first cutscene/world the picture is black, frames take 2-3 s (0.4-0.5 fps), and then the host GPU is reset and the run ends:

    host GPU device removed after a submission of 27 lists ... (0x887A0006) DXGI_ERROR_DEVICE_HUNG

Without diagnostics, the same run logs `slow host submission ms=6192 lists=30` just before the removal.

## Where it hangs (diag build, `VICTORY_D3D12_DRED=1 VICTORY_GPU_TIMING=1`)
Run 1: list 23 stopped at command 129 of 183, op 42 (DISPATCH_MESH). `mesh 115 [mesh 4adfa13bea1c556a]`, a mesh-only pipeline. No page fault address was reported.

Run 2, with `VICTORY_SKIP_PIPELINES=4adfa13bea1c556a`: the hang moved. List stopped at command 1217 of 1404, op 5 (EXECUTE_INDIRECT): `indirect kind 10 max 1 [mesh ae9ee9074f2e971f, pixel 1cb9d385ac8987c4]`. Both hung mesh shaders read the same 182,452,224-byte SRV.

## Mesh work is very slow and data-dependent
From the `slow list command` lines, same shader and group count, very different time:
- `51ff151f75cd5759`, 3 groups: 924 ms in one run, 35-52 ms in another
- `04b9be3756e8f41c`, 1 group: 132 ms
- `a26422c01dcf5612`, 1 group: 108-141 ms
- `5a801f1f568c7abd`, 15 groups: 306-379 ms

One indirect compute dispatch, `8bbcbda6008eaa37`, accounts for about 11 s over 17 slow commands in the first run.

## Likely cause (my reading, not verified)
343 shaders fail to translate, and the draws and dispatches that use them are dropped. In the last frames of the run, about 1,500 draws/dispatches per frame are dropped without a host pipeline, plus 900-1,900 indirect ones.

Counts by stage: 285 compute, 35 pixel, 19 mesh, 4 vertex.

Most common reasons:
- 77: a select on an untracked mask is not supported
- 73: a lane mask holding lanes elsewhere read as data is not supported
- 35: an address in an SGPR that is no root parameter is not supported
- 31: a structured buffer of unknown stride is not supported
- 23: a scalar memory read as data is not supported
- 20: a descriptor read only as data is not supported
- 17: an address not from a root parameter is not supported
- 15: a descriptor neither loaded nor built is not supported
- 11: a 64-bit image atomic is not supported

Examples: compute `fc5e66f8f873d3bb` (a hardware SGPR input), `0452fc2d2e2fc4c3` (image_gather4_l), `17af15c4015cb4b6` (a structured buffer of unknown stride).

My guess is that the dropped compute passes leave the buffers the mesh shaders read holding garbage, so some mesh dispatches run long enough to exceed the Windows GPU timeout. The note at the top of `indirect.rs` describes the same failure mode. The constant buffers in the stopped-list report also hold NaN/denormal values.

## Questions
1. Has this been tried on an NVIDIA GPU? Is a hang here expected while those shaders are unsupported?
2. Is there a way to make the host clamp or time-box direct mesh dispatches the way indirect ones are clamped, so the run survives and I can look at the frame?
3. Which of the translator gaps above would you tackle first?

### Comment 2 — @mohammadallami75-ops — 2026-11-24T06:24:17Z

I reproduced and fixed a D3D12 buffer-view coherency bug relevant to the placed SRV path in this report.

Descriptor creation selected the host buffer using the resource's base and declared width. Draw preparation selected a host buffer using only the view's byte range. When a smaller registered buffer covered that range, uploads or UAV write tracking could use the smaller buffer while the descriptor still pointed to the larger one. The patch uses the declared extent for both lookups and limits synchronization to the bytes covered by the view.

Two synthetic regressions reproduced a stale SRV read and lost UAV copy-back. Both returned zero with the old lookup and passed with the patch on an RTX 2080 SUPER (driver 621.01) and Microsoft WARP. The Windows workspace suite had 266 passed and 4 ignored. The WARP GPU diagnostics suite had 47 passed and 1 ignored. Testing used synthetic assets, so the in-game black screen and DXGI_ERROR_DEVICE_HUNG remain unverified.

This complements #402. That PR addresses misses in the lookup itself. This reproduction uses a valid narrower match, so both callers still need to query the same extent.
