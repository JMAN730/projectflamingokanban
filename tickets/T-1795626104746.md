## Original body

## Summary

On an NVIDIA RTX 3080, GTA VI under VIctory loses the D3D12 device during the world load (before or at the first cinematic). DRED breadcrumbs (`--profile diag --features diagnostics`, `VICTORY_D3D12_DRED=1`) point each time at a dispatch whose UAV slot holds a **null descriptor**. AMD appears to tolerate these; NVIDIA removes the device.

Two of the three causes have a working fix (patch attached). The third needs a design-level change, so I'm reporting it rather than patching it.

## Environment

- GPU: NVIDIA GeForce RTX 3080 (minimum subgroup size 32)
- OS: Windows 11 Pro (10.0.26300)
- VIctory: `d2a4bae` (main, 2026-11-24) + attached patch
- Build: `cargo build --profile diag -p victory --features diagnostics`
- Run: `victory run --execute <game exe>` with `VICTORY_D3D12_DRED=1`, no skipped pipelines
- Package: Xbox Series v1.0.2.1

## Hang 1 — UAV on a depth-stencil texture (fixed)

- DRED: indirect mesh dispatch (`op 5`, kind 10), mesh `ae9ee9074f2e971f` / pixel `54e55d28e6ee4f5c`, command 2131 of 4974; `u8` → heap 330192: null.
- Cause: the title requests a UAV of a depth-stencil texture (`R16_TYPELESS`, flags `0x2`). `fits()` refuses it (`view the host does not allow`), and the slot becomes a null view.
- Fix: `depth_scratch()` in `descriptor/host.rs` gives such views a per-texture scratch texture (same size, typeless family, `ALLOW_UNORDERED_ACCESS`; view format mapped to `R16_UINT` / `R32_UINT`). Writes land in the scratch, so that effect is wrong, but the device survives. Logged once as `depth UAV: scratch stand-in` (seen: format 53, 768×768).

## Hang 2 — packed 16-bit colour textures not creatable on NVIDIA (fixed)

- DRED: indirect mesh dispatch, mesh `899bc578934bc5be`, command 1129 of 3363; `u8` → heap 329720: null.
- Cause: `no host texture` (E_INVALIDARG) for two 2560×1440 textures: `B5G5R5A1_UNORM` (86) with RT|UAV (flags 5) and `B4G4R4A4_UNORM` (115) with RT (flags 1). NVIDIA doesn't support these as render targets / typed UAVs, so every view of them is null.
- Fix: `resource.rs` stores formats 86/115 as `R16_TYPELESS` (same bytes per pixel, so copies line up; clear value → `R16_UNORM`), and `fits()` maps their views to `R16_UNORM` (SRV) / `R16_UINT` (UAV). Channels read as raw 16 bits, so the content is wrong, but the textures exist. After this, no `no host texture` errors before device removal.
- Not handled: render-target views of these textures in format 86/115, if the title makes any.

## Hang 3 — slots that were never written (open)

- DRED: compute dispatch 33×1×1, `e06a21f3cea46973`; `u4` → heap 339972: null, `u6` → heap 726: null.
- No failed-view warning for these slots, so they appear never written (or deliberately left empty) by the title. That works on the console and likely on AMD.
- Suspected root cause: a null descriptor whose kind (texture vs. buffer, dimension) doesn't match what the shader declares. `null_for()` already notes the hardware "does not survive" that in general; NVIDIA consistently removes the device. A real fix likely needs the null view to match the translated shader's declared resource type per slot, which is beyond a local patch.

## Also seen (may be related)

- The title's hang watchdog (`+0x23cf683`, crash annotation `GPU Loc Sig = 7333478d`) killed a diag run ~2 min into loading. The same watchdog fires under XCL. The title's physical pool was at 2.12 / 2.31 GB.
- About 97 distinct shaders that don't translate, and ~10 host pipelines refused with E_INVALIDARG (hashes available on request).
- Release build: ~1 fps in the first cinematic, with many draws dropped (`without a host pipeline`, indirect).

## Attached

`nvidia-null-view-fixes.patch` — the two fixes above, against `d2a4bae`.

No logs, dumps or game files are attached; I can rerun with specific `VICTORY_*` settings if that helps.

D3D12: ID3D12Device::CreateRenderTargetView: The Format (0x56, B5G5R5A1_UNORM) is invalid, when creating a View; it is not a fully qualified Format castable from the Format of the Resource (0x35, R16_TYPELESS). id=38 severity=1

`fits()` remaps the SRV/UAV formats of these textures, but render target views are made in `Host::rtv` (`crates/victory-gpu/src/host.rs`), which doesn't go through `fits()`. So it still asks for B5G5R5A1/B4G4R4A4 on the R16_TYPELESS resource.

## Fix

The same remap in `Host::rtv`:

```diff
@@ -752,6 +752,20 @@ impl Host {
         desc: Option<&D3D12_RENDER_TARGET_VIEW_DESC>,
     ) -> D3D12_CPU_DESCRIPTOR_HANDLE {
         let slot = self.next_rtv.fetch_add(1, Ordering::Relaxed) % RTV_RING;
+        // Experiment (#392): packed 16-bit colour textures are stored as
+        // R16_TYPELESS (see resource.rs); their render target views write
+        // the raw 16 bits as R16_UNORM.
+        let mut remapped;
+        let mut desc = desc;
+        if let Some(d) = desc
+            && (d.Format.0 == 86 || d.Format.0 == 115)
+            // SAFETY: a live resource.
+            && unsafe { resource.GetDesc() }.Format.0 == 53
+        {
+            remapped = *d;
+            remapped.Format = DXGI_FORMAT(56);
+            desc = Some(&remapped);
+        }
         // SAFETY: a slot of our heap and a live resource.
         unsafe {
             let mut handle = self.rtvs.GetCPUDescriptorHandleForHeapStart();
```

### Comment 5 — @marcogravbrot — 2026-11-24T04:49:07Z

A finding from an RTX 3080 Ti that may explain part of this (world stalls of several seconds, then `DEVICE_HUNG`), measured with `VICTORY_GPU_TIMING=1` and a D3D12 debug-layer run.

**One dispatch took 6.3 s on the GPU every frame**: `depth_pyramid:CS_InitDepthPyramidWithCpuOcclusion3x3` (128x64 groups). Its loop bounds are quotients of dimensions it reads with scalar buffer loads from two small structured SRVs (16- and 20-byte structures, one element each). The title's memory held sane values; the shader got zeros for every dword after the first, so a divisor was 0, the bound became infinite and every loop ran to the 2^20 limit.

**Why zeros.** A scalar `s_buffer_load` of an SRV is lowered through a raw handle while the host view is the title's structured one. On NVIDIA that combination does not read bytes: with a view of 16-byte structures, byte offset 4 returned dword 4 (the offset is taken as an element index) and byte offset 24 returned 0 (past the element count). A hand-assembled test on the test host shows it: reading bytes 24 and 4 of `[100, 101, ...]` gives `[0, 104]` instead of `[106, 101]`.

Things I tried on this GPU, in case they save someone time:

- A structured handle of the view's own stride reads correctly, but pipelines with loads from large structures were refused with `E_OUTOFMEMORY` (seen from 336 bytes in one shader, 2044 in others).
- A structured handle of a different stride than the view's reads 0 past element 0.
- Making the host views raw fails the debug layer for views that do not start on 16 bytes of the resource (`CreateShaderResourceView: ... FirstElement must be a multiple of 4`), which title views often do not.
- What works here: the host makes raw and structured title views as views of 4-byte structures (any dword start is legal) and translated code addresses them by dword (`byte >> 2`, element offset 0), root views staying raw. With that the dispatch above takes well under a millisecond and GPU time per world frame fell from about 8 s to about 0.2 s.

Not a complete fix for this issue: after it I still see page faults from unbounded reads and frames dominated by CPU-side copies.
