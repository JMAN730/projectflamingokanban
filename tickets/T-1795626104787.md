## Original body

## What's wrong

At the end of `Shadow::copy_back` (`crates/victory-gpu/src/shadow.rs:237-247`), every page it synced is marked up to date in the host copy (`copied[page] = now`). The `now` comes from **one** write-watch query (`watch::writes(.., reset)`) made after all pieces are done.

That query also clears any title write that happened after a page was read and before the query. The kernel can't tell our own `write_mapped` from a title write, so both are reset together. The page is then marked current, later refreshes skip it, and the GPU keeps reading the old bytes until the title happens to write that page again.

`copy_stale` does this in the safe order (ask first, then copy). `copy_back` reads first and asks afterwards.

## Example

- A large buffer with GPU writes all over it, so `copy_back` takes milliseconds.
- Right after page 0 is synced, a title thread writes new constants into page 0.
- The final query resets the write-watch bit and page 0 is marked current.
- The next refresh copies 0 bytes, and draws read the old constants.

## Evidence

The test `a_title_write_during_copy_back_reaches_the_copy` replays it deterministically:

1. Over 64 write-watched pages, a thread waits until `copy_back` has written page 1, so page 0 is fully done.
2. It then writes 7 into page 0 while `copy_back` still has 62 pages to go.
3. After `copy_back`, a refresh of page 0 should bring the 7 into the host copy.

On `main` (dd54de2), on GitHub's `windows-latest`:

```
assertion `left == right` failed: in the copy
  left: 0
 right: 7
```

The write reached title memory but never reached the copy. The test's code is in the `race_tests` module posted in #721.

## Suggested fix

After the final query, mark a synced page current only if title memory, read again with `read_into`, still matches the host copy:

- A title write before the query shows up as a difference, so the page stays stale and the next refresh copies it.
- A title write after the query is reported by the next query, as usual.

## Related

- #693 adds a check that title memory matched at the time each page was read, which doesn't cover writes after that read.
- #721 is about the same function: the whole-piece write-back.

### Comment 1 — @Yorivel — 2026-11-24T09:25:19Z

A fix as suggested here, with the test from #721's `race_tests` module (credited in the code): https://github.com/Yorivel/VIctory/tree/fix/copy-back-current-pages (on `8e79c80`).

After the final asking, `copy_back` reads each synced page again and marks it current only if it still matches the copy. A title write cleared by that asking leaves the page as written at `now`, after its last copy, so the next refresh copies it. A write after the asking shows at the next one as before. Cost: one 64 KiB read per synced page.

**Tested** (Windows 11 26300, MSVC, Rust 1.98.1, `--test-threads=1`):
- `a_title_write_during_copy_back_reaches_the_copy` on unchanged `main`: 3 of 3 runs fail (`left: 0, right: 7`, "in the copy"); with the fix: 3 of 3 pass.
- `cargo test -p victory-gpu --lib`: 51 passed, 1 ignored. Clippy (`-D warnings`) clean, `cargo xtask policy` ok.

The #721 test is not included, as this branch does not change the whole-piece write-back; the fix doesn't touch the lines xstraok's #721 branch changes, but I haven't tested the two together.
