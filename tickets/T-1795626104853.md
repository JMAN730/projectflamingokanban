## Original body

# Cutscene: audio + subtitles work, the video frame does not — two 2560x1440 textures fail `CreateCommittedResource` (E_INVALIDARG)

This is a separate blocker from the shader translation issues in #784. It explains "background music and
subtitles play, the picture is black" during the intro cutscene.

## Evidence

The cutscene opens `G:\\movies.rpf` and connects the audio decoder (256 streams), i.e. it is **Bink
video**, not a realtime 3D scene:

```
dstorage: file opened path="G:\\movies.rpf"
apu: audio decoder connected streams=256 memory=1064960 options=1
```

Immediately after, its two frame textures fail to be created:

```
WARN victory_gpu::resource: no host texture error=E_INVALIDARG (0x80070057)
  desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, depth_or_array_size: 1,
                      mip_levels: 1, format: 86,  sample_count: 1, layout: 0, flags: 5 }
WARN victory_gpu::resource: no host texture error=E_INVALIDARG (0x80070057)
  desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, depth_or_array_size: 1,
                      mip_levels: 1, format: 115, sample_count: 1, layout: 0, flags: 1 }
```

(`dimension: 3` is correct here — `texture_layout()` maps 3 to `Tex2d`, matching `TEXTURE_2D = 3`.)

## Where it comes from

`crates/victory-gpu/src/resource.rs`:

```rust
pub(crate) fn pc_format(format: u32) -> u32 {
    match format {
        118 => 45,   // console 16-bit depth+stencil -> 24-bit
        119 => 46,
        120 => 47,
        other => other,          // 86 and 115 pass through untouched
    }
}
```

The description then goes straight into `CreateCommittedResource`, which rejects it. So on this title
the console formats **86** and **115** have no valid D3D12 equivalent as they are currently emitted.

## What I would like to know / propose

1. **What are console formats 86 and 115?** Both are 2 bytes per element in `element()`'s table
   (`48..=59 | 68 | 69 | 85 | 86 | 115 => (2, 1)`), and they are used for 2560x1440 video frames —
   so they look like 16-bit-per-channel or 16-bit-two-channel video formats rather than ordinary
   colour. If the console's format table says what they are, the right PC mapping is probably a
   two-channel 16-bit UNORM/FLOAT format rather than the B8G8R8X8-like number the DXGI enum happens
   to give 86.
2. **Is `dimension: 3` + `flags: 5` + `format: 86` a known combination** (a video plane as a
   `Texture2D` without RTV/DSV flags)? If `flags: 5` implies some view the host refuses, that would
   fail the call even with a legal format.
3. If the format is simply unknown, a diagnostic first step would be: on `no host texture`, log the
   format with its `element()` bytes-per-texel and the full `flags` word, then retry once with
   `R16G16_UNORM` / `R16G16_FLOAT` so the cutscene has a chance to show *something* and we learn
   whether the format was the only obstacle.

This path is worth fixing on its own: it does not depend on any of the shader work, and the intro
movie is the first thing a user sees after the start screen.

Host: Windows 10 22H2 UBR 3393, RTX 4070 SUPER 12 GB, VIctory `main` + #729 exports.

### Comment 1 — @lucaseddd — 2026-11-24T11:17:21Z

PR #89 already handles these exact packed formats on devices that cannot expose the requested render-target or typed-UAV support: DXGI 86 is B5G5R5A1_UNORM, and 115 is B4G4R4A4_UNORM. The patch widens those textures to RGBA8 and includes packed transfer conversion. This addresses the allocation failure without guessing a different channel layout.

On a Windows 10 + RTX 3060 test with #89 adapted onto ffe310e, both formats took the RGBA8 fallback, but the first mission cutscene still played with audio and subtitles over a black image. That confirms the fallback was exercised and leaves the remaining cause open; the two allocation failures alone did not account for the black image on this setup. AI-assisted testing and write-up.

(`victory_gpu::queue: a black frame after ...`). `44` is the clear colour, `231–251` is the
artwork/card, `0` is black. On both our hosts the world never produces anything above `44`
after the entry draw, so the next probe is that single draw and what its mesh outputs write.

Not measured yet: pixel content of the 2560×1440 MRTs the world's 72 mesh draws render into.
