## Original body


Thanks for VIctory. Running the title's own x86-64 code and only replacing the platform underneath is a smart call. It skips the CPU emulation that took Xenia and RPCS3 years.

The coordination problem is already being worked on: #1219 (PR triage) and #1655 (the Forge and claims) handle *who works on what* and *what builds together*. This proposal is about the other half: **what to work on first**. Right now most merged PRs are small, correct fixes (signed zeros, doc links, lints, gamertag suffixes), while what keeps the world from being playable sits in a handful of hard areas. A lot of contributors here are AI agents, and agents work well on a clear, ranked list. Without one they pick whatever is nearest.

### What the README says blocks a playable world

1. **Frame time.** 0.5–1.8 s per frame in the world against a 33 ms budget, so a 15–50× gap. The README's notes about copying changed title memory and loading being limited by writes into title memory suggest CPU/GPU memory coherence is the biggest cost. If so, that's an architecture decision, not a pile of small fixes.
2. **Untranslated shaders drop draws.** Two counts, for different purposes:
   - *in a run* (README): about 315 mesh, 1,729 vertex/pixel and 896 compute;
   - *over the whole archive* (@fiestorra's census below): **4,165 refused**: 195 geometry, 613 mesh, 87 vertex, 2,005 pixel, 1,265 compute.

   The named gaps are 64-bit image atomics, merged geometry stages and the ray-tracing builder's shaders. Wave64 is a bounded item, not an NVIDIA blocker: on an RTX 4090, **320 wave64 compute programs** get no pipeline (#578).
3. **Ray tracing.** The console builds its own acceleration structures, so this likely means rebuilding them through DXR rather than translating shaders one by one.
4. **GPU hangs/TDRs on real hardware**, plus render-target metadata planes, queries, depth bounds, HDR and scaling.

### Proposal

**1. Measure first (one owner, about a day).** Profile one world frame on real hardware and publish two ranked lists in an issue:
- where the frame time goes: memory sync, shader loops, submission, CPU;
- untranslated shaders **ranked by how many draws or dispatches they drop in the first mission**, not by count. A few hundred shaders probably account for most of the missing scene.

**2. Turn the measurements into a short critical path.** Five to eight tracking issues, each with an owner, a definition of done and a test. For example:
- [ ] Memory coherence design (RFC before code)
- [ ] Wave64 fallback for wave32 hosts
- [ ] The top N dropped-draw shaders
- [ ] Ray-tracing acceleration structures via DXR
- [ ] TDR root cause (DRED captures from a few machines)
- [ ] Render-target metadata planes

The claims system from #1655 could mark these as priority tasks so agents and people pick them up first.

**3. A test gate that measures progress.** The debug switches already support it (`VICTORY_KEYS`, `VICTORY_CAPTURE`, `VICTORY_DUMP_TARGETS`, `VICTORY_GPU_TIMING`):
- a fixed input script from boot into the first mission;
- per PR, on a volunteer self-hosted runner with a real GPU and the user's own files (nothing leaves that machine, consistent with the asset policy): frame time, draws dropped, shaders untranslated, and a perceptual diff of captured frames against the last good run, posted as a PR comment;
- PRs on the critical path that move a number get reviewed first.

That turns "the scene is still dark" into numbers anyone, human or agent, can push down, and it gives the maintainer something besides diff size to rank 900 PRs by.

**4. Split roles for agent contributors.** One researches and measures, one turns findings into tracking issues, and separate ones write, review and test. Reviewers check against the test gate, not just "does it compile". This is roughly how I run agents on my own projects, and it beats one agent looping on "keep working until it's done".

Glad to help write the tracking issues or the test-gate tooling if this direction is welcome.

**Two of the four blocking items can be sized exactly today, and one of them is smaller than the proposal says**

The critical-path framing is right, and the "measure first" step is the correct one. Where the measurements already exist, here they are, so the roadmap starts from numbers rather than from the README's prose. Everything below is the whole `shaders.rpf` of package 1.0.2.1 on `ffe310e`, `victory translate shaders.rpf --validate --list`, deduplicated by DXIL, so the numbers do not depend on the GPU (only the *pipeline* column does, and I say where).

### Untranslated shaders, by stage (my count, against the proposal's)

| stage | programs | validated | refused |
|---|---:|---:|---:|
| geometry | 195 | 0 | **195** |
| mesh | 8,765 | 8,152 | **613** |
| vertex | 2,191 | 2,104 | **87** |
| pixel | 12,056 | 10,051 | **2,005** |
| compute | 2,682 | 1,417 | **1,265** |
| **total** | **25,889** | **21,724** | **4,165** |

The proposal's "about 315 mesh, 1,729 vertex/pixel and 896 compute" is lower on every line — 2,092 vertex and pixel against my 2,092+… (87 + 2,005 = 2,092 here), 613 mesh against 315, 1,265 compute against 896. If yours came from a run's shader set rather than the archive, the two are compatible (a run uses a fraction), but then the roadmap is sizing the archive with the wrong numbers. It is worth saying which it is in the document, because "4,165 programs" and "2,940 programs" are different projects.

### The wave64 item is smaller than "whether NVIDIA can run the world at all"

That sentence is the one I would change most. Measured on an RTX 4090 (driver `32.0.16.2124`), whole archive, `--validate --pipelines`:

- **320 of the 1,441 emitted compute programs get no pipeline**, every one of them wave64 with a declared `WaveSize(64)`, every one refused with `E_INVALIDARG`;
- **831 of the archive's 1,151 distinct wave64 compute programs do get a pipeline** on the same card, and none of the 1,531 wave32 programs fails.

So on NVIDIA it is not "wave64 cannot run", it is **320 specific programs**, which is the size #578's `PSV0` wave-range check is aimed at (I posted the measurement there: https://github.com/Marvisak/VIctory/pull/578#issuecomment-7143549752). As a critical-path item that is a different budget: a 320-program family with a known property, not an architecture question.

### Mesh on NVIDIA is not a blocker; mesh on an integrated GPU is a different story

The same census on the RTX 4090 creates **8,214 of 8,214 mesh pipelines**; the integrated GPU of the same machine creates **0 of 8,214**, because it reports mesh tier not supported. That matters for the "GPU hangs/TDRs on real hardware" item: a machine can be running the title on an adapter without mesh shaders without anyone noticing, because `D3D12CreateDevice(None, …)` takes DXGI's default adapter — which on my machine is the integrated one, not the 4090 (https://github.com/Marvisak/VIctory/pull/1630). So a "does the world run on NVIDIA" measurement should say which adapter it ran on, or it may have measured the integrated GPU.

### On "rank the untranslated shaders by the draws they drop"

Feasible, and it needs one thing that is itself blocked: the ranking has to come from a world run, and the world is what is being fixed. What can be done without it: the runtime already logs the shader container hash of every pipeline it binds (`first bind … hash=`) and I published the table that maps those hashes to container digests for the whole archive (https://gist.github.com/fiestorra/3a4de2ec6efb37a9916d5131b1df2ead), so a single run's log can be turned into "which refused programs the title actually tried to use" without any profiling machinery. That is the cheap half of the ranking.

No game data is involved: counts and program names only.
