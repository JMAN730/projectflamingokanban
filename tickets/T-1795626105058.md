### Comment 1 — @FunWithFlagsDev — 2026-11-24T19:21:48Z

@GeaorgeAyvazov @srijann07

Thank you both for implementing and validating the diagnostic instrumentation.

The eight-thread experiment independently reproduces the blocking mechanism in our discrete-event model: one initializer and approximately seven times its duration accumulated across waiting workers.

PR #1571 is a useful first step toward measuring this under the actual pipeline workload without changing scheduling semantics.

For the integration measurements, I suggest collecting:

- Cold-cache and warm-cache runs on the same build.
- Dependency lookup time relative to total worker-job time, ensuring both counters cover the same worker population and measurement interval.
- Host preparation/creation time and, if possible, pipeline-library synchronization separately.
- Queue depth, active workers and dependency-blocked workers over time.
- Time to the first 100, 500 and 1,000 completed pipelines.

The key remaining discriminator is whether independent pipeline work is runnable while workers are blocked on shared shader initialization. Dependency waiting alone does not establish the expected benefit of a DAG scheduler.

If the integration measurements show significant avoidable worker occupancy, we can use those distributions to calibrate the existing simulation before implementing the production scheduler.

The synthetic results are encouraging. No title-performance improvement is claimed yet.

### Comment 2 — @Xvania7 — 2026-11-24T19:35:52Z

Implemented a dependency-aware two-stage shader translation and pipeline scheduler on fork branch [`perf/dependency-aware-pipeline-scheduler`](https://github.com/Xvania7/VIctory/tree/perf/dependency-aware-pipeline-scheduler) (commit `322c60e`).

### What changed
1. **Stage selection & deduplicated dependencies (`crates/victory-gpu/src/pipeline/host.rs`):**
   - Extracted `select_stages` and added `required_shaders` so pipelines validate required stages up front and register only the unique host stages they actually need before PSO creation.
2. **Shader dependency tracking & completion fan-out (`crates/victory-gpu/src/pipeline.rs`):**
   - Added `ShaderDeps` (waiting `Pending` list + failure bit) and `scheduled` flag on `Shader` under `#[cfg(windows)]`.
   - `Shader::translated()` calls `finish_translation(ok)` right after `OnceLock::get_or_init`, waking dependent pipelines as soon as a shared shader finishes or fails.
   - Added `register_waiter`, `promote_to_demand`, and `claim_scheduled` so work promoted from prewarm (`early`) to first-use (`demand`) also promotes its unfinished shader dependencies.
3. **Priority-aware DAG scheduler & worker pool (`crates/victory-gpu/src/pipeline/make.rs`):**
   - Replaced the single `mpsc::channel` with `Scheduler` + `Pool` draining 4 queues in strict priority order: `demand_pipelines`, `demand_shaders`, `early_pipelines`, `early_shaders`.
   - `start_with_deps` uses a `+ 1` registration sentinel (`UNREGISTERED`) on `remaining_deps` so concurrent shader completions never race registration.
   - Failed shader translations call `Pending::fail()` directly via `on_shader_done` without launching a host PSO build; workers never sit blocked inside `OnceLock::get_or_init()` waiting on another worker's slow shader translation.
