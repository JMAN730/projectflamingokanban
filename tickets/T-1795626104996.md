## A frozen desktop is not a device removal: check `TdrLevel` before blaming the runtime

Posting this because it changed the meaning of three "crashes" on our host, and because several
issue threads here describe exactly this symptom (#71, #59, #772, #965) without naming the setting.

### Symptom

Running the world stage, the desktop stops responding. No bugcheck, no process exit, no
`DXGI_ERROR_DEVICE_REMOVED` in the log, and a per-second resource guard stops logging too — the whole
machine is frozen until a hard reset. The last healthy numbers in our log were VRAM 6.9 GiB (well under
the card's 12 GiB), RAM 4.5 GiB, and `1366.6 ms/frame` (0.73 fps) in the title's own window title.

### Cause

```
HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers
    TdrLevel = 0        <- TDR detection disabled
    TdrDelay = 900
```

`TdrLevel = 0` disables Windows' timeout detection and recovery entirely. When a frame takes ~1.4 s
and the GPU stops answering, nothing resets it: the desktop is frozen permanently rather than the
title being killed with a device-removed error. That is why no event reached the runtime or our guard.

The setting is a common "stop TDR from killing my slow frame" tweak, and it has the opposite effect:
slow frames are no longer killed, but a genuine hang takes the machine with it.

### What to set instead

```
TdrLevel = 3     (default: detect and recover)
TdrDelay = 10    (or 60, as in #965: give slow world frames room, still recover from a real hang)
```

After changing it, the same workload reports its freeze as a device removal that the runtime can log
and classify, instead of freezing the host. On this machine the difference was between "the app
crashed, we have no idea why" and "the GPU timed out on a 1.37 s frame, here is the frame count".

### Why it matters for reports here

Any report of "the world freezes the whole PC" should state these two values. Without them, a freeze
is indistinguishable from a runtime fault, and it will send people chasing shader or descriptor bugs
that are not there. Our own elimination attempts lost time to this.

Not measured: whether a machine that was never tweaked (`TdrLevel` absent) behaves differently; ours
may have been modified before we started.

## Original comments

### Comment 1 — @bittertea0323 — 2026-11-24T15:22:20Z

Confirmation from the same host after the change: `TdrLevel=3`, `TdrDelay=10`.

The workload that used to freeze the desktop (Emulate wave64, 1066–1281 ms/frame, 0.8 fps, world
rendering at 1600–1863 draws/frame) now runs to completion: **1962 presented frames, no freeze, no
device removal**. Every frame stayed under the 10 s delay, so TDR never needed to fire — which means
10 s is already generous for a 1.3 s frame, and the value only needs raising if a single frame can
exceed it.

The important half is `TdrLevel=3`. With `TdrLevel=0` nothing recovers, and the symptom is
indistinguishable from a crash: no bugcheck, no process exit, no event, and even our per-second
resource guard stops logging because the whole desktop is gone.
