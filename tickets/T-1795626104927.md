## Original body

# VIctory — code review: DXGI typeless SRV remapping needs an aspect-aware path

**Target discussion:** https://github.com/Marvisak/VIctory/issues/876  
**Reviewed patch:** https://github.com/Xvania7/VIctory/tree/fix/issue-850-typeless-view (commit `5e3c9e2` as reported in issue #876)  
**Review type:** static source / public DXGI specification review only. **No game binary, assets, hardware runtime, or integration test was used.**

## Finding

The patch adds `first_concrete(format)` to `crates/victory-gpu/src/resource.rs`, with three explicit cases (90→87, 92→88, 39→41) and a fallback for typeless formats: `f + 1`. `adapt_view_format()` calls that helper when the host resource and requested view are both typeless (or the explicit view uses UNKNOWN).

This helps the demonstrated color case, `DXGI_FORMAT_R8G8B8A8_TYPELESS` (27) → `R8G8B8A8_UNORM` (28). However, the numeric-first-member rule is not valid for all DXGI format families:

| Resource format | Current fallback | Why problematic | Shader-readable view depends on |
|---|---|---|---|
| `R32G8X24_TYPELESS` (19) | **20 = `D32_FLOAT_S8X24_UINT`** | This is the **depth-stencil attachment (DSV)** format, not a generic SRV format. | **21 = `R32_FLOAT_X8X24_TYPELESS`** (depth) or **22 = `X32_TYPELESS_G8X24_UINT`** (stencil). |
| `R24G8_TYPELESS` (44) | **45 = `D24_UNORM_S8_UINT`** | Similarly chooses DSV format (already flagged by another commenter in #876). | **46 = `R24_UNORM_X8_TYPELESS`** (depth) or **47 = `X24_TYPELESS_G8_UINT`** (stencil). |
| `R16_TYPELESS` (53) | **54 = `R16_FLOAT`** | A typed format, but a different **interpretation of bits** from depth data stored as D16_UNORM. The view may be accepted while producing incorrect numerical samples. | **56 = `R16_UNORM`** for D16_UNORM depth; `R16_FLOAT` is correct only if the resource was intended to hold floating-point data. |

## Suggested action

1. Retain the color-specific mapping **27→28** supported by the focused RGBA8 GPU readback in #876. Don't treat `first_concrete()` as a universally valid SRV decision.
2. When a typeless depth/stencil family is encountered, resolve the SRV based on the *intended plane/aspect* and original title view format, or reject/trace the ambiguous case explicitly until that information is available. Do not silently select a DSV format via `f + 1`.
3. Add narrow regression tests for families **19, 44, and 53**, covering depth-vs-stencil SRV selection, rejection of a DSV format as the fallback SRV, and `D16_UNORM` vs `R16_FLOAT` reinterpretation.
4. Test the host D3D12 view creation and readback using synthetic textures (no game assets) before claiming that any remapping addresses black cutscenes or the world-to-output composite.

## Suggested minimal guardrail test

A unit test for the *future aspect-aware view-resolution helper* should assert outputs from a request that carries intended use, rather than asserting that every typeless format maps deterministically:

```rust
// Pseudocode: API shape intentionally left for the implementer.
assert_eq!(resolve_srv(19, Aspect::Depth), Some(21));
assert_eq!(resolve_srv(19, Aspect::Stencil), Some(22));
assert_eq!(resolve_srv(44, Aspect::Depth), Some(46));
assert_eq!(resolve_srv(44, Aspect::Stencil), Some(47));
assert_eq!(resolve_srv(53, Aspect::D16UnormDepth), Some(56));
assert_eq!(resolve_srv(27, Aspect::Color), Some(28));
```

**Important limitation:** This is a code-review edge case, **not a verified root cause** of the missing rendered image. Actual impact depends on whether these formats occur in the game's view requests and how those requests encode plane intent.

### Technical Analysis & Solution Architecture
In crates/victory-gpu/src/resource.rs and crates/victory-gpu/src/descriptor/host.rs:
On console, titles create SRVs using typeless formats or default (0) formats directly on typeless resources. On PC D3D12, ID3D12Device::CreateShaderResourceView requires a concrete, typed format and returns E_INVALIDARG if given a _TYPELESS or DSV format.

As correctly identified in this issue review, a naive f + 1 fallback erroneously assigns DSV formats to depth resources:
- R32G8X24_TYPELESS (19) + 1 = 20 (D32_FLOAT_S8X24_UINT), which is a DSV format and invalid for SRVs.
- R24G8_TYPELESS (44) + 1 = 45 (D24_UNORM_S8_UINT), which is also a DSV format.
- R32_TYPELESS (39) + 1 = 40 (D32_FLOAT), which is a DSV format.
- R16_TYPELESS (53) + 1 = 54 (R16_FLOAT), whereas D16 depth data requires R16_UNORM (56).

### Implementation Plan
1. Add is_typeless(format: u32) -> bool and concrete_srv_format(format: u32) -> u32 in crates/victory-gpu/src/resource.rs:
   - Explicitly remaps depth families to their legal depth SRV formats (19 -> 21 R32_FLOAT_X8X24_TYPELESS, 44 -> 46 R24_UNORM_X8_TYPELESS, 39 -> 41 R32_FLOAT, 53 -> 56 R16_UNORM).
   - Remaps packed and non-contiguous color families (90 -> 87, 92 -> 88, 94 -> 95).
   - Maps standard color families to primary UNORM/FLOAT (e.g. 27 -> 28 R8G8B8A8_UNORM).
2. Update fits() in crates/victory-gpu/src/descriptor/host.rs to adapt typeless view formats using concrete_srv_format, and allow view == 0 on typeless resources by resolving to concrete_srv_format(own).
3. Add unit tests in esource.rs and descriptor/host.rs covering all depth and color families.

Preparing clean branch with Rust 2024 compliance on fork.
