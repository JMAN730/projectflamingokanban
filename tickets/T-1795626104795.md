## Original body

I have a working branch that answers GTA VI's FidelityFX calls with AMD's PC FidelityFX upscaler (D3D12, SDK 2.4.0) in place of the Xbox DLLs:
https://github.com/AwkGrep256/VIctory/tree/pc-fsr

- Off unless VICTORY_FFX_DIR points at the SDK's signedbin.
- Series S: the context is created at 720p → 1080p on the host and the game runs normally.
- Series X (with the diagnostics switch that forces the game's upscaler picker): the 4K context is created fine. The game then stops on its own memory budget, which has no room for FSR's 4K buffers.
- Not tested yet: an actual upscale in the world.

Tested on an RX 9070 XT under Wine + vkd3d-proton. PRs are limited to collaborators right now, so I'm leaving it here. Happy to open the PR when that's possible.

## Windows confirmation of the context — and the upscale never runs: `OUTPUT` (slot 6) has no host texture

Your branch builds and creates the context correctly on native Windows 10, and then fails one step later,
before any picture exists. The author note "haven't checked the image itself yet" is exactly where it
stops here.

**Machine**: Windows 10 22H2 UBR 3393, RTX 4070 SUPER 12 GB, Ryzen 7 7800X3D, 31 GB, driver 591.74, title
1.0.2.1, diag build, native D3D12 (not Wine).
**Tree**: `pc-fsr` `f96ad82` cherry-picked onto `#189` + `#940` + `#729` + `#737` + `#352` + our fixes
(clean, no conflicts).
**Settings**: `VICTORY_FFX_DIR=<SDK 2.4.0 Kits/FidelityFX/signedbin>`, `VICTORY_FFX_SCALE=0.5`,
`VICTORY_UPSCALER=7E93F0`, `VICTORY_WAVE64_EMULATE=emulate`, Series X, `VICTORY_TEXTURE_MIP_DROP=1`.

**What works:**

```
VIctory: upscaler picker at title+0x7e93f0 returns 7 (4 direct calls)
VIctory: FidelityFX render scale at title+0x28ef680 set to 0.5
ffx: upscale context on the host GPU render=[1920, 1080] upscale=[3840, 2160] flags=41 result=0 provider="3.1.6"
ffx: jitter phase count r=0 q.render_width=1920 q.display_width=3840 count=Some(32)
```

The scale override does exactly what it says: the title builds a 1920×1080 render target and asks for a
3840×2160 output. That part is solid.

**What does not:** every dispatch.

```
ffx: an upscale resource without a host texture slot=6
```

`slot 6` is `OUTPUT` in `ffx.rs` (`const OUTPUT: usize = 6`), so the null makes the guard below return
before the SDK is ever called:

```rust
if d.resources[0].resource.is_null() || d.resources[OUTPUT].resource.is_null() {
    return ERROR_PARAMETER;
}
```

The run still completes 7930 presented frames at 25–30 fps with no device removal, i.e. it is a silent
no-op, which is why the window stays empty while everything looks healthy.

**Why the output texture is missing, as far as we can tell.** `host_resource()` returns `None` when
`resource(this).host` is empty, and the output of the title's FSR path is plausibly the swapchain back
buffer we create in `host.rs` (`CreateSwapChainForHwnd`) — that is not a title resource in victory's table,
so it has no host copy and no entry to find. On Linux/vkd3d-proton your run got past this, which fits: the
presentation path differs there.

Two candidate fixes, in the order we would try them:

1. Special-case `OUTPUT` in `ffxDispatch`: when `host_resource` is empty, pass the presenter's current back
   buffer instead of nulling the slot.
2. Register the swapchain buffers as host textures so `host_resource()` finds them like any other.

Not measured: whether the FSR dispatch then succeeds with a valid output (we stopped at the null), and
whether 1920×1080 → 3840×2160 actually reduces the world frame cost. The theory is a quarter of the pixels,
but our GPU time is dominated by mesh emission, so the saving needs measuring rather than assuming.

Happy to test a patched `ffx.rs` on this machine — we have the SDK layout and the exact knobs working
already.


### Comment 8 — @bittertea0323 — 2026-11-24T16:31:53Z

## The output slot is an XMem resource, not a D3D12 one — so it can never have a host texture

Follow-up to my confirmation above, with the shape of the missing slot now measured. This changes the fix
from "register the swapchain buffer" to something structural.

I added the resource's description to the warning; it prints the same every frame:

```
ffx: an upscale resource without a host texture
  slot=6  dim=3  3840x2160  format=67  flags=3145733  mips=1
```

Decoding `flags=3145733` (`0x300005`): the low bits are `ALLOW_RENDER_TARGET | ALLOW_UNORDERED_ACCESS`,
and the `0x300000` above them are the console's VIDMM flags. So this is not a swapchain buffer and not a
plain committed texture — it is a **title-memory (XMem) resource**.

That matters because `host_resource()` returns `None` whenever `resource(this).host` is empty, and XMem
resources never get a `host` at all: victory simulates them with shadow copies, so they never pass through
`host_texture()` / `CreateCommittedResource`. Which means the null is not a lookup that missed — the texture
does not exist in any form FSR could write to.

Two consequences for the branch:

1. **`VICTORY_FFX_SCALE` works and is worth keeping.** With `0.5` on Series X the title builds a 1920×1080
   render target and asks for 3840×2160:
   `render=[1920, 1080] upscale=[3840, 2160] result=0 provider="3.1.6"`. World draws go from ~2500 to
   **5103 draws/frame** and frame time improves from 1565–1799 ms to **1034–1199 ms**.
2. **The upscale never runs, and the title pays for it anyway.** With the output missing, every dispatch
   returns before the SDK call. The title then falls back to its own path: `copies` climbs from ~142 MB to
   **569 MB per frame** (299–422 ms of the frame), which eats most of the gain from rendering at half size.
   Net: 0.6 → 1.0 fps rather than the 4× the scale suggests.

So a working FSR path needs XMem resources to have host textures (or a host-visible XMem surface), not just a
slot fix in `ffxDispatch`. Two smaller notes in passing:

- `format=67` is absent from `resource::family()`, so the typeless retry I added for
  "format has no host unordered access" does not fire for it. That retry is still correct for the formats
  that are in the table; 67 needs its family member added.
- Our run stayed up for 300 s with this configuration and no device removal, so the path is at least stable.

Not measured: what the picture looks like once an upscale actually completes, and whether the 569 MB copy
disappears or merely moves if the output slot starts resolving.
