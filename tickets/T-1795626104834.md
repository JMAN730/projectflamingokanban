## Original body

The DXBC parser can return a successful result when a part points into the container header or the part table. In a synthetic case, a part with offset 0 is read back with the container magic `DXBC` as its FourCC.

I prepared a patch that checks that the part table fits inside the declared container size and rejects parts that start before the end of that table.

- [Patch commit](https://github.com/gustavocosta2/VIctory/commit/fe8b10f)
- [Branch](https://github.com/gustavocosta2/VIctory/tree/fix/dxbc-part-table)

The regression test failed with the original parser and passed with the fix on Apple Silicon macOS using Rust 1.98.1. The full `cargo test -p victory-shader --locked --lib` run passed 97 tests, with one benchmark ignored.

GitHub rejected PR creation from my account, so I'm sharing the patch here for review.

## Patch (one commit on `main` `ffe310e`)

```diff
diff --git a/crates/victory-shader/src/dxbc.rs b/crates/victory-shader/src/dxbc.rs
index 7a20963..54a61ad 100644
--- a/crates/victory-shader/src/dxbc.rs

@@ -80,9 +80,18 @@ impl<'a> Container<'a> {
         if count > MAX_PARTS {
             return Err(ShaderError::Malformed("implausible part count"));
         }
+        let table_end = HEADER_SIZE + 4 * count;
+        if table_end > data.len() {
+            return Err(ShaderError::Malformed("part table out of bounds"));
+        }
         let mut parts = Vec::with_capacity(count);
         for i in 0..count {
             let offset = u32_at(data, HEADER_SIZE + 4 * i)? as usize;
+            if offset < table_end {
+                return Err(ShaderError::Malformed(
+                    "part starts inside the header or part table",
+                ));
+            }
             let fourcc = FourCC(
                 data.get(offset..offset + 4)
                     .ok_or(ShaderError::Malformed("part header out of bounds"))?
@@ -178,4 +187,29 @@ mod tests {
         bytes.truncate(last);
         assert!(Container::parse(&bytes).is_err());
     }
+
+    #[test]
+    fn rejects_parts_starting_inside_the_header_or_table() {
+        let mut bytes = build(&[(FourCC([0; 4]), &[]), (FourCC::HASH, &[])]);
+        let second_entry = HEADER_SIZE + 4;
+        // A zero digest and a zero first FourCC make both bogus sizes zero,
+        // so a part at any offset in the header reads back as "valid".
+        for offset in [0u32, second_entry as u32] {
+            bytes[second_entry..second_entry + 4].copy_from_slice(&offset.to_le_bytes());
+            assert_eq!(
+                Container::parse(&bytes).unwrap_err(),
+                ShaderError::Malformed("part starts inside the header or part table"),
+            );
+        }
+    }
+
+    #[test]
+    fn rejects_a_part_table_longer_than_the_container() {
+        let mut bytes = build(&[(FourCC::SFI0, &[1, 2, 3, 4])]);
+        bytes[0x1C..0x20].copy_from_slice(&7u32.to_le_bytes());
+        assert_eq!(
+            Container::parse(&bytes).unwrap_err(),
+            ShaderError::Malformed("part table out of bounds"),
+        );
+    }
```

### Notes

- **#343 does not fix this issue.** It rejects parts that overlap *each other*, but a single part at offset 0 overlaps nothing, so it still parses with `DXBC` as its FourCC. It is complementary to the other fixes, not a replacement. Its branch is also based on `d2a4bae`. It merges cleanly onto `ffe310e` and passes there.
- **gustavo, davut and studiostephe make the same fix:** a part offset must not be below `HEADER_SIZE + 4 * count`. They differ only in error text and tests. Their extra "part table past the container size" check doesn't change behaviour: on `main` that input already fails with `Malformed("truncated")`. The new tests for it fail on `main` only because the message differs, so they check the wording, not the bug.
- **Existing tests can mislead.** A test that points an offset into the part table usually passes even on `main`, because the bytes read as the bogus size are large and trip `part data out of bounds`. gustavo's test (and C2 above) uses a zero first FourCC so that the size is zero and `main` really accepts the input. That makes it a true regression test.
- **#326** fixes this issue and the overlap cases. It also refuses known FourCCs listed twice and container major versions other than 1. It's a 10-file, +5.5k-line PR, so if it stalls, gustavo's or davut's single-file change is the smaller way to close this.
