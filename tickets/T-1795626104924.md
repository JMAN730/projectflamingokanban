## Original body

# Linux (Arch/CachyOS, RADV): the menus run and respond, 333 draws/frame, 2782 indirect draws dropped

Reporting a working Linux path and the frame statistics that come with it. No Windows machine was
involved anywhere: the workspace cross-compiles from Linux for `x86_64-pc-windows-msvc`.

## Setup

| | |
|---|---|
| OS / kernel | CachyOS, `7.3.5-2-cachyos` |
| GPU | Radeon RX 7900 XT (RDNA3, RADV), Mesa 26.3.1, Vulkan 1.4.363 |
| Wine | 11.22, win64 prefix |
| D3D12 | vkd3d-proton **3.2.0** (from Proton Experimental) |
| DXGI | DXVK's `dxgi.dll` (4.9 MB), plus DXVK `d3d11.dll`, `d3d10core.dll` |
| Overrides | `WINEDLLOVERRIDES="d3d12=n,b;d3d12core=n,b;dxgi=n,b"` |
| Build | `cargo xwin build --release -p victory --target x86_64-pc-windows-msvc`, `ffe310e` |

## What works

The title boots, the menus render, and they respond to mouse input: we clicked through the UI on
the machine. The frame loop runs stably for minutes and the log ends cleanly (`rc=0` after the
window was closed), no crash.

The project's own GPU tests agree with that on this stack:

```
running 51 tests
test result: FAILED. 48 passed; 2 failed; 1 ignored
```

Green are device creation, descriptor heaps and rings, null UAV/SRV replacement, placed heaps over
title memory, view lifetimes, texture layouts and pipeline creation.

## Frame statistics from the menu (the interesting part)

```
0.2 fps, 4566.7 ms/frame
  (4185.5 preparing: copies 3501.0 ms 68.4 MB, textures 600.3 ms 121.9 MB;
   27.9 on the GPU; 348.9 copying back 7.2 MB)
  333 draws/frame,
  dropped 1312 without a host pipeline (0 being made) and 2780 indirect
```

Two things stand out:

1. **2780 indirect draws dropped per frame.** With `VICTORY_INDIRECT` off, that is by design, but it
   means the world cannot draw even if every shader translated. Turning it on is the next step, and
   it needs `D3DCompile` with `cs_5_1`, which Wine's `d3dcompiler_47` refuses: the test
   `indirect::tests::argument_clamp_builds` fails for exactly that reason. Microsoft's
   redistributable `d3dcompiler_47.dll` is the known workaround.
2. **The GPU is idle: 27.9 ms on the GPU against 4566.7 ms per frame.** Almost all of the frame time
   is preparation on the host: 3501 ms of copies (68.4 MB) and 600 ms of texture work. On this stack
   the bottleneck is the copy path, not the graphics pipeline, which matches the `wineserver`
   observation in #340.

Only 333 draws reached a host pipeline, and 1312 more had none and none were being built, so the
remaining translated pipeline work is bounded and measurable.

## Four things a Linux run needs, none of them documented

1. **vkd3d-proton 3.2, not the 3.1 that ships with proton-cachyos.** 3.1 dies during world load with
   an exception inside `vkCreateGraphicsPipelines` (also reported in #752).
2. **DXVK's `dxgi.dll`, not Wine's builtin.** With `dxgi` resolved to the Wine builtin (252 KB) the
   title aborts after about 5 s with `uncaught exception 0xc0000005` at `wined3d.dll+0x165f50`,
   called from `dxgi.dll+0x7415`; the D3D12 device ends up being created through wined3d. With
   DXVK's `dxgi.dll` (4.9 MB) the same build runs for minutes.
3. **Override `d3d12core` as well as `d3d12`.** With only `d3d12`, Wine loads its own core DLL and
   stops with `unimplemented function d3d12core.dll.D3D12GetInterface`. Seeing `libvkd3d-1.dll` in
   the log means the same mistake (as diagnosed under #829).
4. **The graphics session.** Started over SSH, Wine aborts with
   `nodrv_CreateWindow ... no driver could be loaded` and no window appears. Under KDE on Wayland it
   needs `XDG_RUNTIME_DIR=/run/user/<uid>`, `DISPLAY=:0` (XWayland) and
   `XAUTHORITY=$XDG_RUNTIME_DIR/xauth_*`.

## Suggestion

The four points above cost a day to rediscover and are platform facts, not bugs. A short Linux
section in the getting-started docs (prefix DLLs, overrides, session variables) would let every
Linux tester start from a working prefix instead of a black window. Happy to write that section as
a patch to `docs/`; I cannot open a pull request from this account, so it would come as an issue
comment or a branch on my fork.

Also: `victory translate` over the retail shader pack reports DXIL for 2398 of 3411 vertex/pixel
programs (70 %) and 1513 of 1579 mesh programs (96 %), with the largest failure classes being
"scalar memory read as data" (314), "64-bit image atomic" (246) and "packed input half" (172). That
is where the remaining draws lose their shaders, on Windows and Linux alike.

## Shader translation: 12840 → 13421 of 14027 (95.7 %)

Work from today on top of `ffe310e`, measured with `victory translate` over the retail shader pack. Branches are on `mkslzk/VIctory` (`proton-fixes`, `stride-fix`, `addr-fix`, `integrate`), since PRs from this account are still limited.

### What moved

| class | before | after |
|---|---|---|
| `a descriptor read only as data` | 880 | 0 |
| `a structured buffer of unknown stride` | 206 | 0 |
| `a descriptor's dword 0/1/3 read as data` | 812 | 0 |
| `an address from a phi` | 8 | 0 |
| vertex + pixel programs emitted | 12840 | **13421** |

### How, in three pieces

**1. A window onto descriptor heap memory.** A descriptor loaded from a heap has no root parameter pointing at its dwords; `handle()` only built handles from root descriptors. The host root signature now always appends one SRV root parameter (`TITLE_SPACE`, register 0), bound per draw to a buffer holding the heap's bytes. `handle()` uses it for `RootType::Table | ResourceHeap`, and the dword reads become `rawBufferLoad` at the slot's byte offset. A missing `UsedResource` entry is no obstacle: a program that only reads numbers never names the descriptor as a resource.

**2. The window has to be honest.** `record()` in `victory-gpu` writes `[VIEW_TAG, index, generation]` over the first three dwords of every descriptor slot it records, so the heap bytes alone would hand a shader the runtime's tag where it expects an address or a format. The copy feeding the window therefore reconstructs those dwords from the `View` the runtime already holds: base address, stride (`StructureByteStride`, else the format's element, else 4), record count, width/height as split fields, type and last level, depth or layer count.

**3. Sizes the console computes versus sizes we can rebuild.** `descriptor_data` rebuilds the dwords a console compiler reads for an image's dimensions from the host view's `getDimensions`. The dwords it cannot rebuild (address low word, format/stride word, last level) now come from the window instead of stopping the program. A descriptor from a root parameter has no window and keeps its refusal.

**Stride.** Three cases, no guessed number: a heap descriptor with metadata uses it; a descriptor built in the code carries its stride in dword 1 bits 29:16 (mask 0x3FFF); with no stride at all the view stays raw and the index is used as a byte address, which is the console's own form for a raw buffer.

**Address joins.** A phi or `s_cselect_b32` over entries of one table range, where every alternative is the table's heap address plus a term without another parameter, is now traced as that table entry.

### What is left, and what blocks it

Top classes over the pack: 237 `a descriptor whose root is not a descriptor`, 207 `an interpolation with computed barycentrics`, 195 `an address in an SGPR that is no root parameter`, 158 `a cross-lane operation outside compute`, 108 `a biased image sample with 16-bit coordinates`, 73 `an address not from a root parameter`.

The 195 are not statically solvable, and the reason is concrete: user data reaches the pipeline per root parameter only (`pipeline/host.rs`, `draw.rs::user_value`), so a register outside the layout has no value the translator can read. Title memory is reachable from DXIL only through a root SRV the title set, or through the window above.
