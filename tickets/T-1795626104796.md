### Comment 1 — @Conrage — 2026-11-24T09:12:55Z

I would be happy to help with anything, let me know if and how i can contribute

Here are some issues and possible fixes:
### 1. Textures and buffers reached through `ResourceDescriptorHeap[]` are never refreshed or transitioned
Only views in descriptor **tables** get their contents uploaded. `tables()` filters `u.root == RootType::Table` (`crates/victory-gpu/src/draw.rs:649`), and only those entries reach `readable()` (`draw.rs:1105`). `readable()` is the only draw-time caller of `texture::upload` and `shadow.refresh`. Heap-indexed resources (`RootType::ResourceHeap`) never pass through it. The only other upload path is copies (`list.rs:449`, `543`).
**Effect:** a bindless texture keeps its creation contents (black), and a bindless buffer keeps its first-use copy. `host.rs:149` and `shadow.rs:13-16` acknowledge this.
**Fix idea:** at submission, upload and transition the title-written resources that the bound heap's views name.
 
### 2. `DispatchMeshX` with indirect arguments is dropped
`crates/victory-gpu/src/list.rs:1082-1086`: if `indirect != 0`, it warns once ("indirect mesh dispatches dropped") and returns.
**Fix idea:** route it through `State::execute_indirect` with kind `MESH` (10), which already exists and handles mesh (`draw.rs:983`).
 
### 3. `ExecuteIndirect` runs only single-argument signatures
`list.rs:1169` matches `([[kind, ..]], ..)`, which is a slice of exactly one argument. Signatures that also set root constants or views per record (draw-ID patterns) are counted and dropped. They log "indirect execution dropped (first time for this signature)".
 
### 4. A texture that once received a host copy ignores later title writes
`texture.rs:109-113`: once a texture is in `HOST_WRITTEN` (set by `CopyResource`/`CopyTextureRegion`/resolve, `list.rs:454`, `550`, `634`), `upload` always returns early. The flag is cleared only when the resource is dropped (`resource.rs:976`). If the title later writes that texture's memory (for example by streaming), the host never sees it.
 
### 5. `ID3D12Fence::SetEventOnCompletion(value, NULL)` returns `E_NOTIMPL`
`crates/victory-gpu/src/fence.rs:90-95`. D3D12 defines a NULL event as "block until reached". The comment's reason ("nothing can reach it while no GPU work runs") no longer holds, since `signal` runs from queues and the CPU (`fence.rs:99`, `queue.rs:160`).
**Fix idea:** a `Condvar` beside `waiters`, with `signal` calling `notify_all`. This is small and unit-testable.

### Comment 39 — @Dufftwt — 2026-11-24T14:50:03Z

@HrHd the loop cap result settles a lot, thanks. One caveat on the barrier reading: a barrier that can never be satisfied doesn't end because loops are capped, unless it sits inside a capped loop. The simpler reading is a loop whose exit depends on memory that another workgroup or an earlier dispatch writes, and the loop never sees the write. Two known gaps produce exactly that:

1. **Stale `glc` loads.** A loop polls a value through `glc` loads that the host doesn't make coherent, so it never sees the change. That was the `9ef9a9d818b27236` hang, and the #725 fix ended it on an RTX 5060 Ti. The fix is in `test/world-stack`.
2. **Unordered dispatches.** The pipeline syncs do nothing on the host, so a loop bound or counter can be read before the previous dispatch writes it. That's what `test/world-stack-sync` adds.

So the two uncapped runs from my last comment are the direct test: `test/world-stack` first, then `test/world-stack-sync`. With your 6–8 minute reproduction, each run answers within ten minutes.
