How #688 was merged here: the `dynamic: Vec<(usize, u32, u32)>` field became `lease: Arc<Lease>`, and the root-SRV one-view table added by #493 now takes its slot through `self.take_dynamic(host, key, 1)` instead of `host.dynamic(1)` + `self.dynamic.push(...)`. If that is right, reclaim probably wants to be gated on a completed fence value rather than on the list having been executed.

### Comment 5 — @LAKSHYA-cmd-tech — 2026-11-24T08:48:45Z

### Breakthrough: Resolving "a lane mask holding lanes elsewhere read as data" (347 shaders) and "a lane mask read as data" (197 shaders)

Following @chenzhehao1129-eng's real title test run which revealed the downstream failures after unblocking untracked selects:
1. `a lane mask holding lanes elsewhere read as data`: 347 shaders
2. `a lane mask read as data`: 197 shaders

### Root Causes Identified
1. **Immediate failure on non-active ballots in `mask_dword`**: In `crates/victory-shader/src/emit/lower.rs:1181`, `mask_dword` unconditionally aborted with `"a lane mask holding lanes elsewhere read as data"` if `!self.x.st.active.contains(&lo)`. This triggered whenever:
   - The mask was a constant (`Atom::Constant`) or boolean constant (`Bool::TRUE` / `Bool::FALSE`) where taking a ballot is unnecessary (its dword is the constant value itself).
   - The mask was defined in a branch or join where `active` was not tracked, even though `waveActiveBallot(bit)` is valid to evaluate on the host.
2. **Artificial stage limitation on `Atom::Opaque` and `Atom::Constant`**: In `atom()`, lowering of opaque and constant masks via `waveGetLaneIndex` was gated on `if self.console_lanes` (only true for compute), returning `Err("an opaque lane mask")` in Pixel, Vertex, and Mesh shaders.
3. **Restrictive `self.mask_ok` gate in `inst()`**: Reading a lane mask as a scalar operand was restricted to only four intrinsic categories in `MaskData::Host` and completely disabled (`false`) for `MaskData::None` (Mesh shaders), aborting common scalar operations like `s_mov_b32`, `s_and_b32`, `s_or_b32`, and `s_bitcmp` on masks with `Err("a lane mask read as data")`.

### Solution
- **`mask_dword` constant resolution & safe ballot fallback**: Directly returns 0 for `Bool::FALSE`, `u32::MAX` for `Bool::TRUE`, and `k as u32` for `Atom::Constant(k)`. For general masks, `waveActiveBallot(bit)` is emitted safely at `self.def_block` (falling back to `self.cur`), protected against cyclic recursion via `self.balloting`.
- **Lifted stage gates**: Enabled `Atom::Opaque` and `Atom::Constant` lowering across all pipeline stages.
- **Expanded `self.mask_ok`**: Allows scalar moves, bitwise operations, and bitcmp tests across `MaskData::Host` and `MaskData::None`.
- Added unit test `lane_mask_reads_as_data_lowers` in `emit::lower::tests`.

Verified on Windows 11 MSVC: all 90 tests in `victory-shader` passed (`test result: ok. 89 passed; 0 failed; 1 ignored`), clippy clean, policy check ok (152 files).

Branch ready for testing:
https://github.com/LAKSHYA-cmd-tech/VIctory/tree/fix/shader-lane-mask-ballots-and-data-reads

### Comment 28 — @Dufftwt — 2026-11-24T17:48:33Z

@Logan-Gaillard that's the right diagnosis, and #334 (realhenners) is already that design, so it's worth running before taking your prototype further:

- **One owner per list.** `BufferStates` in `host.rs` records each host copy's first and current state in the list. Reads use `GENERIC_READ`, shader writes `UNORDERED_ACCESS`, and a transition is recorded wherever the use changes.
- **Lists start and end in a known state.** The list's prelude moves each buffer from `COMMON` to its first state, and `close` moves it back to `COMMON`. No state leaks into the next list, which is where deferred copies and other lists' writers would otherwise disagree.
- **The source of your 31 mismatches.** `indirect.rs` recorded fixed `UNORDERED_ACCESS -> INDIRECT_ARGUMENT` barriers and moved the buffer back to `UNORDERED_ACCESS` after each `ExecuteIndirect`. The arguments live in the same 174 MB heap as the vertices, so every indirect draw left the vertex data in UAV state. #334 removes those fixed barriers.

Your debug-layer counts make the test: #334 on your tree, or `test/world-stack` (`e0c3385`), which has it with #568. If both counts go to zero there and the removal goes with them, that's strong evidence for #334.
