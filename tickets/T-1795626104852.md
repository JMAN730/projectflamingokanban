## Original body

### Summary

In `crates/victory-gpu/src/list.rs` (`state::targets`, implementing `ID3D12GraphicsCommandList::OMSetRenderTargets`), the `RTsSingleHandleToDescriptorRange != 0` path has four bugs:

1. **Access violation on `count == 0` with non-null `handles`**: `if one_range != 0 && !handles.is_null()` dereferences `unsafe { *handles }` even when `NumRenderTargetDescriptors == 0` (unlike `items(handles, count)` right above it, which guards `count == 0`). In D3D12, depth-only passes may call `OMSetRenderTargets(0, pRTVs, TRUE, &dsv)` with an unread/stale non-null pointer; verified on host Windows 11 D3D12 that `OMSetRenderTargets(0, 0x10, true, None)` succeeds without dereferencing the pointer.
2. **Access violation when `*handles == 0` and `count >= 2`**: stepping `first + 128 * i` from a null handle `0` produces `0x80, 0x100, ...`, which `descriptor::rtv_record` then treats as non-null pointers and dereferences in the null page (`0xC0000005`).
3. **Unchecked `u64` arithmetic**: `first + 128 * i` panics in debug builds (and wraps to low memory in release) if `first` is near `u64::MAX`.
4. **Unbounded `count`**: `count` was not capped at `D3D12_SIMULTANEOUS_RENDER_TARGET_COUNT` (`8`), allowing excessive allocation or invalid counts to reach the host command list.

### Fix on fork

- Branch: `AndyLatimer/VIctory` @ `fix/gpu-om-set-render-targets-bounds` (based on `main` `ffe310e`)
- Commit: https://github.com/AndyLatimer/VIctory/commit/de663d2

Extracted `state::target_handles` in `crates/victory-gpu/src/list.rs` to ignore `handles` when `count == 0`, cap `count` at `8`, preserve null slots (`vec![0; count]`) when a single range starts at `0`, and check `first.checked_add(128 * i)` against overflow.
