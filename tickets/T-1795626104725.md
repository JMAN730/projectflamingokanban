## Original body

On an AMD GPU, `cargo test -p victory-shader --lib` on `main` (`9aef3d9`) sometimes dies with `0xC0000005` (access violation) when tests run in parallel, which is cargo's default. It never crashes single-threaded.

**Measured** (AMD Radeon RX 9060 XT, RDNA4, driver 32.0.32029.2010; Ryzen 7 5800X3D; Windows 11 Pro 26200; Rust 1.98.1; debug; `cargo test -q -p victory-shader …`):

| Run | Crashes |
|---|---|
| `--lib` | 3 / 25 |
| `--lib -- --test-threads=1` | 0 / 10 |
| `valu_tests` only | 0 / 20 |
| `--lib -- --skip valu_tests` | 0 / 20 |
| `--lib -- valu_tests emit::tests::stub_pipeline_is_created` | 1 / 20 |
| `--lib -- emit::` | 1 / 20 |
| with #116's LDS tests: `byte_and_halfword_writes` + `byte_and_halfword_reads` only | 2 / 6 |
| #116, `lds` filter | 4 / 5 |

The log stops mid-run with `process didn't exit successfully: …victory_shader-….exe (exit code: 0xc0000005, STATUS_ACCESS_VIOLATION)`. No test reports a panic.

So it takes two tests that each create a D3D12 device or pipeline (the `Host`s in `valu_tests`, `stub_pipeline_is_created`, #116's `lds_tests`) running at the same time. More such tests make it more frequent. My guess, not checked: something in device or pipeline creation, or in the DXIL validator loaded per test, isn't safe to use from two threads at once on this driver. Either way, it makes the default `cargo test --workspace` flaky on AMD, and new GPU tests will raise the rate. Serializing the GPU tests (one shared lock, or `--test-threads=1` for this crate) would avoid it.

Not tested: NVIDIA or Intel (does it happen there?), a release build.

### Comment 2 — @unknown — 2026-11-24T01:27:09Z

Thanks @DaviTostes. Your Wine result was the key, but on Windows the difference turns out to be **WARP**, not the validator. Under vkd3d-proton there's no WARP, so those tests only ever make the hardware host there. Same card here (RX 9060 XT), Windows 11 26200, `d3d10warp.dll` / `D3D12Core.dll` 10.0.26100.9818, debug:

| `cargo test -q -p victory-shader …` | Crashes (`0xC0000005`) |
|---|---|
| #116 `lds`, as shipped | 3 / 10 |
| #116 `lds`, validator off (`VICTORY_DXIL` pointing at a missing file) | 3 / 20 |
| #116 `lds`, validator on, `load` and `validate` behind one global `Mutex` (local patch) | 6 / 20 |
| #116 `lds`, **WARP only** (`VICTORY_WARP=1`) | **20 / 20** |
| #116 `lds`, **hardware only** (local patch: `Host::new` refuses WARP) | **0 / 20** |
| `main` `d2a4bae` `--lib`, validator off | 1 / 25 |
| `main` `--lib`, WARP only | **10 / 10** |
| `main` `valu_tests`, WARP only | 8 / 10 |
| `main` `--lib`, WARP only, `--test-threads=1` | 0 / 5 |

So it's two or more test threads each using their own WARP device at the same time. The validator and the AMD driver are cleared. It isn't AMD-specific either (I'll fix the title): any Windows machine with WARP should hit it. With a real GPU it's rarer only because WARP is just one of each test's two hosts.

Possible fixes, cheapest first: hold a process-wide lock for the WARP host's work in the tests (`hosts()` / `Host::new(true)` and its dispatches), or share one WARP `Host` between tests. Running this crate with `--test-threads=1` also avoids it, at the cost of speed.
