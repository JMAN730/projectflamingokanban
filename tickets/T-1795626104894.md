VIctory now runs on **Linux under Proton** and gets as far as on Windows: boot, first-boot screens, intro video, start screen, saves, loading, and the opening of the first mission (credits over the scene; the scene is still dark, as on Windows). This PR has the fixes that took, plus two world GPU faults that are likely not Proton-specific.

Tested on CachyOS, RX 9070 XT (RADV, Mesa 26.3.1), Proton Experimental `experimental-11.0-20261112`, built with `cargo-xwin`. **Not tested on Windows**; the Windows paths are meant to be unchanged except for the two fault fixes.

## World GPU faults (likely also on Windows)

Found with `umr` wave dumps at the fault:

- **GPU: mirror heap slots the title writes into its own memory.** GTA VI copies whole descriptor slots inside its own heap memory, and no create/copy call reports it. A mesh shader then read a slot as a constant buffer while the host slot still held a texture view. Its upper half read as a buffer at address 0, and the device was lost. The faulting waves held `s[8:11] = {0, 0x00400000, 0x00248000, 0}`, loaded from heap slot ~1,061,522. This is probably the "world's low-address page faults" in the comment at `null_view`. Before each submission, the heap blocks written since the last one (`watch::writes`) are now mirrored again.
- **GPU: bind root SRVs as bounded one-view tables.** A compute shader read 32 MB past a root SRV's host copy (TCP fault at `s[10:11] + 0x1f0e000`). On the console that address is other title memory; here it's unmapped. Root SRVs are now a one-view raw-buffer table sized to the copy, so out-of-range reads return zeros. Shader bindings don't change.

With both, the world runs without a device loss for as long as I tested: 8 minutes, twice. Before, it was lost after 5–90 s.

## Wine / vkd3d-proton compatibility

- **Indirect argument clamp:** Wine's `D3DCompile` (vkd3d-shader) lacks `RWByteAddressBuffer` methods and doesn't embed `[RootSignature]`, so every indirect execution was dropped. The clamp now uses structured buffers and builds its root signature in code. A new GPU test checks the clamped values.
- **Pipeline library:** vkd3d-proton refuses an empty library given a dangling non-null pointer, so it's now requested with a null one.
- **Shaders: one returning block per program.** A loop left by both a break and a return made dxil-spirv emit invalid SPIR-V, and RADV segfaulted on it (exit code 3). Every `s_endpgm` now branches to one shared `ret` block, like DXC output.
- **HLE:** `WSAConnectByList` and `GetAddrInfoExA` are missing from Wine's ws2_32. They now fail the call instead of aborting.
- **Watch:** Wine emulates write watching page by page (about 1 ms per call; 3,500 calls and 17 GB checked per frame). Under Wine, a range already checked in the current submission is answered from the journal. Windows is unchanged.
- **Shader test:** vkd3d-proton doesn't check DXIL hashes, so that one check is skipped under Wine.

## Linux docs

`docs/linux-proton.md` and `scripts/proton-run.sh` (runs `victory.exe` and works as cargo's test runner), plus a README pointer. One finding there: GE-Proton 11-11's vkd3d-proton crashes RADV on some translated shaders; Proton Experimental works.
