## Original body

got into gameplay on linux today (hud, minimap, footsteps). world is still mostly black, same as on windows. took a few crashes to get there so writing down what fixed each one, might save someone some time.

setup: rx 9070 xt, cachyos, kernel 7.3.5, mesa 26.3.1, wine 11.22, diagnostics build cross-compiled with xwin, series x, 1.0.2.1

**1. you need vkd3d-proton 3.2**

the 3.1.0 that ships with proton-cachyos crashes the moment the world starts loading:

```
err:vulkan:vkCreateGraphicsPipelines Exception 0xc0000005 in Unix call.
```

it's the old dxil-spirv structurizer (#144). on nvidia the driver crashes on it, on amd mesa can't parse the spirv, spirv_to_nir returns null and radv dereferences it (radv_shader.c:547). i grabbed d3d12.dll and d3d12core.dll from GE-Proton11-14 and that crash went away.

**2. #190 #454 #493 #579 + `VICTORY_NO_WATCHDOG=1`**

without these i get the gpuvm fault from #714 about 50s into the world. with them it stayed in-game for about 14 minutes, then hit a different fault (address 0x0, device removed).

**other stuff**

- `WINEDLLOVERRIDES="d3d12,d3d12core,dxgi=n"`, dxgi.dll from dxvk
- needs 12-14 gb of ram once you're in the world
- `VICTORY_KEYS=20:Enter,24:Enter,...` gets through the menus if you don't have a pad set up
- 0.2-1 fps. the gpu only spends about 20ms a frame, the rest is the cpu-side copies
- the black screen isn't a linux thing: 533 of 2679 shaders didn't translate in my run (432 of them compute), same as #293

happy to test prs on this setup if anyone wants amd/linux results.

### Comment 7 — @crashbashash — 2026-11-24T13:13:40Z

Same crash on RDNA2, with the exact dxil-spirv versions, in case it helps people pick a Proton build.

**Setup:** CachyOS, RX 6800 XT (RADV, Mesa 26.2.6), `main` at `ffe310e`, diagnostics build via cargo-xwin, 1.0.2.1.

With GE-Proton11-6 (vkd3d-proton 3.1.0, build `c9c6bf2e`), the game exits with code 3 on the first load:
```
err:vulkan:vkCreateGraphicsPipelines Exception 0xc0000005 in Unix call.
```

- The crash is in the **fragment** shader of that pipeline, not the mesh shader. In a native Vulkan test outside Wine, the same SPIR-V also crashes RADV when paired with a trivial vertex shader.
- vkd3d-proton's SPIR-V for it fails `spirv-val`: `block … exits the loop headed by …, but not via a structured exit`. It's a waterfall loop (from `ffe310e`) whose `LOOP_LIMIT` exit (discard + return) leaves from the latch.
- I ran the same DXIL (from `VKD3D_SHADER_DUMP_PATH`) through the dxil-spirv CLI with `--bindless --enable-shader-demote`:

| dxil-spirv | ships in | result |
|---|---|---|
| `1b949ec` | GE-Proton11-6 (vkd3d-proton `c9c6bf2e`) | crashes in-game (the run above; not run through the CLI) |
| `8b48f0e` (2026-10-26) | vkd3d-proton v3.1 release | invalid SPIR-V |
| `34f0ff84` (2026-11-20) | GE-Proton11-13 / 11-14 (vkd3d-proton `cae8353ed`) | valid |
| `7c04863` (2026-11-24) | dxil-spirv master | valid |

The structurizer commits from 2026-11-16/17 (`4a73ab4f`, `a781dce9`) look like the fix; I didn't bisect.

So any Proton whose vkd3d-proton includes dxil-spirv from 2026-11-20 or later works without swapping DLLs. GE-Proton11-14 is one: with it (plus the `d3dcompiler_47` workaround from #170), the game gets past the load into the first mission's cutscene: subtitles and audio, scene dark as on Windows.

I also tried #844's branch (`b7cc788`) on vkd3d-proton 3.1.0. Its single-`ret` change gets past the pixel shader that crashed `main`, but the same load then crashes in `vkCreateComputePipelines` (`Exception 0xc0000005 in Unix call`, exit code 3) on a compute pipeline. So #844 alone isn't enough on older Proton builds; the newer dxil-spirv is still needed.
