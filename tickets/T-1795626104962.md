## Original body

﻿### Summary

Lowers `image_store` with contiguous partial channel masks (`dmask` = `0x1`, `0x3`, `0x7`, and no-op `0x0`, both 32-bit float and `d16` packed 16-bit) in `crates/victory-shader/src/emit/lower.rs`, unlocking shaders that store to 1-, 2-, and 3-channel float/unorm/snorm UAVs (`RWTexture*<float>`, `float2`, `float3`) instead of failing with `an image store of some channels`.

Because external PR creation is restricted (`collaborators_only`), the CI-green branch is ready on my fork:
- **Branch:** https://github.com/davi713albano-coder/VIctory/commits/shader/image-store-partial-dmask
- **Commit:** `f1c423f` (based on `main` `ffe310e`, 2 files, +218/-9)
- **Compare:** https://github.com/Marvisak/VIctory/compare/main...davi713albano-coder:shader/image-store-partial-dmask

### Changes
- **`crates/victory-shader/src/emit/lower.rs`**:
  - Preserves `dmask == 0` for `image_store` (emitting a no-op instead of defaulting to channel 0 as loads/samples do).
  - Accepts contiguous masks `0x1`, `0x3`, `0x7`, `0xF` (rejecting sparse/non-contiguous masks such as `0x5` because DXIL typed UAV stores cannot perform partial read-modify-write stores without clobbering lower channels).
  - Reads only the `dmask.count_ones()` packed VGPRs (or half-VGPRs for `d16`), zero-pads trailing channels with `0.0f32`, and emits `dx.op.textureStore.f32` with write mask `0xF` as required by the DXIL validator (`store on typed uav must write to all four components of the UAV`); host D3D12 drops extra components according to the bound UAV format.
- **`crates/victory-shader/src/emit/valu_tests.rs`**: adds `image_store_partial_dmask_writes_expected_channels`.

### Tests & Verification
`image_store_partial_dmask_writes_expected_channels` exercises:
- Rejection of non-contiguous `dmask = 0x5` with `Unsupported("an image store of some channels")`.
- Full DXIL validation (`dxil.dll`) and live D3D12 UAV readback across `dmask` = `0x0`, `0x1`, `0x3`, `0x7` (32-bit float) and `0x1`, `0x3`, `0x7` (`d16` packed f16).

### Comment 1 — @fuzeofficlal — 2026-11-24T14:20:34Z

RDNA 2 defines sparse `image_store` masks such as `0x9`. The selected components are packed into consecutive VGPRs and unselected components are written as zero. [AMD RDNA 2 ISA, Table 41 and section 8.2.5](https://docs.amd.com/v/u/en-US/rdna2-shader-instruction-set-architecture)

#332 already implements this for sparse masks while emitting the full `0xF` write required by DXIL. I verified its current head (`a5b0dcb`) with `0x9` f32 and `0xb` d16 against an initialized RGBA32F UAV. Windows hardware and WARP both overwrote the disabled channels with zero, and both shaders passed DXIL validation. The [test and results](https://github.com/Marvisak/VIctory/pull/332#issuecomment-7134205530) cover nonzero masks.

### Comment 2 — @MichaelSmithAI — 2026-11-24T14:25:08Z

Independent four-channel readback on RTX 4090 under Wine/vkd3d-proton 3.2: exact f1c423f refuses sparse mask `0x5`. With sparse lowering added to that branch, the f32 case returned `[1.5, 0, -2.25, 0]`, and packed d16 mask `0xd` returned `[1.5, 0, -2, 4]`. All eleven fixture cases matched their complete expected texels. For the zero-mask control, the shader first stored four distinct nonzero values and all four survived the second store. That checks the branch’s no-op behavior independently of the texture’s initial contents.

The existing [#332 Windows hardware and WARP result](https://github.com/Marvisak/VIctory/pull/332#issuecomment-7134205530) already verifies nonzero sparse masks against an initialized UAV. These Wine results add different masks and the seeded zero-mask control. We have no title shader or rendered frame attributed to this change.
