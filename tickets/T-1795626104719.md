## Original body

## Summary

The title boots, loads all archives, creates the D3D12 device, opens the window, and then crashes within ~2 seconds with `STATUS_ILLEGAL_INSTRUCTION` (`0xc000001d`). The faulting instruction is `clwb` (Cache Line Write Back), which the host CPU does not support. The README lists "a CPU with AVX2" as the only CPU requirement, but the title's own code uses `clwb`, which is not present on all AVX2-capable CPUs (notably Intel Broadwell and earlier).

## Environment

| | |
|---|---|
| **CPU** | 2× Intel Xeon E5-2680 v4 (Broadwell-EP, 2016) — has AVX2, **no CLWB** |
| **GPU** | (D3D12, shader model 6.6 capable) |
| **OS** | Windows 11 |
| **VIctory build** | `b99f876b74d4a77f` (release and diag, `--features diagnostics`) |
| **Title** | Xbox Series X title, TitleID `7952987A`, version `1.0.2.1` |
| **Console mode** | `series-x` (default) |
| **Tested with** | `VICTORY_D3D12_WARP=1` (software adapter) — same crash, confirming it is CPU-side, not GPU-side |

## What happens

The loader maps the image, binds all imports (`game_scarlett_master.exe: 88 hle, 427 host, 72 title, 0 missing`), redirects static TLS (index 12, 53246 patches), opens every `.rpf` archive, creates the host D3D12 device, fits the window, and enters the title's first frames. Then:

```
VIctory: first-chance exception 0xc000001d at victory-image-b99f876b74d4a77f.dll+0x4ecc84a
VIctory: unhandled exception 0xc000001d at victory-image-b99f876b74d4a77f.dll+0x4ecc84a
```

## The faulting instruction

Disassembly of the in-memory image at RVA `0x4ecc84a` (dumped via `VICTORY_CRASH_SAVE=0x4ecc84a:256`):

```asm
0x4ecc84a:  66 41 0f ae 31      clwb   byte ptr [r9]      ; <-- #UD here
0x4ecc84f:  49 83 c1 40         add    r9, 0x40           ; +64 (cache line size)
0x4ecc853:  49 39 c1            cmp    r9, rax
0x4ecc856:  76 f2               jbe    0x4ecc84a          ; loop
0x4ecc858:  48 83 c4 28         add    rsp, 0x28
0x4ecc85c:  c3                  ret
```

This is a cache-line write-back loop, present in the **title's own code** (confirmed at file offset `0x4ecbc4a` in the prepared image, which is the same RVA after section alignment). It is not a VIctory-injected patch — the VIctory runs the title's x86-64 code natively, and the title was compiled for the Xbox Series X's AMD Zen 2, which supports `clwb`.

`clwb` (`66 0f ae /6`) was introduced in:
- **AMD**: Zen 2 (2019)
- **Intel**: Skylake-X / Ice Lake (client: 10th-gen Ice Lake, 2019; server: Cascade Lake-SP, 2019)

It is **not** present on:
- Intel Broadwell (5th-gen, 2015) and earlier — including Xeon E5-26xx v4
- AMD Zen 1 / Zen+ (Ryzen 1000/2000)

These CPUs do have AVX2, satisfying the stated requirement, but cannot execute `clwb`.

Registers at the fault (from the diag build):
```
rax 0x17bc001f  rcx 0x17bc0000  r9 0x17bc0000  rsp 0x8d3dfff3e0
```
`r9` points into the title's mapped memory; `rax` is `r9 + 0x1f` (end of a 32-byte region, though the loop strides by 0x40).

## Suggestion

Could VIctory detect `clwb` support at startup (CPUID `leaf 7, sub-leaf 0, EDX[6]`) and, when absent, trap `#UD` on `clwb` and fall back to `clflush` (or `clflushopt` if available, else `clflush`) on the same address? `clwb` and `clflush`/`clflushopt` take the same `m8` operand, so the emulation is a straight substitution of the opcode bytes. This would let the title run on all AVX2 CPUs, matching the README's stated requirement.

Alternatively, the README's CPU requirement could be updated to "AVX2 **and CLWB**" to set expectations, though emulation seems preferable since the title presumably only needs the write-back effect, not `clwb` specifically.

```powershell
target\diag\victory.exe run <game dir>\game_scarlett_master.exe --execute
```

### Comment 1 — @DaviTostes — 2026-11-24T00:38:24Z

CLWB is the instruction **#45** adds for Intel CPUs before Ice Lake, and it is merged now — `main` `7d33c46` is the merge of #45.

So the first thing worth trying is a build of current `main` (or a release binary from it): the loader's illegal-instruction handler (`crates/victory-loader/src/crash.rs`) should emulate `clwb` instead of faulting.

If it still crashes after that, the neighbouring class is #34 (open): the handler also emulates `clzero` loops and `rdpru` for the same reason. The crash log's exception address plus the CPU model is enough to tell which encoding was not recognised.
