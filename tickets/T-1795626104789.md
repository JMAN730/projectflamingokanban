## Original body

## What's wrong

For a descriptor that comes from the SM 6.6 resource heap, rather than a table, the lowering decides SRV or UAV **per instruction**, from that instruction's name alone:

- `used_kind` returns `None` for any root parameter that isn't a table (`crates/victory-shader/src/emit/lower.rs:3257-3259`).
- So `uav` is true only for stores and atomics: buffers at `:6075`, images at `:5470-5475`, descriptor data at `:2943-2946`.
- `s_buffer_load` takes a raw SRV handle only for a known SRV (`:2830`). Everything else, including a UAV, gets a constant-buffer handle (`:2851`).

The title holds one UAV descriptor in the heap. Its loads get an **SRV**-annotated handle (`annotateHandle` without `IsUAV`, bit `0x1000`) and its stores a **UAV** handle. The annotation doesn't match the descriptor's type, which is undefined in D3D12.

## Example

```
s_mov_b32 s5, 0                                    BE850380
s_load_dwordx4 s[8:11], s[4:5], 0                  F4080202 FA000000
v_mov_b32 v0, 0                                    7E000280
buffer_load_dword v1, v0, s[8:11], 0 offen         E0301000 80020100
buffer_store_dword v1, v0, s[8:11], 0 offen offset:4   E0701004 80020100
s_endpgm
```

With the heap layout, the handles' props come out as `(0xB, 0)` for the load (a raw SRV) and `(0x100B, 0)` for the store (a raw UAV), for one and the same descriptor. I recorded these with a temporary print in `heap_handle`.

- Console: dword 1 = dword 0.
- Host: whatever the driver does with a UAV descriptor read through an SRV handle.

## Suggested fix

Before lowering, mark every descriptor source that has any store, atomic or `glc` access as a UAV, and give every access through it the UAV form. A UAV `s_buffer_load` then uses the raw `(11 | 0x1000)` path instead of a constant buffer. Heap descriptors that are only ever read stay as they are now.

**Not tested:** on a GPU. How often titles use heap descriptors this way, and what each vendor's driver does with the mismatch, are unknown.

## Related

- #180 and #307 change this code; neither infers UAVs across instructions.
- #725 (`glc` loads not globally coherent) needs this inference to know which loads are UAV loads.

### Comment 3 — @Hiiva — 2026-11-24T10:10:43Z

Checked the `readonly` concern against Microsoft's compiler. SDK DXC 1.8.2502.11 compiled a synthetic `globallycoherent RWByteAddressBuffer` store/load/store and polling loop at both `-O3` and `-Od`. It emits `rawBufferLoad` with `{ nounwind readonly }`, stores with `{ nounwind }`, and barriers with `{ noduplicate nounwind }`. The optimized output retains the store-before-load order and the polling load inside the loop. This matches [DXC's operation definitions](https://github.com/microsoft/DirectXShaderCompiler/blob/main/lib/DXIL/DxilOperations.cpp): `readonly` describes the load's effects, not immutable resource contents. No attribute change is needed.

GLC-only inference still needs descriptor-type evidence. The [RDNA2 ISA](https://www.amd.com/content/dam/amd/en/documents/radeon-tech-docs/instruction-set-architectures/rdna2-shader-instruction-set-architecture.pdf) defines GLC as cache policy for reads/writes, so it does not establish SRV versus UAV class. Marking every GLC read as UAV could mismatch an actual SRV. The implementation uses known UAV metadata or stores/atomics at the same tracked heap address, including descriptor reloads. A scalar-only unknown descriptor remains unresolved until its actual view kind is established.
