## Original body

## Summary

On an NVIDIA RTX 5070 Ti the title gets through the intro (video, cutscene audio, subtitles, title cards), then the host device is removed with `DXGI_ERROR_DEVICE_HUNG` (0x887A0006) once world mesh draws start. With DRED on, the hang is always on a **mesh pipeline draw** whose user-data heap indices point at descriptor slots VIctory reports as `null`. Which mesh shader it is varies between runs, so this doesn't look like one bad shader. My guess (not verified) is that NVIDIA is less tolerant than the RX 6700 XT of what these draws read through those slots.

## Environment

- VIctory `main` at `ffe310e`, `diag` profile with `--features diagnostics`
- Windows 10 Pro 22H2 (19045), in-box D3D12 runtime 10.0.19041.5794
- D3D12 Agility SDK 1.620.2 (needed for SM 6.6 on Windows 10, see below)
- NVIDIA GeForce RTX 5070 Ti, driver 32.0.16.2124
- Intel Core i7-8700 (6 cores / 12 threads), 32 GB RAM
- Title: Xbox Series X dump, game version `930.048.020`, title ID `7952987A`

## Steps

1. `VICTORY_SHADER_LOOP_LIMIT=4096` and `VICTORY_D3D12_DRED=1`
2. `victory run <game_scarlett_master.exe> --execute`
3. Let the intro play. Shortly after the cutscene the device is removed.

Without the loop limit it hung earlier (after 11 lists, no breadcrumbs). With it, the intro cutscene finishes before the hang.

## DRED results (from `crashes.log`, trimmed)

Three runs. Each stops inside a run of mesh draws between barriers:

In every hanging draw, the user-data heap indices resolve to slots shown as `null`:

```

f0c7efd2aceb2aaa: u8=0xa12100 [heap 329992: null] u9=0xcdff00 [heap 421880: null] u12=0x0 [heap 0: Shader(...)]
```

A single crash record references 130–160 `null` heap slots. The heap is null-filled at creation (`fill_null`), so these slots hold a generic null view. If the mesh shaders expect another view type (typed texture vs. buffer, or a UAV) there, that mismatch could be what NVIDIA hangs on and AMD tolerates. Or the title writes these slots in a way VIctory doesn't track yet. I can rerun with `VICTORY_D3D12_DEBUG=1` / `VICTORY_D3D12_GBV=1` if that helps.

## GPU test results on the RTX 5070 Ti

In case NVIDIA hasn't been covered yet: I ran `victory-shader`'s unit tests on this card (debug build, Agility SDK 1.620.2 loaded into the test binary through the `D3D12SDKVersion` / `D3D12SDKPath` exports).

```
test result: ok. 120 passed; 0 failed; 1 ignored (bitcode::tests::bench_write, benchmark)
```

- `emit::valu_tests`: 13 GPU tests passed on both the hardware adapter and WARP. None was skipped.
- `emit::waterfall_tests`: 5 passed, including both GPU waterfall tests (`lanes_sample_their_own_texture_in_a_waterfall_narrowed_by_v_cmpx`, `lanes_sample_the_entry_their_offset_names_in_the_console_waterfall`).
- `emit::diff_tests`: 4 passed. None printed "no SM 6.6 device; skipped".

So translated VALU semantics, per-lane waterfalls and the diff tests behave on NVIDIA as they do on AMD. That makes the hang above more likely to be in descriptors or the mesh pipeline than in the instruction translation. Without the Agility runtime, the same tests fail on Windows 10 with "neither hardware nor WARP SM 6.6 device available".

## Related: Windows 10 needs the Agility SDK for SM 6.6

The README lists Windows 10 as supported, but the in-box Windows 10 runtime (19041) has no shader model 6.6. Without it:

- Every host root signature is refused: `root signature: Unsupported bit-flag set (root signature flags c01)` → `host root signature refused (0x80070057)`. Frames report `drawn=0`.
- The title then crashes deterministically during init: null read at `victory-image+0xb5a5f8` (`read 0x68`), in two job threads at once. It reads an entry from a registry at `[0x148981EF0]+0xC78` that was never filled.
- The SM 6.6 GPU tests in `victory-shader` fail ("neither hardware nor WARP SM 6.6 device available") even though the GPU supports SM 6.6.

Exporting `D3D12SDKVersion` / `D3D12SDKPath` from `victory.exe`, with `D3D12Core.dll` in a `D3D12\` folder next to it, fixes all of this. The startup crash goes away and the intro renders. It would help if VIctory failed early with a clear message when the host lacks SM 6.6, instead of failing later in the title.

## Other things noticed

- **Unimplemented device slots `0x218` and `0x1c8`** are called during init (callers `+0x24800db` and `+0x247757e`). Both take `(desc, riid, ppv)`, and the riid is `ID3D12PipelineState` (`765a30f3-f624-4c6f-a828-ace948622445`). So they're console pipeline-creation variants, and the title receives null pipelines from them.
- **`rpcrt4.dll`** is refused by the host policy during init (`a host DLL outside the host policy: refused`).
- **`crash::tests::unwinds_like_the_system_walk`** fails about 12 of 15 times on Windows 10. `RtlCaptureStackBackTrace` returns 0 frames once the test's `CONTEXT` is wrapped in `Aligned16`. With the previous unaligned `CONTEXT` it passed 15 of 15 on the same machine.
- **CPU load**: on a 6-core/12-thread CPU the title plus translation workers keep every core at 100%.

### Comment 1 — @MichaelSmithAI — 2026-11-24T16:37:56Z

The mesh hashes and breadcrumb positions give us specific draws to compare. One caveat when reading the 130–160 null annotations is that `op_text` looks up each user-data word in the heap. For a table it inspects the guest table base. A shader can use an offset within that table, and preparation can bind a freshly copied host table. Literal values also get heap annotations. A null annotation alone therefore leaves the descriptor accessed by the shader unknown.

For the loop-limit comparison, keeping the skipped-pipeline setting identical would help distinguish the two effects. Runs 2 and 3 excluded `45c922763602b723`. If lowering only the loop cap changes how far a matching run gets, that establishes sensitivity to the cap. Identifying a null read would still need the shader register and the materialized descriptor for the draw at that breadcrumb.

[User-data formatter and table preparation on the reported revision](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs)

### Comment 5 — @volvovida1990 — 2026-11-24T16:59:12Z

@pickles976 Answers for this host (RTX 5070 Ti, Windows 10 + Agility SDK 1.620.2, `ffe310e` diag build):

1. **Wave mode:** VIctory on `ffe310e` doesn't log the wave size it picks. From the translator (`emit/lower.rs`), only compute shaders with console-lane operations (ds_swizzle/permute/mbcnt/readlane/DPP, or lane masks read as data) get a `WaveSize` pinned to the console's 32/64. Mesh and pixel shaders get none, so on this GPU they run in NVIDIA's 32-lane waves. That includes all four hung mesh shaders (`45c922763602b723`, `857b2e13c9cc107f`, `f0c7efd2aceb2aaa`, `ae9ee9074f2e971f`). I haven't checked whether their console code is wave64.
