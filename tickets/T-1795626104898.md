### Comment 1 — @MichaelSmithAI — 2026-11-24T12:53:44Z

There is a command-order case worth checking at `c47632f`. The guest list handler saves and forwards `OMSetDepthBounds(min, max)`. On the next bind of a depth-bounds-enabled pipeline, `State::bind` replaces that saved range with `p.depth_bounds` and sends the replacement to the host. The setter test checks the list immediately after the call, so it misses the overwrite at draw time.

On PC the pipeline description ends with the enable flag, and the command list supplies the range. The guest stream parser reads floats at offsets 52 and 56 from the kind-21 payload. A title trace would help establish whether those bytes carry bounds on Xbox and, if so, when they take precedence over an explicit list command. [Pipeline layout](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_depth_stencil_desc1) · [Dynamic range](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist1-omsetdepthbounds)

A focused readback would clear depth to 0.5, set list bounds to [0.7, 0.9], then draw with a bounds-enabled pipeline. Under the PC semantics the clear color should survive. #158 already replays the list's range at bind time and has draw and mesh readbacks on native hardware. This finding on #849 is from source review. [PR #158](https://github.com/Marvisak/VIctory/pull/158)


### Comment 2 — @Xvania7 — 2026-11-24T13:00:36Z

Good catch, @MichaelSmithAI. You're completely right on the command-order issue.

In D3D12, `OMSetDepthBounds` is dynamic command list state, whereas the pipeline state stream only controls the enable flag (`DepthBoundsTestEnable`). Overwriting `self.depth_bounds` inside `State::bind` from `p.depth_bounds` clobbers whatever dynamic range the guest command list explicitly configured prior to binding the pipeline.

The proper fix here is:
1. Decouple the pipeline enable toggle from the dynamic range: the PSO stream only needs `DepthBoundsTestEnable` (in `D3D12_DEPTH_STENCIL_DESC1`).
2. Treat `self.depth_bounds` on `State` as the authoritative dynamic command list state, mutated exclusively when the guest invokes `OMSetDepthBounds`.
3. In `State::bind`, never overwrite `self.depth_bounds` with static PSO values. When binding a bounds-enabled PSO, the host list should simply use the currently active dynamic range from `self.depth_bounds`.

Also, thanks for pointing out PR #158. Since #158 already implements this dynamic replay and includes native hardware draw/mesh readbacks, it makes total sense to consolidate efforts there instead of carrying a duplicate implementation. Appreciate the sharp code review!
