## Original body

This fix addresses the root cause of black cutscenes and missing post-process image rendering identified in #850.

### Root Cause
On console, the title creates shader resource views (SRVs) directly using typeless formats (e.g. `DXGI_FORMAT_R8G8B8A8_TYPELESS` / format `27` on MRT render targets) where the texture unit interprets the underlying data. On PC D3D12, `ID3D12Device::CreateShaderResourceView` and `CreateUnorderedAccessView` return `E_INVALIDARG` if the view description specifies a `_TYPELESS` format.

In `crates/victory-gpu/src/descriptor/host.rs`, `fits()` checked family compatibility but left typeless view formats untouched when the underlying resource was also typeless. As a result, the host view creation failed silently, leaving null descriptors and producing black frames during cutscenes and post-processing.

### Changes
1. **Format resolution (`crates/victory-gpu/src/resource.rs`)**:
   - Added `is_typeless(format: u32) -> bool` to reliably detect root typeless formats across all DXGI families.
   - Added `first_concrete(format: u32) -> u32` to map typeless formats to their primary typed view format (`R8G8B8A8_TYPELESS` -> `R8G8B8A8_UNORM`, `B8G8R8A8_TYPELESS` -> `B8G8R8A8_UNORM`, `R32_TYPELESS` -> `R32_FLOAT`, etc.).
2. **View adaptation (`crates/victory-gpu/src/descriptor/host.rs`)**:
   - Added `adapt_view_format()` to remap typeless and unknown view requests on typeless resources to the concrete format before dispatching to D3D12.
3. **Unit tests**:
   - Added tests covering typeless-on-typeless remapping, typed-on-typeless preservation, and UAV linear conversion.

### Comment 17 — @Xvania7 — 2026-11-24T18:40:26Z

@luisaugustz That explains the flat 2560x1440 RGBA16F buffer completely.

The dropped compute pipelines you observed are the RT resolution passes (`CS_RaytracingResolve` variants for direct/indirect lighting) and directional shadow passes (`rtdirectionalshadows`), which hit `image_bvh_intersect_ray` (opcode `0x0e6`) and `image_bvh64_intersect_ray` (opcode `0x0e7`). Since `crates/victory-shader` had no lowering path for BVH intersection opcodes, the translation bailed with `ShaderError::Unsupported`, dropping all 40 compute pipelines and leaving the HDR accumulation buffer unwritten.

I have implemented an emulation pass for `image_bvh_intersect_ray` / `image_bvh64_intersect_ray` on branch [`feat/bvh-raytracing-fallback`](https://github.com/Xvania7/VIctory/tree/feat/bvh-raytracing-fallback):
1. **Fallback as Miss**: Zeroes out the 4-dword intersection result vector (`vdata`). On RDNA2, zero child hit mask terminates the BVH traversal loop as a clean miss.
   - For shadows: ray misses occluders -> surfaces are treated as lit.
   - For RTGI / reflections: ray misses geometry -> shader falls back to probe / skybox radiance.
2. **Descriptor mapping**: BVH descriptors are mapped as raw byte buffers so dimension queries succeed without image layout mismatches.

This allows all dropped compute programs to compile and execute their shading loops, populating the 2560x1440 HDR buffer before TAA and FSR4.

Could you test branch `feat/bvh-raytracing-fallback` on your RX 9070 XT setup to verify if the accumulation target now receives lit pixels?
