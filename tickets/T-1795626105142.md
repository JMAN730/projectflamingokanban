Follow-up to #579. This is about the code as of its head 4a6e696c, and it only applies once that PR or something like it is in.

## What

With #579, which levels of a streamed 2D texture get uploaded is chosen from the placed view (`placed_first_mip`: the view's `MostDetailedMip`). When the title's memory is only partly committed, `Staging::refresh_now` uses `committed_prefix` to find the first level whose bytes are all there. It uploads from that level and clears the levels that are not there.

I can't find anything that narrows the **host view** to match. So if a view's `MostDetailedMip` is finer than the first committed level, the view still includes the cleared levels. A sample whose level of detail lands on one of them would read zeros, not the nearest level that has arrived.

## Evidence and limits

This is from reading the code. **I have not observed it in a run**, and I don't know how often a title creates a view that is finer than what is committed (for example, if it relies on a LOD clamp while the texture streams in). `ResourceMinLODClamp` already limits sampling where the title sets it to cover this.

One possible fix, if it does happen: when making the SRV, move `MostDetailedMip` to the first resident level (reducing `MipLevels` by the same amount), and remake the view when more levels arrive. I wrote that against an older tree without #579. It conflicts with #579's changes in `texture.rs`, so I'm not opening a PR yet. I can port it once #579 has landed, if it's wanted.

Not tested on NVIDIA hardware. Nothing in this path depends on the vendor. Written with AI assistance.
