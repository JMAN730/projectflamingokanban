## Original body

**Symptom.** With a wireless receiver plugged in and its pad switched off, the keyboard never reaches the title. `XInputGetState` answers for the dead pad, so `host::pad()` returns `Some(PadState::default())`, `State::poll` sets `any_pad = true`, and the keyboard's stand-in pad is never connected. `host::keys()` still reads the keyboard while our window has focus, but the stand-in is the only device that carries those keys, so nothing arrives.

**Measured** on Windows 11 26300, RX 9070 XT, main `ffe310e`, diag build:

```
slot 0 -> CONNECTED buttons=0x0000      (wireless receiver, pad off)
slot 1 -> not connected (err 1167)
slot 2 -> not connected (err 1167)
slot 3 -> not connected (err 1167)
```

- Real key events (`keybd_event`, ENTER/X/Y) with the title in true foreground (ALT unlock, then ESC to dismiss the system menu ALT opens, `GetForegroundWindow()` confirmed equal to the title's hwnd): account picker and wizard do not react.
- `VICTORY_KEYS=…:Enter,…` in the diag build fires on schedule and produces no visible change either.
- Turning the pad on, or unplugging the receiver, makes input work immediately.

**Rule proposed** (branch below): a host slot is a pad once it has reported anything other than rest, and stays a pad after that. A slot that has only ever reported rest is not one.

- A dead pad behind a receiver: never becomes a pad, stand-in connects, keyboard works.
- A pad that is played with: appears on the first press, and does not connect/disconnect on every button release.
- A pad that starts idle: invisible until its first press, which is the same press the title would act on.

**Fix on a fork**

Branch: [`Numbers-iwnl/VIctory@fix/idle-receiver-keyboard`](https://github.com/Numbers-iwnl/VIctory/tree/fix/idle-receiver-keyboard), commit [`517f277`](https://github.com/Numbers-iwnl/VIctory/commit/517f2775796f7e797c209fd74db6951b9f6b7634), based on `origin/main` `ffe310e`. One file, `crates/victory-hle/src/modules/gameinput.rs`:

- `State::seen_input: [bool; PADS]`, set when a slot reports non-rest input.
- `State::poll` filters each slot through it before computing `any_pad` and before `update()`.
- New test `modules::gameinput::tests::a_receiver_with_a_switched_off_pad_does_not_hide_the_keyboard_stand_in`: an all-zero slot leaves the stand-in connected and reports `DEVICE_DISCONNECTED` for the slot; the first press connects the pad and disconnects the stand-in; a pad back at rest stays connected with no further callbacks.
- `unregistering_waits_for_a_running_callback` seeded an all-zero pad and waited for its connect callback, which the new rule no longer sends; it presses a button now.

**Tests**

- `cargo test -p victory-hle -- --test-threads=4`: 95 passed, 0 failed, 0 ignored.
- `cargo test -p victory-shader --lib`: 120 passed, 0 failed, 1 ignored (unchanged, run for the asset-policy hook).

**Not tested**

- No title run with this change, so the end-to-end case (dead receiver, keyboard drives the first-boot screens) is not demonstrated by a run — the branch is the unit-level evidence only.
- Whether the real XInput slot churns when a pad sleeps mid-run (a pad that has reported input keeps its slot here, so it should not).

### Comment 4 — @Numbers-iwnl — 2026-11-24T13:33:34Z

On the missed-press observation: tested at the poll level, head now `a6884a3`.

`the_first_press_is_still_current_after_the_connect_callback`: the press that makes an idle slot a pad arrives in the same poll as the connect callback, and that reading stays current until the pad reports something else. A title that only starts reading after its callback gets the pressed state on its next read; the release then produces a new reading.

The residual case is narrower than "a title that reads late": a press that starts and ends between two polls is lost, which is true of any poll-level input path and not something this branch can change. No title run either way, so the callback-ordering question stays open until something drives the first-boot screens through it.
