## Original body

### What this is

A second, independent GTA VI Xbox→PC attempt (project *Project Leonida*) ran this repository, built from source at `ffe310e`, against a retail title dump, and classified every shader that failed to translate during world load. Counts, error strings and hashes only — no game bytes, no shader names, no paths.

**Assembled with AI assistance**, then checked line by line against the raw logs. Every number below is reproducible with the commands in the appendix.

The short version:

> **303 translation failures in a three-minute world window. 283 of them (93.4%) are dataflow the translator has not modelled, not instructions it does not implement.**
> The three gaps the README names — 64-bit image atomics, merged geometry stages, the ray-tracing builder — account for **6 of 303 (2.0%)**, and two of the three are zero in this window.

### The failure taxonomy

| **B** | Descriptor tracking | **62** | 20.5% | `a descriptor read only as data` (51), `a descriptor read from the first lane of computed VGPRs` (4), `a descriptor's address or format read as data` (3), `a descriptor neither loaded nor built` (2), `a descriptor partly joined by control flow` (1), `a descriptor chosen by control flow` (1) |
| **C** | Address / root-parameter tracking | **49** | 16.2% | `an address in an SGPR that is no root parameter` (31), `an address not from a root parameter` (16), `an address from a phi` (2) |
| **D** | Structured buffer / scalar memory | **45** | 14.9% | `a structured buffer of unknown stride` (27), `a scalar memory read as data` (18) |
| **E** | Instruction not implemented | **12** | 4.0% | `image_gather4_l` (7), `image_sample_d_cl` (3), `an LDS write of bytes or halves` (2) |

### The world frame draws more than it drops, but it drops a lot

| Metric | run 2 | run 3 |
|---|---:|---:|
| Draws per frame, peak | 1,976 | **3,919** |
| Dropped per frame, peak | **3,587** | 2,966 |
| Dropped per frame, range over world frames | **352 – 3,587** | 1,219 – 2,966 |
| of which indirect, range | 0 – 3,549 | 0 – 3,175 |
| Dropped in the menu segment | **0** | **0** |
| Frame time, worst | 11,689.7 ms | 9,315.2 ms |

The log line is `N draws/frame, dropped M without a host pipeline (K being made) and I indirect`. Note the range lower bounds: the first world frames drop little (draw 5 / drop 25 as the world starts), so the peak figure is not a floor. We have written the full range rather than the peak-loading subset, because the peak-loading subset is the misleading one.

**No GPU hang.** `device removed`, `0x887a0005`, `TDR` and `gpu hang` are **0** in both real-GPU runs. There were 24 (run 2) and 26 (run 3) `slow host submission` events over 250 ms, worst **5,727 ms** — close enough to the default 2 s TDR threshold that the risk you document is real, but it did not fire here.

**Read together with the taxonomy:** the dark world is not a GPU that stopped. It is a frame that issues 900–3,900 draws and simultaneously drops 1,200–3,600 because the pipelines do not exist.

### Title-memory copies during the world segment

Same runs, CPU-side preparation per frame:

| Metric (world segment) | run 2 | run 3 |
|---|---:|---:|
| CPU preparation, worst frame | 626.6 ms | **1,013.4 ms** |
| — of which copies | 489.9 ms | 679.2 ms |
| — bytes copied | 312.6 MB | **435.4 MB** |
| Copies throughput | 1.57 ms/MB | 1.56 ms/MB |

Several hundred MB of copy per frame at ~1.5 ms/MB sits in the same order of magnitude as the GPU time on those frames. Anything that reduces copied bytes hits both sides. We are **not** proposing a design here — `watch.rs` already journals dirty 64 KiB pages with an asking number so overlapping host copies do not re-copy each other's pages, and `shadow.rs`'s `copy_stale` coalesces stale pages into runs before copying. This section is only the numbers.

For comparison, from a different title state in our own project, four independent implementations we compared: a content hash on top of write watching measured **25 MB/frame down to 3 MB/frame** of actual upload on their corpus. That is a different title state and a different corpus, so treat the ratio as an illustration, not a prediction.

---

### What we are not claiming

- Three minutes, one machine, one title build. The proportions will move with run length and content; the method is what transfers, not the constants.
- G, H and I being 0 means *not reached in this window*. A longer run or a different save may reach them. We are reporting what the window contains, not what the title contains.
- We have not verified that fixing A–D is sufficient to light the scene. Given that the frame drops more draws than it issues, our own read is that it is necessary and probably not sufficient.

### Comment 1 — @Ingenioeren — 2026-11-24T18:24:13Z

One way to make the 93.4% figure easier to use for prioritization: on `ffe310e`, `Shader::translated` logs a failed translation once per distinct container in the process. The 303 warnings measure the breadth of shader failures. Their relative frequencies do not weight how often a shader's pipelines drop work. [Container deduplication and translation warning](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/pipeline.rs#L74-L129)

I verified the distinction with a synthetic `victory-gpu` diagnostics unit test against that revision. Two distinct non-translatable containers, with the first requested eight times, emitted two warnings. Feeding the same sequence into the drop counter recorded nine shader-related drops. A separate sample recorded three drops under `being made` without any new translation warnings. One test passed. No title or GPU was involved.

For a second, workload-weighted view, the existing `dropped …/frame without a host pipeline` lines can rank the biggest reasons within logged samples. They report the top 40 reasons for the sampled interval, and a failed pipeline can list multiple shaders on one line. Treat those combined entries as one drop bucket if aggregating them. [Drop reasons](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/pipeline/make.rs#L71-L90) · [Sampling and output](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L1502-L1546)
