## Original body

While comparing hardware and WARP results for #533, a run with `VICTORY_D3D12_WARP=0` still showed `d3d10warp.dll` in the crash stack. Removing the variable was the workaround.

At `d2a4bae`, `crates/victory-gpu/src/host.rs` checks only whether the variable exists with `var_os(...).is_some()`. The adapter-selection proposal in #208 retains that behavior.

I tested a small patch that treats `0` like an unset variable and preserves the documented `1` and existing behavior for other values. Keep the diagnostics feature gate and change the predicate to:

```rust
std::env::var_os("VICTORY_D3D12_WARP").is_some_and(|value| value != "0")
```

On Windows, `cargo test --locked -p victory-gpu --features diagnostics warp_` passed both the setting regression test (unset, `0`, `1`, empty) and the existing adapter test. This addresses adapter selection for diagnostics. The world-rendering crash is tracked in #533.
