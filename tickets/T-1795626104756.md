## Original body

## Setup

- GPU: NVIDIA GeForce RTX 4060 Laptop GPU (Ada, 32-wide subgroups), driver 32.0.16.2124
- CPU: Intel Core i9-12900H, 16 GB RAM
- OS: Windows 11 Pro 64-bit (build 26300)
- VIctory: commit d2a4bae (main), `diag` profile with `--features diagnostics`, `VICTORY_D3D12_DRED=1`
- Title: Xbox Series package 1.0.2.1

## What happens

Boot, menus, intro, start screen and loading all work at 30 fps, as in the README.
The first mission's title card renders. After it, the screen stays black, with sound.

### 1. Compute pipelines refused, draws dropped

114 host pipelines are refused during the session. All are compute, all with the same error:

```
WARN victory_gpu::pipeline::host: host pipeline refused error=The parameter is incorrect. (0x80070057) shaders=[compute 13dfdd3b1136e407]
WARN victory_gpu::pipeline::host: host pipeline refused error=The parameter is incorrect. (0x80070057) shaders=[compute 88994c3496045f51]
WARN victory_gpu::pipeline::host: host pipeline refused error=The parameter is incorrect. (0x80070057) shaders=[compute 02384a60fda6f2d0]
```

A typical frame in the world:

```
0.3 fps, 3403.9 ms/frame (2232.0 preparing: copies 751.7 ms 99.2 MB, textures 844.6 ms 185.7 MB; 833.2 on the GPU; 304.0 copying back 2.0 MB), 601 draws/frame, dropped 690 without a host pipeline (127 being made) and 916 indirect
```

My guess, not verified: these are the wave64 compute programs the README mentions, which an NVIDIA
device cannot create.

### 2. Device removed on the default 2 s TDR

With the default Windows TDR, the device is removed shortly after entering the world:

```
slow host submission ms=5773 lists=32
ERROR victory_gpu::host: host GPU device removed after a submission of 32 lists; breadcrumbs (done/count, list) [all complete ...]
```

Without `VICTORY_D3D12_DRED`, the same failure is reported as `no breadcrumbs (... 0x887A0004)`, which
looks like an unsupported feature but is only the missing DRED data.

Setting `TdrDelay=60` and `TdrDdiDelay=60` (HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers)
stops this crash. It might be worth a line in the README for slower GPUs.

### 3. GPU fault after ~2 minutes in the world (with TDR raised)

The last submission took only 519 ms, so this is not a timeout:

```
slow host submission ms=519 lists=32
ERROR victory_gpu::host: host GPU device removed after a submission of 32 lists; breadcrumbs (done/count, list) ["2/2 None", "2/2 None", ...]
```

The Windows System log shows `nvlddmkm` event 13 (graphics exception) at the same second, then event 153 (reset).

## Possibly related

AnyPS5 handled wave64 programs on 32-lane NVIDIA hosts by narrowing them to 32 lanes or running them on
the mesh path: https://github.com/boykopovar/AnyPS5/issues/2783

I can run more diagnostics builds or capture more logs on this GPU if that helps.

## 3. Why, and what would fix it

XCL's `docs/wave64-on-wave32.md` states the constraint that matters here:

> **One console wave per group** (≤ 64 threads …): `GroupMemoryBarrierWithGroupSync` …
> Portable and cheap. **Several console waves per group** (mesh: 128 threads, compute > 64
> threads): a group barrier would also wait for the *other* console waves, whose control flow
> may differ.

#189 uses `barrier(1 | 8)` in all four exchange sites (`exchange_two_halves`, `exchange_64`,
`emulated_readfirstlane`, the lowest-active-lane `atomicMin`) regardless of group size. Our
world's dispatches are 1024–4096 threads, i.e. 16–64 console waves per group. A group barrier
then waits for waves that may be at a different point of the program — a deadlock with no page
fault, which is exactly the signature above.

The shape of the fix, per that document, for groups with more than one console wave: fence
without sync, an arrival counter per (virtual wave, half) in LDS, a **bounded** wait that gives
up into half-local values instead of hanging, and double-buffered slots by the parity of the
exchange number. Until that lands, #578's refusal is the safe default, and it is what keeps
this machine from removing the device.

I implemented the third piece first (console thread ids claimed from a group-wide counter
instead of `waveReadLaneFirst(flat) & !31 + lane`, which XCL documents as wrong on NVIDIA for
3-D groups) and it is not the hang: with the claim in place the 10 `Emulate` GPU tests in
`wave64_tests.rs` fail on output comparison, because the permutation changes which host thread
produces which index. It needs to land together with the exchange, not before it.

## 4. One correction for anyone following the loop-limit trail

Shader `8bbcbda6008eaa37` (compute, ray-march, 21 samplers) was taking 805–1206 ms per indirect
dispatch. Its loop is **not** mistranslated: the emitted DXIL carries the console's own
`icmp sgt i32 %i, 9999` cap, and the select chain can only turn the continue mask from true to
false, so the loop is guaranteed to leave by the cap. `VICTORY_SHADER_LOOP_LIMIT=64` makes it
look 150× faster by truncating legitimate work. When the scene upstream is correct (the
emulation builds the data those passes need), the march converges early and the cost goes away
on its own.
