## Original body

### What happens

The title boots, opens its archives (dstorage), creates the offline user, and starts presenting – then crashes **in Game Init, with no input**, ~0.5 s after `XUserAddAsync`. Nothing is drawn on this machine (`draws=96 drawn=0`, see the SM 6.5 note below). The game's own WER crash log says `Game State: Game Init`, `Frame: 0`.

**The crash signature is byte-for-byte identical to one reproduced under XCL** (a separate, independent Xbox→Windows layer), filed there as [ivall/xcl#598](https://github.com/ivall/xcl/issues/598). Two different loaders/HLEs/recompilers faulting at the same instruction with the same registers points at the title's own offline-account/auth init path rather than either project's setup.

### Separate machine limitation: SM 6.5, nothing drawn

This PC's inbox D3D12 reports **SM 6.5** (probed via `D3D12CreateDevice` + `CheckFeatureSupport(D3D12_FEATURE_SHADER_MODEL)` requesting 6.6 → returns 6.5). VIctory emits SM 6.6 DXIL and has no Agility SDK loading (unlike XCL, which activates an app-local `D3D12Core.dll` through `ID3D12SDKConfiguration1` – verified working on this same build of Windows). Hence `drawn=0`. The README's results were on Windows 11; on Windows 10 an Agility SDK path (or a 6.5 fallback for the non-mesh stages) would be needed to render anything. This is listed separately because it is not the crash: XCL rendered fine and still hit the identical init fault.

### Question

The README's status (boot, first-boot screens, start screen, profile and saves working) was measured on Windows 11 + RX 6700 XT, also offline by design. What differs there that lets the title past this init path – timing, or something the XUser/profile HLE answers differently? The identical fault under two independent layers suggests the title reads an object during offline account/auth init that neither platform supplies yet.

### Comment 1 — @DaviTostes — 2026-11-24T02:33:51Z

The XCL log in ivall/xcl#598 shows the same fault right after its Rockstar token requests are refused (`0x80072EFD`), and VIctory's HLE does the same thing by design:

- `crates/victory-hle/src/modules/xuser.rs:211-228` — `token_async` logs `token and signature: offline` and completes the block with **`FAILED_TO_GET_TOKEN`** for every request, including `CreateTicketXbl3` and the `ros.rockstargames.com` one.
- The crash follows that completion on both layers and at the same title offset (`+0xb5a5f8`, read at `0x68`, `rax=0`), so the title's auth path is dereferencing something it only fills in when the token call succeeds.

Two cheap experiments that could confirm it, without touching the online path:

1. **Return a dummy success** from `token_async`: `S_OK` with an empty but non-null token/signature buffer (and a matching size). The title would then try the network request, fail at connect, and hopefully take its normal "no connection" branch instead of the null read. This does not contact Xbox Live or Rockstar by itself; the sandbox/no-network rule still applies.
2. **`maximum users` is a `missing` stub** (`xuser.rs:272`, slot 0x30, `E_NOTIMPL`). If the title calls it during the same auth init, it gets an error and no output value. It should be one line: write `1` and return `S_OK`.

I cannot test either without the title (no copy here), but the blame is narrow enough that a build with (1) and (2) would tell us quickly whether the fault is the failed token or something else in that path. If you can run such a build, I can prepare the diff.

No game data used.

## Corrections to the record

1. **Not the offline auth path.** I implemented the dummy-success token experiment proposed above (opt-in `VICTORY_XBOX_LIVE_TOKENS`, a well-formed `XBL3.0` token + base64 XSTS v1 signature, relocated result pointers, `*data` set): the crash was unchanged – and the trace showed VIctory faults **before any token API is called** (~0.5 s after `XUserAddAsync`, no `token_async` invocation at all). The `FAILED_TO_GET_TOKEN` completion is real but not this crash's cause, consistent with @GamingRipperDoc's runs.
2. **My "renderer-independent" claim was wrong.** On Windows 10, WARP goes through the same in-box SM 6.5 runtime and shows the same `c01` refusals – the WARP run did not separate the renderer from the runtime, as @GamingRipperDoc pointed out.
3. A third hypothesis (unmapped console `D:` drive, `D:\decorations\presets\*` enumeration failing with `ERROR_PATH_NOT_FOUND` = 3 = `rbx`) was also disproven: creating the folders left the crash identical.
4. **Mechanism**, consistent with the guess above: with the SM 6.5 runtime every translated pipeline's root signature is refused, the title keeps null objects and later reads a field of one (`rcx=0`, read `+0x68`). Disassembly of the faulting leaf (`title+0xb5a5d8`): `mov rax,[rcx]; … mov r14,[rax+0x68]` – it dereferences the first field of the object it is handed; one caller fetches that pointer from a table. With the Agility runtime the objects exist and the read is valid.
5. **XCL nuance:** XCL crashed at the same RVA *with* its Agility SDK active (SM 6.6 verified), so ivall/xcl#598 stands for XCL – its root-signature serialization path still refuses the `0x400`/`0x800` flags and it has a separate null-object gap (`DeserializePipelineStateX` writes null + `E_NOTIMPL`, and the title's wrapper swallows the failure). Same leaf, different trigger; tracked there.

The local experiments (placeholder tokens, a `VICTORY_DUMP_PSO_CACHE` diagnostic) stay on a local branch; they are not part of this conclusion. The deserialize gap is real but non-fatal once the runtime accepts the root signatures – worth its own issue if it bites later.

Thanks @GamingRipperDoc for the six-run comparison and @DaviTostes for the narrow blame – the token experiments were still useful to rule the path out.
