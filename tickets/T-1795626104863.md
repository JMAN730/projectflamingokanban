## Original body

**Mesh shaders hang the GPU until TDR on NVIDIA (RTX 2060) – DRED shows null u9/u10 descriptors**

Commit: ffe310e (main), diag build. GPU: NVIDIA GeForce RTX 2060 (wave32), Windows 11, 16 GB RAM.
TdrDelay raised to 60 s, `VICTORY_SHADER_LOOP_LIMIT=256`, `VICTORY_D3D12_DRED=1`.

The world loads and runs at ~0.5–2 fps (HUD/minimap visible), then a single submission
never finishes and the device is removed. The hang always lasts exactly the TDR delay
(2 s → ~20 s submissions earlier, 60 s → 63 s), so it is infinite, not slow. Lowering
the loop limit from the default to 4096 and 256 does not change it.

DRED stops in a mesh draw every time, a different mesh shader each run:

| mesh | pixel | DRED stop | user data |
|---|---|---|---|
| 857b2e13c9cc107f | 63051e97862e7dad | cmd 433/604, op 42 | u8, u9, u10 null |
| db4835a364449a45 | c10e7d95d8266d2a | cmd 133/205, indirect kind 10 | u8, u9, u10 null |
| 021f72334f3cabe7 | – | cmd 11/24, op 42 | u12 = heap 0 |
| e04ae5b1486d5e77 | 18d9739d319d1110 | cmd 3758/3932, indirect kind 10 | u8 null |
| 38ad582f523fd7cf | d42a2d8a9d2c954a | cmd 198/1118, op 42 | u8, u9, u10 null |

Skipping one with `VICTORY_SKIP_PIPELINES` only moves the hang to the next one.

Guess: a lane that hits the loop limit returns early (`abort_block` → `Ret`) while the
rest of the mesh group waits at a barrier, which deadlocks on hardware that does not
count exited lanes. Mesh programs keep the console's wave64 layout, which wave32
hardware cannot declare. Full DRED dumps in the attached crashes.log.

Also needed on this setup: the title's hang watchdog (fn at title+0x2215a60) kills it
when world frames stall the main loop for ~30 s; I nop'd its three branches to the kill.

This matches what I took apart on an RTX 2080 in #71. Two other Turing cards (RTX 2070 SUPER, RTX 2080) and an RTX 4080 now stay up in the world on the same three open PRs on top of main:

- **#493** (its commit `c48b240`, root SRVs as bounded one-view tables): this fixed the mesh hang at **`857b2e13c9cc107f`**, the first row of your table.
- **#206** (an off-element structured view becomes a raw view): this fixed the load-path mesh hang at `04b9be37…`.
- **#189** (wave64 compute on 32-lane hosts): this fixed the compute-dispatch hang that shows up once the mesh ones are gone.

With all three merged, the 2080 ran 3 of 3 seven-minute runs and one 21-minute run with no device removal. That held at the default loop limit too. `VICTORY_SHADER_LOOP_LIMIT=32` makes frames about 40% faster. The ablation, with what each PR fixes, is in https://github.com/Marvisak/VIctory/issues/71#issuecomment-7123718229. In my runs, skipping a pipeline also just moved the hang, as you saw. The cause was the descriptors (your null `u8`–`u10`), not one program.

Two more things that helped on the same card:
- **#747:** with the capped NVIDIA view heap, `MIN_DYNAMIC = 1 << 18` stops the "no dynamic slots" drops. On the 2080 it took the world from ~430 to ~2,400 draws per frame and put the first real geometry into the colour G-buffer.
- **#790:** if the title stops at an assertion right after window creation (more likely with a big pipeline cache or the debug layer), that's the 32-bit memory window running out.
