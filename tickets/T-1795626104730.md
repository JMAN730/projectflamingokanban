## Original body

## Bug report

### Description

VIctory crashes during initial system initialization due to an illegal CPU instruction (`CLWB`).

The host CPU supports AVX2 but does not support the `CLWB` instruction.

### Error details

```text
Exception code: 0xc000001d (ILLEGAL_INSTRUCTION)
Faulting instruction: clwb [r9]
Module: victory-image-b99f876b74d4a77f.dll
Offset: 0x4ecc84a
```

### Steps to reproduce

1. Build VIctory successfully.
2. Configure the game directory.
3. Run the title using `victory.exe run --execute`.
4. The executable and its dependencies are mapped successfully.
5. During system initialization, VIctory crashes with exception `0xc000001d`.

### Expected behavior

VIctory should detect whether the host CPU supports `CLWB` before executing it and provide a compatible fallback when the instruction is unavailable.

### Actual behavior

An unsupported `CLWB` instruction is executed, causing an illegal instruction exception (`0xc000001d`) and terminating the process.

### Additional information

- All imports are successfully bound (0 missing imports).
- The D3D12 host device initializes successfully.
- The crash occurs before the first frame is rendered.
- The crash happens before world loading begins.
- Searching the repository with `git grep -i clwb` does not find a direct reference to this instruction.

### Possible solution

Could a CPU feature check or a fallback implementation be added for systems that support AVX2 but do not support `CLWB`?

Is this an expected hardware limitation, or could it be addressed in VIctory?

### Comment 1 — @DaviTostes — 2026-11-24T01:32:33Z

Current `main` handles this instruction, so the first thing to check is the build.

- `crates/victory-loader/src/crash.rs` emulates `clwb m8` (`66 [rex] 0f ae /6`) in the illegal-instruction handler: `clwb_len` skips a single write-back hint, and `clwb_loop` completes a whole write-back loop in one exception. That came in with **#45**, merged as `7d33c46`.
- If the binary was built before that commit (for example `97c78d1`), rebuild from current `main` (`d2a4bae` as of now) and the `clwb [r9]` at `+0x4ecc84a` should no longer fault.
- If it still does on current `main`, the useful datum is the crash log's refused-instruction bytes plus the exact CPU model. The handler matches by encoding, so a segment prefix or a REX variant it does not expect is what would explain it. **#198** (open) adds those bytes to the crash report, which makes this diagnosable without a debugger.
- AMD Ryzen 7: Zen 1/Zen 2 lack CLWB (Zen 3+ have it), which fits the report; the emulation is the intended path for those CPUs.

Related: #7, #106 and #108 are the same class (CLWB/CLZERO/`rdpru`); #34 (open) extends the handler to `clzero` loops and `rdpru`.

No game data used.
