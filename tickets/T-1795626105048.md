## Original body

## What

The world load of the retail Xbox Series dump dies at `0xc0000005` inside **game code**, and the address is the same when a second, independent layer runs the same dump.

## Hardware / OS

RTX 5060 8 GB (7896 MiB VRAM), Windows 10 19045, 32 GB RAM, i5-14490F.

## Layer 1: this repository (Machad3x tree, 31f4a19)

Hand-merged on top: #902's `mirror()` out-of-bounds degradation and a 2K present fallback whose candidate is locked by index.

| | result |
|---|---|
| menus, settings, legal notices | **fully correct** (Chinese typeset, artwork, 30 fps, 66 draws) |
| world entry | reaches it, 663 draws/frame, 5 fps |
| 2K present | `presenting 2560x1440` fires |
| blinking | **gone** (the eight 1440p candidates no longer alternate) |
| picture | stable dark blue-grey, not lit colour |
| crash | none over several minutes |

## Layer 2: a different compatibility layer, same dump

`16906 draws with translated pipelines (0 skipped), 1024 dispatches (0 skipped)`, audio `429 Opus packets, 0 errors`, then after the intro:

```
Game exited with code 0xc0000005 (3221225477)
thread ...: ntdll < KERNELBASE < game_scarlett_master.exe+0x22511f
           < game_scarlett_master.exe+0x25782e2 < +0x2578607 < **game_scarlett_master.exe+0x2215eca**
```

This repository's own stack shows the same frame:

```
victory-image-*.dll+0x221c29c < victory-image-*.dll+0x2215eca
```

(`victory-image-*.dll` here is the mapped module of the same title image.)

## Reading

Two unrelated implementations of the console stack stop at **the same function in the title**, so this looks title-side rather than a translation gap: the world-load path reaches a call that returns a bad pointer (the first-chance exception reads `0xffffffffffffffff`, i.e. -1) and the title dereferences it.

One observation that may matter: with no Xbox Live the title logs `XUser: token ... no Xbox Live (0x80072EFD)`. The crash sits right where the world finishes loading, which is where social / session / online init would run.

## Ask

Does anyone know what `+0x2215eca` is (is it the online/session or PLS path), and is the -1 return from a missing service something that can be answered with a valid stub instead of a failure? If that is the blocker, it is the last one between "menus" and "gameplay" on this hardware.

So the crash address is now confirmed on **three** independent implementations:

```
Machad3x tree : victory-image-*.dll+0x2215eca
#439 tree     : +0x23cf683 < +0x2215c35 < +0x2215eca
other layer   : +0x22511f < +0x25782e2 < +0x2578607 < +0x2215eca
```

and this time the fault is a **write to 0x0**, previous ones were a read of `0xffffffffffffffff`. Same caller.

## What #439 itself refuses

```
console wave64 lanes in a group of more than 64 threads
on a host without 64-lane waves is not supported
```

Several compute shaders (GPU-driven culling / streaming) hit this and are dropped; 461 `does not translate` lines accumulated, plus `dropped N/frame without a host pipeline` at 12-17 per shader, per frame. Which means the world is built with those compute passes missing, and that lands exactly on the null write above.

## Why I think these two are one problem

`console wave64 lanes in a group of more than 64 threads` is the compute counterpart of what #439 already does for mesh. On a 32-lane host the group must be split and the shared LDS kept coherent across the two halves; without that the pass is refused rather than emulated. The title then loads its world against buffers that were never filled, and dies writing through a pointer that pass was meant to publish.

So the remaining question is not "which layer", it is: **can the console-flow emulation be extended to compute groups above 64 threads on 32-lane hosts?** If yes, this is likely the last blocker before gameplay on NVIDIA hardware.

### Comment 2 — @brunomrtns — 2026-11-24T19:01:13Z

Another data point on the same fault, RTX 3060 12 GB / Windows 11, release build @ ffe310e, retail 1.0.2.1 dump.

Environment notes:

Crash (after several minutes in-world, dark scene, draws being dropped for untranslated shaders):

```
VIctory: unhandled exception 0xc0000005 at victory-image-b99f876b74d4a77f.dll+0x23cf683 (write 0x0: nothing mapped there)
  #0  victory-image-b99f876b74d4a77f.dll+0x23cf683
  #1  victory-image-b99f876b74d4a77f.dll+0x2215c35
  #2  victory-image-b99f876b74d4a77f.dll+0x2215eca
```

Same `+0x2215eca` return address as reported above. I disassembled the fault site: `+0x23cf683` is `mov dword ptr [0], 0x4d8bd421`, reached only when `cmp byte ptr [rsp+0x34], 1` fails — i.e. a deliberate fatal-error write to null, not an accidental dereference. So whatever check feeds `[rsp+0x34]` is the real failure; the crash site itself is just the RAGE fatal handler.

Preceding log is dominated by dropped draws from untranslated compute/mesh shaders (`a select on an untracked mask`, `a descriptor read only as data`, `a 64-bit image atomic`, `a scalar memory read as data`) and one `a draw or dispatch dropped: no dynamic slots for its tables dropped=32768`. If the assert is downstream of missing world buffers, shader coverage may be the trigger — but I can't prove that from here.
