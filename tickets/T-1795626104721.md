## Original body

In `MaskData::Host` (`lower.rs:226-232`) a ballot is taken over the **host** wave, "whatever its size", and the high half of that ballot pair is dropped by the four uses that read a mask as a number. Nothing forces the host wave to be 32 lanes for a pixel or vertex shader: `s.wave_size` is only set on the compute path (`lower.rs:382-386`), so `wave_size` stays `None` and the driver picks the wave size at PSO creation.

If a driver runs one of those shaders 64-wide, the upper 32 lanes are invisible to:

- `s_bcnt1_i32_b32` (`lower.rs:2549-2557`) - `WaveActiveCountBits` over a 64-lane wave counts at most 32.
- `s_ff1_i32_b32` (same block) - a first active lane of 32 or above reports 0.
- `s_cmp_eq_u32` / `s_cmp_lg_u32` (`lower.rs:2322-2353`) - a mask compared against another mask only compares the low halves.
- `v_mbcnt_lo_u32_b32` (`lower.rs:4879-4927`) - `WavePrefixCountBits` over a 64-lane wave stops at 32.

On my machine this does not bite: an AMD Radeon RX 9060 XT (RDNA4) on Windows 11 runs the pixel shaders wave32, so the high half is zero anyway. That is a property of the current driver's default, not of the code, which is why I am reporting it rather than sending a fix.

## What I can show

A unit test on `main` (`4926f72`) that lowers a synthetic wave32 pixel program through `Lower` and inspects the emitted module. The program is hand-written GFX10, no game data:

```
0xBE80_0F7E              // s_bcnt1_i32_b32 s0, exec_lo
0xBE81_137E              // s_ff1_i32_b32 s1, exec_lo
0xD765_0002, 0x0001_007E // v_mbcnt_lo_u32_b32 v2, exec_lo, 0
0xD765_0003, 0x0001_00C1 // v_mbcnt_lo_u32_b32 v3, -1, 0
0x7E00_0200              // v_mov_b32 v0, s0
0x7E02_0201              // v_mov_b32 v1, s1
0xF800_180F, 0x0302_0100 // exp mrt0, v0, v1, v2, v3 done vm
S_ENDPGM
```

After `ir::build(&code, false, 8)` -> `resource::track` -> `io::raise` -> `structure::structure` -> `Lower`, with a `#[cfg(test)]` helper that counts the operands referring to a value:

```
assert_eq!(l.mask_data, MaskData::Host);
assert_eq!(l.s.wave_size, None);
let &(lo, hi) = l.ballots.values().next().unwrap();
assert!(l.s.m.uses_of(hi) >= 3);   // fails on main: uses_of(hi) == 0
```

`cargo test -p victory-shader` gives `61 passed; 1 failed`, and the failure is that last assertion. The low half is used three times as expected.

## The question

Is dropping the high half deliberate, on the grounds that a `MaskData::Host` ballot only has to be exact for the uses the comment lists and the driver's default is 32 lanes? If it is deliberate, the four sites may deserve a comment saying the upper half is unreachable, and I will keep the test out. If it is not, the fix looks small: share the 64-bit `countbits`/`firstbitlow` logic that `s_bcnt1_i32_b64` (`2363-2378`) and `s_ff1_i32_b64` (`2379-2397`) already have, and take both halves of the ballot in those four places.

I have not opened a PR because I could not measure a wrong result on this GPU with only the tools here (no game package, so no title run). The test is ready and I can send it as a draft PR if you want it.

### Comment 1 — @NolanCotter — 2026-11-24T03:10:10Z

Claiming this (renderer-path, no overlapping claim or PR found — #320's console flow covers wave64 compute on wave32 hosts and documents mask reads there; the PS/VS `MaskData::Host` path is untouched).

The defect: for `MaskData::Host` (Ps/Vs — no `WaveSize` attribute, host wave size is driver-chosen), `mask_dword` returns the ballot's first dword for every lane mask read as a number (`s_bcnt1_i32_*`, `s_ff1_i32_*`, `v_mbcnt_*`, `s_cmp_eq/lg_u32/u64`). On a 64-lane host wave the upper 32 lanes are a second console wave whose bits land in the ballot's second dword — they get the first console wave's mask values instead of their own.

Fix plan, all in `crates/victory-shader/src/emit/lower.rs`:
1. `mask_dword`: for `MaskData::Host` on a wave32 program, pick the ballot half by host lane (`lane >= 32 ? y : x`). No-op on 32-lane host waves.
2. `v_mbcnt_lo` in that mode: count bits of the lane's own half below `lane & 31`.
3. `v_mbcnt_hi` in that mode: a wave32 mask has no high half, so the count is `src1`.

Verification: synthetic wave32 pixel-program test in `emit::lower`'s test module (mask from `v_cmp`, read by `s_bcnt1`, exported via `exp`) asserting the emitted DXIL takes the lane index; `cargo test -p victory-shader` on Linux. No game data.

Out of scope: the host-lane-vs-console-lane space for `v_readlane`/`v_writelane` computed lanes — that's the lane-space problem #225/#320 handle in the console flow, not a mask read.
