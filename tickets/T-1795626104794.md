## Original body

I can't open pull requests here (they're limited to collaborators), so here are two small fixes on my fork, one branch each, based on current `main` (787f665). Happy to change anything, or for you to cherry-pick them.

Tested on Windows 10 22H2 with an NVIDIA GPU and a Wooting keyboard.

## 1. Windows 10: `CreateRootSignature` fails with `E_INVALIDARG`

Branch: https://github.com/grindersky/VIctory/tree/feat/agility-sdk-win10 (commit https://github.com/grindersky/VIctory/commit/4aae06c)

The D3D12 runtime built into Windows 10 predates shader model 6.6 and rejects root signatures that index the descriptor heaps directly, even on GPUs that support them, so the title fails at startup.

`victory.exe` now exports `D3D12SDKVersion` (620) and `D3D12SDKPath` (`.\D3D12\`), so the loader uses a newer `D3D12Core.dll` placed in a `D3D12` folder beside the exe (new `apps/victory/src/agility.rs`, plus a `build.rs` adding the linker exports). Without that folder the system runtime is used as before; Windows 11 is unaffected. The DLLs are not added to the repo; the README explains where to get them (Microsoft.Direct3D.D3D12 NuGet, 1.620.x).

Result: the title reaches the start screen and menus on Windows 10.

## 2. No keyboard input when a keyboard also presents an XInput pad

Branch: https://github.com/grindersky/VIctory/tree/fix/keyboard-beside-xinput-pad (commit https://github.com/grindersky/VIctory/commit/d6b8716)

Some keyboards (Wooting) also present an XInput pad that never reports input. Because the keyboard stand-in pad was disconnected while any XInput pad was connected, there was no usable input at the start screen.

The stand-in now stays connected alongside host pads (`crates/victory-hle/src/modules/gameinput.rs`); the README input section and gameinput tests are updated to match. `cargo test -p victory-hle` passes.

Result: Enter works at the start screen.

### Comment 1 — @bittertea0323 — 2026-11-24T09:32:49Z

# Confirmed on Windows 10: the `D3D12SDKPath` + `D3D12SDKVersion` export route clears the root-signature refusals (measured A/B)

Follow-up to #729 and #749. I reproduced grindersky's branch on a second Windows 10 host and
falsified my own alternative in the same session. Numbers only.

## Environment

Windows 10 22H2 UBR 3393 (KB5029331) · RTX 4070 SUPER 12 GB · Ryzen 7 7800X3D · VIctory `main`
@ `8e79c80` + the commit from #729 cherry-picked · Agility `D3D12Core.dll` 1.620.2 in
`release\D3D12\` beside the exe.

## A/B, same host, same title, same minute

**A — explicit `ID3D12SDKConfiguration::SetSDKVersion` at device creation** (my attempt; calling
`D3D12GetInterface(CLSID_D3D12SDKConfiguration)` then `SetSDKVersion(620, path)` right before
`D3D12CreateDevice`):

```
root signature refused: 3
Unsupported bit-flag (c01): 3
host pipeline refused: 3
frames with drawn > 0:   0
```

**B — the two `DATA` exports from #729** (`D3D12SDKVersion = 620`,
`D3D12SDKPath = ".\\D3D12\\\0"`, linked with `/EXPORT:...,DATA`):

```
root signature refused: 0
Unsupported bit-flag (c01): 0
host pipeline refused: 0
frames with drawn > 0:   11
```

## What this means

1. The export route is the one that works; a runtime-side `SetSDKVersion` call before device
   creation did **nothing** on this host (the loader had already bound the in-box core).
2. With it, the 1.1 heap-indexing root signatures (`0xc01`) are accepted, every PSO is created,
   and draws actually reach the GPU on Windows 10 — `drawn=0` becomes nonzero for the first time
   on this machine.
3. The remaining cost is time per frame: frame gaps of 17–34 s during the first two minutes,
   i.e. shader translation dominates. Not a correctness problem, and it should shrink as the
   DXIL cache fills.

## Note for the issue as a whole

The #729 keyboard fix (an XInput-presenting keyboard kept the stand-in pad disconnected) matters
on this host too: the title needs Enter at the start screen and nothing could send it.


### Comment 2 — @danekbiglike — 2026-11-24T10:24:52Z

I ran a before/after check for the keyboard part of this issue on native Windows. I used the existing GameInput fake host to model an idle XInput device in slot 0, then pressed and released Enter on the keyboard. The same test ran against both revisions in separate build directories.

| Revision | Result |
| --- | --- |
| Parent `787f665` | Reading the keyboard’s stand-in gamepad while the idle XInput device was connected returned `DEVICE_DISCONNECTED`. |
| Input fix `d6b8716` | Enter registered as A on the stand-in while slot 0 stayed idle. After release the stand-in returned to neutral, and slot 0 independently reported B and a left-stick X value of 0.5. All eight GameInput tests passed, including the added case. |

This exercises the input API with synthetic device readings. Physical Wooting hardware and the Agility SDK change were outside this check.

<details>
<summary>Regression test for the existing tests module in gameinput.rs</summary>

```rust
#[test]
fn keyboard_press_and_release_beside_xinput_pad() {
    let (hub, host) = fake();
    let slot = 0;
    host.lock().unwrap().pads[slot] = Some(PadState::default());
    host.lock().unwrap().keys = vec![key(0x0D)];
    hub.poll();
    let enter = current(hub, GAMEPAD_KIND, FALLBACK)
        .expect("keyboard stand-in disconnected while XInput is present");
    assert_eq!(pad(enter).buttons, A);
    release(enter);
    let idle = current(hub, GAMEPAD_KIND, slot).unwrap();
    assert_eq!(pad(idle), PadState::default());
    release(idle);

    host.lock().unwrap().keys.clear();
    let controller = PadState { buttons: B, left_x: 0.5, ..Default::default() };
    host.lock().unwrap().pads[slot] = Some(controller);
    hub.poll();
    let released = current(hub, GAMEPAD_KIND, FALLBACK).unwrap();
    assert_eq!(pad(released), PadState::default());
    release(released);
    let held = current(hub, GAMEPAD_KIND, slot).unwrap();
    assert_eq!(pad(held), controller);
    release(held);
}
```

Run `cargo test --locked --lib -p victory-hle gameinput`.
