## Original body

A CPU-side cost that #400's table does not separate: **copies that meet an unmapped page retry in the kernel 64 KiB at a time**, and rediscover the same holes every frame.

**Setup:** NVIDIA RTX 4060 Ti (driver 32.0.16.1656), Ryzen 9 5900X, 64 GB, Windows 11; Xbox Series 1.0.2.1; diag build (`--profile diag --features diagnostics`) of an integration tree at `2b1a569` (about 50 PRs on `main`); `VICTORY_NO_WATCHDOG=1`; `TdrDelay=60` set machine-wide on this box. No game data used.

## What the log says

In the world, one frame:

```
33 129 title copies 16.3 MB; 34 490 refreshes 29 201 MB
moves 29.06 ms; 652.74 MB unmapped; 2 479.5 fallbacks
... copies 120 ms 302 MB
```

`moves` (the timed first attempt) is 29 ms; the copies take 120-275 ms. The difference is the fallback path, and its counter is the only one that scales with `fallbacks`.

## The path

`copy_mapped` reads the range with one `ReadProcessMemory`. If **any** page of it is unmapped, it redoes the whole range in 64 KiB pieces (then 4 KiB inside a piece that fails), one `ReadProcessMemory` per piece, zeros where nothing can be read.

- A 174 MB shadow with a single hole is 2 784 kernel calls for one copy.
- 2 300-2 500 fallbacks a frame re-discover the same holes, so the cost grows with the size of the ranges, not with how much is unmapped.
- The holes are real: `VICTORY_COPY_MODE=plain`, which copies the range blindly, ends the run inside a minute on this machine.

## The change (gist below)

On the fallback, walk the range with `VirtualQuery` and copy what the region says is committed and readable, zeros for the rest - same bytes in the destination as today, but one query per **region** instead of one kernel call per 64 KiB piece. The regions of the big pools are megabytes long, so a 174 MB range is a handful of queries. The same change in `write_mapped` for the copy-back, over writable regions, leaves the rest alone as before.

The comment above `copy_mapped` notes that `VirtualQuery` cost about 2 ms per copy in these pools; that was querying *before every copy*. Here it runs only on the fallback and replaces thousands of calls.

## A/B, one binary, same save

`VICTORY_COPY_FALLBACK=pieces` (diagnostics builds only) keeps the old path, so both arms are the same binary, written save, 120 s after world entry, 10 frames each:

| Fallback | frame (avg) | copies | copies MB | ms/MB | fallbacks |
|---|---:|---:|---:|---:|---:|
| region scan | **910 ms** | **120 ms** | 302 MB | **0.40** | 2 479 |
| 64 KiB pieces | 978 ms | 275 ms | 233 MB | 1.18 | 2 325 |

The region arm also had more content (2 823 draws/frame against 2 400). The win is bounded by what copies cost in the scene: 15 % of the frame here, and the earlier opening-cutscene frames on this machine showed `copies 1 799 ms` of a 4 400 ms frame, where this path is most of it.

**Not tested:** AMD, release builds, `main` itself (the function and its callers are unchanged since `d2a4bae` as far as I can tell, but I only built the tree), and the case where the title unmaps a page between the query and the `memcpy` of its region.

Patch: https://gist.github.com/rocobalt1/1edb3c0dad03f54c05f972b95475b14c

If it is useful, a collaborator is welcome to take it as a PR; I do not have write access here.

Same shape as #776: both costs come from asking the kernel about the same pages again every submission. They are independent (copy bytes vs write-watch askings) and should stack.

*AI-assisted: an agent working with the tester, which built the change and ran the A/B.*

### Comment 1 — @MartinIndra02 — 2026-11-24T10:58:36Z

Clean `main`-based implementation ready on a fork (since PR creation is currently collaborators-only): https://github.com/MartinIndra02/VIctory/tree/perf/gpu-copy-mapped-region-fallback (based on `main` `ffe310e`).

### Two improvements over the gist in the description
1. **Race-safe per-region copy (addresses the unmap-between-query-and-copy caveat):** instead of raw `memcpy` after `VirtualQuery`, each committed region is copied with a single `ReadProcessMemory` / `WriteProcessMemory` call, and only if that call fails (a concurrent unmap/reprotect between `VirtualQuery` and the copy) does it fall back to the existing 64 KiB → 4 KiB `for_pieces` loop on that region. Unmapped / `PAGE_NOACCESS` / `PAGE_GUARD` regions are still zeroed in one `write_bytes(0, n)` (or skipped in `write_mapped`).
2. **Reuse the initial partial copy (`done`):** when the initial `ReadProcessMemory` / `WriteProcessMemory` hits the first unmapped page (`ERROR_PARTIAL_COPY`), Windows already copied `lpNumberOfBytesRead` (`done`) bytes before the hole. Starting `for_regions` at `start + done` avoids re-copying the committed prefix a second time.

### Verification
Windows 11 Pro 26200, Ryzen 7 5800X3D, NVIDIA GeForce RTX 3080 (`621.24`), Rust 1.98.1 (`x86_64-pc-windows-msvc`):
- New unit test `host::batch::copy_mapped_and_write_mapped_handle_holes_across_regions`: 2 MiB reserved range with two 512 KiB committed regions and two 512 KiB unmapped holes — verifies `copy_mapped` copies committed regions and zeroes holes, and `write_mapped` writes committed regions while skipping holes.
- New release microbenchmark (`cargo test --release -p victory-gpu --lib -- --ignored --nocapture copy_mapped_hole_benchmark`, 16 runs each):
  - `64 MiB (4 KiB hole at 32 MiB)`: `136.35 ms` → **`81.03 ms`** (**1.68×**)
  - `64 MiB (32 MiB hole at 16 MiB)`: `608.11 ms` → **`49.82 ms`** (**12.21×**)
- `cargo test -p victory-gpu --lib -- --test-threads=1`: **51 passed, 0 failed, 2 ignored**
- `cargo clippy -p victory-gpu --all-targets -- -D warnings` (default and `--features diagnostics`): **0 warnings**
- `cargo xtask policy`: **154 files ok**
