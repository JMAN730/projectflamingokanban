## Original body

### What's wrong

A windowed boot asks the host for two 2560×1440 textures and never gets them. Both `CreateCommittedResource` calls fail with `E_INVALIDARG`, in both of my 900-second runs, at the same two descriptions:

```
WARN victory_gpu::resource: no host texture error=The parameter is incorrect. (0x80070057)
  desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, depth_or_array_size: 1,
  mip_levels: 1, format: 86, sample_count: 1, sample_quality: 0, layout: 0, flags: 5 }
WARN victory_gpu::resource: no host texture error=The parameter is incorrect. (0x80070057)
  desc=ResourceDesc { dimension: 3, width: 2560, height: 1440, depth_or_array_size: 1,
  mip_levels: 1, format: 115, sample_count: 1, sample_quality: 0, layout: 0, flags: 1 }
```

Format 86 is `DXGI_FORMAT_B5G5R5A1_UNORM`, 115 is `DXGI_FORMAT_B4G4R4A4_UNORM`; flags 5 is render-target and unordered-access, flags 1 is render-target. 2560×1440 is the title's internal render size, and both appear **6 and 11 seconds into a run that presents**, right after `presenting to a window width=3840 height=2160` — never in a run that cannot present (mine could not, today). A texture with no host copy cannot be an RTV, an SRV or a UAV, so every draw that names one is lost, and nothing in the log says *which* argument the host refused.

### What the host actually accepts

An ignored GPU test asks for exactly those descriptions on the hardware adapter (`cargo test --release -p victory-gpu -- --ignored --nocapture packed_formats`). Three findings:

- **The descriptions themselves are legal.** Formats 86 and 115 are accepted with every flag combination tried (0, `ALLOW_RENDER_TARGET` 1, `ALLOW_UNORDERED_ACCESS` 4, both 5, and the neighbours 87 and 28 too). Only `ALLOW_RENDER_TARGET | ALLOW_DEPTH_STENCIL` (3) is refused, as documented.
- **A colour clear value must name the resource's own format**: format 86 with a clear naming 86 works, naming 0 or 28 gives `E_INVALIDARG`.
- **A depth clear value must name the pair's *other* format, and the rule is inverted from the colour one**: a resource made as `D32_FLOAT_S8X24_UINT` (19) is **refused** with a clear naming 19 and **accepted** with a clear naming `R32_FLOAT_X8X24_TYPELESS` (20); `R16_TYPELESS` (53) is accepted with a clear naming `D16_UNORM` (55) and refused with 53. Victory passes the title's clear through untouched, which is exactly what the host wants here: those depth textures have always been created, and a first version of this patch that dropped every clear whose format differed from the resource's silently dropped 358 legitimate depth clears in a 60-second boot. That version is not what is below.
- **Some initial states are refused**: for format 86 with flags 5, states `0xC` (render target and unordered access together), `0x1`, `0x2` and `0x200` (buffer-only states) fail, while `0x4`, `0x8`, `0x40`, `0x80` and `0xC0` pass.

So the description is fine, and one of the two other arguments — the initial state, or the clear value's format — is what the host refuses on those two colour targets. Neither was in the log, which is the defect worth fixing first: a failure that cannot be diagnosed from the run.

### The patch

`crates/victory-gpu/src/resource.rs`:

- The failure log now names `state` (what the host was asked for), `title_state` (what the title named) and `clear`.
- `host_texture` tries a short ladder of descriptions, most faithful first: what the title asked for; then in the common state; then without the clear value; then without unordered access; and last as plain memory. The state and the permission the title asked for are kept as long as the host takes them, the first description the host accepts is used, and a warning names what was given up (`flags_asked`/`flags_made`, `state_asked`/`state_made`, `clear_asked`/`clear_dropped`), once per texture.
- It returns the state the texture was really made in, so the transitions that follow start from the truth (`HostTexture::state` used to assume the asked state).
- A depth target keeps its depth permission through the ladder, nothing is tried twice, and permissions only ever go down.

### Verification

- `cargo test -p victory-gpu --locked` → **56 passed, 0 failed** (2 ignored: an existing benchmark and the new GPU probe), including a test of the ladder's order and of its first attempt being exactly what the title asked.
- `cargo clippy -p victory-gpu --all-targets --locked -- -D warnings` → clean, with and without `--features diagnostics`.
- A 60-second boot with the debug layer on and this patch: 1,024 frames, the same 11 programs, **no** `no host texture`, **no** fallback taken — identical to unpatched `ffe310e` in the same state, so nothing that worked before changes.

**What I could not do:** name which argument the host refuses in those two cases. My machine cannot create a swap chain today (`CreateSwapChainForHwnd` → `0x887A0022`, `step="swap chain"`, after the backoff patch in #1591), and these two textures are only asked for once presenting works, so the failure does not reproduce headless. Anyone with a presentable desktop can settle it with one boot of the diagnostics build at `VICTORY_LOG=info`: the `no host texture` line now carries `state`, `title_state` and `clear`, and if the ladder took over there is a `host texture made only as a fallback` line. - **`B5G5R5A1_UNORM` (86), asked with `ALLOW_RENDER_TARGET | ALLOW_UNORDERED_ACCESS`:** the RTX 4090 refuses the UAV permission for that format, so the host copy is a render target only (`flags 1`). The clear value is the one the resource names and is kept, so the UAV permission was the refusal — the same refusal the `packed_formats` probe reproduces directly.
- **`B4G4R4A4_UNORM` (115), asked with `ALLOW_RENDER_TARGET`:** the RTX 4090 refuses the render target too, and refuses the creation even with the clear value in the resource's own format (`clear_asked=115`), so the only description it takes is plain memory (`flags 0`) with no clear. So on this GPU that target cannot be rendered into at all.

What that means for the boot, honestly: the ladder keeps the textures (without it there is no host copy and every draw that names them is lost), but it cannot keep what the host refuses. A `flags 0` texture can still be a shader resource; it can never be a render target, so the draws that render into (115) have nowhere to land, and the UAV writes to (86) go nowhere. Both are logged once, which is the only way anyone would know.

Two things I would like the maintainers' judgement on, because they are policy and not measurements:

1. Should the ladder go as far as plain memory? It is the difference between "a texture exists" and "nothing exists", but a texture that can never be bound as an RTV is a quiet way for a frame to come out empty. The alternative is to stop at the last description that keeps a permission and report the target as missing.
2. Should a refused UAV permission on a *colour* format (86 here) be a warning rather than a once-per-texture line, since a shader writing through it is a silent no-op?

The other refusal in the same run is the one already noted at the top: `view the host does not allow unordered=true format=53 flags=2`, a UAV view of a typeless depth resource, which is a different case and is correctly refused.

No game data is involved: descriptions, flags, states and counts only.
