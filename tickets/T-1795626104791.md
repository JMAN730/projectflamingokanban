## Original body

Title: `v_med3_f32(1.0, 2.0, NaN) returns 2.0 on NVIDIA; the RDNA2 result is 1.0`

Running the test suite on an NVIDIA RTX 5060 Laptop (driver 591.74, Windows 11
26300) with the default hardware device, the whole suite is green except:

```
emit::valu_tests::v_med3_f32_matches_rdna2_with_nan
assertion `left == right` failed: hardware: v_med3_f32(1.0, 2.0, NaN) = 2 (0x40000000), want 1
```

The lowering models the RDNA2 `v_med3_f32` NaN rule (with a NaN among the
three, the result is the smaller of the two numbers). The DXIL path evidently
maps it to an intrinsic/host expression whose NaN propagation picks the other
side on NVIDIA hardware; AMD (RX 6700 XT, where the suite is reported green)
matches the console behavior. All other NaN VALU tests in the same module
(`v_med3_f16...` passes on NVIDIA already) are fine, so only the f32 lowering
needs the NaN-safe form.

Repro: `cargo test -p victory-shader --lib -- --test-threads=1`
Environment: any NVIDIA D3D12 adapter with SM 6.6; the failure is stable in
serial and parallel runs. The same run under `VICTORY_WARP=1` is fully green,
which fits a hardware-intrinsic difference rather than a code bug.

No game files involved — synthetic tests only.

### Comment 9 — @Sunkiller-qc — 2026-11-24T13:21:18Z

There's an open PR for this from before this issue: #110 (lordon1a, opened 00:36 UTC). It replaces `fcmp uno` in `Lower::med3()` with DXIL's `IsNaN` (`dx.op.isSpecialFloat.f32`, opcode 8), because the driver compiler folds `fcmp uno x, x` to false under fast-math. The symptom is the same: `v_med3_f32(1.0, 2.0, NaN)` returns 2.0 instead of 1.0. It was found on Intel Iris Xe, which matches ayanbarosan's Intel UHD result on #745. #154 extends the same fix to the other unordered and ordered compares.

So there are two fixes now, #110 and the bit-compare branch on #745. If someone with a failing card (the 5060 Laptop here, or the 3050 Ti Laptop on #745) could run `v_med3_f32_matches_rdna2_with_nan` on #110, that would settle which one to take.
