## Original body

# The cutscene picture is missing but audio and subtitles render: here is the elimination chain down to descriptor sampling

Posting the full chain so nobody re-runs these steps. Audio, subtitles and the menu UI render; the
cutscene picture and the 3D scene come out as flat clear colour (`0x20202C`, captured, 99.8% of
texels plus 8 stray pixels). Everything below was measured on this host with a diag build.

## What is already ruled out (with the evidence)

| suspected cause | measurement | verdict |
|---|---|---|
| packed formats 86/115 (#797) | `packed 16-bit render targets are R8G8B8A8_UNORM on this GPU format=86/115` | **excluded** — PR #89's core commit fixes it, `no host texture` count went 2 → 0 |
| viewport too small | `viewport set x=0 y=0 w=3840 h=2160 min_z=0 max_z=1` | **excluded** — full 4K |
| render target wrong / missing | `targets ["3840x2160 f28"]` (RGBA8, 4K) | **excluded** — correct target |
| depth or culling discarding geometry | `depth=D3D12_DEPTH_STENCIL_DESC { DepthEnable: 0 ... }`, `cull=1` (NONE) | **excluded** — nothing culled |
| draws not submitted | `draw draw 3 from 0 topology 4 pipeline 0x9b0d2e00 ...`, `drawn=1` | **excluded** — it runs |
| textures missing entirely | `textures 2.5 ms 12.7 MB` per frame at the menu | **excluded** — uploads happen |

## Where it actually points

The frames that should show the cutscene reduce to a full-screen triangle whose only input is a
descriptor read:

```
draw 3 from 0  topology 4  vb 0x0+0 stride 0  targets ["3840x2160 f28"]
     reads ["dfafaf385b2f94e8 Srv s0+0: Descriptor"]
```

`vb 0x0 stride 0` with three vertices is the normal full-screen-triangle form, so the geometry is
not the problem. The triangle samples `s0`; if the view behind `s0` holds no data, the output is
exactly the flat clear colour we captured.

So the remaining suspect is **descriptor binding for sampled textures** — the same family as the
`a descriptor read only as data` class (143 of the remaining translation failures in #784). That is
translator/runtime-internal work, and I am stopping here rather than guessing at the fix.

## Why this is worth recording

- It removes format, viewport, render target, depth/culling, submission and upload from the list of
  suspects for the black-cutscene reports (#797, xcl#878), which is most of what those threads
  speculate about.
- It gives a crisp next probe for anyone with the runtime knowledge: log what the `s0+0` descriptor
  resolves to (resource, format, and whether the resource has been written) at the draw that should
  paint the cutscene.

Host: Windows 10 22H2 UBR 3393, RTX 4070 SUPER 12 GB, VIctory `main` @ `ffe310e` + #729 exports +
#89 core, diag profile.

## Answer to the probe at the end of #850: the `s0+0` root descriptor is not empty

I built exactly the probe #850 asked for — at bind time, for every root SRV the
translated shaders declare (`RootType::Descriptor`), log the title GPU address, which host
copy it lands in, and the bytes a shader would read there — and ran it.

**Result: the descriptor resolves on every draw, into a host copy that has data.**

| measurement | value |
|---|---|
| root SRVs bound over the run | 256 distinct addresses, **0** without a host copy |
| bytes at the address on first use | 32 of 32 zero (the copy is refreshed at the *next* submission) |
| bytes at the same slot on later draws | non-zero; the sampled 32-byte window holds two IEEE-754 `±1.0` constants at fixed offsets |
| where the copy lives | a 4 MiB shadow window over title linear memory, `0x20000` further along per draw |
| what sits at that address | title memory, not a committed or placed texture (no texture resource at the address) |

So `s0+0` is a **root SRV (a raw buffer view) into title memory**, not an empty
descriptor, and `SetGraphicsRootShaderResourceView` runs on every draw. `root_view`
returning `None` — which silently skips the call and leaves the argument at 0 — never
happens in this run: 0 of 256.

That retires the last suspect in #850's chain. It also means the full-screen triangle with
`reads ["<hash> Srv s0+0: Descriptor"]` is not where the cutscene picture is lost.

@MartinIndra02 Great catch — that completely reframes the issue. If `dfafaf385b2f94e8` is purely a vertex shader without textures, then `s0+0: Descriptor` was indeed a red herring and the cutscene video blit/presentation pipeline is never reaching the draw call stream (or is getting dropped beforehand).

Regarding where the video blit / presentation might be getting lost, a few concrete places in the codebase come to mind for the next investigation:

1. **Pipeline drops (`crates/victory-gpu/src/pipeline/make.rs`)**:
   Check if `pipeline::note_drop` / `take_drops()` is catching any failed PSO creation during cutscenes. If the fullscreen blit or color conversion shader (YUV/NV12 $\to$ RGB) failed translation or validation, the draw or dispatch gets silently dropped.

2. **Video surface formats (`crates/victory-gpu/src/resource.rs` & `crates/victory-formats/src/texture.rs`)**:
   Currently, video and planar DXGI formats (such as `DXGI_FORMAT_NV12`, `P010`, `YUY2`) return `None` when creating host textures. If the video decoder outputs frames to a video-format surface and attempts to create an SRV/RTV, resource creation will return `None`, preventing any subsequent blit.

3. **Compute dispatches (`crates/victory-gpu/src/list.rs`)**:
   Many video playback pipelines perform color conversion and blitting via compute shaders (`Dispatch` / `DispatchIndirect`) rather than graphics draws. It is worth checking whether compute dispatches are being recorded and executed during cutscene playback, or if they are missing or dropping.
