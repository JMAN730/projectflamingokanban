## Summary

The title boots, runs its menus, loads the world, and stays alive for a long time
(one run lasted 55 minutes). **The world never draws anything visible**: the
window is black apart from a thin column of coloured pixels at the left edge.
`draws/frame` counts in the thousands, so draws are being submitted  - they are
being dropped.

The dominant warning is not a shader-translation failure:

```
WARN victory_gpu::draw: a draw or dispatch dropped: no dynamic slots for its tables dropped=32768
```

Load screens and 2D do render correctly (see *What does render* below), so the
texture, UI and present paths are fine. The gap is 3D only.

## Reproduction

1. `cargo build --release -p victory --features diagnostics`
2. `victory.toml` with only `game_dir` pointing at the dump
3. `target\release\victory.exe run "<dump>\game_scarlett_master.exe" --execute --unimplemented zero`

Menus appear (black, `30 fps`, `10-11 draws/frame`). With key presses
(`VICTORY_KEYS=8:Enter,20:Enter,35:Enter`) it proceeds into the world:

```
Americas | VIctory 1 fps 1165.7 ms/frame 2645 draws/frame
```

Screen stays black. Within 60-180 s the host device is removed.

3D world rendering produces nothing.

## What I tried (and it made things worse)

Since `descriptor/host.rs` documents the cap:

```rust
/// 2^16 ran out seconds into the world (every world run on an RX 9070 XT,
/// each a device removal shortly after; #59).
const DYNAMIC: u32 = 1 << 18;
const MIN_DYNAMIC: u32 = 1 << 16;
const PORTABLE_VIEWS: u32 = 1_000_000;
```

I raised them to `DYNAMIC = 1 << 20` and `PORTABLE_VIEWS = 4_000_000`, expecting
the slot exhaustion to go away. Result:

```
Americas | VIctory 30 fps 33.3 ms/frame 10 draws/frame
```

`30 fps` is not an improvement  - `10 draws/frame` means almost nothing is drawn.
`make(count + DYNAMIC)` fails past the tier-3 limit of 1,000,000 shader-visible
descriptors, so both the `DYNAMIC` and `MIN_DYNAMIC` paths fail, `HostHeap::new`
returns `None`, and every draw loses its heap. Reverting to the shipped constants
restores the original behaviour.

So raising the constants is not the fix; the slot shortage needs more heaps or a
remapping layer, not a bigger single heap. Posting in case it saves someone else
the experiment.

## Related

- #59  - the `2^16 ran out seconds into the world` note points at this same
  exhaustion; this report adds a tier-3 NVIDIA data point and shows that raising
  the constant fails on the 1,000,000 cap.

## Minor: `rust-toolchain.toml` pins an unavailable toolchain

`rust-toolchain.toml` asks for `channel = "1.98.1"`, which `static.rust-lang.org`
and the Tsinghua mirror both return 404 for. `Cargo.toml` states
`rust-version = "1.88"`, so a `stable` toolchain builds the workspace fine
(1.100.0 here). Changing the pin to `stable`, or to a version that exists, would
unblock anyone building from source.

### Comment 2 — @MichaelSmithAI — 2026-11-24T18:51:50Z

The `no dynamic slots for its tables, dropped=32768` line counts **32,768 rejected binds over the process lifetime**. The binder already has a host pipeline when it reaches this counter. It increments once when a bind fails to reserve a contiguous range for a fresh descriptor table, then logs at powers of two. The per-frame “without a host pipeline” count in the report measures a separate failure. Intersecting the 32,768 milestone with a list of shader refusal hashes therefore cannot identify the missing draw. [Counter and early return](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/draw.rs#L461-L472) · [Reservation failure](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/draw.rs#L717-L734)

For a capture over the same world-frame window, the most useful numbers would be the requested contiguous span, the selected heap's dynamic capacity, total free slots, and the largest free span at failure. Those distinguish a full heap from a failed search with enough slots free. The pending/recovered slot counts in [#911](https://github.com/Marvisak/VIctory/issues/911) would also show how many slots earlier declined binds retained.

## What your data settles

**1. The cap is not vendor-specific.** Agreed, and that is now demonstrated rather than assumed: same `PORTABLE_VIEWS` math, same lost tail, on a wave64-native driver.

**2. More importantly, you drop draws `without a host pipeline` too - 61 of them.** That is the part I did not expect. If the refusals came from a wave-size mismatch, RADV should refuse none, because RDNA runs 64-lane subgroups natively and vkd3d-proton accepts `requiredSubgroupSize=64`. It refuses anyway. So whatever produces those refusals is not lane width.

There is a detail in the original #71 analysis worth flagging: `0x80070057` is `E_INVALIDARG`, which is an *argument* validation failure, not a capability code. It has been read in that thread as evidence about hardware, and your result suggests it should not be.

## What would help most, in priority order

**First, the exact refusal line for those 61 draws.** Whatever VIctory prints per pipeline - `no host pipeline: <reason>` or a translation error - with the stage and hash. If I can diff those against my 115 broken-out compute hashes, an intersection names a shared trigger; no intersection means the two problems are separate and both threads should stop cross-referencing.

**Second, and this is the fork I actually care about:** for the two refused pipelines you mentioned, do you have the **HRESULT** and the **failing descriptor index**? Specifically:

- If RADV returns `E_INVALIDARG` for them too, then the wave-size reading of #71 is dead and both drivers are rejecting on the same non-hardware grounds.
- If instead it returns an out-of-descriptors style failure, the refusal is pinned to the 934,464 mirror, and the 2,556-byte compute becomes the prime suspect for the pass that assembles the presented frame.

Either answer resolves it. A hash alone does not - it tells us *which* pipeline, not *why*.

## Our #1548 result, so you know what to expect

I built the branch on the NVIDIA machine (RTX 3080 Ti, driver 32.0.16.2101, Windows 11 build 26300, release+diagnostics). For comparison, my instrumented main build reported the first slot failure as:

```
requested=11  capacity=65536  free_slots=482  largest_free_run=10
```

One short of the request, with 482 slots free but no run longer than 10 - fragmentation plus the shrunken `MIN_DYNAMIC` region, not a full heap. After the PR:

```
WARN host view heap capped at 1000000 count=1245184 capped=737856 dynamic=262144
no dynamic slots for its tables: 0 occurrences over a 150 s world run
```

Bind rejections went from 32768 to zero, and captured frames grew from a 1.8 MB peak to 4.1 MB. **The 3D world is still mostly black.** So the heap cap was a real blocker and the PR removes it, but it is not what darkens the world - that stays on the refused-pipeline path.

Worth knowing before you rebuild: the PR lowers `count` from 934,464 to 737,856 while raising `dynamic` to 262,144 (same 1,000,000 total). The addressable window shrinks by 196,608, so more indices go through the remap path. On my run that was fine, but a tree with #994 + #491 might exercise indices mine never touches. If you see new out-of-range complaints after applying it, that rebalance is the first place to look.
