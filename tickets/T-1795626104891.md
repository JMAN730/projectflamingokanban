### Comment 10 — @LooperSalty — 2026-11-24T15:16:29Z

*From a tester working with Claude (AI-assisted); measured on my own machine (i7-13700KF, RTX 4070 Super, Windows 11), own copy of 1.0.2.1.*

Two things from today that may help everyone chasing the black world, both measured in the world after the prologue starts (the "Move / Move the camera" tutorial prompt is on screen, so the player has control; the UI composes over a black 3D image, as described here).

**1. Speed: 0.2 → 2.3–2.5 fps in the world, from three host-side changes (no shader change).**
- `VICTORY_D3D12_DRED=1` costs ~2.5× in the world: the title's 5 command-list recording threads spent ~50 % of their samples in `VirtualQuery` building the per-draw breadcrumb text. Leave it off unless you are chasing a device removal (5 s → ~2 s per frame).
- The copy-back's `write_mapped` used `WriteProcessMemory`, which queries the region first (`NtQueryVirtualMemory`, ~2 ms per call on the title's big heaps, one call per changed 64 KiB page): 66 % of the submit thread. Writing with `NtWriteVirtualMemory` directly (same per-page success/failure semantics) took the copy-back from ~1.5 s to ~0.13 s per frame.
- `copy_mapped` without the up-front `VirtualQuery`, and the pre-GPU snapshot, the copy-back comparison and the texture blake3 hashing spread over a persistent pool of threads created at start-up (creating threads per call runs the title's DLL_THREAD_ATTACH callbacks).
Remaining per frame (~410 ms): GPU ~145 ms (fence wait, CPU and GPU still serialized; #595 is the obvious next step), copy-back ~73, texture hashing ~20, snapshot ~50.

**2. Ray-traced passes no longer dropped (diagnostic option, local).** With `VICTORY_SKIP_BVH_BUILDER=1` the RT passes (`GatherVBuffer` irradiance cache, `RTDistantShadowTrace`, `TraceShadowRays`, `RaytraceShadows`, `LaserLightShadowRaytracing`) stayed dropped on "an address not from a root parameter": they read the acceleration-structure VA from a descriptor, then `s_load` the node count at +48 and branch over the traversal when it is ≤ 0. A `VICTORY_RT_MISS=1` option (off by default) makes those unresolvable loads read a null view (0) and `image_bvh_intersect_ray` return 0xFFFFFFFF, and folds the resulting scalar branches so the dead traversal loop is removed: every ray misses (no RT shadows or bounces), but the passes run and feed what follows. Offline, 36 of 47 RT containers emit and validate instead of 18; in game the six RT producers that `VICTORY_PRODUCERS` flagged now run. Untranslated programs seen in the world: 131.

*AI-assisted (Claude Code). Measured on my own machine and my own 1.0.2.1 copy; counts only, no captures.*

Some measurements on why the output stays zero, from an **RTX 5080** (32-lane waves, view heap capped at 1,000,000), Windows 11 26300, Ryzen 7 9700X, 64 GB, Series X mode, diag build.

**Tree.** Not `integration/testers`: an older integration of `main` (the #414 set) plus #641, #413, #432, #439, #489, #500, #546, #591, and local changes named below. So read these as one more route, not as a run of the tester tree.

### 1. The lit scene target is exactly zero, not just the 4K output

The 2560x1440 `R16G16B16A16_FLOAT` target that tiled lighting draws into is all zero at the end of every world frame (no NaN, no infinities), while the G-buffer targets beside it hold the scene. A copy of that target taken right after each enabled tiled-lighting draw is zero too, so nothing clears it later. Everything downstream (upscale, composite) then has nothing to show, which would explain a zero 3840x2160 target without any of those passes being wrong.

### 2. Tiled lighting is drawn as rectangle lists placed by vertex number

`VS_TiledLighting` has no vertex buffer: tile = `SV_VertexID / 3`, corner = `SV_VertexID % 3`, 720 vertices per draw (240 tiles of a 20x12 grid), through `ExecuteIndirect`. `expand_rects` and the GPU expansion (#282, #346) make the fourth corner from vertex buffers, so these draws have nothing to expand. With #346's behaviour they ran with twice the vertices and vertex numbers the shader does not expect. I opened #1020 for this (a generated geometry stage completes the rectangle). Per enabled lighting draw, from a pipeline-statistics query around it:

| draw | geometry stage in → out | after clipping | pixel invocations |
|---|---|---|---|
| no-directional-light variant | 240 → 480 | 120–140 | 740,000–900,000 |
| directional-light variant | 240 → 480 | 0 | 0 |

The indirect arguments of these draws are written by the CPU. About 90 material classes each have a draw; in the opening scene 4 have instance count 1 (standard and standard-wetness, each with and without directional light).

### 3. Albedo was zero for a separate reason: material textures read by direct heap index

The G-buffer albedo target was zero where geometry was drawn. The G-buffer pixel shaders load their texture descriptors from the resource heap at indices read from a material record (seven indices at a byte offset passed in a root constant, in the large material buffer). Those slots hold placed block-compressed textures. With #413 they were still not made when drawn: for 60 materials drawn late in the world, only the shared 4x4 defaults and one array had host views. My reading is that the sweep goes over all placed slots (about 67,000 here) in index order under the 4,096-texture cap, so it does not reach what the scene uses. Making the seven slots a material names when its draw is bound (a local hack tied to this record layout, not a PR) filled the albedo target: characters, ground, buildings, the picnic table. #641 was needed as well; without it partly streamed textures were skipped.

### 4. With 2 and 3 in, lighting still writes zero, and here is where it stops

- The directional variant draws no tiles because its vertex stage keeps a tile only where a 20x12 `R8_UNORM` tile texture is non-zero. `tiled_lighting:CS_ShadowRevealTiles` writes that texture, and it is all zero.
- Upstream of it: `cascadeshadows_classify` (3 compute programs) → `shadowmask:CS_GenerateShadowMasks_*` → `CS_ShadowRevealTiles`. The three `cascadeshadows_classify` programs are refused here with *console wave64 lanes in a group of more than 64 threads on a host without 64-lane waves*.
- Forcing that tile texture to read 1 (a diagnostic switch) makes the directional variant draw 40 tiles and run about 650,00
