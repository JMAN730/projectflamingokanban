test suite on RDNA3, which runs wave32 and wave64 natively. No game data was used.

on `ffe310e`.

  and the same 4 skips.

where a native wave64 device may help separate translation bugs from
hardware limits.

### Comment 1 — @fiestorra — 2026-11-24T19:47:23Z

**One test on `ffe310e` fails on a machine whose session has no display — the test's assumption, not the runtime's**

`cargo test --workspace --locked` from `ffe310e` on this machine: everything passes except

```
---- modules::display::tests::sdr_and_display_deferrals stdout ----
panicked at crates\victory-hle\src\modules\display.rs:188:9:
assertion `left == right` failed
  left: -2147024846
 right: 0
```

`-2147024846` is `0x80070032`, `HRESULT_FROM_WIN32(ERROR_NOT_SUPPORTED)`, which is exactly the module's own `NOT_SUPPORTED`. The test calls `XDisplay`'s deferral acquire, which asks the host to keep the display awake (`PowerCreateRequest`, then `PowerSetRequest(..., PowerRequestDisplayRequired)`); on a session with no display to keep awake that call answers `ERROR_NOT_SUPPORTED`, and the runtime hands the title the failure, which is the right thing to do. A console always grants it, so `assert_eq!(…, S_OK)` holds on a machine with a real display (yours, presumably) and fails where I am today — the same session cannot create a swap chain either (`CreateSwapChainForHwnd` → `0x887A0022`).

That matters past this machine: it is the kind of test that goes red on headless CI or a locked session, and its failure hides the real signal in the suite.

**The fix** (patch below, against `ffe310e`):

- The test now checks the contract that holds anywhere: a granted deferral comes with a handle and closes cleanly; a refused one is `NOT_SUPPORTED` and leaves no handle; closing a null handle is fine. It no longer asserts that the host has a display.
- `acquire_deferral` logs the refusal at `debug!` (`the host refuses to keep the display awake`, with `code`) and a failed `PowerCreateRequest` (`no power request for a display deferral`), so the condition is visible in a log instead of guessed.

**Verified:** without the patch, `cargo test --workspace --locked` on `ffe310e` has that one failure; with it the whole workspace suite passes (56 in `victory-gpu`, 94 in `victory-hle`, 120 in `victory-shader`, and the remaining crates), and `cargo clippy -p victory-hle --all-targets --locked -- -D warnings` is clean.
