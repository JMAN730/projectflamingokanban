## Original body

## What

Every frame crosses two address spaces. Title memory is Windows pages the title's CPU code writes; host copies of it are GPU buffers. `shadow.rs` brings the ranges a submission reads up to date before it runs and, after it, diffs them against a `before` snapshot to put back what shaders wrote; `watch.rs` keeps a journal of written pages, and guarded physical-page views take write faults and hand access back.

This issue proposes deleting that bridge: let the title's memory *be* GPU memory.

## Where the cost is

- `host.rs` `execute` (about line 491): one global `submitted` lock and a `WaitForSingleObject(event, INFINITE)` per submission. It has to be synchronous because copy-in and copy-back bracket the submission. A title frame spans 8–10 submissions (#135), so nothing overlaps and frame time is their sum.
- `shadow.rs` (about line 149): one snapshot per copy and submission, grown to span every declared range — the world declares overlapping views of its 174 MB heap dozens of times, "~2.3 million page faults per world frame".
- `watch.rs` (about line 27): 64 KiB pages, chosen because "finer units made the checks of the world's big buffers cost more than the copies they saved".
- #334: the same 174 MB heap is written as a UAV and read as vertices. #336: fault addresses and descriptors read out of slots that hold something else, because a table could not be made. #293: the two largest drop reasons are an address the tracer lost and a descriptor it never saw built.

So a large part of the open list is symptoms of two address spaces: staleness, wild bases, use after release, reads of freed memory, page faults per frame, and a submission model that cannot overlap.

Current work extends the bridge and none of it removes it: #185 (coherency for directly indexed SRVs), #261 (copy-back only what shaders wrote), #334 (transitions of the copies), #367 (one state tracker for the copies), #124 (page-check reuse), #322 (skip the region query), #202 (skip unmapped holes), #294 (safe fallback VAs, Root SRV extents).

## Proposal

Title memory is allocated in a D3D12 heap the CPU maps, and its GPU address *is* the title address.

- xmem allocates physical pages from an arena held by one `CreateReservedResource`, its 64 KiB tiles mapped from a `D3D12_HEAP_TYPE_CUSTOM` heap with `CPUPageProperty = WRITE_BACK` and `MemoryPoolPreference = L0` — the heap `host.rs` `shared_buffer` (about 1754) already uses, and `shadow.rs` (about 416) already allocates the copies from.
- A buffer the title exposes to the GPU is a resource placed at the title address; root views and table descriptors pass the title VA unchanged.
- Those buffers lose their `Shadow`, and with it copy-in, copy-back, the snapshot, the dirty journal, the write guards and per-draw translation (`Shadow::gpu` becomes the identity).

Parts of it already exist and are unused for this: `resource.rs` `create_placed` (about 1180) places a resource at an address the title chose, `texture_at` (about 1150) resolves a texture by title address, and a test at `resource.rs` (about 1787) already asserts that committed and placed resources map at their GPU address.

## Staged, and reversible

1. `Host::unified_buffer`, the arena and a capability probe that answers `Option`, wired to nothing. Synthetic test: custom heap, buffer placed at a chosen address, `Map`, a CPU write, a root SRV read and a UAV write in one dispatch, read back. Asserts the resource's GPU VA is the chosen address and that each side sees the other's bytes with no barrier and no flush.
2. xmem asks the arena first for physical pages that are GPU-visible and otherwise keeps `VirtualAlloc`, behind `[memory] unified` (default off). Arena allocations skip `Shadow` on read and write.
3. Coherency from the bus removes the bracket around submission, so submission can be asynchronous — which needs #32 and #367 anyway.

Not all-or-nothing: the fallback is per allocation, `shared_buffer` already returns `Option`, and a heap the host refuses keeps today's path.

## Expected effect

- Copy-in, copy-back and the snapshot diff go to zero for those allocations, and a frame's CPU preparation overlaps the previous frame's GPU work instead of adding to it.
- Staleness and guard races stop existing: a shader sees what the title wrote, in the order it wrote it.
- Descriptors, strides and addresses the tracer lost (#193, #293's "an address in an SGPR that is no root parameter", #336's bases) become reads of the console's own structure at that address.

Not covered: this does not make the world render. It is the memory model the rest of the bring-up is still fighting; #293's drop reasons and #292's loop budgets remain.

## What is uncertain, and how to find out

- **D3D12 assigns GPU virtual addresses and cannot be told which to use.** The arena base therefore lands where the driver puts it, and the title is given `base + offset`. Title code or shaders that bake an absolute console VA are where this can break. The translator already resolves addresses through root parameters, so a biased base should be one constant there — that needs checking early and cheaply rather than assumed.
- **A custom heap with a CPU page property is not universal.** `shared_buffer` is relied on today, but the probe and the per-allocation fallback are what keep it safe, and the supported set on NVIDIA and Intel is unknown.
- Reserved resource tiles are 64 KiB, and the residency budget and alignment the title actually needs have to be measured.

## Verification without the game

Step 1 needs a device and nothing from the title, which is why it is first: it answers per vendor in seconds. After that, `VICTORY_GPU_TIMING`, `copystat` and a `VICTORY_D3D12_WARP=1` run measure it.

I can prepare step 1 as a PR on its own. I have neither the dump nor a Windows GPU here, so the run has to come from someone in this thread; the code would land behind `Option` and opt-in, so merging it cannot regress a current run.

**Questions:** is this model worth changing at all, or is finishing the bridge as it stands the preference? Would step 1 be taken as a standalone PR?

### Comment 12 — @itsRevela — 2026-11-24T12:42:35Z

Two inputs for this design. First, evidence from the opening cutscene that the per-buffer shadow model is now the limit. Second, how another project solves it.

**1. What the shadow model costs in the opening cutscene.** These are local builds of `main` plus #302/#489, #294, #709 and #710, measured with DRED and `VICTORY_GPU_TIMING`. Counts only.

- **The current device hangs are root-UAV compute programs.** A single `dispatch 1x1x1` that never completes is in flight at the hang: `4ddd6f9702fab2a7`, or `5552dac6a2b7a1fd` once that one is skipped. The first has no loop: 52 instructions and straight-line raw loads and stores. Its two root UAVs are the same title address, and the only host copy behind them is a 394 KB shadow. A root view has no size, so an access past the innermost shadow lands outside it. Details are on #294.
- **The tracer refusals left are all "where does this address come from" cases:**
  - an address advanced in a loop or chosen through a phi;
  - an address loaded from memory (pointer chasing);
  - an address passed as two root constants (#710 handles only the last, and only for reads).

  In a flat address space none of these needs tracing.

**2. How ivall/xcl does it.** xcl runs Fortnite and XDefiant fully. It's **GPL-2.0-only**, so this is a description of its design in my own words, from reading it, with no code copied. Paths are in that repo at `47efa2e`.

- **One address space, in up to four 4 GiB windows.** Each sits at a fixed, 16 GiB-aligned base, so the title's address is the GPU address. Translated shaders see the windows as raw byte-address buffers and pick a window from the high dword of a 64-bit address. All `global_*`, `flat_*` and `s_load` accesses are plain address arithmetic, with no per-instruction tracing (`src/gpu/uma.rs`; `src/gpu/recomp/emit.rs`, `window_read` and `window_write`). Reads outside the windows return 0 and writes are dropped.
- **Committed graphics heaps:** these are opened as a coherent window with `OpenExistingHeapFromAddress`, so CPU and GPU see the same bytes with no copy (`src/hle/kernelx.rs`, the `VirtualAlloc` hook).
- **Large reservations:** these become 4 GiB tiled buffers whose 64 KiB tiles map onto VRAM heaps as the title commits pages. CPU writes are write-watched. Only the 64-byte chunks that changed are uploaded through a staging ring before submission, and the queues wait on an upload fence (`src/hle/d3d12x/sparse.rs`).
- **Root arguments:** these live in memory in the console's layout, a raw 8-byte address per root descriptor. The shader builds its own buffer descriptor from it, so a root UAV is just an address into the window.
- **Caveat:** xcl's README lists this title as menus-only for now, so none of this is proven on our world.

If it helps Step 1+, I can run any branch of this through the opening cutscene. I have a sandboxed setup that captures render targets from the heavy frames (#500) and records DRED, GPU timing, and pipeline statistics per depth target. Before and after numbers would show whether the root-UAV hangs and the untranslated address classes go away.
