### Comment 1 — @FIocker — 2026-11-23T23:09:50Z

Same hang here on an **RTX 5080** (driver 621.1), and I think it is the two refused textures you listed. With the patch below the title no longer hangs at the menus here.

**Why.** NVIDIA's D3D12 driver has no `TYPED_UNORDERED_ACCESS_VIEW` support for `B5G5R5A1_UNORM` (86) and no `RENDER_TARGET` support for `B4G4R4A4_UNORM` (115); the title creates both at 2560x1440 (flags 0x5 and 0x1). With `no host texture`, the descriptors that name them point at nothing, and `draw::State::set_targets` skips the slot with `continue`, so every render target after a missing one moves down a slot. The DRED trail then stops on the same 6-vertex quad as yours (`vertex 0602c2384acbb3b2 / pixel a78d088fa55aa495`, sampling the 3840x2160 R8G8B8A8 target). WARP, which accepts both formats, runs past that point. None of the shaders in that submission has a backward branch, DRED has no page fault and the debug layer reports nothing, as in your log.

**Fix (in the patch):**
- `resource::host_texture`: when `CreateCommittedResource` fails, ask `CheckFeatureSupport(FORMAT_SUPPORT)` which of the RT/UAV uses the format lacks, and create the texture again without them (logged once per format and flags). Nothing changes for textures the host accepts.
- `draw.rs`: a render-target slot whose texture is missing or has no render-target use binds a null RTV (writes discarded) instead of being skipped, so later targets keep their slots.
- `list.rs`: `ClearRenderTargetView` on such a texture is skipped. Views of it are already refused by `fits`, and `legal_for` already drops the RT state bit.

**Result on the RTX 5080** (release and diag builds, no input): first-boot screens and menus at 30 fps for about 2.5 min, loading-screen artwork renders, then the title loads into the world (about 500 draws per frame, mesh pipelines, 0.1-0.2 fps). It runs there until the device is lost on the first world mesh pass, which looks like the README's AMD world failure, not this one. Black frames still alternate with drawn ones in the menus.

On the 1,000,000 shader-visible heap cap you mention: I see the same `host view heap capped` line and have not ruled it out for the world failure yet.

`cargo test --workspace` passes with the patch (214 passed, 0 failed). It needs nothing else from my branch.
