## Original body

An observation from Linux/Wine. I'm filing it because I found no issue or PR that mentions it. It is one run so far, and **I have not shown that the lock is what stops the title**, so read it as a lead.

### Setup

* RTX 3060 12 GB, driver 620.73.04, CachyOS (kernel 7.3), 31 GB RAM.
* Proton-CachyOS 11.0 wine run directly (not through the Proton script) with `WINEDLLOVERRIDES="d3d12,d3d12core,dxgi,d3d11,d3d10core,d3d9=n"`. vkd3d-proton 3.2.0 (from Proton Experimental), DXVK dxgi.
* Diag build of `main` `8e79c80` + #151 #190 #454 #493 #579 + #177's key fix, cross-compiled with xwin. Own 1.0.2.1 copy.
* `VICTORY_NO_WATCHDOG=1`, `VKD3D_DISABLE_EXTENSIONS=VK_NV_raw_access_chains`, network off.
* `WINEDEBUG=err+vulkan,err+seh`. The default `err` channel would show the same lines; they were hidden in my earlier runs only because I ran with `-all`.

### What happened

* **Menus, loading, world:** the menus run at 27–30 fps. The world load opens the `story000*` archives. World audio plays, and the screen stays mostly black, as expected on this host.
* **~3 min into the world:** from that point Wine logs, 231 times and from three different threads (`01ec`, `0224`, `021c`), on **one** lock address:
  ```
  01ec:err:sync:RtlReleaseSRWLockExclusive Lock 000000002CEF84A0 is not owned exclusive!
  ```
  The first one comes right after a batch of `shader does not translate` warnings and vkd3d-proton's "application has stopped creating new PSOs" disk-cache flush.
* **Afterwards:** the frame-progress lines stop. The last was frame 1024, about 2 minutes before the first lock message, and no frame 2048 followed. The audio stops a little later. The process stays alive with no exception, no `crashes.log` entry, and no device removal, until killed.

### Why it may matter

Wine checks this case and Windows does not. `ReleaseSRWLockExclusive` on a lock that is free or held shared silently corrupts the lock state on Windows, while Wine prints the error. VIctory has no SRW-lock code of its own (`grep -ri srwlock crates` finds nothing), so the caller is the title through its kernel32 imports, or vkd3d-proton, DXVK or the driver underneath. A lock released by someone who doesn't hold it, by three threads, could be what deadlocks the title's threads here. The world hangs reported on Windows (#71, #325, #619, #625) end with the host GPU hung. This one ends with no GPU error.

* A second run to see whether it repeats (running now; I'll add the result here).
* A run on Windows for comparison (I have no Windows machine).

### Comment 4 — @Mumogg — 2026-11-24T15:08:40Z

Two findings for this issue, from an RTX 5070 Ti under Wine: who releases the lock, and what the process is doing when the frames stop. They turn out to be separate things.

**Setup:** RTX 5070 Ti, driver 615.78.08, Nobara 44, Wine 11.21 Staging, vkd3d-proton and DXVK `dxgi.dll` from GE-Proton11-14. Diag build of `ffe310e` + #454 #177 #259 #233 #646 #578 + #334 #493 #724 #725 + the #783 fallback + #909. `VICTORY_NO_WATCHDOG=1`, `VKD3D_DISABLE_EXTENSIONS=VK_NV_raw_access_chains`.

### 1. The lock is vkd3d-proton's, and it is released twice by one function

`WINEDEBUG=+relay` with `RelayInclude` set to the `ntdll.Rtl*SRWLock*` entry points gives the return address of every call. Kept only for the lock named in the error (it ends in `…F84B0` here in every run), one run into the world:

| Call on that lock | Return address | Count |
|---|---|---|
| `RtlAcquireSRWLockExclusive` | `d3d12core.dll+0x4a3bc8` | 1,545 |
| `RtlReleaseSRWLockExclusive` | `d3d12core.dll+0x4a3cf4` | 1,547 |
| `RtlReleaseSRWLockExclusive` | `d3d12core.dll+0x4a3c55` | 1,292 |
| `err:sync:RtlReleaseSRWLockExclusive … is not owned exclusive!` | | 1,295 |

Every error follows the same three calls on one thread: acquire at `+0x4a3bc8`, release at `+0x4a3c55`, release at `+0x4a3cf4`. The title is not involved (no call on that lock comes from the title's image), and neither is VIctory.

The strings next to that code name the function: `vkd3d_try_allocate_device_memory` (`libs/vkd3d/memory.c`), and the lock is `memory_info->budget_lock`. The path is still in upstream `master` as I read it today: inside the candidate loop, when the fixed ReBAR budget would be exceeded the lock is released and the loop `continue`s (a failed `vkAllocateMemory` releases it too); if that was the last candidate, the loop ends with `rebar_budget` still true, and the block after the loop skips its own `pthread_mutex_lock` (it assumes the lock is still held when `rebar_budget && respect_budget`) and calls `pthread_mutex_unlock` again. So each allocation refused for the ReBAR budget releases the lock twice. Wine reports it; on Windows the second release goes unreported.

That makes the message a symptom of those refused allocations rather than of a title lock. Its start "right after a batch of shader warnings" fits a point where the host starts allocating a lot. I have not reported it to vkd3d-proton.

### 2. When the frames stop, one title thread is spinning and nothing is inside VIctory

The stop is intermittent here: about half of the 6 to 8 min runs, 3 to 5 min after launch, with no Xid in the kernel log and no device removal. With `VICTORY_STACKS` every 40 s, one run that stopped at 231 s has four dumps taken after the stop:

- No thread is in `victory_gpu` or any other VIctory code except idle waits (DirectStorage workers, pipeline workers, the decoder).
- Of the 60 unnamed threads (55 with title frames), 59 are stopped inside `ntdll` system calls (waits), the same in both dumps.
- **One title worker thread is running, at the same place in two dumps 40 s apart:** `title+0x50eb81f`, called from `+0x31962` < `+0x317fd` < `+0x25d801b` < the job loop at `+0x221c29c`. Before the stop that thread was idle in the job loop like the others.

From its code that place is a lookup in an open-addressing table that compares a group of tags and, on no match, steps to the next group with no test for an empty slot, so it never ends for a key that is not in the table. I have not found which key or table it is, or why the key is missing; a registration that did not happen (a load that failed or came late) would do it. Nothing here shows the lock of point 1 is related: the double release happens over a thousand times in runs that do not stop as well.

So on this machine the "world stops, process stays alive" case is the title waiting on a worker that will not return, not a host lock.

**Not tested:** Windows, AMD, whether the same thread and place show in other people's stops (a `VICTORY_STACKS` dump after the stop would tell), more than one stopped run with dumps.

### Comment 5 — @Mumogg — 2026-11-24T17:30:15Z

Follow-up on the stop (part 2 of my earlier comment): two more freezes caught with a debugger attached, and the picture is now consistent. Same machine and stack as before (RTX 5070 Ti, Wine 11.22 Staging, GE-Proton11-14 vkd3d-proton). Offsets are for 1.0.2.1; no title code attached.

**What the spinning worker is looking for.** The lookup at `title+0x50eb750` builds its key from the pool element it is handed: pool type, slot index, and a small field taken from that slot's word in the pool's per-slot table at the time of the call. The insert side (`+0x35b70c0` / `+0x35b7200`) builds the key the same way, at the time of the insert. In both captures the table holds an entry for the same type and slot whose field is exactly one lower than what the lookup computes:

| capture | key the job asks for | entry in the table | slot word now |
|---|---|---|---|
| 1 (250 s) | `0x0c81928` | `0x0881928` | not read |
| 2 (420 s) | `0x18813cb` | `0x14813cb` | field = 6, low bits a link to another slot |

So the key is not missing because it was never inserted: the slot's word changed between the insert and the job's lookup. The low bits of the slot word in capture 2 point at another slot rather than holding the all-ones value its allocated neighbours have, which reads like a generation counter on a slot that has been freed since. In capture 2, 64 of the 691 live entries in the table no longer match their slot's current word, and every one I decoded is off by exactly one. So objects registered in the table are routinely released before the table is next cleared, and the freeze is the case where a job still holds one of them. The lookup has no exit for an absent key (a sibling at `+0x56c6340` does stop at an empty slot), so it probes forever.

**What it is not.** The clear-all at `+0x55bfa00` is behaving: the job counter at `+0x8d7a9b0` reads `0x80000001` in both captures (waiter bit set, exactly one job outstanding, the stuck one), so the clear is correctly waiting on a job that never ends, and the table pointer and mask the job cached match the globals. Not a torn grow, not an early wake of the wait, nothing inside VIctory's or Wine's synchronisation.

**My reading (inference, not shown):** the title relies on the registration and the jobs that use it happening close together, and on the console they do. Here a world frame takes 0.5 to 2 s, while whatever releases these objects keeps its own pace, so the window in which a registered object can be released before its job runs is far wider. That would also fit the stop appearing only in the world and more often on slower configurations. What I have not found is who releases the objects and whether that is supposed to be held off while jobs are pending; if someone knows that side of the title, that is the missing piece.

If that reading holds, the options on VIctory's side are to get the frame time down (the real cure) or to give that one lookup an exit for an absent key, which would need a way to patch title code that I do not think exists yet.

Method, for anyone who wants to repeat it: a loop that restarts the title until the frame lines stop for 45 s, then `gdb -p` on the Wine process with a small Python script that reads the stuck thread's registers, the table globals at `+0x876fc48`/`+0x876fc50` and the pool table at `+0xabbe7c0`. Freezes here: 3 of 5 runs today, at 250 to 420 s.

### Comment 6 — @crashbashash — 2026-11-24T19:59:35Z

@Mumogg @r4tedx a measurement on whether VIctory's copy-back can be what changes the slot words behind this stall. Local diagnostics patch on `94e0ea5` (r4tedx's update 9, which has the most copy-back traffic), not for upstream. RX 6800 XT, RADV, GE-Proton11-14, three 10-minute runs in the world.

In `Shadow::copy_back`, for every 64 KiB piece that is written back, I count:
- **title writes reverted:** bytes the shader left alone that the title changed between the piece's read and its write-back (the race r4tedx described on #293). Counted by reading the piece again right before `write_mapped`, so it's a lower bound.
- **title writes lost to a shader byte:** bytes the shader wrote that the title also changed since the submission, to a different value. The write-back puts the shader's byte over the title's newer one.
- **overlap** of each written-back piece with the lookup table (`+0x876fc50`, 144-byte groups, count at `+0x876fc48`) and with every pool's slot words (pool array at `+0xabbe7c0`, slot words at pool `+0x28`), re-read every 5 s.
