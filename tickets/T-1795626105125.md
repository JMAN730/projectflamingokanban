## Original body

### Summary
On commit `d2a4bae`, the initial boot prompt (`PLAYER A`), first-boot setup screens, and menu artwork render cleanly at 30 FPS with audio. After updating to `ffe310e` (and clearing both `data` and `cache` directories), audio still plays normally, but the entire window remains black on first-boot screens and menus.

### Regression Range
- **Last working commit:** `d2a4bae`
- **Broken commit:** `ffe310e`

### Steps to Reproduce
1. Delete existing `data` and `cache` folders for a clean first boot.
2. Build and run `victory.exe run <path>\game_scarlett_master.exe --execute` on `ffe310e`.
3. Frame rate stays at 30.0 FPS and menu/intro audio plays, but the screen stays completely black (whereas checking out `d2a4bae` renders the UI and artwork immediately).

### System Specs
- **OS:** Windows 11 x64
- **CPU:** AMD Ryzen 5 5600
- **GPU:** AMD Radeon RX 6500 XT (8 GB, RDNA2)
- **Console Mode tested:** `series-x` (default) and `series-s`

### Comment 1 — @BastienRodz — 2026-11-24T12:22:16Z

Likely the same cause as #736: #612 (merge `9a92ccf`, between `d2a4bae` and `ffe310e`) stops 323 programs that translated before from translating, 42 of them vertex/pixel. A menu whose shaders no longer translate has its draws dropped, so you get a black screen while the title keeps presenting at 30 fps with sound.

A quick check that needs no bisect:

```
git checkout ffe310e
git revert -m 1 --no-edit 9a92ccf
```

Then clear `cache` (translated shaders are cached by program) and run again. If the menus come back, it's #736, and the fixes being discussed there (e.g. `53e39cc`, measured to restore 285 of the 323) are the ones to try. If they stay black, `git bisect start ffe310e d2a4bae` takes about 6 steps over the 59 commits in between. A log line `shader does not translate` for the menu's shaders, compared between the two commits, would also point at the cause.

### Comment 2 — @MichaelSmithAI — 2026-11-24T12:51:03Z

Derek checked the proposed #612 revert on `ffe310e` with a source-built shader. On unchanged `ffe310e`, the translator reports the unsupported `s_getpc_b64` both when its result is used directly and when that result passes through two control-flow joins before it controls a branch. With #612 reverted, the direct case still reports it, but the two-join case gets accepted. The regression test is `a_pc_read_stays_missing_through_two_live_joins`. The earlier `53e39cc` candidate also fails that control.

For the RX 6500 XT menu regression, a same-machine comparison of `204bdcc` (the first parent of #612) and `9a92ccf` (the merge), with a separate fresh shader cache for each and the same Series X or S build, would isolate whether the first-boot image changes at #612. If it does, the first missing menu draw and its shader hashes would help narrow the fix while preserving the two-join behavior. We haven't run the title on either revision locally.
