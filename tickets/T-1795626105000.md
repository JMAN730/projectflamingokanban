## Original body

**No game data here.** Offsets, counts, register values and our own analysis only — no decompiled listing, no game bytes.

## Setup
- Windows 11, **NVIDIA GTX 1660 SUPER (6 GB, Turing)**, driver current, Ryzen 5 5600, 32 GB RAM
- VIctory `ffe310eb` (`main`), `cargo build --release -p victory`
- `victory run <exe> --execute`, own 1.0.2.1 package; exe SHA-256 `e95020b2…` (the one in #630)
- No diagnostics variables except `VICTORY_D3D12_DRED=1` for one run

## What happens
1. Boots; first-boot screens and menus run at a stable 30 fps.
2. Loads the world — `ttdb` data and `core_*` archives open, ~150–288 frames presented, the title reports `Game State: Game Running`.
3. About **12 s into Game Running (frame 106)** the title kills itself: `0x80000003` at the title image **`+0x1330a44`** (fault on several threads).

## Not memory, not pools, not BCPack
- DRED enabled: no `E_OUTOFMEMORY`/`0x8007000E`, no device-removed report, and `GetResourceAllocationInfo` sizes are small (the title never allocates more than a couple of MB per texture here).
- The title's own crash report (`temp\*.crash.log`) shows **every pool `0/0`** (INSTANCE_LIST 0/0) and `TileHeap: used 271 / total 6236 MB` — so this is not #698's pool overflow.
- `bcpack_mb=0`: BCPack never ran in this run.
- No `runtime API area not implemented` (the runtime areas the title queried are all implemented).

## Where it stops (measured)
`+0x13308e0` is a streaming range-decompress: it decodes a stream in chunks and calls the dispatcher `+0x1330a50`; when the dispatcher returns 0, the caller executes `int3`. The dispatcher returns 0 in exactly three cases:

1. no codec provider — `[inst+0x50] == 0`;
2. bad codec id — `[inst+0x58] == -1`;
3. the chunk guard fails.

A live read at the fault (best-effort `VirtualQuery`-guarded deref of the registers in our crash handler) shows:

| field | value |
|---|---|
| stream instance `[param_2+0x10020]` | `0xd153c0e00` |
| provider `[inst+0x50]` | `0xd1596b80` (**present**) |
| codec id `[inst+0x58]` | `0x70817` (**not -1**) |

so it is **case 3**. The guard compares the bytes to produce against the destination descriptor `param_1[8] = [inst+0x40]`:

- **bytes to produce** `param_1[1] = 0x10000` (65536)
- **destination descriptor** `[inst+0x40] + 8 = 46586`, `+ 0x20 = 4096`

`46586 < 65536` → the guard refuses, the fallback handler (`[handler+0x30]`) also returns no, `+0x1330a50` returns 0, and the title asserts. In short: **the title asked for a 64 KiB decode into a destination buffer with 46,586 bytes left.**

For reference, `+0x1330ad0` (same provider object) queries codec ids `0xba180afb232d1b4b`, `0x33f70dfaf2c50989`, `0x4eaa16dd829995bc`, and the dispatcher's main path uses `0xe0c12d7a5d4884c5`. If those ids are yours, naming them may name the stream (world streaming vs. something else).

## Secondary (may or may not be related)
Two host textures are refused just before, both `0x80070057`:
- a **2560×1440 BC7** (format 86) with `ALLOW_RENDER_TARGET|ALLOW_UNORDERED_ACCESS`, `mips 1`;
- a **format 115** texture with `ALLOW_RENDER_TARGET`.

D3D12 rejects a UAV on a BC format, so the first is expected to fail — flagging it in case the title relies on that resource later.

## Ask
Who owns the destination descriptor at `[inst+0x40]`, and what sets the 65536-byte decode request? My read is that the two should agree and one of them is being computed from state we may be feeding wrong. Happy to run any instrumentation you want (I have a diagnostics build and a working crash-report walk).

Verified in my copy of the hash-pinned image and registering it on the shared map (Marvisak/VIctory#630) as the **sixth deliberate stop** — plus the decode of what it actually asks:

- **The predicate is `+0x1330a50`**, not your fault PC: it loads an interface from `[obj+0x50]`, takes a u16 field at `[obj+0x58]` (sentinel `0xFFFF` = pass without asking), then issues **`call [vtable+0x3f0]` with a 128-bit key `0xe0c12d7a5d4884c5` as the query id** — a *capability question to another component*, whose owner answers no → `test al,al / je → int3`. So the fix lives with whoever services slot `0x3f0` in your runtime: the honest answer for a 64 KiB decode buffer is what removes the stop.
- The tail is the same **report-then-dispatch** pattern as the 2 MiB cap: three int3 variants (`+0x1330a44`, `+0x1330a4a`, filler) each paired with a `jmp` to a different return path (`+0x13309e3` / `+0x1330976` / back-edge), reporting via `+0x4ec6670` / `+0x4ec6720` — a **different reporting routine** from the `0x4e9b660` family, which says the title classifies decompressor pre-failures separately. Your patched-prefix knob (#917) makes the confirmation cheap: NOP the taken `int3`, see which `jmp` continuation the run survives.
- **Sibling cross-check, two-sided:** (1) our runtime answers this scenario with an *error*, not a suicide — the DirectStorage request validator (`dstorage.rs`, `E_DESTINATION_SIZE = 0x8924_000F`) rejects undersized destinations (`destination_size <= source_size` etc.) and the title degrades instead of killing itself, which is evidence the slot-`0x3f0` "no" is survivable in principle. (2) Heads-up from the same shader-corpus work: our instruction spec has **zero coverage for `v_mad_u32_u16`, `v_mad_i32_i16`, `v_lerp_u8`** — the exact trio of your #1068 — so if the title contains them (check your corpus counts the way you did for the 16-bit compares), they land in our BC-refusal-class gap list and we want the synthetic vectors shared either way.

### Comment 3 — @roon9e — 2026-11-24T17:30:46Z

**Runtime confirmation of the slot-`0x3f0` predicate, from a run that reaches the stop in the title (own 1.0.2.1 copy, SHA-256 `e95020b2…`, Xbox Series build, VIctory main + PR #189, Windows 11, **GTX 1660 SUPER 6 GB, 32-lane waves**). No game data below — RVAs and our own object walk only.**

The assert fires at `title+0x1330a44`. At that instant, walking from the faulting thread's registers (`rsi` is the stream instance; every read is `VirtualQuery`-guarded):

```
exception 0x80000003 at <title>+0x1330a44
  [walk rsi] reg=<stream> +0x10010=0 +0x10018=65536  inst=<heap>  prov=<heap>  cid=(unreadable that instant)
  [inst] +0x0=<stream> +0x8=0x10000 +0x10=0 +0x18=<heap> +0x20=0x1000 +0x28=0 +0x30=0
  [prov<rsi>] vtable=<title>+0x62fd480            ; the provider's vtable is the title's own .rdata
  [inst+0x40] -> +8=46586 +0x20=4096 ; [inst+8]=65536
```

So, as you decoded: `inst = [stream+0x10020]`; `prov = [inst+0x50]`; the query `prov->vt[0x3f0](prov, key, codec_id)` decides. **The provider is a title object — its vtable is `<title>+0x62fd480`, all its methods are title code — so the "no" is title logic over title data**, not a runtime object we can substitute.

Following that vtable site by site:

- `vt[0x3f0] = title+0x28ce0a0` → `title+0x28ce1b0` *(`this = prov+0x28`)*: it linear-searches a table of `0x18`-byte entries (`[this+0x20]`, count at `[[this+8]+0x20]`) for the **64-bit interface key** you named, and on a hit calls
- `title+0x144db65b0(this, codec_id, index)`: reads a **per-codec entry** from a table at `[this+0x28]` or `[this+0x38]` (`title+0x144db6600` does `entry = table[(class_count)*index + slot]`, width from a size-class byte), and
- an entry of `0xffff` (`u16` class) or `0xff` (`u8` class) makes `0x28ce1b0` return **0**, i.e. unsupported → `test al,al / je → int3` at `0x1330a44`.

So the condition is: **the interface key is found, but the codec id's entry in that table is the `0xffff`/`0xff` "absent" marker.** That is the "honest answer for a 64 KiB decode buffer" question.

Two things I can't resolve from the image alone, which is why I'm posting here:

1. **What populates `[prov+0x28]`'s tables.** They are heap; the provider object is built at run time. Is that table the title's *codec registry* filled from the GPU/subsystem capabilities it probed earlier — i.e. does a codec go in only when some earlier capability answer was "yes"? If so, the real fix is upstream of this stop (whatever makes the title register — or not — the codec), and the `int3` is just where it surfaces. A `dump` of `prov+0x28..+0x60` before and after the subsystem-ready gate would say which.
2. **The codec id at `[inst+0x58]`.** It was unreadable in the same instant (the object is being mutated by the decoding thread); a snapshot taken while the thread is suspended would pin it. Knowing the id would name which codec's entry is `0xffff`.

For the sibling runtimes: this is a *title-side* capability table, so the equivalent of xcl's `E_DESTINATION_SIZE` degrade happens one level down from where I first filed it — the stop is "codec id not present in the provider's table", not "destination too small", even though the 64 KiB/46,586 mismatch (`[inst+8]=0x10000` vs the destination's `46586`) is real and visible in the same `[inst]`.

Also worth carrying to the map (#630): VIctory **main emits `WaveSize(64)`** for lane-dependent compute, and this Turing host reports `wave_lane_max=32`, so those pipelines cannot be created at all; **PR #189** (default `<64`-lane hosts to `Emulate`) fixes that class (it now logs `wave64_mode=Emulate`) — but it does **not** move this stop, which is why the provider table above is the next question.
