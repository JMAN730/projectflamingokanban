## Original body

## What's wrong

Microsoft's GDK documentation for [`XGameUiTextEntryInputScope`](https://learn.microsoft.com/en-us/gaming/gdk/docs/reference/system/xgameui/enums/xgameuitextentryinputscope) specifies for `Password` (`31`):

> This will be a fully localized keyboard where the textbox hides characters as the user types.

In VIctory, `text_entry_async` ignores the input scope parameter (`crates/victory-hle/src/modules/xgameui.rs:60`, `_scope: u32`) and never passes it to `ask` (`crates/victory-hle/src/modules/xgameui.rs:66`). The Win32 dialog template in `dialog::ask` always builds the edit control with `wm::WS_BORDER | tab | wm::ES_AUTOHSCROLL as u32` (`crates/victory-hle/src/modules/xgameui.rs:176-177`), without `ES_PASSWORD`.

Concretely, calling `XGameUiShowTextEntryAsync` with `inputScope = XGameUiTextEntryInputScope::Password` (`31`) and typing `"abc123"` displays `"abc123"` in clear text instead of masking the characters.

## Impact

Anyone looking at the screen sees a password a title asks the user to enter. Whether GTA VI uses the `Password` input scope is unknown.

## Fix

Define `const PASSWORD: u32 = 31`, pass `scope == PASSWORD` into `ask` as `password: bool`, and OR `windows_sys::Win32::UI::WindowsAndMessaging::ES_PASSWORD` into the edit control's window style when `password` is true (factored into `dialog::edit_style(password: bool) -> u32` and covered by a unit test). Open PR #370 also renames `_scope` to `scope` and defines `const PASSWORD: u32 = 31` for length-limit handling; keeping the same parameter name and constant lets both changes combine cleanly so `text_entry_async` passes `scope` to the limit logic and `scope == PASSWORD` to `ask`.

The fix is ready on a branch of my fork, since PR creation is limited to collaborators: https://github.com/BastienRodz/VIctory/commits/hle/password-entry-hides-characters (one commit on `main` `ffe310e`, `xgameui.rs` +53/-8).

## Tests

`a_password_entry_hides_what_is_typed` checks the edit-box style:
- without `password`: `WS_BORDER | ES_AUTOHSCROLL`, no `ES_PASSWORD`;
- with it: the same plus `ES_PASSWORD`.

On `main`, the edit box is always built without `ES_PASSWORD`, whatever the scope.

On GitHub's `windows-latest`, with the upstream CI's commands (clippy `-D warnings` with and without `--all-features`, then `cargo test --workspace --locked`): everything passes; `victory-hle` 95 passed, 0 failed (https://github.com/BastienRodz/VIctory/actions/runs/45401505829).

**Not tested:** the dialog shown interactively; a title that uses the `Password` scope.

No game data used. AI-assisted: found with GPT-6.2 Astra, written with Gemini 4 Neon, reviewed and verified with Claude Code.
