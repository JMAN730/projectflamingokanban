## Original body

Shaders that fail translation are translated again in every run. `shader_cache.rs` stores only successful translations: `Translate::convert` returns the error and `victory-pipeline`'s cache keeps only `Ok` results. A program that fails therefore fails again on the next start, with the same input and the same result.

**Measured** on an RTX 3060 Ti, own 1.0.2.1 copy, five warm runs of one build:
- About 400 programs fail translation in each run. 405 of the 408 failures in one run also failed in the run before.
- The big compute ones fail 64–96 KiB into their code and take 2–3 s each on the 6 creation workers.
- For about 1.5 min after world entry the workers do nothing but re-fail them. The per-frame summary shows 150–270 pipelines "being made" in every warm run, and their draws are dropped until the queue drains.

**Why caching the error is safe:** translation is a pure function of the container and of what `build()` already hashes (our executable and the loop limit). The same key gives the same error. A new build changes the key, so it tries again, and so does a new loop limit.

**Change** (one file, `crates/victory-gpu/src/shader_cache.rs`):
- `convert` stores a failed translation as a `VSF1` entry (magic, then the error text) under the same key.
- `cached` returns `Err(text)` for such an entry and counts it as a hit.
- A damaged `VSF1` entry is treated like a damaged shader entry: it is a miss and is tried again.
- The test assertion "Failures are not stored" is replaced by two tests:
  - `failures_come_back_from_the_cache_too`: a second lookup comes from disk, another build tries again, a damaged entry is retried;
  - `failure_entries_round_trip_and_are_no_shader`.

Branch: [`lines9686-rgb/VIctory@fail-cache`](https://github.com/lines9686-rgb/VIctory/tree/fail-cache) (commit `1c2b2d6`), one commit on `main` `ffe310e`. `cargo test -p victory-gpu --lib shader_cache` passes 4/4, and `cargo clippy -p victory-gpu --all-targets -- -D warnings` is clean. The changed file is `rustfmt`-clean. Other files on `main` show existing `cargo fmt --check` differences, which I left alone.

I checked the three ways this could go wrong and none does: the key holds the build fingerprint, so a rebuilt translator retries rather than trusting a cached refusal; a truncated `VSF1` entry decodes to nothing and is retried as a miss; and nothing outside `host_shader` reads the entry.

### Comment 2 — @pickles976 — 2026-11-24T15:42:14Z

Cross-check from ivall/xcl: **we have this gap twice over**, and your issue is the trigger to write it up on our side. (1) Your exact case: `compile_cached_in_with` on failure only bumps a `counters.failure` — no negative artifact — so a deterministically failing DXC compile re-pays the full compile every run (your measured per-run cost is our cold-boot tail too). (2) A **worse upstream variant** on us: translator refusals (the "`X is not supported`" errors — e.g. your #1062 log's 64-bit image atomic / untracked-mask select) occur **before** the DXIL cache exists, so refused programs are re-emitted from scratch every single launch, forever — our cold-boot time on mesh-storm titles is dominated by re-translating an unchanging refusal set.

The one trap your design (and ours) has to survive: **negative-cache invalidation**. A refusal is only as durable as the capability set that produced it — a translator update (your #1068 trio landing, our BCPack merge turning 512 refusals into successes) must *not* be poisoned by yesterday's marker. So the negative key must include everything the positive key includes **plus** anything capability-shaped: our positive key already folds toolchain identity; a negative entry additionally needs translator/spec revision and any config knob that changes lowering (wave mode, post-#1398: GVN-retry state) — or the strictly safer design: key the marker by the **refusal reason string plus lowering-revision digest** and refuse to trust markers whose digest drifted. If your measurements land per-program refusal timings, share them — on our side the same numbers would justify an xcl issue + a cache-version bump scheme, and both projects should converge on one invalidation story rather than invent two incompatible ones.


### Comment 3 — @lines9686-rgb — 2026-11-24T15:46:44Z

Thanks @adamdotpy for carrying it to #1094 and for checking it.

**Hit-rate wording:** agreed. A second commit on the same branch, [`lines9686-rgb/VIctory@fail-cache`](https://github.com/lines9686-rgb/VIctory/tree/fail-cache) (`HEAD`), counts refusals found in the cache in their own counter. `counts()` now returns `(hits, misses, refusals)`, and the per-frame line in `queue.rs` reports all three. @pickles976, on invalidation: here the key isn't a version number. It's the BLAKE3 of the whole executable plus the loop limit (`build()`). On stacks with #439 it is also keyed by the host's wave-lane range (`key(build(), target)`). Any change to the translator, or to a constant that changes lowering, produces a new executable and a new key, so every refusal is retried once per build. No marker can outlive the translator that wrote it. The one caveat is run-time switches that change lowering without changing the binary. Such a switch has to go into `build()`'s hash, as the loop limit already does. A diagnostics-only switch that changes translation (wave-mode experiments, for example) needs to be added there too.
