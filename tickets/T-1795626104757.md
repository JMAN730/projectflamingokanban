## Original body

﻿## What happens

World load dies with the allocator's own message, not a crash report:

```
memory allocation of 52428800 bytes failed
memory allocation of 182452224 bytes failed
memory allocation of 786432 bytes failed
memory allocation of 70426816 bytes failed
```

Exit `-1073740791` (`0xC0000409`). Nothing in `crashes.log`, which is expected:
the abort/fastfail path does not go through the VEH in `crash.rs`.

The size in the message tracks nothing in the code ÔÇö 50 MiB, 174 MiB, 768 KiB
and 67 MiB are all "whatever was asked for at that moment", and the 768 KiB one
is the tell: a small allocation failing is the commit limit, not a huge buffer.

## Measured

Windows 11, 16 GB, RTX 5060 8 GB, Xeon E5-2680 v4. Release build. Committed
memory sampled every 3 s (`PrivateMemorySize64`, `PeakPagefileUsage`, system
commit):

| t | private | system commit |
|---|---|---|
| 7 s | 7.2 GB | ÔÇö |
| 59 s | 11.3 GB | ÔÇö |
| 111 s | 11.8 GB | ÔÇö |
| 124 s | 15.2 GB | ÔÇö |
| 138 s | 16.8 GB | ÔÇö |
| 141 s | **18.0 GB** | 48.8 GB |

The system commit sits at 48.8 GB of a 49.0 GB limit when it dies. About 29 GB
of that is other processes; the machine only gets there because the page file
was still the old 32 GB (raising it needs a reboot to take effect).

The rise is +6 GB in the last 30 s of the load, while fps goes 23.3 -> 7.7 and
preparing time goes 8.9 -> 15.9 ms of a 129 ms frame.

## Where the memory goes

Not from one place, and the four that showed up first are all in the copy
bridge:

- `shadow.rs` `writing`: the snapshot is grown to span every declared range,
  and growth allocated a second buffer while the old one stayed alive.
- `shadow.rs` `give_back`: the pool kept its eight largest buffers regardless
  of size ÔÇö eight 174 MB snapshots, ~1.4 GB, never shrunk.
- `texture.rs`: each `Staging` kept a `Vec` of the whole texture, forever.
- `dstorage.rs`: `intermediate_size` counted against no limit.

## Patched locally, measured, not enough

Those four are in #472. They build and pass `cargo test -p victory-gpu
-p victory-hle` (130 passed, 1 ignored), but the run still died, now at 67 MiB
with 18.0 GB private. They reduce the slope, they do not remove the ceiling.

Not comparable to earlier runs: those measured the page file (14.3-14.8 GB
peak), these measure `PrivateMemorySize64` (18.0 GB peak), so "did the peak go
down" cannot be read from the two side by side. There are no per-component
counters (pool bytes, scratch capacity, staging bytes) to attribute the growth
to, which is why the four above are a list and not a ranking.

## Why this is not #407

#407 is the fix: one address space, the copies deleted. This is what happens
until stage 2 there lands. Worth keeping the report separate ÔÇö the numbers are
the argument for #407 being worth its cost, and the four bridge leaks are what
a machine without commit headroom hits first.

## To reproduce

`VICTORY_GAME_DIR` at the dump, `victory run <exe> --execute`, sample
`PrivateMemorySize64` every 3 s. It dies between 60 and 180 s, always in the
world load, never in the menus.

## What would settle it

A per-component counter (pool bytes, scratch capacity, staging bytes) printed
with `PrivateUsage` from the existing `K32GetProcessMemoryInfo` call in
`copystat.rs` would turn the list above into a ranking, and show whether the
rest is title memory and shared buffers (`shadow.rs` `shared_buffer`, the 4 MiB
loose windows) which no copy-path patch reaches.
