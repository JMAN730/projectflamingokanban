## Question

Mesh shaders written for 64-lane waves use first-active-lane reads, lane-mask counts and barriers. On a 32-lane host, how do they keep those semantics: by extending the approach chosen for compute, by a scheme of their own, or by being refused? The report below is the evidence.

## Report

## VIctory build

Diagnostics builds based on `820bc3b`, with local capability checks and frame capture. Shader translation was also tested against `28aca3b`, a tree carrying the console-flow approach to wave64 compute. Local package version `1.0.2.1`.

## Environment

Windows 11 build `26300.10075`, Ryzen 9 7900X, GeForce RTX 4070 Ti SUPER, driver `32.0.16.2124`. The D3D12 device reports `WaveLaneCountMin=32` and `WaveLaneCountMax=32`.

## What happened

1. Run a diagnostics build on the hardware D3D12 adapter with `victory.exe run <title-exe> --execute --console series-x`.
2. Advance past loading. With `VICTORY_SKIP_WAVE64=mesh,compute` or a local adapter-aware filter, capture the first 3D scene and inspect the pipeline drop counters.
3. The final output is black. Selected full-scene colour targets are already black or flat before presentation. A warm Series S profile sample also dropped these mesh programs frequently, even though the presented menu and loading screens worked.

Observed mesh shader IDs from VIctory's pipeline log:

| Shader hash | Offline check against `28aca3b` with a 32-lane target |
| --- | --- |
| `db875f50a166bd91` | DXIL validates, no explicit 32-lane contract |
| `6016f52cd61f30f6` | DXIL validates, no explicit 32-lane contract |
| `8ded0d53f8c51e1f` | DXIL validates, no explicit 32-lane contract |
| `cf9ea039f3cdb04d` | DXIL validates, no explicit 32-lane contract |
| `b7a81f5b96f4ca93` | DXIL validates, no explicit 32-lane contract |
| `ef5409053e14aa82` | Translation refuses a lane mask read as data |

All six use wave64 first-active-lane reads, lane-mask counts and barriers. Valid DXIL can still use one first active lane per physical 32-lane wave. Logical lanes 32–63 must observe the first active lane of the entire emulated console wave. Keeping these programs out of submission prevents unsupported execution. The observations do not establish that this accounts for every missing render pass.

## Expected behaviour and validation

Preserve wave64 mesh semantics on a 32-lane host, starting with synthetic coverage where the two halves contain different input values. Verify the first-active-lane result and exported vertex, primitive or index data on RTX before enabling the affected real pipelines. Then compare the G-buffer on the same machine with the same settings.

Related work elsewhere: a report of partial geometry on an RTX 5080 with a different stack and a remaining device hang; a console-flow approach to wave64 compute; and a change that refuses wave64 programs on hosts without 64-lane waves.

Only textual diagnostics are included.
