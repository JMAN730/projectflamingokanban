## Original body

Four open PRs lower the same instructions (`ds_read_{u,i}{8,16}[_d16[_hi]]`, `ds_write_b{8,16}[_d16_hi]`). All four are based on main `ffe310e`. I measured them the same way so review can pick one and close the others. I wrote #116, so I tried to measure all four by the same rules.

### On a retail dump (`victory translate --validate --list`, dxil.dll 10.0.26100)

| | validated | gained vs main | lost |
|---|---:|---:|---:|
| main `ffe310e` | 21,736 | | |
| #101 | 21,752 | +16 | 0 |
| #571 | 21,752 | +16 | 0 |
| #632 | 21,750 | +14 | 0 |
| #116 | 21,752 | +16 | 0 |

- All the gains are compute programs: 9 were refused for `ds_write_b16`, 7 for `ds_read_u16`.
- #101, #571 and #116 gain the same 16 programs.
- #632's 14 are a subset. The other 2 use `ds_read_u16_d16_hi`, which #632 refuses on purpose ("an LDS read into half a register").
- No PR loses a program that validates on main.

### On hardware, one form at a time

I ran #116's `lds_tests` against each PR's lowering, with the same tests and a per-form filter. This ran on an RTX 5060 Ti and on WARP, 64 lanes. The tests check:
- each read form at every byte or halfword address of two dwords, and that `_d16`/`_d16_hi` keep the other half of the register;
- each write form, with the dword read back;
- 64 lanes writing their own bytes or halves of shared dwords, where no write may be lost.

| | 4 plain reads | 6 d16 reads | 4 writes | shared dwords |
|---|---|---|---|---|
| #101 | pass | pass | pass | pass |
| #571 | pass | pass | pass | pass |
| #632 | pass | refused (by design) | pass | pass |
| #116 | pass | pass | pass | pass |

### Each PR's own tests (`cargo test -p victory-shader`)

- main: 120 passed.
- #101: does not compile on `ffe310e`. Its test calls `resource::track` with 3 arguments; main now takes the structure as a 4th.
- #571: 124 passed.
- #632: 123 passed.
- #116: 125 passed.

### Differences that the numbers don't show

- **Unaligned halfwords.** #571 handles a halfword at byte 3 of a dword: it reads across into the next dword, and writes into it with a second pair of atomics. The other three assume halfwords are 2-aligned. The cost in #571 is that every 16-bit access goes through 64-bit arithmetic (`flags::INT64`) and a second load. Every `ds_write_b16` becomes four atomics, aligned or not.
- **Concurrent writes.** All four write with an atomic and to clear the bits, then an atomic or to set them. So lanes that write other bytes of the same dword keep theirs, and the shared-dword test passes for all four.
- **d16 reads.** #632 refuses them, so it misses 2 programs in the dump. The other three keep the other half through `inst.read` of the destination. That works on main because the IR already records every vector instruction's destination as a read. The extra read #116 adds in `ir.rs` is redundant, and I'll drop it from #116.

No game data, shader bytes or shader names are included here. The counts come from a local dump.

### Comment 2 — @MoonYueya — 2026-11-24T18:20:48Z

Useful comparison — the per-form hardware runs are the part that decides between #101, #571 and #116, which the validated counts alone cannot.

One implementation choice that is orthogonal to which PR you pick, in case it helps settle the write side. `ds_write_b8` / `ds_write_b16` update *part* of a dword, so a plain store clobbers the neighbouring bytes; and `ds_read_u8` / `ds_read_i16` and friends read a sub-range and sign-extend for the `i` forms. We express the partial write as a masked read-modify-write:

```
shift = (address & 3) * 8;   mask = (1 << bits) - 1;
InterlockedAnd(slot, ~(mask << shift));
InterlockedOr (slot, (value & mask) << shift);
```

and the read side as `(slot >> shift) & mask`, sign-extended for the signed forms. The atomics are not for concurrency — they are the portable way to say "write these bits, leave the others" on a `groupshared` slot without a second pass.

Two things we would check in whichever PR wins, because both are easy to get subtly wrong and neither shows up in a validated-program count:

- **`_d16` / `_d16_hi` must leave the other half of the destination register untouched.** #1343 already notes #632 refuses `ds_read_u16_d16_hi` on purpose — that is the right call for a partial implementation, but it means the winning PR needs the "keep the other half" test as a first-class case, not a rounding-up.
- **Sixty-four lanes writing their own byte or half of shared dwords, with no write lost.** #1343 lists this test and it is the one that would catch an implementation that serialises per wave by accident.

*(AI-assisted write-up, checked against our own LDS lowering.)*

Context: failure measurements in #1481.
