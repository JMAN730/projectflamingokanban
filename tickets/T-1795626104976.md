## Original body

PR creation is limited to collaborators, so this is a branch ready to merge: [EduAzevedo/VIctory@diag/black-frame-tail](https://github.com/EduAzevedo/VIctory/tree/diag/black-frame-tail) (one commit, `2e2f167`, on top of `ffe310e`).

### Why

The black-frame trace (`VICTORY_LOG=info,victory_gpu::draw=debug`) kept a frame's **first 256 draws**. A world frame runs thousands, so the trace stopped in the geometry passes and never reached the lighting, composite and full-screen draws that end the frame, which is what a black picture (#850, #293) is about. In a run on `integration/testers` every black frame in the world was cut at 256 lines, all of them G-buffer mesh draws.

### What

- The trace keeps the **first and the last half** of the limit, with one line in between: `... N draws not kept here (VICTORY_BLACK_FRAME_DRAWS raises the limit)`.
- `VICTORY_BLACK_FRAME_DRAWS=<n>` sets the limit (default 256, as before; at least 2). Documented in the README's diagnostics table.
- The `DROPPED` mark still goes on the draw traced last, when it was kept.
- Diagnostics builds only; release builds are unchanged.

### Tested

- `cargo test -p victory-gpu --lib`: 53 passed, 0 failed, 1 ignored, including three new tests (`frame_trace_tests`: a short frame is kept whole; a long frame keeps both ends and counts what was left out; the drop mark lands on the last kept draw and not on one left out). No GPU needed.
- `cargo clippy -p victory-gpu --all-targets -- -D warnings`, with and without `--features diagnostics`: clean. `cargo xtask policy`: 154 files ok.
- In the title: RTX 2070 SUPER (driver 610.88), Windows 11 26200, diag build of `ffe310e` + #493 + #189 + #206 with this commit, `VICTORY_SHADER_LOOP_LIMIT=32`. Two black frames in the first world minutes now read `... 106 draws not kept here` and `... 1,108 draws not kept here`, followed by the frame's last 128 draws (shadow and 2560x1440 passes and their drops), which the old trace never showed.

No game data in this PR.
