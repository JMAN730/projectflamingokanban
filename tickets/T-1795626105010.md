## Original body

On an NVIDIA RTX 4060 Laptop the title boots, plays the intro and reaches the opening credits over the first mission, then the device hangs (TDR, `DXGI_ERROR_DEVICE_HUNG`) a few minutes in. A diagnostics build with `VICTORY_D3D12_DEBUG=1` and `VICTORY_D3D12_DRED=1` shows two NVIDIA-specific problems that probably don't show up on the RX 6700 XT the README mentions:
111 compute shaders request a wave lane count of 64; the device maximum is 32. The D3D12 runtime rejects them and VIctory logs `host pipeline refused … (0x80070057)` 107 times, so those dispatches are dropped.
The descriptor heap is capped at 1 000 000 (the title asks for 1 245 184), followed later by `no free dynamic descriptor slots`.
DRED output for the hang is included below. Full diagnostics log attached (`victory-diag.log`, Windows user name redacted, ANSI colour codes stripped; Russian system messages are from the localized OS).
Environment
	
VIctory	diagnostics build (`cargo build --profile diag -p victory --features diagnostics`), commit `<fill in: git rev-parse --short HEAD>`
OS	Windows `<fill in: winver>` x64
GPU	NVIDIA GeForce RTX 4060 Laptop GPU, 8 GB (hybrid laptop with Intel iGPU)
NVIDIA driver	`<fill in>`
Console mode	Xbox Series X (default)
Output	VIctory reports `presenting to a window width=3840 height=2160`
Run: `VICTORY_D3D12_DEBUG=1`, `VICTORY_D3D12_DRED=1`, `target\diag\victory.exe run <game dir>\game_scarlett_master.exe --execute`
1. Wave64 compute shaders refused on NVIDIA
```
WARN victory_gpu::host: D3D12: ID3D12Device::CreateComputeShader: Shader wants wave lane count of 64 but maximum wave lane count for device is 32. To check for support, check device caps via the CheckFeatureSupport() API id=622 severity=1
WARN victory_gpu::pipeline::host: host pipeline refused error=… (0x80070057) shaders=[compute 13dfdd3b1136e407]
```
111 × the debug-layer message, 107 × `host pipeline refused`. The same refusals (120 of them) also happen in a release build, where the debug layer isn't there to explain them. NVIDIA only supports wave32, so any shader translated with a fixed `WaveSize(64)` can't be created there. A wave32 path, or a check of `WaveLaneCountMax` before requesting 64, would be needed.
2. Descriptor heap cap
```
WARN victory_gpu::descriptor::host: host view heap capped at 1000000 error=… (0x80070057) count=1245184
…
WARN victory_gpu::descriptor::host: no free dynamic descriptor slots: a table is not made n=9
```
1 000 000 is the usual NVIDIA limit for a shader-visible CBV/SRV/UAV heap.
3. The hang (DRED)
```
WARN  victory_gpu::host: slow host submission ms=4477 lists=30 …
WARN  victory_gpu::host: D3D12: ID3D12Device::RemoveDevice: Device removal has been triggered for the following reason (DXGI_ERROR_DEVICE_HUNG …). As a result, the TDR … has been triggered. … id=232 severity=1
ERROR victory_gpu::host: host GPU device removed after a submission of 30 lists; breadcrumbs (done/count, list) [… "91/188 None", "0/1 None", "0/2 None", "0/2 None", "0/200 None"]; a list stopped at command 91 of 188 (op 42), commands 0..188 between its barriers: …
```
The commands the DRED report shows for the list that stopped (`list 6 of 30, of its 26`) are all indirect mesh draws (`indirect kind 10 max 1`) with these pipelines:
`[mesh f9c79a2d484bd75a, pixel a144abbc586fa5b2]` (×3)
`[mesh 1fa93fcea4869fa8, pixel d603540bd3056c4b]` (×2)
`[mesh 66516eaaae261850, pixel 7ce2f1e3371945c7]` (×1)
Their `u8` / `u9` user-data descriptors resolve to `null` in most entries (e.g. `u8=0xa51580 [heap 338092: null] u9=0x165d100 [heap 732808: null]`), and the pixel shaders write UAVs `2048x2048 f28` and `64x64 f61`.
Guess, not verified: if the compute passes that are supposed to write these draws' indirect arguments or descriptors are among the 107 refused wave64 pipelines (or the draws dropped for lack of descriptor slots), the indirect mesh draws may read stale or garbage arguments and spin the GPU into a TDR. The release-build log also has `indirect execution dropped` lines with arguments like `[10, 0, 3273746095, 32763]`.
Other observations
Frame rate after world load: 0.4–0.9 fps. Most of the frame is host-side preparation (copies of 150–450 MB per frame), not GPU time.
Translator gaps logged as `shader does not translate`: the most common are "a select on an untracked mask" (66), "a lane mask holding lanes elsewhere read as data" (64), "a descriptor read only as data" (50), "an address in an SGPR that is no root parameter" (31), "a structured buffer of unknown stride" (27) — all compute.
In an earlier release-build run, one frame took 9.2 s on the GPU without a TDR, and the fatal submission was only 509 ms, so the hang does not look like a plain "frame too slow" timeout.
Happy to rerun with other switches or a test build.

### Comment 1 — @pickles976 — 2026-11-24T15:51:14Z

Cross-runtime datapoint that should collapse this issue: **a wave64 shader on a wave32-max device is not infeasible — it is the normal case for our sibling runtime (ivall/xcl) and every AMD RDNA3/RDNA4 host**, and we have zero refusals for it because the program is *lowered*, not refused: split-wave64 compiles the console wave64 program onto 32-lane waves (the `wave32_only_for_device` decision path, `pso.rs:597` — "device wave range includes/equals 32 ⇒ split", unknown range also splits). RDNA3/4 hardware max is 32, and the ~5-min in-world record runs on a 7900 XTX with the full wave64 corpus lowered, so the 107 pipelines here are translatable, not hopeless.\n\nMechanically your issue is the same root as your #1086 row 2 with the volume knob up: with wave64 emulation off, NVIDIAs advertised max of 32 either legalizes-without-remap (row 2, silent wrong) **or outright refuses at PSO creation** (this issue, loud) — one policy decision producing two symptom classes. So the A/B to run on this exact host is the same one: `VICTORY_WAVE64_EMULATE=emulate` should take these 107 refusals toward zero the way our split path does; if it only fixes some of them, the remainder is a second, genuinely translation-gapped class worth splitting out of the 107.\n\nFor your project-level decision (#1086 argued the default): this corpus is the evidence that native Wave32 default costs *both* classes at once — silent corruption where the driver legalizes and mass refusals where it does not. One honest line in the refusal text ("wave 64 > device max 32 — wave64 emulation off; see #189") would have made this report a config question instead of a hardware-mystery week.
