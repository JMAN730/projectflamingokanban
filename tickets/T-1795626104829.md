## Original body

## Summary

Title: GTA6 Xbox build `1.0.2.1` (`game_scarlett_master.exe`).
The title reaches the main menu and renders it at 30 fps, and it loads into the world
(the world's pipelines translate and thousands of draws are issued per frame), but the
host GPU device is then removed with `0x887A0004` / `0x887A0006` after 60–150 s. With
`VICTORY_D3D12_DRED=1` the removal reports a page fault inside an already **freed**
texture, plus descriptor handles past the end of the view/sampler heap.

## Build

- VIctory at `8e79c80` (`8e79c80e4b71e252bcd271e0587aa662c4770008`).
- `cargo build --release` and `cargo build --profile diag --features diagnostics`, both clean.
- One local patch: Agility SDK opt-in (`D3D12Core.dll` 1.620.2 in `D3D12\` next to the
  exe, `D3D12SDKVersion = 620`, `D3D12SDKPath = .\D3D12\` exported via `build.rs`).
  Needed because Windows 10 19045's inbox `d3d12.dll` rejects the title's
  `CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED | SAMPLER_HEAP_DIRECTLY_INDEXED` root signature
  flags (`root signature: Unsupported bit-flag set`).
  With 1.722.1-preview / version 722 I get `0x887E0003`; 1.620.2 / 620 works.

## System

- Windows 10 Pro 22H2, `10.0.19045`.
- AMD Radeon RX 6900 XT (`0x73bf`), driver `32.0.21045.29003` (26.11.2, 2026-11-17).
- 6 cores / 12 threads, 31.1 GB RAM, pagefile 8 GB on C: + 64 GB on E: (commit limit 99.1 GB).
- `victory.toml`: `game_dir` = the title, `cache_dir`/`data_dir` on E:.

## Reproduction

```
victory.exe run "<...>\game_scarlett_master.exe" --execute
```

`VICTORY_KEYS` (diag build) advances the menus: legal notices → first-run wizard →
ToS → world. Menu renders fine, 30 fps, `drawn = 5376/5376`.
World entry: frames take 1.5–2.1 s, `drawn` 1135–4703, private memory 23.6–24.3 GB,
`Srv s0+40: placed dim 1 42991392x1`, then the device is removed.

## What did *not* fix it

- `VICTORY_COPY_MODE=none`: removed after 4 lists.
- `VICTORY_COPY_MODE=plain`: crash inside the menu.
- `VICTORY_SHADER_LOOP_LIMIT=64`: 0 fps.
- `VICTORY_D3D12_DEBUG=1` + `VICTORY_GPU_TIMING=1`: removed at frame 1337.
- Snapshot pool 8 → 64: page faults 661k → 841k, removed at world entry.
- Splitting submissions into bundles of 8 lists (each submission then waits ~371 ms):
  still removed, after a submission of 27/16/30 lists — so this is not "submission too long".
- `VICTORY_SKIP_PIPELINES=0184869d6e47e5fa` (a compute pipeline that shows up in every slow
  submission): still removed.

## Reading

Two separate things point at **descriptor liveness** rather than at data content:

1. The fault address lies inside a texture that was already freed. Some draw or dispatch
   that runs later still holds a descriptor (or a directly-indexed slot) for it.
2. `view heap ... slot 566987264` / `sampler heap ... slot 1139159808` are absurd slot
   numbers derived from a handle (or from a value read out of title memory as a handle),
   i.e. a descriptor table is being built from a stale/garbage index rather than from a
   live allocation.

Question: is "resource freed while a submitted draw still references it" a known gap for
this title — e.g. the title frees a render target between frames and we still execute the
previous frame's list against it, or a dynamic-descriptor slot gets recycled while a
descriptor table built earlier still points at it? Anything you would like me to dump
(`VICTORY_DUMP_TARGETS`, per-draw descriptor tables, `VICTORY_CRASH_SAVE`) to pin it down?

I have the full `run30` log (breadcrumbs of all 30 lists, heaps, the freed allocation
report) and can paste it or attach it.

## Original comments

### Comment 1 — @MartinIndra02 — 2026-11-24T10:15:35Z

Two quick pointers on the DRED output:

1. **Freed texture page fault (`inside freed ["texture 1024x1024 f83 ..."]`):** yes, this is a known lifetime gap on `main` — PR **#431** (`GPU: free host textures only after running submissions, and make them on first use`) specifically addresses host textures being freed while a recorded/submitted command list still references them.
2. **`view heap ... 0x436914000 past its end (slot 566987264)` / `sampler heap ... slot 1139159808`:** those aren't garbage descriptor indices — DRED's reporter just prints the byte offset from each descriptor heap's GPUVA to the faulting address (`0x104fa0000 + 0x2e00000 + 0x436914000 == 0x53e6b4000`, the freed texture's address). So the fault itself is the freed texture, not an out-of-bounds heap slot.

*No game data; AI-assisted.*


### Comment 2 — @Sunkiller-qc — 2026-11-24T12:54:15Z

Same signature as #557 (device removed, page fault "inside freed" a 1024x1024 texture during world rendering). The latest results there change the picture: h0useadv found that the faulting texture had no view at all, and that the fault is most likely a read past the end of a 4 MB title-memory host copy. The freed texture is just whatever was at that address before. KingKaom confirmed it on RDNA4.

So #431 alone may not fix this. Your log would be more useful on #557, and I'd close this as a duplicate.
