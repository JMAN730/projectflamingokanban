## Original body

### What's wrong
The driver compiles host pipelines on VIctory's pipeline worker threads (`victory-pipelines-N`, `crates/victory-gpu/src/pipeline/make.rs`). Those threads use Rust's default 2 MB stack.

On an RTX 5080 (driver 32.0.16.1692), NVIDIA's compiler recursed past that while creating a world compute pipeline:

```
thread 'victory-pipelines-4' (1400) has overflowed its stack
VIctory: first-chance exception 0xc00000fd at ntdll.dll+0x55b00
  #6  nvgpucomp64.dll+0x63413f
  #7  nvgpucomp64.dll+0x1588d86
  #8  nvgpucomp64.dll+0x254c38b
  #9… nvgpucomp64.dll+0x254c175 / +0x254c362, repeating
WARN victory_gpu::pipeline::host: host pipeline refused error=Not enough memory resources are available to complete this operation. (0x8007000E) shaders=[compute c7d7a6283fad3cd6]
```

The driver catches the overflow and reports it as `E_OUTOFMEMORY`. The program's dispatches are then dropped every frame. The `E_OUTOFMEMORY` refusals after a first-chance exception in `nvgpucomp64.dll` reported on #233 and #334 may have the same cause on some drivers.

### Fix
`GPU: pipeline workers get a 64 MB stack for the driver's compiler`
- Branch: https://github.com/Peppacodes/VIctory/tree/fix/pipeline-worker-stack
- Compare: [main...Peppacodes:VIctory:fix/pipeline-worker-stack](https://github.com/Marvisak/VIctory/compare/main...Peppacodes:VIctory:fix/pipeline-worker-stack)
- Commit: `d09c31b`, on `main` (`ffe310e`). One file, +8 lines: `Builder::stack_size(64 << 20)` on the workers.

A 64 MB stack is reserved address space; only the pages the compiler actually uses are committed.

### Result
Same game build and scene on the RTX 5080. The tree is #940's branch plus #587 and #452.

| | Stack overflow | `c7d7a6283fad3cd6` |
|---|---|---|
| 2 MB workers (run 20) | yes, at frame ~1420 | refused, `0x8007000E` |
| 64 MB workers (run 21) | none | `host pipeline shaders=[compute c7d7a6283fad3cd6]` |

### Checks
Run on the branch itself (`main` + this commit), Windows 11, Rust 1.98.1, with the CI's commands:
- `cargo test --workspace --locked --no-fail-fast`: 342 passed, 0 failed, 6 ignored. `frame::tests::waits_end_on_ticks_and_count_frames` failed once in a first run under load and passed three times alone; #689 is about that test.
- `cargo clippy --workspace --all-targets --locked -- -D warnings`, with and without `--all-features`: clean.
- `rustfmt --edition 2024 --check` on `make.rs`: no new differences (the file has the same 3 on `main`).
- `cargo xtask policy`: 154 files ok.

### Not checked
- Which program shapes trigger the recursion, and whether other drivers need more than 64 MB.
- Whether the other `std::thread::Builder` threads in `host.rs` ever run the driver's compiler.

No game files used. AI-assisted (Claude Code).

```rust
#[link(name = "kernel32")]
unsafe extern "system" {
    fn GetCurrentThreadStackLimits(lo: *mut usize, hi: *mut usize);
    fn VirtualQuery(at: *const u8, info: *mut Mbi, len: usize) -> usize;
}
/// MEMORY_BASIC_INFORMATION (x64).
#[repr(C)]
#[derive(Default)]
struct Mbi {
    base: usize,
    allocation_base: usize,
    allocation_protect: u32,
    partition: u16,
    region: usize,
    state: u32,
    protect: u32,
    kind: u32,
}
/// Bytes of this thread's stack committed so far. Stack pages are committed
/// on first touch and never given back, so this is the deepest it has been.
fn committed_stack() -> usize {
    let (mut lo, mut hi) = (0usize, 0usize);
    // SAFETY: plain queries on our own stack.
    unsafe {
        GetCurrentThreadStackLimits(&mut lo, &mut hi);
        let mut at = lo;
        while at < hi {
            let mut m = Mbi::default();
            if VirtualQuery(at as *const u8, &mut m, size_of::<Mbi>()) == 0 {
                break;
            }
            // MEM_COMMIT and not PAGE_GUARD: the lowest page in use.
            if m.state == 0x1000 && m.protect & 0x100 == 0 {
                return hi - at;
            }
            at = m.base + m.region;
        }
    }
    0
}
```
