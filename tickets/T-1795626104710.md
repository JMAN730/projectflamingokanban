## Original body

Follow-up to #16, which was closed after #21. On NVIDIA the menus are fine now; the world still hangs. I narrowed it down with four diag runs: the hang is not one program, not translated loops and not group barriers.

## Setup

RTX 5070 Ti, driver 621.01 (32.0.16.2101); Ryzen 7 9800X3D, 32 GB; Windows 11 Pro 26200. `main` at `97c78d1`. Diag build (`--profile diag --features diagnostics`), `VICTORY_D3D12_DRED=1`, no input. Xbox Series 1.0.2.1, `build unknown (b99f876b…)` as in #5.

## What happens

Since #21 the menus and loading screens run at 30 fps without flicker. The title then loads into the world (1–6 fps), and about 20–75 s later the device is removed with `0x887A0006` (DEVICE_HUNG). One `slow host submission` of about 4.8–6.9 s comes right before it, and DRED reports no page fault. So this is a TDR on work that never finishes.

## Narrowing it down

Each row is one run with one change, using two local switches (patch below) and the switch from #46:

| Change | Hang? | Where DRED stops |
|---|---|---|
| none (`1dd7afd`) | yes | `command 148 of 175 (op 42)`, commands 107..175: mesh `6b57e37fe499c6e7`/`573d1857e903fab5`, `1921f28ef78e3a4b`/`80b3065a4477c8c4`, `0f73a9ae763e96e2`/`ce1481325c93bb70` |
| #46, `VICTORY_SHADER_LOOP_LIMIT=4096` | yes | the same pass, `command 138 of 155 (op 42)`, same three pairs |
| `VICTORY_SKIP_SHADERS=` those three mesh programs | yes | `command 280 of 302 (op 42)`, commands 279..301. It stops at the first command after the barrier: mesh `51ff151f75cd5759` / pixel `7fe75645c406cac6` |
| `VICTORY_SKIP_SHADERS=mesh` (every mesh dispatch dropped) | yes, after about 75 s at a steady 5 fps | `command 187 of 419 (op 6)`, commands 126..206: dispatches of compute `d3e44e754b3eb6aa` (a release run on `d222b87` also hung in a compute-only submission with this program in it) |
| `VICTORY_SHADER_NO_BARRIERS=1` (every translated `s_barrier` left out) | yes | `command 354 of 496 (op 42)`, commands 337..495: mesh `857b2e13c9cc107f` / pixel `63051e97862e7dad` (after a run of `51ff151f75cd5759`) |

What the runs show:
- **It is not one program.** Dropping the suspect mesh programs moves the hang to other mesh programs. Dropping all mesh dispatches moves it to a compute pass.
- **It is not translated loops.** A limit of 4096 hangs in the same place.
- **It is not group barriers.** With every `s_barrier` left out, it still hangs in a mesh pass.
- Vertex/pixel-only work (menus, loading screens) has been fine since #21. Only mesh and compute passes hang.

## Possibly related: 77 compute pipelines refused on NVIDIA

Every run I checked (three of them) logs `host pipeline refused error=0x80070057` for **77–78 different compute programs**, and none for other stages. `emit` declares the console's wave size (`WaveSize`) for compute programs that depend on the lane layout (`lower.rs`, `console_lanes || one_wave && lds_dwords > 0`). This NVIDIA card has only 32-lane waves, so I assume these are the `WaveSize(64)` programs. I have not verified that. Their dispatches are dropped, so whatever they write (culling lists, counts, indirect data) is never produced on NVIDIA. That would explain why later mesh and compute passes then run on stale or zero data, which an AMD card (wave64 supported) never sees. If that's right, a wave64 fallback for those programs, or at least zeroing or skipping their consumers, would be where to look.
