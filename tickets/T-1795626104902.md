## What it does

ffe310e handled the console compiler's waterfall loops that sample a per-lane table entry. Its message noted that the programs behind #736 also need per-lane size queries in loops without an access. This commit handles those loops.

The loop: `v_readfirstlane_b32` of the lane's table offset, `v_cmpx_eq_u32`, `s_load_dwordx8` of that entry, `s_bfe_u32` of a size field from the descriptor bits into a VGPR for the matching lanes, `s_andn2_wrexec`. There's no sample or load in it, so nothing proved it a waterfall and every lane got the first lane's size.

- **`resource::track`**: such a load goes through the waterfall proof, with the loop's per-lane VGPR writes standing in for the access. It's only taken when another load of the same entry (same table address, same lane offset) is used by an access, because that access tells the view's kind. Matches are recorded in the new `Waterfall::sizes`. Without such a load nothing changes: the size stays the first lane's.
- **`Lower::descriptor_data`**: when its own load has no access, it takes the view's kind from that other load. The per-lane handle comes from `Waterfall::loads`, as for the sampling loops.

## Tests

- `resource`: tracking tests for the proven size loop and for one with no access to its entry (stays unproven).
- `lower`: both handles read each lane's own entry, and no wave operations are left.
- `waterfall_tests` (GPU, Windows-only): even lanes sample a 1x1 texture, odd lanes a 1x3 one; the result is red plus height − 1.

## Verification

- `cargo test -p victory-shader` passes on Linux (99 tests).
- `cargo clippy -p victory-shader --all-targets -- -D warnings` is clean for `x86_64-pc-windows-msvc`.
- **Not run yet:** the GPU test (needs Windows and D3D12) and the translation census over the title's programs. The synthetic test program follows the loop form described above, not the real programs, so a census run would confirm it covers the 249 programs.

### Comment 5 — @FabianDU — 2026-11-24T12:56:56Z

**Relation to #180:** #180 (c78056c) also handles size-only waterfall loops by taking the view's kind from a twin load. The two are complementary, not duplicates:

- With **#180 alone**, the size loop translates but keeps a real `waveReadLaneFirst` loop (wave operations, tied to the console's wave size).
- With **this change on top**, `resource::track` proves the loop, so each lane reads its own entry's size directly: no wave operations, and the result doesn't depend on the host's wave size.

If #180 is merged first, this change conflicts in one place in `descriptor_data`. The resolution keeps #180's code and adds the proven twin before its own twin match:

```rust
let proven = self.x.res.waterfall.sizes.iter().find(|s| s.0 == site);
let use_at = uses(&|load| load == site)
    .or_else(|| uses(&|load| proven.is_some_and(|s| s.1 == load)))
    .or_else(|| uses(&|load| self.twin_loads(site, load)));
```

With that resolution, `main` + #180 + this change passes `cargo test -p victory-shader` (99 tests) and Windows clippy.
