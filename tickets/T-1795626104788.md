## Original body

## What's wrong

View memory (xmem's physical-page views) is tracked by making 64 KiB blocks read-only (`guard`, `crates/victory-gpu/src/watch.rs:125`). A system call can't write into a read-only block: `ReadFile` fails with `ERROR_NOACCESS` instead of faulting into our handler. So the HLE announces kernel writes first, with `victory_gpu::kernel_will_write`:

- `files.rs:531` and `:539` (`ReadFile`, `fread`);
- `dstorage.rs:954` (DirectStorage reads).

`kernel_will_write` (`writing`, `watch.rs:212`) only opens the blocks. The next `guard()` call covering them, from **any** thread, sees them as written and makes them read-only again. The submitting thread calls it on every refresh. If that happens between the announcement and the kernel's write, the read fails.

## Example

- A title thread calls `ReadFile` into view memory. `kernel_will_write` opens the block.
- Before the kernel writes, the render thread refreshes a buffer covering that block, and `guard()` protects it again.
- `ReadFile` fails with `ERROR_NOACCESS`. DirectStorage returns the error to the title, and `fread` returns short.

The window is as long as the read: an overlapped read, or the whole DirectStorage read loop.

## Evidence

A single-thread replay of the two threads' order, using a real pagefile view and a real file read:

1. Guard the view.
2. Call `writing(view + 100, 13)` (the title thread's announcement).
3. Call `writes(view, view + 2 * BLOCK, true)` (the render thread's refresh).
4. `read` 13 bytes from a temp file into `view + 100`.

On `main` (dd54de2), on GitHub's `windows-latest`, the read fails:

```
the announced kernel read failed: the refresh guarded the block again
```

<details><summary>Test (inside <code>crates/victory-gpu/src/watch.rs</code>'s <code>mod tests</code>)</summary>

```rust
    /// An announced kernel read stays open until it lands.
    #[test]
    fn an_announced_kernel_read_survives_a_refresh_before_it() {
        use std::io::{Read, Seek, Write};
        use windows_sys::Win32::System::Memory::{
            CreateFileMappingW, FILE_MAP_WRITE, MapViewOfFile, UnmapViewOfFile,
        };
        // SAFETY: a pagefile section of two blocks, mapped read-write.
        let view = unsafe {
            let section = CreateFileMappingW(
                -1isize as _,
                std::ptr::null(),
                PAGE_READWRITE,
                0,
                (2 * BLOCK) as u32,
                std::ptr::null(),
            );
            assert!(!section.is_null());
            MapViewOfFile(section, FILE_MAP_WRITE, 0, 0, 2 * BLOCK).Value as usize
        };
        assert_ne!(view, 0);
        assert!(guard(view, view + 2 * BLOCK).is_some());
        let mut file = tempfile::tempfile().unwrap();
        file.write_all(b"from the disk").unwrap();
        file.rewind().unwrap();
        writing(view + 100, 13); // the title thread, in `ReadFile`
        let _ = writes(view, view + 2 * BLOCK, true); // the submitting thread
        // SAFETY: 13 bytes of our view, nothing else refers to them.
        let into = unsafe { std::slice::from_raw_parts_mut((view + 100) as *mut u8, 13) };
        let read = file.read(into).is_ok_and(|n| n == 13);
        // SAFETY: our view.
        unsafe { UnmapViewOfFile(windows_sys::Win32::System::Memory::MEMORY_MAPPED_VIEW_ADDRESS { Value: view as *mut _ }) };
        title_memory_remapped(view, 2 * BLOCK);
        assert!(read, "the announced kernel read failed: the refresh guarded the block again");
    }
```

</details>

## Suggested fix

Count in-flight kernel writes per block in `Guards`:

- `kernel_will_write` increments the count.
- A new `kernel_wrote(at, len)` decrements it. The HLE calls it once the read returns.
- `guard()` reports a block with a nonzero count as written but doesn't protect it.

A cruder alternative on the HLE side: on `ERROR_NOACCESS`, announce again and retry.

## Related

#393, #413, #464 and #490 change `guard` / `title_memory_remapped`, but none keeps an announced block open.
