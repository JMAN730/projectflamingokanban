## A configuration that gets the world stage running on a 12 GB Windows 10 card, and what each change fixed

Posting this as one place to copy from, because the result took nine stacked changes and four of them
were only discoverable from the others' failures. Everything below is measured on this host with a
diag build; the branch is linked at the end.

### Environment

Windows 10 22H2 UBR 3393 (KB5029331), RTX 4070 SUPER 12 GB (32-lane waves), Ryzen 7 7800X3D, 31 GB RAM,
driver 591.74, title 1.0.2.1, Series X, `--execute`, diag profile.

### The stack, in the order it matters

| # | change | what it fixed | who |
|---|---|---|---|
| 1 | `TdrLevel=3`, `TdrDelay=10` | "the world freezes the whole PC" — with `TdrLevel=0` nothing recovers, so a 1.4 s frame froze the desktop instead of raising a device-removed | registry, see #1054 |
| 2 | `VICTORY_WAVE64_EMULATE=emulate` | **the world pass was never submitted at all**: `recommended_wave64_mode` picks `Wave32` on NVIDIA, which legalises the PSO without remapping lanes, so every cross-lane compute result is wrong and the title's own gating never passes | #189 (`c047885`) |
| 3 | `#729` Agility SDK opt-in | 237 root signatures refused on Windows 10 | #729 (`e6428ad`) |
| 4 | `#940` mesh lane numbering | wave64 mesh code counted console lanes on a 32-lane host | #940 (`e9f68f8`) |
| 5 | `VICTORY_TEXTURE_MIP_DROP=1` | VRAM 11.3 → 10.3 GiB, without which the world stage cannot fit a 12 GB card | #737 (`6c6bbf8`) |
| 6 | mip drop spares textures under 2048 on either axis | the switch turned **every presented frame to flat colour**: the loading artwork is a plain 1920×1080 sampled texture | ours (`e50eaa8`), author fixed it in `4c84a09` |
| 7 | copies routed around dropped mips | `E_INVALIDARG` → invalid command list at frame 1405 (4K copy into a 1×1 texture) | ours (`2097faf`) |
| 8 | 1 MiB windows for title memory outside buffers | RAM 12.6 → 3.7 GB; at 4 MiB each those windows were 1.7 GB of a 31 GB host | ours (`d7d6c58`) |
| 9 | two translator inferences (descriptor read only as data; scalar use points) | 771 → 0 of the largest offline failure class, +231 DXIL programs | ours (`b6a9bdc`, `c8353a8`), issue #979 |

### The result

```
before:  black frame, 97 compute pipelines refused, 353 shaders untranslated, 
         11.3 GiB VRAM, 12.6 GB RAM, desktop freeze on world entry
after:   world stage renders at 2296–3111 draws/frame (1200–1943 indirect),
         0 refused, 0 untranslated, 10.3 GiB VRAM, 3.7–6.6 GB RAM,
         1962 presented frames with no freeze
```

Frame time in the world is 1066–2500 ms (0.4–0.9 fps), which is where this stops being playable.

### What is still in the way, with the measurements

1. **~512 pipelines are recompiled every run.** `made` stays at 502–534 across four runs while
   `loaded` climbs 586 → 705, so the library works but cannot serve that many. #780 describes the same
   symptom (47 on that host). We ruled out translator non-determinism: two independent offline
   translations of the full container dump produce identical counts (26,084 programs; 12,309 / 1,451 /
   8,380 DXIL). The remaining candidates are the fields `GraphicsState::describe()` does not hash
   (`NodeMask`, pipeline `Flags`) and a description the library compares but the name does not cover.
2. **Copies dominate the frame, not compilation.** Our split of one world frame is
   `preparing 530 ms (copies 406 ms) | on the GPU 90 ms`; #400 reports the same shape on a 5070 Ti
   (399 ms preparing, 304 ms of it copies). #407's single address space over title memory is the
   structural fix.
3. 190–233 pipelines are in flight at any moment during the world, which is what the
   `dropped … (N being made)` counters show.

### Code

Branch `try/wave64` on our fork: https://github.com/bittertea0323/VIctory/tree/try/wave64
It is #189 + #940 + #729 + #737 with our six commits on top:

```
6090ffb  gpu: trace every mesh draw
e50eaa8  gpu: mip drop spares textures under 2048 on either axis
d7d6c58  gpu: 1 MiB windows for title memory outside buffers
2097faf  gpu: route copies around mips VICTORY_TEXTURE_MIP_DROP leaves out
c8353a8  shader: a scalar use point infers the descriptor's view
b6a9bdc  shader: a descriptor read only as data infers its view from the binding
```

Happy to open individual PRs for any of them on request; two of the six are already superseded by
upstream fixes (#737's `4c84a09` covers the size floor, our version is the one measured here).

Not measured: whether the 0.4–0.9 fps is dominated by copies or by pipeline compilation moment to
moment; we have the two separately but not their ratio per frame.

All three of your points are right, and one of them needs a correction that only our side could see.

**On default immunity: your direction, and Victory's opposite.**
`recommended_wave64_mode` prefers `Wave32` whenever the device reports wave32 support, and `Wave32`

is the unsafe one. Reporting it as the runtime's choice rather than a user error is the point of

### Comment 10 — @bittertea0323 — 2026-11-24T16:31:54Z

## Two corrections to this configuration, learned the hard way

Both are about item 1 in the list (the TDR change) and about the resolution question this thread left open.

**`TdrDelay=30` is worse than `TdrDelay=10` for our workload.** With the pipeline library warm
(`made=1` via #352) the 13.3 s submission that forced us to raise the delay never occurs again — our longest
world frame measured 1198 ms and the slowest submission 1031 ms. So 30 buys nothing and costs a lot: when the
GPU does hang, the desktop stays unresponsive for the full delay instead of recovering. We sat through a hard
freeze that only ended after the 30 s window. Current setting here is `TdrLevel=3`, `TdrDelay=15` — enough
headroom for every frame we have measured, half the recovery time.

**Forcing the title's 4K is not fixable from the DXGI side, but `VICTORY_FFX_SCALE` does fix it.** The one
place that reports a display mode (`dxgi.rs`, `GetDisplayModeList`) hardcodes a single 3840×2160 entry, and
adding an override there changes nothing: the title builds a 4K window and 4K targets regardless, so
`presenting to a window width=3840 height=2160` still holds. What does work is the PC FSR branch (#730): with
`VICTORY_FFX_SCALE=0.5` and `VICTORY_UPSCALER` forced, the title creates its own **1920×1080** render target
and asks for a 3840×2160 output:

```
render=[1920, 1080] upscale=[3840, 2160] result=0 provider="3.1.6"
world draws  2500 -> 5103 per frame
frame time  1565-1799 ms -> 1034-1199 ms
```

**But the upscale itself does not run yet**, and that is the real stop: the output slot (6) is an XMem
(title-memory) resource, which never gets a host texture, so every `ffxDispatch` returns before the SDK call.
The title then compensates on its own and `copies` climbs from ~142 MB to **569 MB per frame**, which cancels
most of the half-size gain. Net 0.6 → 1.0 fps. Details and the decoded flags are in #730.

So the accurate summary of item 1+resolution for other people copying this configuration:

| setting | effect |
|---|---|
| `TdrLevel=3`, `TdrDelay=10` | correct; keeps a hang recoverable |
| `TdrDelay=30` | harmless but pointless once #352 is in, and a longer freeze when it does hang |
| `VICTORY_MODE=...` (our patch) | no effect: the title ignores `GetDisplayModeList` |
| `VICTORY_FFX_SCALE=0.5` + `#730` | really renders at 1080p (+2× frame time) but the upscale cannot complete on XMem output |
