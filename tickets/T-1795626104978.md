## Original body

Follow-up to #468, as its own report: an A/B matrix on the same RTX 4060 Laptop (8 GB VRAM, 16 GB RAM, driver 32.0.16.2124, Windows 11 26300), to see whether any existing switch or tree gets a picture on an 8 GB NVIDIA laptop. Short answer: none does.

**Setup:** diag builds, `VICTORY_D3D12_DRED=1`, `TdrDelay=60`, same scripted input in every run (`VICTORY_KEYS`: Enter through the menus, then W/L in the world), 330 s per run (about 3 min in the world), captures every 25 frames, dedicated GPU memory and process commit sampled every 5 s. Title 1.0.2.1. No game files or images attached.

- **A** = `main` `ffe310e` + #579 merged locally (clean merge)
- **B** = mpDom `pr/present-1440p-fallback` `d6897fa` (r4tedx `integration/testers` `92bc27b` + `VICTORY_PRESENT_1440P`), built unmodified

| # | Tree | Console | Switches | World fps (median) | Draws/frame | Refused | GPU / commit (max) | World picture |
|---|---|---|---|---|---|---|---|---|
| 1 | B | series-s | `PRESENT_1440P=1`, `SKIP_WAVE64=mesh,compute`, `SHADER_LOOP_LIMIT=32` | 0.7 | 181 | 0 | 7.0 / 20.6 GB | black |
| 2 | B | series-x | `PRESENT_1440P=1` | 0.1 | 68 | 0 | 7.2 / 22.6 GB | no world capture (see below) |
| 3 | B | series-x | `PRESENT_1440P=1`, `SKIP_WAVE64=mesh,compute` | 0.3 | 198 | 0 | 7.1 / 24.7 GB | black |
| 4 | A | series-s | `SKIP_WAVE64=mesh,compute` | never reached the world | 4-11 | 81 | 2.3 / 9.1 GB | black from the first screen |
| 5 | A | series-x | `SKIP_WAVE64=mesh,compute`, `SHADER_LOOP_LIMIT=32` | 1.5 | 406 | 81 | 7.0 / 22.3 GB | black, 2D fine |
| 6 | A | series-x | `SKIP_WAVE64=mesh,compute` | 2.1 (up to 3.0) | 392 | 81 | 7.1 / 22.3 GB | black, 2D fine |

No `ERROR` line and no device removal in any run.

### Notes per run

- **Run 3:** the fallback does fire (`VICTORY_PRESENT_1440P: presenting 2560x1440 world target as plane 0 width=2560 height=1440 format=28`), and the presented frame is still black: `a black frame after a frame that was not frame=2041 ... draws=773`. So on this card, with the wave64 programs skipped, the 2560x1440 target itself is black. The missing step here is before the present, not the 1440p-to-4K composite.
- **Run 2:** wave64 programs running, no skip. 6.8-7.3 s per frame, of which 5.6-5.9 s on the GPU, so the run ended before the first listed world frame was reached. No picture evidence either way from this run. (In #468, the same `92bc27b` tree without the skip did give some non-black world frames, at 0.2 fps.)
- **Run 4:** Series S on tree A stays at 30 fps with 4-11 draws/frame on a black screen and never leaves it (repeated twice, the second time with Enter held for 140 s). The log has `no host texture error=The parameter is incorrect. (0x80070057)` for 1920x1080 and 1280x720 textures. Series S on tree B (run 1) does reach the world.
- **Runs 5 and 6:** the loop limit makes no measurable difference with the skip on; 1.5 vs 2.1 fps is within what I see between runs.
- `92bc27b` did not end with `0x8007000E` this time (it did twice earlier today on this machine). Page file is still 50 GB, commit limit 64.5 GB. I do not know what changed.

### My reading

(On an 8 GB NVIDIA laptop, what decides the black world is the wave64 programs. With them refused or skipped, the device survives and everything 2D renders, but the world targets stay black on every tree, console mode and switch above, including the 1440p present fallback. With them running through the current lowering, the frame takes about 7 s. So nothing a user can set fixes this; the fix is the wave64-on-32-lane work (#223 / #233) landing in a form that is fast enough, and the skip in #579 is only a way to keep the device alive until then. #940 points the same way from the other side: on an RTX 5080, once the wave64 mesh programs run, world geometry reaches the 2560x1440 targets.)

One run per configuration, about 3 minutes in the world each, so small fps differences are not significant.

### Comment 2 — @zaidlutfi — 2026-11-24T17:00:30Z

Update on the same laptop with r4tedx `integration/testers` at update 9 (`94e0ea5`), built as is, with `VICTORY_PRESENT_1440P=1` and `VICTORY_SHADER_LOOP_LIMIT=32`. Three runs, one after the other.

### What I saw

- **Run 1 (12 min): black the whole time.** The reason was simple: the shaders of this update were being built for the first time, and the world's draws are skipped while their pipelines are still in the queue (about 1,750 were still waiting at the end). So the first run of a new update looks black here. It is not a regression, and I nearly reported it as one.
- **Run 2: the world came up as the queue emptied.** First thin lines, then a few solid objects. About 4 minutes into the world the game itself crashed (access violation at title `+0x536dfae`, read of `0x60000003f`).
- **Run 3 (shaders ready): the opening scene is recognisable for the first time on this machine.** I can make out two picnic tables, a basketball hoop, power poles with their wires, fences and metal frames, a bin, and then people: one seen from behind up close, others standing further away. The shapes are right and in the right place. The colours are false (it is the 1440p target shown raw) and there is no ground or sky. After about 3 minutes in the world the GPU device was removed (`0x887A0005`) on a compute dispatch, `24317e785c8688e3`.

### Numbers for run 3

About 2,500 draws per frame, one frame every 7 to 10 seconds (most of it preparing and copying; 0.4-0.7 s on the GPU), 0 pipelines refused.

### Compared with update 8

Update 8 kept more draws per frame (about 3,960) and stayed up for 12 minutes, but showed only lines and a few surfaces. Update 9 shows real objects and people, is slower, and ended after 3 to 4 minutes in both runs that reached the world.

Images stay local (rule #1).
