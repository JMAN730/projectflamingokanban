### Comment 5 — @DrTardis1963 — 2026-11-24T10:44:16Z

Root cause measured on Windows 10 22H2 (`10.0.19045.5794`), Intel i7-9700K, RTX 3070 (`32.0.16.1088`), Rust `1.98.1`:

### Root cause
On fresh Rust test threads on Windows 10 `10.0.19045`, `Rsp - TEB.StackLimit` (`gs:[0x10]`) frequently starts around `0x260..0x6c0` bytes above the committed stack limit. Inside `RtlCaptureStackBackTrace`, `RtlWalkFrameChain` walks caller frames toward higher stack addresses; when the stack proximity triggers the stack `PAGE_GUARD` mid-walk, Windows lowers `TEB.StackLimit` by `0x1000` and `RtlCaptureStackBackTrace` aborts and returns `0` frames (an immediate second `RtlCaptureStackBackTrace` call then sees the expanded `StackLimit` and returns `8` frames). Our `unwind()` reads via SEH/unwind tables directly and therefore still succeeds when the first OS walk returns `[]`.

### Fix on fork (preserves full system-walk parity)
- **Branch**: https://github.com/DrTardis1963/VIctory/tree/fix/win10-stack-unwind-root-cause
- **Commit**: `559756c5b617a68e698a82db895383c2ad386f77` (`crates/victory-loader/src/crash.rs`, test-only `+10` lines)
- Adds `#[inline(never)] fn ensure_stack_headroom()` (touches one `4096`-byte stack buffer with `std::hint::black_box`) at the top of `unwinds_like_the_system_walk` so the guard page is expanded before `RtlCaptureStackBackTrace`, keeping the full `assert!(walked.starts_with(&frames[..4]))` parity check intact on Windows 10.

### Verification (after `559756c`)
