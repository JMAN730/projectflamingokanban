## Original body

Three independent implementations of console wave64 compute on hosts without 64-lane waves are open, none reviewed yet. They conflict with each other textually, so one has to become the base. This puts their synthetic GPU tests on one NVIDIA machine and lists what each covers, to make that choice cheaper. No game files were used: only `cargo test`, no title run and no `translate` over title data.

- NVIDIA GeForce RTX 4060 Laptop, driver 32.0.16.1714, D3D12 waves 32..32

### Two test-harness problems on a laptop with two GPUs

**1. The default test device is adapter 0, which on a hybrid laptop is the iGPU.** `emit::host::Host::new(false)` calls `D3D12CreateDevice(None, …)`. On `main`, #189 and #734, every "hardware" GPU test therefore ran on the Intel UHD, not the RTX 4060. A "tested on an RTX 4060 Laptop" report from such a machine may not have touched the NVIDIA GPU. #233/#439 add `VICTORY_ADAPTER`, which helps if you know to set it. Picking the device with `IDXGIFactory6::EnumAdapterByGpuPreference(0, DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE)` would make the default the discrete GPU. That is the local patch I used:

```rust
let f6: IDXGIFactory6 = CreateDXGIFactory2(DXGI_CREATE_FACTORY_FLAGS(0)).map_err(err)?;
let a: IDXGIAdapter = f6
    .EnumAdapterByGpuPreference(0, DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE)
    .map_err(err)?;
D3D12CreateDevice(&a, D3D_FEATURE_LEVEL_12_0, &mut device)
```

A side effect on this machine: `valu_tests::v_med3_f32_matches_rdna2_with_nan` fails on `main` on the Intel UHD (`v_med3_f32(1.0, 2.0, NaN) = 2, want 1`). That is #971 reproduced on Intel Xe-LP, not only Arc.

**2. #233/#439: the split tests assume every hardware adapter runs 32- or 64-lane waves.** `emit::host::adapters()` drops WARP by its flags and name, but this Intel UHD reports 16..16. Every test that loops over `adapters()` stops on it with `console wave64 lanes on a host without 64-lane waves is not supported`: 10 failures on #233 and 30 on #439 (all `split_tests`, both `lane_read_loop_tests`, `each_adapter_gets_what_it_runs`). The translator does the right thing (it refuses), but the tests expect a pipeline. Filtering `adapters()` on `WaveLaneCountMax >= 32` instead of on the name would cover WARP and these iGPUs alike.

Related to #189: `wave64_tests::with_hosts` stores `Host::new(..).ok()` and `run_on_hosts` does `continue` on `None`, so on a machine where device creation fails, the 26 GPU tests pass without running anything and print nothing. A line on stderr, or a failure when neither host exists, would make that visible.

### What each line covers (from the PR descriptions and code, not re-measured on the title)

| | #439 stack | #189 | #734 |
|---|---|---|---|
| One console wave (≤ 64 threads), lane reads in uniform code | yes | yes | yes |
| Lane reads / exchanges inside divergent branches and loops | yes ("console flow") | refused in `Emulate`; in `Wave32`, `v_readfirstlane` under divergence returns each half's own first lane (documented as inexact) | refused |
| Groups of more than 64 threads that need an exchange | refused (next step is on a fork) | yes (uniform blocks) | refused |
| LDS shared inside one wave without `s_barrier` | yes | yes, with `plan_lds_fences`; refuses unfenceable cases | yes, barrier before each access |
| Whole-wave reductions and prefix sums | yes, groups of exactly 64 | yes | yes |
| `ds_bpermute_b32` | in-half | – | – |
| Hosts narrower than 32 lanes (WARP, 16-lane iGPUs) | refused | `Emulate` (no wave size, all through TGSM) | runs (no wave size declared) |
| Host lane range in the shader-cache key | yes (`Target`) | yes (mode byte) | yes |
| Title reports by testers | many (#439, #233 threads) | some (#189 thread) | one (RTX 4080, #734) |
| Size | +3,167 / −117, 16 files | +3,077 / −231, 10 files | +1,091 / −23, 6 files (incl. the unrelated `v_mad_*64`, `ldexp`/`frexp` commits) |

Merge check (`git merge-tree`): every pair of the three conflicts in `emit/lower.rs`, `emit/mod.rs` and `valu_tests.rs` (and #439 + #189 also in `host.rs`, `shader_cache.rs`, `translate.rs`).

### Reading

- #439 and #189 cover complementary halves, as #233's description already notes: #439 is exact under divergence within one console wave, #189 handles multi-wave groups and narrow hosts. #734 is roughly the intersection of the two, with fewer tests.
- With #439 as the base, #189's multi-wave exchange and `Emulate` mode could follow as a separate PR on top of `Target`, instead of a second `Wave64Mode` plumbing next to it.
- Whichever lands, the two harness fixes above are small and independent, and they would stop dual-GPU laptops from producing confusing reports.
