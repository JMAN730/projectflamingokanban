## Original body

A compute program that counts (or otherwise reads as a number) a lane mask after control flow its lanes took differently gets a wrong value in the per-lane form, without any error. The commonest shape is the loop compilers emit: lanes that are done are added to an exit mask, EXEC loses them, and after the loop the mask is counted.

## Reproduction (hand-assembled GFX10, no game data)

A wave32 compute program, 32 threads per group, `v0` = the thread's index in the group, result in `v2`:

```
v_add_nc_u32   v1, 1, v0            ; lane i loops i + 1 times
s_mov_b32      s10, 0               ; exit mask
loop:
v_subrev_nc_u32 v1, 1, v1
v_cmp_eq_u32   vcc_lo, 0, v1
s_or_b32       s10, vcc_lo, s10     ; lanes that are done
s_andn2_b32    exec_lo, exec_lo, s10
s_cbranch_execnz loop
s_or_b32       exec_lo, exec_lo, s10
s_bcnt1_i32_b32 s9, s10             ; all 32 lanes are in the mask
v_mov_b32      v2, s9
```

Words: `4A020081 BE8A0380 4E020281 7D840280 880A0A6A 8A7E0A7E BF89FFFB 887E0A7E BE890F0A 7E040209`. The wave64 form is the same with `_b64` operations (`BE8A0480`, `888A0A6A`, `8AFE0A7E`, `88FE0A7E`, `BE89100A`) and 64 threads.

On the console every lane ends with `v2 = 32` (64 for the wave64 form): one wave, one mask.

## What happens

| program | host | result in every lane | expected |
|---|---|---|---|
| wave32 | RTX 5070 (32-lane waves) | **1** | 32 |
| wave32 | Radeon iGPU (32-64) | **1** | 32 |
| wave64 | Radeon iGPU (32-64) | **1** | 64 |

Measured with the readback harness of #233 at its head `ededb1b`, where lane masks are handled as on `main` (the per-lane form). On `main` `ffe310e` itself both programs lower without a refusal (checked with a unit test through `lower`); I have not run them on a GPU from `main`, which has no multi-thread readback harness, so the table is #233's.

A second shape, a mask grown inside a branch only some lanes take and counted after it, is refused on a 64-lane host with `a lane mask holding lanes elsewhere read as data`, which is at least not silent.

## Why

In the per-lane form each lane knows of a mask only what its own path saw. A mask joined across paths the lanes took differently, when read as a number, is then each lane's own view of it (here: its own bit), not the wave's.

## How common

Offline over the title's shader pack (local title data, CPU only, counts only): about 400 compute programs read a lane mask as a number after such a join, about 300 of them wave32. That is a count of the shape, not of programs known to misbehave, and I have no title measurement of the effect. Counts feeding compaction and culling are the obvious candidates.

## A fix, and where it is

The console flow of #320 (every lane runs every block, branches are the wave's) gives the wave's mask. A rule that sends such programs there on a host that runs their wave size, keeping the per-lane form where the console flow cannot lower them, makes all three rows exact and changes no program's outcome over the pack (no program gained or lost for a 32-lane or a 32-64 host). It sits on the fork branch after #439 ([r4tedx/VIctory `shader/wave-per-group`](https://github.com/r4tedx/VIctory/tree/shader/wave-per-group)), because it needs the console flow, which is not on `main`. Two of the fixtures and the detection of joins lanes reach by different paths come from @mohammadallami75-ops's patch on #439.

Related: #225 (named lane reads where lanes branch differently, the same family), #269.
