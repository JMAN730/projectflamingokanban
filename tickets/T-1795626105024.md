### Comment 1 — @pickles976 — 2026-11-24T16:34:26Z

Cross-runtime read of your breadcrumb, from the sibling with the null-descriptor evidence trail: `u4=0xa67600 [heap 340912: null]` says the hung compute reads a **slot whose descriptor was never written** — and that is exactly the class that *cannot* fault in ivall/xcl: a zeroed descriptor becomes a zero-record buffer view at bind time (the `buffer_view` 0-record clamp we verified for Marvisak/VIctory#912 — same reasoning applies to a never-written slot), so the read returns zeros and the title survives to complain about garbage instead of losing the GPU. Practical consequence for your side: binding an **empty-view fallback for null SRV/UAV slots instead of leaving a stale/garbage binding** converts this whole device-removed class into wrong-pixels-and-a-log-line, which is debuggable; a hang at *list 1 of 1* with a null heap slot is about the cleanest repro of that gap a breadcrumb ever wrote. The 52416×1 typed-buffer dim also says the title asked for that size from the null slot's *consumer* — meaning the descriptor memory the runtime read was zero, so the fallback binds even when the shader asks non-trivially.


### Comment 2 — @MichaelSmithAI — 2026-11-24T16:37:54Z

I checked how VIctory produces these two fields. An empty `breadcrumbs (done/count, list) []` means the report has no breadcrumb node from which to read GPU progress. The 585 comes from the number of operation notes VIctory collected while recording that list. The GPU could have reached any point in the submission.

The final note gives a concrete hash to compare across captures. Dispatch `407e2119439e40e1` lists a 2560×1440 UAV. Whether the dispatch executed or wrote pixels is still open. Likewise, the `[heap …: null]` annotation beside a user-data word describes a lookup made by the formatter. Identifying a failing descriptor would need a matching shader binding and the host table offset used for that command.
