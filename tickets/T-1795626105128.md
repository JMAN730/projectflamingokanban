## Original body

## Bug description

While reviewing the indirect execution implementation in `victory-gpu/src/indirect.rs`, I identified a potential integer overflow in the GPU workload budget mechanism.

The current implementation uses a 32-bit atomic addition to accumulate workload costs. However, rejected records continue increasing the counter, eventually allowing it to wrap around and reopen the workload budget.

## Affected code

https://github.com/Marvisak/VIctory/blob/main/crates/victory-gpu/src/indirect.rs

```hlsl
uint before;
budget.InterlockedAdd(0, cost, before);

if (before >= BUDGET || before + cost > BUDGET) {
    args.Store(at, 0);
}
```

## Reproduction

Using 66 consecutive records, each with a workload cost of `2^26`:

- Configured budget: 134,217,728
- Accepted workload with the original implementation: 268,435,456
- Accepted workload with the proposed implementation: 134,217,728

The original implementation can therefore accept twice the intended workload in this synthetic example.

## Proposed fix

Replace the unconditional atomic addition with a saturating atomic counter using compare-and-exchange.

```hlsl
uint before;
budget.InterlockedAdd(0, 0u, before);

[allow_uav_condition]
while (true) {
    if (before >= BUDGET) {
        args.Store(at, 0);
        return;
    }

    uint remaining = BUDGET - before;
    uint next = before + min(cost, remaining);

    uint observed;
    budget.InterlockedCompareExchange(
        0, before, next, observed
    );

    if (observed == before) {
        if (cost > remaining) {
            args.Store(at, 0);
        }
        return;
    }

    before = observed;
}
```

## Expected benefits

- Prevents workload budget wraparound.
- Preserves the intended upper workload limit.
- May reduce GPU hangs caused by excessive indirect workloads.
- Does not require changes to game assets.

## Validation

Five CPU-side regression tests passed, including overflow reproduction, boundary conditions, zero-cost operations, and 51,200 randomized operations.

These tests validate the arithmetic model, not actual GPU execution.

HLSL compilation, GPU execution, and contention-related performance still require validation. I have not established whether this overflow occurs during normal gameplay or whether it contributes to the currently reported GPU hangs.

I am attaching the proposed patch and regression tests for review.

Thank you for your work on this project.

### Comment 4 — @FunWithFlagsDev — 2026-11-24T13:11:25Z

Thank you for pointing out the existing work. I missed #583 and the earlier hardware reproduction in #597 when checking for duplicates.

After reviewing #583 and #242, I found that:

- #583 rejects oversized reservations without consuming the remaining budget, allowing subsequent smaller records to fit.
- My proposed CAS implementation saturates the counter when a reservation exceeds the remaining budget.
- #242 already implements a very similar saturation strategy, while also respecting the count buffer and preserving the original argument buffer.

More importantly, rouges78's hardware results in #583 demonstrate severe contention in the CAS reservation loop when many small records fit within the budget. My proposal shares that potential limitation, and the available tests do not establish its scalability.

I agree that maintaining another independent implementation is unnecessary. Consolidating the existing work and addressing the contention issue would be more valuable.
