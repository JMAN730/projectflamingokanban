## Original body

### What's wrong

In `crates/victory-pipeline/src/cache.rs`, `Cache::get_or_convert` writes to a staging file `.tmp-<pid>-<n>` and publishes it via `std::fs::rename(&tmp, &path)`. When `rename` fails, it removes `&tmp` and unconditionally returns the error.

On Windows, if two worker threads (or two processes) convert the same content-addressed key concurrently and the winner's published file is opened for reading before the loser's `std::fs::rename(&tmp, &path)` runs, Windows rejects `MoveFileExW` with a sharing/access violation even though `path` is now a valid published file for that exact immutable BLAKE3 key.

### Fix

Separate `file.write_all` error handling from `std::fs::rename` error handling:
- If `write_all` fails, remove `&tmp` and return the error.
- If `rename` fails, remove `&tmp`; if `path.is_file()` is now true (another worker won the race to publish this content-addressed entry), return `Ok(path)`. When `path` is not a file (e.g., an obstructing directory as in `failed_publication_removes_the_staging_file`), the error is still propagated.

Because external PR creation is restricted (`collaborators_only`), the CI-green branch is ready on my fork:

### Concurrency & Correctness Analysis
- **Root Cause Verified**: On Windows, `std::fs::rename` delegates to `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`. When multiple worker threads convert the same key concurrently, the winner successfully renames its `.tmp` file to `path`. If a consumer or another thread opens `path` (default Windows sharing without `FILE_SHARE_DELETE`), concurrent losers attempting to rename their own staging files over `path` receive `ERROR_SHARING_VIOLATION` / `ERROR_ACCESS_DENIED`. The unpatched code treated this as a hard error.
- **Content-Address Invariant**: Because cache paths are strictly content-addressed by BLAKE3 hash (`converter.id()`, `converter.version()`, `input`), an entry at `path` is guaranteed to be bit-for-bit identical to what the losing worker produced.
- **Atomicity Invariant**: Because entries are only ever placed at `path` via atomic rename from completed staging files, an existing file at `path` is guaranteed to be fully written and not a partial write.
- **Error Propagation Preserved**: If `rename` fails due to a directory collision (as in `failed_publication_removes_the_staging_file`), `path.is_file()` is `false` and the error is correctly returned.
- **Resource Hygiene**: In both error paths (`written` failure and `rename` failure), the temporary staging file is guaranteed to be removed, preventing orphan `.tmp-*` files from accumulating in the cache hierarchy.

### Test Coverage
- `concurrent_publication_reuses_existing_entry_and_removes_staging`: Deterministically exercises the Windows sharing violation by holding `target` open with `share_mode(1)` (`FILE_SHARE_READ` without `FILE_SHARE_DELETE`). Verified that the winner's file is preserved, the loser's staging file is cleaned up, and `Ok(target)` is returned.
- `concurrent_threads_converting_same_key_all_succeed`: 8 barrier-synchronized threads racing on the same key all succeed, and `read_dir` verifies exactly 1 file remains in the bucket directory.
- `#[cfg(windows)]` gating on `OpenOptionsExt` correctly keeps the test suite portable and warning-free across non-Windows targets.
