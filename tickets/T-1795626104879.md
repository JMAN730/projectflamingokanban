## Original body

### Hardware / host
- Linux (CachyOS, kernel 7.2), NVIDIA RTX 6000 Ada + RTX 5080 (run used the Ada; wave64 noted below)
- Proton 11.0 standalone (wine-11.0, prefix 11.0-100, ntsync active), bundled vkd3d-proton
- `victory.exe` built on Linux, `--target x86_64-pc-windows-gnu`, rustc 1.99.1, HEAD `ffe310e` — cross-build was clean; useful data point for #232's interim Linux CI
- Xbox Series X profile; own verified user-supplied 1.0.2.1 copy; `VICTORY_D3D12_WARP=1` and native-adapter runs both tested

### Result
Boot is *far* along: `imports bound ... 0 missing` (88 hle + 427 host + 72 title), all four title DLLs mapped incl. Bink, `D3D12.X device version=0x20004`, `host D3D12 device ready`, DirectStorage queues created, **frame 1 presented**, the title's own Breakpad handler installed (Victory correctly blocks its telemetry phoning-home).

Then, every run, both WARP and native:

```
WARN victory_gpu::object: method not implemented object="device" slot=0x218 caller="+0x24800db"
WARN victory_gpu::object: method not implemented object="device" slot=0x1c8 caller="+0x247757e"
INFO victory_gpu::queue: frame presented ... frame=1 draws=0
VIctory: unhandled exception 0xc0000005 at libvkd3d-1.dll+0x3e7b0 (read 0x0: nothing mapped there)
  rax 0x0 rbx 0x2c5fdb70 rcx 0x0 rdx 0xfffffffb ...
```

Same fault offset across WARP and native adapter runs (3/3 repro, current HEAD). This matches the mechanism discussed in #518 (closed): `E_NOTIMPL` leaves the title's out-parameter uninitialized; the title hands it to vkd3d, which dereferences null. #417/#29 show AMD/MS-D3D12 users get past this point to menus — suggesting either the slots behave differently on MS D3D12 or vkd3d-proton hits the null where MS's runtime tolerates it.

### Asks
1. Any plan for device slots `0x1c8`/`0x218` (indices 57/67) — D3D12X-proprietary beyond the `ID3D12Device` surface?
2. Could the `missing` fallback zero-fill out-parameters alongside `E_NOTIMPL`, to contain this class of downstream crash regardless of which side fixes the slots?
3. For #340 compat docs: happy to run any probe build; logs (full `victory` INFO traces, both adapter modes) available.

Caveat per #778: NVIDIA subgroups are 32-wide, so wave64 behaviour here is emulated — but the crash precedes any wave64-heavy work (first frame).

### Comment 6 — @cobrajet302gt — 2026-11-24T15:04:06Z

Root fault, symbolized — it is **not the two slots**. A first-chance `0xc0000005` fires inside the host swap-chain path on the present thread; the title's own crash handler then faults while unwinding it inside Wine's `dbghelp.dll` (`dbghelp+0x1fe75`, `movq (%rcx),%rax`, `rcx=0xffffffffffffffff`), which is why reports show `dbghelp` on top. The real chain, from the exception record + Wine's SEH unwind:

```
#0 libvkd3d-1.dll+0x3fbd0    (read 0xffffffffffffffff; Proton-11.0's bundled build faults at +0x3e7b0 reading 0x0)
#1 dxgi.dll+0x6e6a
#2 dxgi.dll+0xe5ac
#3 victory.exe+0x17d42c  →  windows::Win32::Graphics::Dxgi::IDXGIFactory6::CreateSwapChainForHwnd
                            (victory-gpu/src/host.rs:1699 `presenter`, inlined through windows-0.62.2 dxgi/mod.rs:2882)
#4 victory.exe+0x1b12d2  →  <victory_gpu::host::Host>::present (victory-gpu/src/host.rs:1600)
#5 title+0x24824c7   (same function family as the 0x218 call site at +0x24800d5)
#6 title+0x2215eca → kernel32 → ntdll   (thread entry)
```

Faulting registers: `rax=rcx=0xfe976f3ffd9f0caa rdx=0xfffffffb r8=r9=0` (bundled build: `rcx=0 rdx=0xfffffffb`). Sequence each run: device ready → HDR/SDR → `frame presented frame=1 draws=0` → (second) `CreateSwapChainForHwnd` from `presenter` → fault. Pipeline-creation traces from other threads fill the log concurrently — unrelated noise.

So on vkd3d(-proton) hosts the death is in the **swap-chain create path reaching into vkd3d with something null/sentinel**, right after the first present; the slot pair is non-fatal exactly as argued above (and matches the RTX 3090 report in this thread — worth checking whether that crash's top frame is also `present → CreateSwapChainForHwnd`).
