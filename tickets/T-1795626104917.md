## Original body

*AI-assisted (Claude Code). Tested on my own machine.*

Seen once in 13 boots: `main` `ffe310e`, diag build, RTX 3090, Windows 11 26200, title 1.0.2.1 (`b99f876b74d4a77f`). It came on the very first boot, with empty cache and data folders, about 18 s in (title frame 82, `Game State: Game Running`) and before any key was pressed. The other 12 boots, including one more with an empty cache and empty data, did not hit it. So this is a report to match against, not a repro.

```
VIctory: unhandled exception 0x80000003 at victory-image-b99f876b74d4a77f.dll+0x4dcbc9d
  rax 0x17fb0 rbx 0x50 rcx 0xd075b7f38 rdx 0xcea6cf7370 rsi 0x6c0 rdi 0xd075b7f38
  r8 0x6c0 r9 0x20
  #0 +0x4dcbc9d  #1 +0x4e52a83  #2 +0x4e529c4  #3 +0x5ab13ed  #4 +0x21b70b1
  #5 +0x1d83996  #6 +0x81afb9  #7 +0x53ec079  #8 +0x53ebf66  #9 +0x661f0
  #10 +0x1d109c9 #11 +0x5a91c0d #12 +0x56a1e5a
```

**What the title is doing there** (static reading of 1.0.2.1):

- `+0x4dcbc40` is an append into a fixed buffer. Capacity is `[rcx+0x10]`, used is `[rcx+0x18]`, and the data goes at `[rcx+8]+used` via memcpy. When `capacity - used < len` it jumps to the `int3` at `+0x4dcbc9d`.
- The registers fit that: `rax` = used = `0x17fb0`, so capacity = `0x18000` (96 KiB). `rbx` = free = `0x50`, and `rsi`/`r8` = length = `0x6c0`.
- The caller (`+0x4e52a5x`) holds a lock and appends another buffer's `[rbx+8]`/`[rbx+0x18]` into it. That is a flush of one queue into a shared 96 KiB one.
- `+0x4e529a0` then clears a per-thread field reached through `gs:[0x58]` (TLS) `+0x10e0`. So this looks like per-thread records being merged into a shared buffer that a consumer is expected to drain.

A full shared buffer after 18 s, seen once, suggests whatever drains it fell behind on that run. That could be a thread starved or not woken under our runtime while shaders compiled on the first boot. I have not found which thread drains it. The crash context the title writes (`T:\victory-*.crash.log`) has no assert text.

Posting so others who see `+0x4dcbc9d` can add their run.

### Comment 1 — @Sunkiller-qc — 2026-11-24T13:09:13Z

This is the same stop as #834: same `int3` at `+0x4dcbc9d`, and the first six frames are identical (`+0x4e52a83`, `+0x4e529c4`, `+0x5ab13ed`, `+0x21b70b1`, `+0x1d83996`). It even happens at the same point, around title frame 82, 18–19 s in. On #834 it happens 12 of 12 times under Wine/Proton. There, one thread sits in `XMemMapPhysicalPages`, and the one-page `MapViewOfFile3` calls get slower with each view.

That fits your reading: whatever drains the 96 KiB buffer falls behind. On native Windows it would only happen on a slow first boot, which would explain 1 in 13. It might be worth adding your static notes on `+0x4dcbc40` to #834 so it's all in one place.


### Comment 2 — @MichaelSmithAI — 2026-11-24T13:22:37Z

One more detail worth capturing if this recurs naturally is which Windows playback endpoint was active and whether audio initialized during that boot. On Fedora/Wine, the #222 author observed this same title offset with the prefix audio driver off and passed the loading screen with winepulse on the same machine. An independent Windows report in XCL also passed the offset with a silent renderer on a PC that had no active playback device. [VIctory comparison](https://github.com/Marvisak/VIctory/pull/222) · [Windows XCL report](https://github.com/ivall/xcl/pull/887#issuecomment-7132280693)

Your successful second empty-cache boot makes a single successful retry a weak discriminator here. If the original run already has audio initialization logs, comparing those with a successful boot would help. The thread stacks and the mapping timings from #834 leave the endpoint state on this particular boot open.
