## Original body

## What happens

On an 8 GB NVIDIA laptop, `main` never reaches the world: after 79 packs are opened, host
texture creation starts failing with `E_OUTOFMEMORY` on completely ordinary textures, and the
failure is turned into a device removal instead of a degraded frame.

```
WARN victory_gpu::resource: no host texture error=... (0x8007000E)
     desc=ResourceDesc { dimension: 3, width: 2048, height: 2048, mip_levels: 10, format: 71, flags: 0 }
WARN victory_gpu::resource: no host texture ... 1024x1024 mip_levels: 9, format: 98
WARN victory_gpu::resource: no host texture ... 2048x2048 mip_levels: 12, format: 78
ERROR victory_gpu::host: a host command list did not close (0x8007000E):
      a command recorded into it was invalid
VIctory: host GPU failure: ... device removed
```

Machine: RTX 5070 Laptop (8 GB VRAM), 15.4 GB RAM, 24.8 GB system-managed pagefile
(commit limit 40.2 GB), retail 1.0.2.1 on SSD, Windows 11, `ffe310e` release build, built with
`cargo-xwin`. Same failure with the diagnostics build, with #1133, #472 and #561.

## Why it is not "the GPU is out of VRAM"

Measured during the failing load:

- `nvidia-smi` never reported more than **501 MiB** of VRAM in use out of 8151;
- the process peaked at **15.6 GB private** on a machine with **15.4 GB** of RAM, with system
  commit climbing towards its 38.3 GB limit;
- the Windows Application log has **no** event for the run (no WER entry, no driver reset), so
  the process exits on its own error path.

The textures that fail are BC1/BC3/BC7, 1024-2048 px, 9-12 mips, DEFAULT heap, flags 0. It is
the committed size that the driver refuses, not residency — which is why texture size, not
allocation order, is the lever.

## What is already proven to work

#737's `VICTORY_TEXTURE_MIP_DROP=1` (branch `antikohza:feat/texture-mip-drop-budget`, `06603c7`)
makes the world load on this exact machine: 79 packs, 0 `no host texture`, 0
`command list did not close`, no removal, **29-30 fps, 34.4 ms/frame, 11 draws/frame**, menus
unchanged at 30.0 fps / 33.3 ms. Reported in #653 as well.

## The gap

That switch is opt-in, so `main` on an 8 GB card still crashes by default, and the failure path
itself is hostile: a failed allocation leaves the resource null and the commands recorded
against it are what remove the device. A machine that cannot fit one texture should lose that
texture, not the whole device.

## Proposed change (`fix/auto-mip-drop-on-oom`)

Keep #737's drop machinery, but drive it from allocation pressure instead of an env var:

- add a process-wide `PRESSURE` level, `compute_mip_drop` returns
  `max(VICTORY_TEXTURE_MIP_DROP, PRESSURE)`;
- in `host_texture`, on `CreateCommittedResource` returning `E_OUTOFMEMORY`, raise `PRESSURE`
  to `drop + 1` (capped at 3), recompute the drop and retry once; log
  `host memory pressure: dropping N mips automatically`;
- otherwise behave exactly as today, so a machine with enough memory translates bit-exactly.

Effect on the machine above: the first tessellated world texture that does not fit drops one
mip, every later texture follows, and the run should reach the world with slightly softer
textures instead of removing the device — no environment variables required.

Test plan: same machine, same route, release build of the branch without any `VICTORY_*`
variable; expect the world to load, `no host texture` to disappear, and the frame rate to be
in the same 29-30 fps band as the manual `VICTORY_TEXTURE_MIP_DROP=1` run, with a visible
quality difference on large world textures only.

### Comment 1 — @pickles976 — 2026-11-24T16:37:12Z

Two-layer read from the runtime whose 8 GB cohort does *not* have this failure — the contrast is architectural, and this issue is the cleanest evidence of it yet.

**Why it cannot happen in ivall/xcl (same hardware class):** we do not keep host textures. Title texture data is placed **in place** on the title's own pages — physical-backed regions opened as D3D12 heaps (windowed UMA model, `gpu/uma.rs`), with system-memory spillover — so "create the host texture, sized 2048²×12 mips, *again*" is not a step that exists. Your log's `E_OUTOFMEMORY (0x8007000E)` on "completely ordinary" 1024–2048 textures after 79 packs is the mirrored-copy architecture meeting a real VRAM budget: the console memory is already paid for, and the mirror is the overdraft. That is also why your nine-change #1086 needed mip-drop to fit a 12 GB card, while our 8 GB reports reach world/story-load on unmodified budgets — and why the residual 8 GB death in *both* runtimes has moved to places the title itself convicts (`title_memory_mb` over-planning on our side, xcl#1337).

**The immediate bug is still yours though, and it is narrower than the issue title suggests:** your WARN line proves a *degrade path exists* ("no host texture" → render without it) — what removes the device is the **same E_OUTOFMEMORY surfacing mid-recording** (`a host command list did not close (0x8007000E)`). Two error channels for one allocation failure: the view path degrades, the record path escalates. Pin the allocation failure to a creation-time `E_OUTOFMEMORY` answer (which the title's own budget logic can consume — it has one; we mapped its fatal variant at `+0x193e00f` and its 2 MiB-range refusal style at `+0x247af2d` on the shared kill-map, so titles demonstrably branch on these), and never let the resource-creation status reach `Close`. A missing-detail frame is exactly what your WARN was already promising the user.

**Structural option, since your physical-page work (#1147) is one step from it:** in-place binding for the sparsely-used texture classes removes the mirror — and with it this entire failure class — at the cost you measured there (SEC_COMMIT windows, ≤4095 MiB sections). If the page-table probe results stay green, "host texture" becomes a view, not an allocation, and `0x8007000E` stops being a runtime error at all.
