## Original body

With about 900 open pull requests, most can only be tried one at a time against `main`. Many touch the same files, some fix the same thing twice, and nobody can test them together, so people build their own bundles (#231, #1439) that conflict in turn.

I built a merge train for everyone to use, and it's public:

- **Branch `forge/main`** in [KevinPratap/VIctory](https://github.com/KevinPratap/VIctory/tree/forge/main): `main` (`ffe310eb20`) plus every open pull request that merges cleanly and still builds. Each one is a separate merge commit (`Forge: #N title`), merged oldest first. **281 of 928** open pull requests are in it.
- **[STATUS.md](https://github.com/KevinPratap/VIctory/blob/forge-status/STATUS.md)** gives each pull request's result:
  - in the branch;
  - conflicts with `main` (rebase needed);
  - conflicts only after other pull requests (which ones, and on which files);
  - breaks `cargo check` (first error shown);
  - held, for pull requests known to break the title in testing, with the reason.
- **[forge.py](https://github.com/KevinPratap/VIctory/blob/forge-status/forge.py)** is the tool. It needs only git, `gh` and cargo, so anyone can rerun it or check it.

What this gives:

- **Contributors** see whether their pull request still combines with the rest, and who else is working in the same place before they duplicate it.
- **Testers** can try one branch instead of picking pull requests by hand.
- **Maintainers** get a list of pull requests that merge and build together. Duplicates and stale pull requests show up in the conflict columns.

A merge needs `cargo check --workspace --all-targets` and the asset policy (`cargo xtask policy`) to pass. The policy check has already caught something: #1030 adds `VIctory_GTA6_Progress.zip`, a binary archive the policy refuses, so it is held out.

On the combined branch, `cargo test --workspace` gives 1,005 passed and 5 failed. Of the 5, one fails on `main` too, and the rest come from how pull requests combine. Details are in STATUS.md.

Only the build and the policy gate a merge. GPU tests per pull request would take days, so the final branch's test results are reported separately. Nothing from the game is in the branch, the status page or the tool.

I'll rerun it regularly. Suggestions welcome, for example the merge order, or a hold list kept by the maintainers.

**#1608 breaks its own four tests**, deterministically: 3 of 3 runs at its merge commit `954b1cd` and 10 of 10 at the train tip. The emitted DXIL is invalid — `dx.op.binaryWithTwoOuts.i32` called with opcode 42 (`UMul`), then two `extractvalue`s on an `i32`. Since the runtime validates emitted shaders, in the game this would be a *refused program*, not a wrong number. Details and the one command in https://github.com/Marvisak/VIctory/pull/1608#issuecomment-7144459772. The four tests have never passed anywhere: they live in that pull request, its CI is waiting for approval, and the forge runs `cargo check`.

**#1450 and #1549 encode contradictory texture layouts.** Each passes on its own (`c3b045f` alone: 49 passed, 0 failed), and together they fail: for a `Tex3d 4×4×16`, 5 mips, 4 bytes per element, our layout says **16,384 bytes** where addrlib — the reference #1549 compares against — says **8,192**, exactly double. Reverting #1450's merge (`git revert -m 1 c3b045f`) makes #1549's test pass again. Since #1549's expectation comes from addrlib and #1450 changes the padded-depth rule, the evidence points at #1450; at runtime that would be a thick 3D mip tail allotted twice the memory it needs and off-tiled from the wrong offsets.

**For the train tool**, two suggestions from the exercise:

- running `cargo test --workspace --no-fail-fast` as a *reporting* step (not a gate) would have put all six in `STATUS.md` next to the conflicts;
- when a pull request's CI is `action_required` (a first-time contributor's), `cargo test` on the merged tree is the only place its tests ever run — which is exactly how #1608 got into the train with four failing tests.

No game data is involved: test names and assertion values only.
