### Comment 5 — @yeifer125 — 2026-11-24T08:35:36Z

## Independent confirmation from a fresh Linux build attempt (2026-11-25)

Built `main` today on Kali (rustc 1.97.1, distro) and hit the **same E0425** (`host_resource`, `resource.rs:284`).

### Where the cascade ends

After locally stubbing that (and gating `super::xmem` in `victory-hle`), the build moves into `windows-future` and dies with 12-16 errors:

```
error[E0425]: cannot find type `IMarshal` in module `windows_core::imp`
error[E0425]: cannot find function `marshaler` in module `windows_core::imp`
```

### Root cause (verified in crate source, not the lockfile)

`windows-core` 0.61.2 **and** 0.62.2 only compile their COM plumbing on Windows:

```
// $CARGO/registry/.../windows-core-0.62.2/src/imp/mod.rs (line 1-2)
#[cfg(windows)]
include!("windows.rs");
```

...and `windows.rs` (line 10-11) is where `marshaler` lives:

```rust
mod marshaler;
pub use marshaler::*;
```

So on Linux `imp::IMarshal` / `imp::marshaler` simply do not exist, and `windows-future` (0.2.1 with core 0.61, 0.3.2 with core 0.62) cannot compile. Tested 0.61.3 and 0.62.2 + fresh `Cargo.lock`: identical.

### Impact for the "native runtime, no Wine" goal (#526)

Any native-Linux victory needs either:
1. a patched/vendored `windows-core` that exposes `marshaler` off-`cfg(windows)` (with a std-only implementation), or
2. dropping `windows-future` from the native path.

Happy to push the 3 local gates we already wrote (`host_resource` stub, `view_format` split, `xmem` ungate) as a PR if useful - they track what #39 did, so no duplication intended, just confirmation the failures reproduce on 1.97.1.

### #235: `victory-gpu` tests depend on test order

These four tests fail or hang under a normal `cargo test` run, and **each one passes when run alone**:

- `queue::host_free_tests::fence_waits_complete_without_blocking_the_queue`: fails at `queue.rs:594`, `left: -2147467263` (E_NOTIMPL), `right: -2147024809` (E_INVALIDARG)
- `queue::host_free_tests::page_mapping_batches_run_through_the_runtime_mapper`: fails
- `queue::host_free_tests::present_succeeds_without_copying_to_a_window`: fails
- `queue::host_free_tests::timestamp_frequency_refuses_null_and_reports_the_rate`: **hangs**, which would stall a CI job

Running each test alone after every other test in the crate, I found the one that causes it: `device::tests::newer_device_levels_are_the_same_device`. Any of the four fails or hangs when it runs after that test:

```
victory_gpu-<hash> --test-threads=1 --exact \
  device::tests::newer_device_levels_are_the_same_device \
  queue::host_free_tests::fence_waits_complete_without_blocking_the_queue
```

Likely cause, from reading the code: that test creates the device as `ID3D12Device11`, which sets the process-wide `NEWER` flag (`device.rs:154`). Every queue created after that gets the newer layout (`newer_slot`, slots from 0x70 moved by two). The new `host_free_tests` call fixed offsets such as 0x78, 0x80 and 0x100, so after the flag is set they hit different methods. Using `newer_slot` and `crate::device::newer()` in those tests, or not letting tests share the flag, should fix it. I haven't tried a fix, and I haven't checked whether the same order dependence affects the Windows-only tests.

On Linux, **#523 is the only one I could confirm builds and passes all tests merged onto current `main`.** #235 builds but needs the test-order fix above. #112 and #526 pass on their own bases but need a rebase first.
