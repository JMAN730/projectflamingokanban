## Original body

## What happens

A `v_readlane` inside a loop that the lanes leave at different iterations is translated wrongly on every GPU tried, both for wave32 and for wave64 programs.

On the console a wave runs a loop while any of its lanes does, and `v_readlane` reads the lane it names whatever EXEC holds. The translation runs such loops per lane (structurisation turns EXEC into per-lane branches), which loses two things:

1. A lane that has left the loop is not there for the later iterations' lane reads. `WaveReadLaneAt` of a lane that is no longer active is undefined; here it reads 0.
2. A lane that skips the loop never sees the scalar the loop set.

## Minimal repro

Hand-assembled GFX10, one wave per group (32 or 64 threads). Lane t runs the loop t times, reading lane L's thread id (L = 20 of 32, 40 of 64) into s9 in each iteration, and then stores t + s9. On the console every lane stores t + L.

```
s_mov_b32 s9, 0
v_mov_b32 v2, 0
v_cmp_ne_u32 vcc, 0, v0
s_and_saveexec_b64 s[10:11], vcc          ; _b32 for wave32
s_cbranch_execz end
loop:
v_readlane_b32 s9, v0, L
v_add_nc_u32 v2, 1, v2
v_cmp_lt_u32 vcc, v2, v0
s_and_b64 exec, exec, vcc
s_cbranch_execnz loop
end:
s_or_b64 exec, exec, s[10:11]
v_add_nc_u32 v2, s9, v2                    ; store v2 at dword t
```

A self-contained test (it runs on every hardware adapter, lists each wrong lane, and is `#[ignore]`d so the suite stays green) is on [`r4tedx:repro/loop-lane-read`](https://github.com/r4tedx/VIctory/tree/repro/loop-lane-read), commit a7f34b7, file `crates/victory-shader/src/emit/lane_read_loop_tests.rs`:

```
cargo test -p victory-shader lane_read_loop -- --ignored --nocapture
```

## Results on main (d2a4bae)

| adapter | wave32 (L = 20) | wave64 (L = 40) |
|---|---|---|
| NVIDIA RTX 5070 | 12 of 32 lanes wrong | no wave64 pipeline (host range 32..32) |
| AMD Radeon iGPU (RDNA2) | 12 of 32 lanes wrong | 24 of 64 lanes wrong |

The same lanes are wrong on both GPUs: lane 0 stores 0 (it skipped the loop, so s9 stayed 0), and every lane above L stores t (lane L had left the loop when their later iterations read it).

## Possible direction

Run such programs as the console does: every lane of the wave through every block, vector instructions guarded by the lane's EXEC bit, and the console's `s_cbranch_*` taken wave-wide. Lane reads then see lanes outside EXEC, as on the console. This is now #320 (on top of #233's "console flow"): a compute program with `v_readlane` / `v_writelane` and a branch its lanes take differently runs that way on every host, and this repro is exact for wave32 and wave64 on the RTX 5070 and the Radeon iGPU with it.

Not verified against console hardware; the expected values follow the ISA's `v_readlane` and EXEC semantics.

- In the title on an RTX 5070 Ti, [no program that ran on `main` stops with #320](https://github.com/Marvisak/VIctory/pull/320#issuecomment-7120271524).

Not shown: a title program whose picture changes because of this. In compiled shaders these lane reads mostly come from SGPR spill slots, which PRs such as #54 and #309 resolve more cheaply, so the bug may be rare in practice.
