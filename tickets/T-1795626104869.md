## Original body

**Environment**
- VIctory `ffe310e`, `cargo build --profile diag -p victory --features diagnostics`
- Windows 11 Pro build 26300, Intel i5-12400 (6C/12T), 31.8 GB
- NVIDIA GeForce RTX 4060 Ti 16 GB, driver 32.0.16.2114 - Ada, mesh shaders present, **32-lane waves only**
- Title: retail 1.0.2.1, Xbox Series X build

**What happens**

The title reaches its account screen and stays there (no input is given). Menus draw and present
normally. In that run:

- **406 compute pipelines are created**
- **103 are refused**, one `WARN` line each, 103 distinct hashes:

  ```
  WARN victory_gpu::pipeline::host: host pipeline refused error=... (0x80070057) shaders=[compute 13dfdd3b1136e407]
  ```

- each refusal is followed by `a dispatch without a host pipeline dropped`; at the account screen
  about **5-6 dispatches per frame** are dropped for these hashes (5.0/frame for each of several,
  6.0/frame for one, plus indirect ones).

**The reason, only visible with `VICTORY_D3D12_DEBUG=1`**

Every refusal is followed by the same info-queue message (104 occurrences, one more than the refusal
count, presumably a retry, and **no other `CreateComputeShader` reason in the whole run**):

```
D3D12: ID3D12Device::CreateComputeShader: Shader wants wave lane count of 64 but
maximum wave lane count for device is 32. To check for support, check device caps
via the CheckFeatureSupport() API  id=622 severity=1
```

So all 103 are the same cause: the translated DXIL asks for a 64-lane wave and this device offers 32.
Without the debug layer the log only says `0x80070057`, which reads like a root-signature or shader
bug and is not one: the shaders translate fine (`shader translated stage="compute" hash=...`
immediately before the refusal).

**Three things that could be done (your call)**

1. **Diagnostics, small**: the refusal line could carry the wave sizes, e.g.
   `compute 13dfdd...: translated for 64-lane waves, device max 32 - skipped`.
   The wave size is in the translated shader, and the device maximum can be queried once with
   `CheckFeatureSupport(D3D12_FEATURE_D3D12_OPTIONS1)`, so this needs no debug layer. A count at the
   end of the run (`103 compute programs skipped: 64-lane waves`) would tell an NVIDIA user in one
   line why parts of the screen are missing.
2. **Documentation**: the README's Shaders row says "some compute programs need a GPU with 64-lane
   waves" but not how many. On this card it is 103 of the 1,441 compute programs that emit at all
   (whole pack, `victory translate --validate`, numbers in #293) - i.e. the gap is not theoretical.
3. **The real fix** is emulating a 64-lane wave as two 32-lane halves. I know that is a large change
   and not what this issue asks for; it is here only so that (1) can point at it.
