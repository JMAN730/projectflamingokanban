### Comment 1 — @pushkarreddyy — 2026-11-24T12:00:42Z

Claiming this issue for investigation and resolution.

### Architectural Context & Root Cause Analysis
In `crates/victory-hle/src/modules/audio.rs`, `APU_BASE` is defined as `0x0001_0000`, and `heap_alloc` issues 32-bit device addresses (`apu`) in that range (such as `0x217800`). However, `heap_alloc` allocates backing host buffers via standard heap `alloc_zeroed`, keeping the 32-bit `apu` device address virtualized only in `HEAP.by_apu`.

When the audio DSP or middleware expects CPU-visible direct access to the APU buffer or assumes device addresses correspond to accessible virtual memory, passing `0x217800` directly into `memset` faults because `0x00010000..` is unmapped in the title process virtual address space.

We are investigating establishing a fixed low memory mapping or ensuring APU allocation addresses mirror a reserved virtual region so direct CPU accesses by audio worker threads do not fault.

### Verified Patch Ready on Fork

The implementation resolving APU device address mapping is verified and available on my fork:
- **Branch:** https://github.com/pushkarreddyy/VIctory/tree/fix/audio-apu-address-mapping
- **Commit:** [`161cdc7`](https://github.com/pushkarreddyy/VIctory/commit/161cdc7) based on `main` (`ffe310e`)

#### Changes (`crates/victory-hle/src/modules/audio.rs`):
- Updated `heap_alloc` on Windows to allocate backing APU memory using `VirtualAlloc(apu as *mut c_void, size, MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE)` directly at the 32-bit device address `apu` (starting at `APU_BASE = 0x0001_0000`).
- If fixed allocation is unavailable, falls back gracefully to `std::alloc::alloc_zeroed`.
- Added `free_apu_memory` to properly release via `VirtualFree` or `std::alloc::dealloc`.
- Because the buffer memory is committed at `0x217800`, direct CPU operations by title audio worker threads (such as `memset(0x217800, 0, len)`) execute without access violations (`0xc0000005`).
- Added unit test `apu_alloc_memory_is_accessible`.

### Comment 3 — @imjustprism — 2026-11-24T20:45:11Z

i hit this crash on my machine and traced it. the write to 0x217800 is not an apu device address being used as a pointer. the title asks ApuAlloc for one block of about 401 MiB and passes null for the device-address out-param, so it never sees a device address at all.

on my machine the host refused that allocation: windows was almost out of commit (ram + pagefile) because of other work, the title's own telemetry showed about 8 MB left. the call failed, the title did not check the result, and then cleared memory at null plus an offset inside that block. that offset is 0x217800.

i can reproduce it on demand: running the title in a job object with a 7.1 GB per-process commit cap gives the same crash at the same address. with commit free it boots to the menus, peak private memory about 7.3 GB.

so mapping memory at the device addresses would at best let the write land in an unrelated block and hide the crash. if you hit this, check free commit before launch and your pagefile size.

i have a small change that writes the refused allocation to crashes.log with the size and the system commit, so this shows up by name. pr coming.
