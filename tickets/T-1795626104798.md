## Summary

On an RTX 4060 Laptop the title reaches the first mission's title card, then the host D3D12 device is removed during world load, as in #653 and #468.

Two new pieces of evidence:

1. **Control:** 1920×1080 with `rtDynamicShadows=false` does not change the failure; it still dies on the same 30-list submission. Not resolution/VRAM/RT load.
2. **Debug layer:** `B5G5R5A1_UNORM` + `ALLOW_UNORDERED_ACCESS`, `B4G4R4A4_UNORM` + `ALLOW_RENDER_TARGET`, and a 1,310,720-entry shader-visible heap against a 1,000,000 limit.

Details, environment and logs are in the local draft; this is a placeholder body.

### Comment 1 — @LAKSHYA-cmd-tech — 2026-11-24T09:02:24Z

Verified the root cause of both issues identified by the D3D12 debug layer and implemented a fix on fork branch \ix/gpu-resource-format-flags-and-heap-limit\:

### 1. Descriptor Heap Size Exceeding 1,000,000 (1.31M Heap)
- **Root Cause**: In \crates/victory-gpu/src/descriptor/host.rs\, \HostHeap::new\ attempted \make(count + DYNAMIC)\ first. When the title requested 1,048,576 descriptors (\1 << 20\), adding \DYNAMIC\ (\1 << 18\ = 262,144) requested **1,310,720** descriptors. On NVIDIA drivers, \CreateDescriptorHeap\ returns \Ok\ at creation time without failing, but the D3D12 runtime/debug layer caps shader-visible \CBV_SRV_UAV\ heaps at \1,000,000\ (\D3D12_MAX_SHADER_VISIBLE_DESCRIPTOR_HEAP_SIZE_TIER_1\ and \_TIER_2\), reporting \STATE_CREATION ERROR #645: CREATE_DESCRIPTOR_HEAP_INVALID\ and triggering device removal on access.
- **Fix**: Gate heap sizing so that if \count + DYNAMIC > PORTABLE_VIEWS\ (\1_000_000\), it never requests >1,000,000 descriptors. When \count + MIN_DYNAMIC > PORTABLE_VIEWS\, it caps at \make(PORTABLE_VIEWS)\ with available slots \PORTABLE_VIEWS - MIN_DYNAMIC\ and extra \MIN_DYNAMIC\.

### 2. Invalid Resource Flag Combinations
- **B5G5R5A1_UNORM + ALLOW_UNORDERED_ACCESS**: In D3D12, \DXGI_FORMAT_B5G5R5A1_UNORM\ (86) and \B5G6R5_UNORM\ (85) do not support typed unordered-access views (\D3D12_RESOURCE_FLAG_ALLOW_UNORDERED_ACCESS\).
- **B4G4R4A4_UNORM + ALLOW_RENDER_TARGET**: In D3D12, \DXGI_FORMAT_B4G4R4A4_UNORM\ (115) does not support render-target output (\D3D12_RESOURCE_FLAG_ALLOW_RENDER_TARGET\).
- **Block-compressed formats**: BC1-BC7 formats cannot support \RENDER_TARGET\, \DEPTH\, or \UNORDERED\.
- **Fix**: In \crates/victory-gpu/src/resource.rs:host_texture\, explicitly clear these unsupported flag combinations before calling \CreateCommittedResource\.

Verified with 52 passed unit tests in \ictory-gpu\ on Windows 11 MSVC (\incompatible_host_texture_flags_are_cleared\ and \large_view_heap_is_capped_at_portable_limit\), \cargo clippy\, and \cargo xtask policy\.

### Comment 3 — @Sunkiller-qc — 2026-11-24T13:08:59Z

The two formats the debug layer flags are the ones #89 (open) handles: B5G5R5A1_UNORM (86) with UAV and B4G4R4A4_UNORM (115) with render target. NVIDIA supports neither as a typed UAV or render target, so #89 creates those textures as R8G8B8A8_UNORM when `CheckFeatureSupport` says the format isn't supported. #797 shows the same two 2560x1440 textures refused.

The 1,310,720-entry heap against NVIDIA's 1,000,000 limit is expected on main. When the driver refuses a view heap that big, main caps it, and since #21 (`97c78d1`) the tables past the cap are rebuilt. So that debug-layer message alone isn't the cause.

Could you try #89 on its own? That would tell whether the device removal on the 30-list submission is related to those textures or not.
