## Original body

## Device removed when the world starts drawing (hardware: DEVICE_HUNG, WARP: internal removal)

### Summary
The game reaches the menu and loading screens, then starts drawing the world at around 1 fps. Within about 90 s the host D3D12 device is removed, right after a large batch of command lists, and VIctory exits with `host GPU failure`. It reproduces on hardware and on WARP.

### Environment
- VIctory `main` at `ffe310e` (with #566 included), release build with `--features diagnostics`
- Windows 11 Pro 10.0.26300
- AMD Radeon RX 6750 XT, driver 32.0.21045.29003
- Also reproduced on the WARP software adapter (`VICTORY_D3D12_WARP=1`)

### Repro
```
cargo build --release -p victory --features diagnostics
victory run <title>\game_scarlett_master.exe --execute
```
No input is needed. The crash follows on its own once the world starts drawing.

### Hardware result (RX 6750 XT)
```
host GPU device removed (0x887a0006) after a submission of 30 lists; no breadcrumbs
(The specified device interface or feature level is not supported on this system. (0x887A0004));
device removed: The GPU will not respond to more commands ... (0x887A0006)
```
- Frame 1370, about 100 s after launch.
- Draw load at this point is 300–2000 draws/frame, with about 1000 dropped for missing pipelines and about 1000 indirect draws dropped.
- `DXGI_ERROR_DEVICE_HUNG` usually means a shader that loops forever, or a fault from an out-of-bounds or garbage descriptor access.

### With DRED enabled, it doesn't crash (hardware)
With `VICTORY_D3D12_DRED=1` on the same RX 6750 XT, it ran for the full 240 s, past frame 3218 at 400–3700 draws/frame, with no device removal. Without DRED it is removed at frame 1370 every time. So far this is one DRED run against two crashing runs.

DRED's auto-breadcrumbs change submission timing, so this looks like a **synchronization or lifetime race**, not a bad shader. Possible causes: a missing barrier or fence wait, a resource or descriptor reused or freed while still in flight, or a copy-back read racing the GPU. The heavy per-frame copy traffic, 150–860 MB of copies plus copy-back, may make the window wider.

### WARP result
- The removal reason is `0x887a0005`. With `VICTORY_D3D12_DEBUG=1`, the debug layer reports no API errors, only `RemoveDevice ... Plug-and-play stop`, which points to a removal from inside WARP rather than API misuse.
- `VICTORY_D3D12_DRED=1` breadcrumbs are empty on WARP, so the "in flight" list it reports means nothing.
- It always happens right after the same 32-list submission.

### Bisecting by `VICTORY_SKIP_PIPELINES` (WARP)
- 49 shaders first bind in the batch before the removal.
- Skipping the 16 most likely suspects (hair, fog/density, new compute) still crashes. In every quarter split of those 16, the device removal no longer appeared in the log, but each run still exited with code 5. The control run that skipped all 16 behaved the same way, so these splits don't isolate a culprit.
- Skipping all 49, or the other 33, keeps the device alive, but then the game segfaults (exit 139), probably because it depends on the output of those passes. So we couldn't narrow it down to one shader by skipping groups.

### Two translator bugs found and fixed along the way
These are on a local branch, one commit on top of `ffe310e` (I can open a PR), with all 120 victory-shader tests passing:
1. `s_buffer_load` on a descriptor read from `ResourceDescriptorHeap[]` was emitted as a CBV load. It is now a raw buffer load. This fixed GBV errors and garbage reads in the hair shaders.
2. `image_sample` in compute shaders (for example `CS_DensityShadowBlur_H`) used implicit-derivative sampling, which fails validation outside pixel shaders. It now samples at level 0. `image_sample_o` and `image_sample_b` outside pixel shaders are reported as unsupported instead of emitting invalid DXIL.

The commit also adds the `GetDeviceRemovedReason` code to the failure message, and prints the runtime shader hash in `shader-info --verbose` so log hashes can be matched to containers.

Neither fix changes the device removal.

### Untranslated shaders in the same run (405 warnings, for context)
| count | reason |
|---|---|
| 79 | a select on an untracked mask |
| 71 | a lane mask holding lanes elsewhere read as data |
| 54 | a descriptor read only as data |
| 43 | a structured buffer of unknown stride |
| 35 | an address in an SGPR that is no root parameter |
| 33 | a scalar memory read as data |
| 17 | an address not from a root parameter |
| 14 | a 64-bit image atomic |
| 11 | a lane mask read as data |
| 8 | an address from a phi |
| 7 | `image_gather4_l` |

A pass whose producer shader is dropped may leave buffers that a later, translated shader then indexes with garbage. That is one plausible cause of the hang.

### Suggested next steps
- Look for a missing barrier, fence wait or early free around the copy and copy-back paths, since DRED hides the hang.
- Use PIX or RGP with the hardware device to see which dispatch or draw hangs. On AMD, DRED with real breadcrumbs should name it too.
- A per-draw breadcrumb or flush mode, run one shader at a time, to bisect the batch without the game crashing.
