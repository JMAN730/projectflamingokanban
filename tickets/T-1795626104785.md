## Original body

## What's wrong

For a cube-map **array**, RDNA2 takes the face operand of `image_sample*` / `image_gather4*` (dim `CUBE`) as `8 × layer + face`. Mesa's `ac_nir_lower_tex_coords.c` (`prepare_cube_coords`) builds it exactly that way: `id = ffma(layer, 8.0, face)`.

The lowering treats that operand as a bare face id:

- `cube_direction` (`crates/victory-shader/src/emit/lower.rs:5923`) converts it with `FpToUi` and matches it only against 0–5. For any layer ≥ 1, no face matches, so it falls back to **+X**.
- dim 3 is always declared `TextureCube` (kind 5, `:5427-5441`), so the layer is never passed to the host.
- `image_get_resinfo` on a cube reads 1 for the array size (`:5636`).

The code already marks this as a `shortcut:` (`:5921`). I'm filing it because the result isn't a refusal or a log line but silently wrong texels: layer 0's data, from the +X face.

## Example

A 2-cube array, `image_sample_lz` with s = t = 1.5 and a face operand of 10.0 (layer 1, face 2 = +Y):

- Console: the centre texel of layer 1's +Y face.
- Ours: direction (1, 0, 0), the +X face, through a `TextureCube` handle on a cube-array view.

A shader of the encodings below lowers without any refusal today:

```
s_mov_b32 s5, 0
s_load_dwordx8 s[8:15], s[4:5], 0                   F40C0202 FA000000
s_load_dwordx4 s[20:23], s[4:5], 32                 F4080502 FA000020
(immediate sampler in s[16:19])
v1 = v2 = 1.5, v3 = 10.0 (0x41200000)
image_sample_lz v4, v[1:3], s[8:15], s[16:19] dmask:1 dim:CUBE    F09C0118 00820401
buffer_store_dword v4, off, s[20:23]                E0700000 80050400
```

## Suggested fix

1. Split the operand: `layer = floor(face × 0.125)` and `id = face − 8 × layer`, then pass `id` to `cube_direction`.
2. When the shader can be an array (the operand isn't a bare `v_cubeid_f32` result; titles build it with `v_fma`/`v_fmac`/`v_madak` by 8.0), declare `TextureCubeArray` (DXIL kind 9) and pass the layer as coordinate 3. GFX10 MIMG has no DA bit, so the kind has to be inferred like this, or taken from the bound view.
3. In `image_get_resinfo`, return the array size for kind 9. I'm not sure whether titles expect it in cubes or in faces.

**Not tested:** on a GPU. A WARP test with a cube-array view whose texels hold `10 × layer + face` would show it: a face operand of 10.0 should read 12.0, and gives 0.0 today. A face operand of 2.0, the control, should already pass.

## Related

#109, #138, #317 and #563 touch cube sampling, and #568 adds null cube-array descriptors; none decodes the layer.

### Comment 11 — @AwkGrep256 — 2026-11-24T12:46:32Z

@Dufftwt BASE_ARRAY ≠ 0, same 2-cube texture (DEPTH = 11, the last face), run with BASE_ARRAY 6 and 3, wave32.

**The layer counts from the view's first face**, even when that isn't a multiple of 6. One rule fits all 87 results across BASE_ARRAY 0, 3 and 6:

```
face   = min(f % 8, 5)
first  = min(BASE_ARRAY + 6 * (f / 8), DEPTH - 5)   // the cube is clamped to stay inside the view
texel  = face (first + face) of the resource
```

| BASE_ARRAY | operand 0–5 read slices | operand 8–11 read slices | `resinfo` array size |
|---|---|---|---|
| 0 | 0–5 | 6–9 | 12 |
| 3 | 3–8 | 6–9 (clamped: 3 + 6 = 9 would run past face 11) | 9 |
| 6 | 6–11 | 6–9 (clamped) | 6 |

`resinfo` returns `DEPTH - BASE_ARRAY + 1`, the view's face count, not rounded to whole cubes. `image_load dim:CUBE` takes its slice relative to BASE_ARRAY as well, and reads 0 past DEPTH.

So for the lowering: the host view's first array slice already covers BASE_ARRAY, and the layer from the operand is relative to it. The clamp only matters for out-of-range layers.


### Comment 12 — @Dufftwt — 2026-11-24T12:48:37Z

@AwkGrep256 that's a complete answer, thank you. Read against VIctory, it means the host already behaves like the hardware for every view a title can create, except for one detail:

- **The layer counts from the view's first face.** Host views are made from the title's own `D3D12_SHADER_RESOURCE_VIEW_DESC` (`srv_desc`, `descriptor/host.rs`), so `BASE_ARRAY` arrives as `First2DArrayFace`, and D3D's cube index is relative to it too. Nothing to change.
- **`resinfo` = `DEPTH − BASE_ARRAY + 1`.** A D3D cube-array view always holds whole cubes (`NumCubes`), so for any title-made view that's `NumCubes × 6`, exactly what Altorru's `a51d7c3` returns. Your `BASE_ARRAY 3, DEPTH 11` case (9 faces) is a view D3D can't describe, so it can't reach us through the API.
- **The cube is clamped inside the view.** For whole-cube views, `min(BASE + 6 × layer, DEPTH − 5)` is the same as D3D clamping the cube index to `NumCubes − 1`, so that matches too.
- **The face is clamped to 5** (`min(f % 8, 5)`). This is the one place both fork fixes differ, as in my comment above (6 and 7 fall back to +X).

So #720 is settled: Altorru's branch plus that one-line face clamp matches RDNA2 for everything a title can bind.
