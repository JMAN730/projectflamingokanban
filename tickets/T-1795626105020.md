## Original body

A float wave prefix sum is lowered to `wavePrefixOp` kind 0 (`WavePrefixSum`). On an AMD Radeon driver the value a lane gets is wrong when that lane's **own** term is NaN, +infinity or 2^60 (the one large value tried).

Found with a synthetic test while testing #470: hand-written console programs, no game files. I have not seen it in a game and do not know whether any game shader takes a float wave prefix sum over such values. It does not come from #470: the float prefix sum already on main lowers the same way, and the same lanes are wrong on `ffe310e`.

**Setup.** One group of 32 threads, `WaveSize(32)`, `dxil.dll` validation on. Each lane loads a float from a structured buffer, a whole-wave section scans it, and each lane stores its prefix to a raw UAV. Compared lane by lane with the section's instructions run on the CPU. The terms are small multiples of 0.25, so their sums are exact in any order; then a term is replaced (NaN in lanes 9 and 20, or in lane 0; the other two in lane 11).

| the lane's own term | exclusive prefix in that lane | inclusive prefix in that lane |
|---|---|---|
| NaN | NaN, want the sum of the lanes below (-3.75 in lane 9, 0 in lane 0) | NaN, as wanted |
| 2^60 | 0, want -17.75 | 2^60, as wanted |
| +infinity | NaN, want -17.75 | NaN, want +infinity |

Every other lane is as wanted, and the set with no such term is exact.

- **Where:** Radeon iGPU of a Ryzen 7 7700X, driver 32.0.21030.2001 (September 2025), waves of 32 to 64. One GPU and one driver version.
- **Not there:** an RTX 4080 (driver 621.14) is exact in every case, and the integer prefix sum is exact on both.
- **Not the translator:** plain HLSL `WavePrefixSum` compiled by DXC 1.8.2502.11 (Windows SDK 10.0.26100) gives the same wrong lanes and values on the Radeon (shader below).
- **Documentation:** Microsoft defines the result as the sum over the active lanes with smaller indices, and says the lowest active lane always receives 0; with a NaN in lane 0 that lane reads NaN. The same page says the order of operations is not guaranteed. No order of the lanes below gives these values, but the 2^60 row is the one a vendor could call rounding.
- The three results fit a prefix made as the sum up to and including the lane, less the lane's own term. That reading is mine; the driver is closed.
- The exclusive prefix is the raw result of the op, so it is the exposed one. The inclusive one adds the term back, and of the cases tried only the infinite term shows there.

I have not tried a fix.

<details>
<summary>HLSL that shows it without the translator</summary>

```hlsl
#define RS "DescriptorTable(SRV(t0)), DescriptorTable(UAV(u0))"
StructuredBuffer<float> In : register(t0);
RWByteAddressBuffer Out : register(u0);

[RootSignature(RS)]
[WaveSize(32)]
[numthreads(32, 1, 1)]
void main()
{
    uint lane = WaveGetLaneIndex();
    float x = In[lane];
    Out.Store(lane * 4, asuint(WavePrefixSum(x)));
}
```

`dxc -T cs_6_6 -E main`, one group dispatched, `In` holding 32 floats. This is the exclusive form; `WavePrefixSum(x) + x` is the inclusive one.
</details>

It is not on main: added to `ffe310e` with its two lines in `emit/mod.rs`, the sum tests need no other change. On the Radeon `an_exclusive_prefix_sum_of_f32_reads_back` fails on the NaN, 2^60 and infinity sets and `an_inclusive_prefix_sum_of_f32_reads_back` on the infinity set; every set is exact on the RTX 4080.

### Comment 1 — @pickles976 — 2026-11-24T16:21:42Z

Divergence note from ivall/xcl, plus a possible structural exit: **we do not emit `WavePrefixSum` at all** — our lowering has no dependency on the vendor prefix intrinsic, so this Radeon-driver defect cannot reach our users, and it suggests your fix need not be a lane-correction hack: a **shift-and-add Hillis-Steele lowering** (5 log-rounds of `WaveReadLaneAt(v, lane - step)` guarded for `lane >= step`, IEEE-754 add) is bit-exact under the sequential order the ISA defines (`v_peres`-style prefix semantics) while touching no vendor fast path. Cost: 5 cross-lane reads vs one intrinsic — on the affected driver that is the difference between wrong and right; on healthy drivers a one-line capability switch keeps `WavePrefixOp`.\n\nTwo rows worth adding to your synthetic before this settles: ① **integer prefix on the same driver** — if the int path is correct, the defect is in the float fast path specifically and your capability table can be typed; ② **`WaveExclusivePrefixSum` float** on the same NaN/+inf/2^60 lanes — vendor fast paths for inclusive and exclusive variants are often different code, and if both are wrong the "replace the float path" conclusion generalizes immediately instead of needing a second bug report later. On 2^60 specifically: that looks like the driver specializing associativity-reordered sums past IEEE (any reassociation changes the exact result once saturation-like fast adds enter) — if so, plain large-but-normal pairs (2^60, 1.0, repeated) would reproduce without exotic values, which matters for judging whether a real title can hit it.


### Comment 2 — @Paull007 — 2026-11-24T16:38:09Z

[0001-Shaders-a-float-wave-prefix-sum-from-lane-reads-not-.patch](https://github.com/user-attachments/files/35357728/0001-Shaders-a-float-wave-prefix-sum-from-lane-reads-not-.patch)

A possible fix (patch attached): float prefix sums are built from lane reads instead of `WavePrefixOp`, so the driver's float prefix path is never used. Each lane points at the nearest active lane below it (from a ballot), and each round adds that lane's partial sum and takes its pointer, so inactive lanes are never read. Integer sums keep `WavePrefixOp`. The inclusive sum now comes straight from the scan, which also fixes the +infinity inclusive row.

Checked: a CPU model of the emitted steps matches a sequential sum over random masks, wave sizes 32/64/128, and NaN/+inf/2^60 terms; a new lowering test goes through the new path; all shader tests pass. Not run on a GPU yet: could someone with the Radeon iGPU run `wave_prefix_tests.rs` with this applied? It also touches the same match arm as PR 470.
