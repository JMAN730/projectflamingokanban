## For the maintainers

- **CI.** Every bundle branch has one workflow run in `action_required` (first-time contributor approval); the API lists 1,039 such runs for the repository as I write this. Approving a bundle's run gives CI for all of its components at once, 25 runs for 243 PRs.
- **Merging.** The repository merges with merge commits, and the bundles are built for that: the component heads stay in the history, so authorship is kept and GitHub should mark the component PRs as merged. A squash would lose that. Stacked bundles go in order: #1319, then #1402, then #1492, then #1504, then #1511, then #1589, #1593 and #1644 (all on #1511); and #1418, #1426 and #1439, then #1542 (each says on which it is stacked); the others are independent of each other, apart from the files they share, so after one lands the next may need a rebase (the bundle checks each PR only against `main`, or against the stack it names).
- **One by one.** Each bundle lists its components with their heads, and what it left out, so the same set can be merged PR by PR in the order given.

## What a bundle does not tell

- The title was not run. A bundle says the tree builds, lints and passes its tests, not what it does in game.
- Where two PRs do the same thing, the bundle keeps one and names the other under "Left out"; where two PRs disagree (for example #446 and #1199, #174 and #319) the bundle says which way it went.
- A bundle merges only PRs that merge with each other without conflict, or with a stated resolution. The PRs that conflict are listed per bundle and need a rebase after it lands.
