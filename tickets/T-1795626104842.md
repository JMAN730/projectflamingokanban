## Observed behaviour

### 1. Pre-existing DXIL readback message (likely benign)

```
descriptor's address or format read as data is not supported
```

First line after start, no `WARN` prefix. Looks like a known/separate limitation and does not abort the
run.

### 2. Main finding: 14 compute pipelines fail to translate → their draws are dropped

All emitted from the same site (`victory_gpu::pipeline`), three distinct error kinds, exclusively
`stage="compute"`:

| # | Hash | Offset | Error kind |
|---|------|--------|------------|
| 1 | `2c2cefe06f048390` | `0xbca8` | select on an untracked mask is not supported |

| 3 | `dbdad6ff83aadb1c` | `0xa290` | select on an untracked mask is not supported |
| 4 | `a0a074e2d868e618` | `0xba10` | select on an untracked mask is not supported |
| 5 | `05b939a0705f27ed` | `0xe008` | lane mask holding lanes elsewhere read as data is not supported |
| 6 | `2bf91065944bcff4` | `0x3974` | structured buffer of unknown stride is not supported |
| 7 | `2582aab1c7e668e5` | `0x3780` | structured buffer of unknown stride is not supported |

| 13 | `52b84c47ea411af2` | `0x926c` | lane mask holding lanes elsewhere read as data is not supported |

Three root causes, each hit repeatedly:

- **A. `select on an untracked mask`** (4×) — a VCN/VALU select form whose mask is not tracked by the
  converter. Directly related to the recently merged per-lane work (`r4tedx/shader/per-lane-phi`).
- **B. `lane mask holding lanes elsewhere read as data`** (5×) — lane masks belonging to other
  waves/groups are made readable as data; the converter cannot represent that.
- **C. `structured buffer of unknown stride`** (5×) — StructuredBuffer whose stride is not known at
  translation time; offsets cluster tightly around `0x32xx–0x39xx`.

Graphics pipelines (mesh/pixel, vertex/pixel) appear only in the pipeline list, **never** in the error
lines → the defect is compute-side.

### 3. Slow submission right before the crash

```
WARN victory_gpu::host: slow host submission ms=5710 lists=26 pipelines={...}
```

5.7 s of host submission across 26 lists with ~90 loaded pipelines (~80 compute plus mesh/pixel and
vertex/pixel combos). This is a symptom, not proof, but it shows the host building one large command
list into which the missing/dropped compute pipelines are embedded.

### 4. The crash

```
ERROR victory_gpu::host: host GPU device removed after a submission of 26 lists; no breadcrumbs
  (Die angegebene Geräteschnittstelle oder Featureebene wird auf dem System nicht unterstützt. 0x887A0004)
  device removed: Die GPU antwortet auf keine weiteren Befehle mehr ... (0x887A0006)
VIctory: host GPU failure: ...; a diagnostics build with VICTORY_D3D12_DEBUG=1 names the command
```

- **0x887A0004 = DXGI_ERROR_UNSUPPORTED** — the interface/feature level is not supported.
- **0x887A0006 = DXGI_ERROR_DEVICE_REMOVED** — the GPU driver stopped servicing the device.
- **`no breadcrumbs`** — the breadcrumb/marker instrumentation could not name the offending command.
  That is a second defect in its own right (diagnostics regression) and hides where the removal came
  from.

## Expected behaviour

1. No Device Removed; the guest keeps running.
2. Compute shaders using untracked-mask selects, foreign lane masks, and unknown-stride
   StructuredBuffers are either translated or cleanly marked "not translated" **without** invalidating
   the subsequent submission.
3. `no breadcrumbs` should not happen on a diagnostics build — the breadcrumb for list 26 must be
   attributable.

## Hypotheses / leads for the root-cause hunt

- The three converter error kinds are the prime suspects for emitting invalid GFX10 code. A dropped
  draw should not invalidate the list; if the host proceeds anyway, invalid state results.
- **Offset clustering:** 5 of the 14 failures sit at `0x3268–0x3974` (stride), 4 at `0xa290–0xba10`
  (selects). That points at two compact code regions inside the same DXIL module — likely one shared
  shader/dispatch.
- **Relation to the last merge:** `Shaders: the console's waterfall loop over a first-lane table offset`
  (`ffe310e`) and `shader/per-lane-phi` (`ca48fbe`) touch exactly this VALU/lane-mask area. A
  regression comparison against `ca48fbe^` / `74a9d33` is the fastest test available.
- `ms=5710` may be a timeout/overshoot that finally flushes the poisoned list.

### Comment 5 — @MichaelSmithAI — 2026-11-24T11:05:07Z

We checked what happens after a compute shader is refused. On `ffe310e`, direct dispatch already returns when there is no host compute pipeline. Ordinary indirect dispatch also drops the requested dispatch, but it prepares the argument buffer and can record its separate argument-clamp operation before checking the pipeline.

[This focused change and regression test](https://github.com/MichaelSmithAI/VIctory/commit/166cb8a8d785596c762c8a437cb1fa197ce260c3) move the check ahead of that preparation. In the recording test, the original code queued an argument refresh for a dispatch it had already lost. The change queued neither the refresh nor the clamp. A separate supported indirect-dispatch control still returned the expected GPU output on RTX 4090 under Wine/vkd3d.

This establishes unnecessary work on the drop path. The log’s shader refusals do not identify which GPU operation caused the later device removal, and we haven’t measured a frame-time or stability change in the game.

The two HRESULTs in the log come from different calls. The device-removal reason is `0x887A0006` (`DXGI_ERROR_DEVICE_HUNG`). The breadcrumb query returned `0x887A0004` (`DXGI_ERROR_UNSUPPORTED`), which Microsoft documents when auto-breadcrumbs were not enabled. On this revision, a diagnostics build uses `VICTORY_D3D12_DRED=1` at startup to enable breadcrumbs before device creation. `VICTORY_D3D12_DEBUG=1` enables the separate debug layer. The existing log leaves the last GPU operation unknown. [Microsoft’s GetAutoBreadcrumbsOutput reference](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12deviceremovedextendeddata-getautobreadcrumbsoutput)
