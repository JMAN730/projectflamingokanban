## Original body

Environment
- VIctory commit: `ffe310eb2098e52169f4c44db5ffdabf43a72622` (2026-11-24)
- Build: `cargo build --release -p victory --features diagnostics`, run with `VICTORY_D3D12_DEBUG=1`
- GPU: NVIDIA GeForce RTX 5070, driver 32.0.16.2124 (NVIDIA 621.24)
- OS: Windows 11 Pro 10.0.26200
- Game files: package 1.0.2.1, `game_scarlett_master.exe`, blake3 `b99f876b74d4a77f03af5f878223b27bd647b5c35a79d5decd9f716504239e93`
- Console model: series-x (default)

Summary: the title reaches the first mission intro, renders it, and then the host GPU device is removed. 449 distinct shaders fail to translate, and the submission that kills the device takes 3 seconds, past the Windows TDR limit.

## Where it stops

Frames 0-1248 run. Menu screens are fine; the first world frames are not:

```
30.1 fps, 33.2 ms/frame, 16 draws/frame, dropped 0 without a host pipeline (129 being made)
 1.1 fps, 917.4 ms/frame, 4 draws/frame, dropped 1 without a host pipeline (363 being made) and 0 indirect
 0.8 fps, 1234.2 ms/frame, 1841 draws/frame, dropped 1897 without a host pipeline (420 being made) and 1215 indirect
```

Seven "a black frame after a frame that was not" warnings appear, which matches what the window shows: a dark scene with occasional frames.

## The crash

```
WARN  victory_gpu::host: slow host submission ms=3024 lists=26 pipelines={...}
ERROR victory_gpu::host: host GPU device removed after a submission of 26 lists; no breadcrumbs
      (0x887A0004); device removed: ... (0x887A0006)
```

Slow submissions over the run (ms / lists):

```
7733 / 11
3024 / 26   <- the fatal one
1912 / 24
 907 / 17
 832 / 33
```

23 slow submissions in total, maximum 7733 ms. The fatal submission is 3.0 s against the default 2 s TDR timeout, so the device removal looks like a timeout of a single oversized submission rather than one bad command: it records 26 lists covering 11 compute, 67 mesh and 1 vertex pipelines, and pipelines are still being created while it runs ("420 being made" in the frame line above).

`an address in an SGPR that is no root parameter` (35 shaders) is the most repetitive single site: 28 of them report it at `0x30`, 4 at `0x40`, which suggests one common prologue pattern rather than 35 unrelated cases.

## What is probably worth fixing first

1. The TDR: a 3 s submission cannot succeed on any driver with the default timeout. Splitting the submission or finishing pipeline creation before recording would turn the hard crash into slow frames.
2. `image_gather4_l` and `a 64-bit image atomic` are named instructions with a narrow implementation, unlike the mask-tracking messages.
3. The mask-tracking family (`untracked mask`, `lane mask ... read as data`, `lane mask read as data`) accounts for 191 of 449 shaders, so it is the single largest group.
