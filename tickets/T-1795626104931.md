## Original body

### Environment

- VIctory: `main` zip + Wasler's `fix/shader-top5` (commit `66252c0`, #728) + #876 branch `fix/issue-850-typeless-view` (commit `5e3c9e2`) applied on top
- OS: Windows 10 Pro 22H2 build 19045 (TdrDelay/TdrDdiDelay raised to 180 s; the defaults kill the world load)
- CPU: i5-14490F, 32 GB RAM
- GPU: NVIDIA RTX 5060 8 GB
- DirectX 12 Agility SDK 1.614 via local `D3D12\D3D12Core.dll` and `D3D12SDKVersion = 614` exports (Win10's inbox d3d12 rejects the `0xC01` root-signature flags outright, which cost us every pipeline before this)
- Title: 1.0.2.1, blake3 `b99f876b74d4a77f03af5f878223b27bd647b5c35a79d5decd9f716504239e93`

### What #876 fixed here

Before the typeless remap, every cutscene and the world came out as flat clear colour (`0x20202C`) while 451 mesh pipelines were created and `drawn` looked normal; frames took 62 s.

After applying #876, the same host renders:

- the Lucia key art in full colour (correct lighting, signage and car paint) at 30 fps / 11 draws
- the prologue title card `VICE CITY, TWO YEARS AGO` with the Chinese subtitle 【两年前，罪恶城】
- `no host texture` count stays at 0

So the typeless view remap is confirmed as the root cause of the black frames (#850) on this host, and it is the first time this machine has drawn anything but a blank screen.

### New blocker right after it

Entering the world, frames take 14.7 s, and the CBV/SRV/UAV descriptor heap gets capped:

```
WARN victory_gpu::descriptor::host: host view heap capped at 1000000
     error=参数错误。 (0x80070057) count=124518
```

Then draws start dropping:

```
WARN victory_gpu::draw: a draw or dispatch dropped: no dynamic slots for its tables
```

with the power-of-two counter reaching `65536`, and the title faults:

```
VIctory: first-chance exception 0xc0000005 at victory-image-b99f876b74d4a77f.dll+0x23cf683
         (write 0x0: nothing mapped there)
  #0 +0x23cf683  #1 +0x2215c35  #2 +0x2215eca
```

Frame statistics at the fault: `0.1–1.5 fps`, `3360–5553 draws/frame`, 17 GB working set, no device removal (TDR 180 s held).

So with `count = 124518` title views the heap cannot take `count + DYNAMIC` (2^18) — every attempt returns E_INVALIDARG — and the fallback leaves too few dynamic slots for a world frame that keeps thousands of tables alive until its lists reset.

### Questions

1. Is the `count + DYNAMIC` refusal expected on 8 GB NVIDIA parts, i.e. should the dynamic range live in its own shader-visible heap instead of stacked on top of the title's 124518 views?
2. Is `dropped=65536` the cumulative counter (it only logs at powers of two), not a single table asking for 65536 slots?
3. Given the per-frame table churn (tables rebuilt per draw, held until the list resets) and 14 s frames, is a larger `MIN_DYNAMIC` the intended lever, or does this need the list-lifetime rework?

I can rerun a diagnostics build with `VICTORY_D3D12_DEBUG=1`, `VICTORY_CAPTURE` and `VICTORY_DUMP_TARGETS=1` and attach whatever would help narrow it down.

### Comment 2 — @MichaelSmithAI — 2026-11-24T13:38:49Z

Yes to question 2. On upstream `ffe310e`, `dropped=65536` is the cumulative number of draw/dispatch bind attempts that failed for lack of dynamic table slots in the process. It logs at powers of two. That number gives neither the size of one table nor the number of drops in a single frame. [Counter](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/draw.rs#L461-L472)

For questions 1 and 3, the reported count and warning point to different branches of the upstream constructor. At 124,518 guest views it first tries 386,662 descriptors (adds 262,144), then 190,054 (adds 65,536). If both requests fail, that path logs “no host descriptor heap.” The million-slot cap warning requires the second request to exceed 1,000,000. Could you share the original unwrapped heap warning lines with the count attached to each, and the exact main ZIP revision or the constructor from the integrated tree? That would distinguish a different heap or build from a failure to allocate within a successfully created heap. [Heap constructor](https://github.com/Marvisak/VIctory/blob/ffe310e/crates/victory-gpu/src/descriptor/host.rs#L105-L121)

The named #728 commit changes four shader files and leaves the heap constructor intact. [Wasler’s commit](https://github.com/Wasler/VIctory/commit/66252c063f62b00560b09c709cbe895fede6b457)

D3D12 lets a draw bind one shader-visible CBV/SRV/UAV heap. If a draw uses both mirrored title descriptors and fresh tables, a second heap would have to hold all the resource descriptors that draw uses, with table handles and directly indexed slots preserved or remapped appropriately. The sampler heap is separate. [SetDescriptorHeaps](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-setdescriptorheaps)

A larger minimum or a second heap would be premature from this count alone. #871 also identified a case where a valid contiguous range spanning the search cursor was missed. Its contribution on this run is still unknown. [Allocator regression](https://github.com/pushkarreddyy/VIctory/pull/1)

Separately, your same-host comparison establishes a concrete visual gain with #876: the Lucia key art and prologue title card appeared. Which view supplied those pixels, and what caused the later world stop, remain open.

### Comment 9 — @Xvania7 — 2026-11-24T18:00:07Z

@bailu12300 Spot on. We investigated why the FSPX compute modules end up with a valid "no-shaders PSO" and drop every dispatch in `crates/victory-gpu/src/draw.rs`.

### Root Cause
1. **Container format:** `amd_fidelityfx_upscaler_xbox.dll` (FSR4 post-process upscaler) packages 29 compute pipelines either as raw `FSPX` payloads or as `DXBC` containers with an `ACCC` chunk and **no `DXIL` part**.
2. **Device Slot 67 vs Slot 62:** The DLL initially queries `DeserializeComputePipelineStateX` (slot 67 / `0x218`). In upstream `main`, slot 67 was unmapped (`missing_table`, returning `E_NOTIMPL`). Upon failure, the DLL sets `FFX_FSR4_XBOX_ACO_ACTIVE=0` and falls back to "NewBE" via slot 62 (`create_compute_x` / `0x1f0`).
3. **No-shaders PSO creation:** `create_compute_x` defers host pipeline compilation to first use and immediately hands out a valid guest `ID3D12PipelineState` handle with `S_OK`. The DLL receives a valid pointer and does not fault.
4. **Translation refusal:** When the pipeline is dispatched, `Shader::translated()` calls `victory_shader::emit::translate()`, which strictly checks for `FourCC::DXIL` (`c.part(FourCC::DXIL).ok_or(...)`). Because FSPX has no DXIL chunk, translation fails. `HostPipeline::new` returns `None`.
5. **Dispatches dropped:** In `crates/victory-gpu/src/draw.rs`, `host_pipeline(self.pipeline)` returns `None`, logging `"a dispatch without a host pipeline dropped"`. Every single compute dispatch for post-processing / lighting composition is skipped. As a result, the 2560x1440 target remains untouched at background clear (44), and only 2D HUD / subtitle graphics draws are composited on top.

### Branch with Fix & Diagnostics
We opened a branch with full FSPX container parsing, slot 67 dispatch wiring, and diagnostic tracing:
**https://github.com/Xvania7/VIctory/tree/fix/issue-887-fspx-shaders** (commit `d7d0770`)

- **Slot 67 implemented:** `DeserializeComputePipelineStateX` (0x218) is now wired and extracts kind 0 (dispatch state: `NumThreadsX/Y/Z`, `wave32`/`wave64`, RSRC1/2), kind 1, kind 6 (RDNA2 program code), and kind 7.
- **FSPX container inspection:** `inspect_fspx` parses bare FSPX containers and DXBC `ACCC` chunks.
- **Diagnostic logging:** `Shader::translated()` and `create_compute_x` now print the exact shader hash, thread group dimensions, wave size (`wave32` vs `wave64`), and bytecode size.
- **Drop attribution:** `missing()` in `pipeline/make.rs` now tags dropped pipelines as `compute <hash> (FSPX compute module)` so drops are attributable in frame statistics.

If you test this branch with your setup, the log will output the exact hashes and thread dimensions of the 29 FSPX modules being executed by the upscaler.

### Comment 10 — @Xvania7 — 2026-11-24T18:13:50Z

@bailu12300 We put together an experimental branch designed to test how `amd_fidelityfx_upscaler_xbox.dll` and the game engine respond when FSPX compute pipeline creation fails:

**Branch:** https://github.com/Xvania7/VIctory/tree/experiment/fspx-force-dxil (commit `e60e91c`)

### The Hypothesis
In upstream `main`, slot 67 returned `E_NOTIMPL`, causing the DLL to fall back to slot 62 (`CreateComputePipelineStateX`). VIctory was returning `S_OK` from slot 62 without a compiled host shader, fooling the DLL/engine into believing the FSR4 compute pipelines were active, only for every dispatch to drop in `draw.rs` (black screen with clear color 44).

Modern game engines integrating upscalers (FSR/DLSS) usually have an internal fallback (engine-native TAA / resolution resolve) if the upscaler context or its pipelines fail to initialize. The engine's internal resolve shaders are compiled into `shaders.rpf` as standard DXIL, which VIctory *can* translate.

### What to Test

1. **Default run (`E_FAIL` on slot 67):**
   Just run the branch as-is. Slot 67 will log:
   `DeserializeComputePipelineStateX (slot 67) called for FSPX; returning E_FAIL (0x80004005) to force DXIL fallback`
   - Observe if the DLL falls back to standard DXIL shaders or if it attempts slot 62.

2. **Reject FSPX across both slots:**
   If the DLL still attempts to push FSPX bytecode through slot 62 (`create_compute_x`), set:
   ```cmd
   set VICTORY_FSPX_REJECT_SLOT62=1
   ```
   This rejects FSPX creation in slot 62 with `E_FAIL` as well. This will definitively fail the upscaler's pipeline creation and test whether the game engine catches the error and activates its internal DXIL post-process fallback.

3. **Testing `E_INVALIDARG`:**
   If `E_FAIL` causes an unhandled fault in the DLL, you can test `E_INVALIDARG`:
   ```cmd
   set VICTORY_SLOT67_HR=E_INVALIDARG
   ```

If either fallback activates, we should see actual pixels rendered to the presented 2560x1440 target instead of clear color 44. Even if it doesn't immediately draw, the log will show exactly how the DLL handles non-`E_NOTIMPL` failure codes.
