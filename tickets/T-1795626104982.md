## Original body

## What

`a scalar memory read as data` is the largest single translation failure class in the corpus — 771 of 26,084 programs offline. I diagnosed which of its three return points produces them and found a fix that clears the class and raises DXIL emission by 231 programs.

## Diagnosis

Splitting the three returns (`descriptor_data`: non-register operand / unusual load width / use-instruction kind) into distinct messages and re-running the batch puts **all 771** on the third one. A second split of that branch by instruction prefix shows the use instruction is always an `s_` operation — never an image or buffer access, and never another `s_load` or `s_buffer_load`.

So these programs read a descriptor's words as data (dimension or address arithmetic) and never sample or store through it. The lowering insisted on an image/buffer use point to learn the view's kind, and refused the program when the only use was scalar.

## Fix

That branch now infers the view from the used-resource entry the load falls in — the same way the "no use point at all" path already does:

- 8-dword descriptor → 2D image (properties `0x409`, kind 4)
- 4-dword descriptor → structured buffer when the stride is known and a multiple of 4, raw otherwise
- constant-buffer descriptors stay refused (a CBV's words are not a view)

Sizes are rebuilt through `getDimensions` and written back as the descriptor's dwords.

## Measured offline

`victory translate` over the title's shader container dump (26,503 containers / 26,084 programs), release build, same host, both runs:

| metric | before | after |
|---|---|---|
| `emit: a scalar memory read as data` | 771 | **0** |
| vertex+pixel programs emitting DXIL | 12252 / 14027 | **12309 / 14027** |
| compute programs emitting DXIL | 1443 / 2582 | **1451 / 2582** |
| mesh programs emitting DXIL | 8214 / 8713 | **8380 / 8713** |
| `emit: a descriptor's address or format read as data` | 92 | 589 |

+231 programs (mesh +166, vertex/pixel +57, compute +8).

The last row is the next failure being exposed, not a regression: those programs now translate further and reach the address/format class, which is a different problem — those dwords genuinely have no host value. It becomes the second largest class at 589.

## Not measured

- Runtime behaviour: offline translation only. Whether the inferred views sample correctly in the world is untested (this host freezes on device removal during world load).
- The 3D/cube-image minority of that class is taken as 2D, which is a guess.

Patch is on our fork (`try/pr89`, commit `0691fdb`); happy to open a PR on request.

### Comment 4 — @fuzeofficlal — 2026-11-24T17:18:53Z

Cross-checked all three `Lower::descriptor_data` failure slices raised here (`s_buffer_load*` `Fields::Smem` + `dword 2` size read, twin `s_load_dword*` to the same 32-byte heap slot, and pure `s_load_dwordx4/x8/x1` size queries backed only by `UsedResource`) against `#953`, `#1067`, and `#1130`, and verified a combined branch on **NVIDIA GeForce RTX 5090**, **D3D12 WARP**, and **`dxil.dll`**: [`fuzeofficlal/VIctory@66a9fde`](https://github.com/fuzeofficlal/VIctory/commit/66a9fde8f8c1c163f460c81d7eef9b49f52af519) (`fix/descriptor-data-infer-view-979`).

Key subtleties uncovered during GPU + `dxil.dll` verification:
- **`Fields::Smem` (`s_buffer_load*`)**: `Lower::smem` only emits a raw SRV `(11, 0)` when `used.is_some_and(|u| u.kind == ResourceType::Srv)`, and declares CBV `(13, 0x1_0000)` when `used` is `Some(Cbv)` **or `None`** — so `descriptor_data` must require `Some(Srv)` (and keep `uav = false`) to avoid emitting conflicting CBV + SRV handles on the same slot.
- **Twin-entry lookup before `UsedResource` fallback**: Matching `b.offset + 4 * other_first == (a.offset & !31)` preserves exact 1D/2D/3D/Array/Typed dimensions when another load accesses the same 32-byte entry, while keeping `site`'s own `first = 0` and `in_slot = (a.offset & 31) / 4`.
- **Pure-data `UsedResource` fallback**: Checking `in_slot + count <= u32::from(used.dwords)` and restricting 4-dword raw buffers to `used.stride == 0` supports narrowed `+0x08` single-dword `NUM_RECORDS` loads while preventing non-multiple-of-4 structured strides from silently returning byte counts instead of element counts.

### Comment 5 — @EduAzevedo — 2026-11-24T17:32:47Z

finding: "a descriptor's address or format read as data" can't be fixed from host view dimensions. Programs read real V# fields that a host view doesn't have.

**Where:** `crates/victory-shader/src/emit/lower.rs`, `descriptor_data`, the `None =>` arm that stores `Val::Missing(OTHER)`. That function rebuilds only the size fields (image dwords 1–4, buffer dword 2) from `getDimensions`.

**How it was measured:** I ran `victory translate --jobs 8` offline on all 26,148 programs of a retail dump, twice:
- on `main` (ffe310e);
- on `main` with only Machad3x's `bc2b1b5` (#979) cherry-picked. `0691fdb` from the issue body is no longer on `try/pr89`.

A local, uncommitted census renamed each `OTHER` refusal by dword index and by the first instruction consuming that dword. Only counts are given here.

**On main: 92 programs**

| Dword | Programs |
|---|---|
| image dword 0 | 39 |
| buffer dword 1 | 22 |
| buffer dword 3 | 17 |
| image dwords 5–7 | 14 |

- Buffer dword 1: all 22 are raw buffers. They do `s_cmp_lt_u32 dword1, 0x1000000`, i.e. "is the stride below 256?".
- Buffer dword 3: these are copied whole with `v_writelane_b32`.

**With #979: about 600 programs, matching the issue's 92 → 589.** Almost all are raw buffers (kind 11, which #979 gives `s_buffer_load` sites).

| Dword | Programs (approx.) | First consumer |
|---|---|---|
| buffer dword 1 | ~250 | stride bits 16–23: `s_bfe_u32 …, 0x80010`, `s_and_b32 …, 0xff0000`, `s_cmp_eq_u32 …, 0x80`, `s_cmp_lt_u32 …, 0x1000000`; a few test bit 8 or bit 20 |
| buffer dword 0 | ~145 | `s_and_b32 …, 0x100000`: bit 20 of the base address; a few test bit 8 |
| buffer dword 3 | ~110 | `s_and_b32 …, 0x100`: bit 8, inside dst_sel_z; or the whole dword via `v_writelane_b32` |
| image dwords 0, 5–7 | ~50 | address shifts, layout fields, `v_writelane_b32` |

**Why it matters:** these bits pick the program's path, and a ByteAddressBuffer view has no stride, address or dst_sel. Synthesising them, for example `stride << 16` with a made-up stride, would be a guess. Rebuilding more fields from the host view can't fix this class.

The fix that looks correct is to give the program the descriptor's real dwords: the runtime already reads them from title memory to build the views, so they could be passed to the program. That changes the root signature and how the translator and runtime hand off descriptors, so it needs a maintainer's call before anyone writes code.
