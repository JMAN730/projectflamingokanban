# RTX 4060 Laptop: 435 runtime shader translation failures, then host device removed at world load

## Environment

- **GPU:** NVIDIA GeForce RTX 4060 Laptop GPU (8 GB), driver `32.0.15.6607` (Vulkan `1.3.289`, `driverInfo 566.07`)
- **CPU:** Intel Core i7-13620H (10C / 16T, AVX2)
- **RAM:** 15.6 GB
- **OS:** Windows 11 Home 中文版, build `26200`
- **Rust:** `1.98.1` (pinned by `rust-toolchain.toml`), MSVC 19.43
- **VIctory commit:** `ffe310e`
- **Package:** Xbox Series 1.0.2.1, 107 of 108 manifest files byte-exact; `game_scarlett_master.exe` SHA-256 `e95020b2fa4a721db3df59fdecf75621730ac559d8835252f6c3b658d5a08993`

## What works

The first-boot flow is solid: boot, accessibility/language/settings/legal pages, **30 fps / 33.3 ms/frame / 21 draws/frame**, continuously for **628 s** before the world-load failure. This matches #653 and #314 exactly, on a card neither of them tested.

## What happens

```powershell
victory.exe run <game>\game_scarlett_master.exe --console series-x --unimplemented zero --execute
```

1. Accepting the legal terms starts the world load.
2. Loading artwork plays, then the screen goes black partway through.
3. Artwork reappears, then the process exits.

Log tail:

```
WARN victory_gpu::host: slow host submission ms=2258 lists=11 pipelines={...}

ERROR victory_gpu::host: host GPU device removed after a submission of 11 lists; no breadcrumbs
      (指定的设备接口或功能级别在此系统上不受支持。 (0x887A0004));
      device removed: GPU 不响应更多的命令，最为可能的原因是调用应用程序传递了无效的命令。 (0x887A0006)

VIctory: host GPU failure: host GPU device removed after a submission of 11 lists
```

Process exit code: **`0x887A0005`**.

Worth flagging: the process exits with `0x887A0005`, while the host layer logs `0x887A0004` / `0x887A0006`, **on the hardware adapter** (no `VICTORY_D3D12_WARP`). #653 records `0x887A0006` for the real GPU and `0x887A0005` for WARP; this run got `0x887A0005` on hardware, so the outer code may not be a reliable WARP indicator.

## `translate` reports 100% on the same build

`victory translate <game> --list` over the whole package:

```

structured   26148 of 26148 (32660347 vector instructions, 822675 guarded, 49485 on opaque masks)

             used-resource entries 432763: 187 not traced
```

**Zero failures**, immediately before a run that fails 435. So `translate` does not see the programs that actually break the world load. Per `docs/architecture.md` shaders are translated at pipeline creation from the bytes the title passes, wherever it loaded them from — these 435 are evidently not in any container `translate` walks.

This matters for users: `26148 of 26148 translated` looks like a clean pre-flight and is not one. If the gap is by design, a line in the `translate` summary saying how many containers/files it could not reach would stop it reading as a green light.

## The submission that kills the device

**11 lists**, **2258 ms**, first-using a batch of compute pipelines plus mesh+pixel pairs and a few vertex+pixel pairs:

```
[compute 0c0380d9ec648626] [compute 0ccc14877cbec21e] [compute 1c8165626a581de4] ...
[mesh 0b15057954f1321e, pixel 055dd1a8f7b02013] [mesh 0d9d1c59733d6340, pixel c9443dc523f51e29] ...
[vertex 37ab3687378a8761, pixel f705157e661e716f] ...
```

Different shape from #653 (31–32 lists there, 11 here), same phase. The 2258 ms slow submission immediately precedes the removal — consistent with #1082's suggestion of logging the TDR settings.

## Ruled out on this machine

- **Memory:** reproduced from a clean start with 6.8 GB free; same point.
- **`--console series-s`:** identical failure.
- **`rpcrt4.dll` refused by the host policy:** adding it to `HostPolicy::default()` silences the warning and changes nothing else; the world-load removal is unchanged. Reverted.
- **`appdata0.rpf` placement:** this *was* the cause of an earlier `0x80000003` at `title+0x2237178` (issue #12). Fixing it reached the menus; it is **not** related to this failure. Confirming #12's finding on a third machine.

## Ask

1. Is `a descriptor read only as data` (62 here, 62 = 14% of my failures) known/expected, or new relative to #653's table? It does not appear in that issue's top five.
2. Would a `--features diagnostics` build with `VICTORY_D3D12_DEBUG=1` + `VICTORY_D3D12_DRED=1` identify the offending command? Happy to run it and paste the DRED breadcrumbs.
3. Should I bisect with `VICTORY_SKIP_PIPELINES=<hash>,...` over the compute pipelines in that submission to see whether the removal follows one in particular? If so, which subset is most useful — the 370 compute failures, or the 18 that were first-used in the killing submission?

### Comment 2 — @antikohza — 2026-11-24T19:58:55Z

@imrealynailong — regarding your hybrid laptop setup here (i7-13620H + RTX 4060 Laptop 8 GB, 15.6 GB RAM) hitting `0x887A0004` after 11 lists:

Two parts of what hits this hardware class (same laptop class profiled in #1226) are now fixed in **PR #1296** (`a6f3ccb`, [Windows CI green](https://github.com/antikohza/VIctory/actions/runs/45470890213)):
1. **Integrated GPU default (`0x887A0004`):** `D3D12CreateDevice(None, ...)` defaults to the 128 MiB Intel iGPU on hybrid laptops unless overridden; #1296's `best_adapter()` probes FL 12.0 non-software adapters and creates the device directly on the discrete RTX GPU.
2. **8 GB VRAM / 15.6 GB commit exhaustion:** #1296 matches the device's own LUID and auto-enables `VICTORY_TEXTURE_MIP_DROP=1` on `<= 8.5 GiB` GPUs (verified saving ~1.1–1.2 GiB VRAM and eliminating `E_OUTOFMEMORY` on 8 GB laptops in #1226 and #737).

Note that your 435 runtime shader translation failures are still separate (#653 / Wave64 PRs), so you'd want those stacked too, but #1296 takes care of the adapter choice and 8 GB / 15.6 GB memory ceiling.

I tried two local patches against the world-load failure. Both are **reverted**; the tree is clean at `ffe310e` again. Recording them because the negative results are informative.

`VICTORY_CAPTURE=<dir> VICTORY_DUMP_TARGETS=1`, diagnostics build.

So "skip the failing compute pipelines" does **not** fix the world: it removes the visible errors while the picture stays black. I think that is the worst of the three outcomes to report as an improvement, and I would not submit it as a patch.

It also means the "it ran 441 s instead of 142 s" framing is misleading — the extra time is spent presenting black frames, not making progress.

### What I take away

1. The 64-lane compute refusals are a real defect (`Shader wants wave lane count of 64 but maximum wave lane count for device is 32`), but they are **not** the only thing keeping the world from rendering, since skipping them all does not produce a picture.
2. The descriptor heap truncation is also real, and fixing it changes the failure mode, but not the end state.
3. The baseline failure on this machine is an access violation **inside `nvwgf2umx.dll`** right after a slow 18-list submission — different in character from the `DEVICE_RESET` / `DEVICE_HUNG` removals in #653, and from the DRED `Kernel memory failure` I reported earlier. Across my runs I have seen all three of these outcomes, which suggests the failure is timing- or order-dependent rather than one deterministic bad command.
