## Original body

On `ffe310e`, the placed-buffer source of `CopyTextureRegion` is filled from CPU memory before the GPU list runs. When a GPU command writes the source buffer earlier in that same list, the texture receives the old bytes even though the source contains the new bytes after submission.

I reproduced this through the guest copy call with a synthetic 4×4 RGBA8 texture on RTX 5090 and WARP. Stock and main + #334 both read back **0/16** new pixels after a tracked same-list GPU copy. With the follow-up both read back **16/16**. A tracked native UAV dispatch also passed with source offsets 512 and 516, including replay with changed inputs. CPU uploads recorded before a late CPU write, two ordered CPU snapshots, and the partial-write snapshot control all passed. The probes reported zero D3D12 debug-layer errors.

[Source follow-up `517a2a5`](https://github.com/fuzeofficlal/VIctory/commit/517a2a5dedfe890fff580bc0ba4c0509bf594d4b) is stacked on #334 at `af2aecf`. It uses the host buffer with #334's read transition when the latest tracked GPU write in that list covers the footprint. Other cases use the existing upload snapshot path. The unaligned offset is rebased with a GPU buffer copy.

### Comment 1 — @DrDarkDK — 2026-11-24T10:46:57Z

I tested a boxed-copy case on `517a2a5` with a 4×4 RGBA8 placed footprint, 256-byte row pitch, and source box `[0, 0, 0, 2, 1, 1]`. An earlier tracked `CopyBufferRegion` on the same list wrote the first 8 bytes, covering both pixels the box reads.

On both RTX 4070 Ti (621.01) and WARP, all 8 source bytes contained `0x6d` after submission, but both destination pixels still contained the old `0x11` bytes. With the same box and a 1024-byte GPU write covering the full footprint, both destination pixels contained `0x6d` on both adapters.

`placed_copy_source` checks write coverage against the full footprint, so the 8-byte case takes the CPU snapshot path even though the GPU produced every byte the box reads.
