### Comment 1 — @pickles976 — 2026-11-24T18:07:15Z

Before deeper triage on this Turing host: one variable is unlogged and load-bearing on **every** NVIDIA card — wave mode. Turing advertises 32-lane waves, and Victory's default `recommended_wave64_mode` picks native Wave32 (legalize-without-remap → silently wrong cross-lane compute; eternal loading or gates-never-open, healthy GPU, clean log — the documented class in #1086 row 2, and the reason the world-running nine-stack sets `VICTORY_WAVE64_EMULATE=emulate` explicitly). Same-card-class A/B costs one run: add `emulate`, everything else identical, and if the intro/crash behavior moves anywhere, this report becomes a data point in the default-policy debate rather than a new mystery. Second screening line (both projects' intake list now): `TdrLevel` from the tester's registry, so a future "whole desktop freezes" duplicate does not get filed as a separate class (your #1054). 11 GB is above the budget-kill band, so wave mode is the first suspect, not memory.


### Comment 2 — @NuraadGit — 2026-11-24T18:20:14Z

Same card family here (RTX 2080, Turing, 8 GB, driver 616.56), so here is what keeps it in the world on this side, in case it saves you some runs.

On plain `main` my 2080 behaves much like yours: slow host submissions, then 0x887A0006. These keep it up (12+ minutes in the world, ~0.7–0.9 s/frame, ~2,300–2,800 draws/frame, no device removal):

- #493 (root SRVs as bounded one-view tables)
- #189 (Wave64 emulation on 32-lane hosts; its head defaults to emulate, which is the wave-mode point pickles976 raised above)
- #206 (structured views off a host copy's elements as raw views)
- `MIN_DYNAMIC` raised from `1 << 16` to `1 << 18` in `descriptor/host.rs` (#747); without it the world's tables run out of dynamic slots and the indirect/mesh draws drop
- `VICTORY_SHADER_LOOP_LIMIT=32`
- #1009 if you ever see startup failures from 32-bit title allocations

On your two dropped shaders: compute `0873f80dd84a3c5c` ("an address not from a root parameter") is still refused on that stack too, so it isn't what separates a working 2080 from a hanging one. Pixel `e78420aa96677632` never shows up in my runs (I load from a save, so I don't pass through the intro credits).

One difference worth ruling out: 46.2/47.4 GB committed with the pagefile disk at 100% means the host was paging hard during those 510–685 ms submissions, which could stretch them on its own. A run with more free RAM (or the pagefile on a less busy disk) would separate that from the GPU side.
