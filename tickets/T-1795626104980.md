## Original body

# Intel Arc (Xe-LPG): `v_med3_f32` with a NaN operand returns the median, not the minimum

## Environment

- Windows 11 Pro for Workstations (26200), Core Ultra 9 185H, 32 GB
- GPU: Intel(R) Arc(TM) Graphics (integrated, `vendor 8086`), driver
  **32.0.101.6127**
- Rust 1.98.1 (the pinned toolchain), MSVC 14.51
- `main` as of 2026-11-24 ~13:30 UTC (codeload zip; head at the time was
  `ffe310e`)

## What happens

```
cargo test -p victory-shader --lib v_med3_f32_matches_rdna2_with_nan
```

```
thread 'emit::valu_tests::v_med3_f32_matches_rdna2_with_nan' panicked at
crates/victory-shader/src/emit/valu_tests.rs:296:27:
assertion `left == right` failed:
hardware: v_med3_f32(1.0, 2.0, NaN) = 2 (0x40000000), want 1
```

The first four cases (no NaN) pass on this GPU. The first NaN case fails:
`v_med3_f32(1.0, 2.0, NaN)` gives `2.0`, where RDNA2 gives `1.0`.

## What it is not

- **Not the test's WARP half.** `VICTORY_WARP=1 cargo test -p victory-shader
  --lib v_med3_f32_matches_rdna2_with_nan` passes: WARP agrees with RDNA2 on
  every case, so the emitted DXIL is right and this is the Intel driver's
  handling of it.
- **Not `v_med3_f16`.** `v_med3_f16_matches_rdna2_with_nan` passes on the
  same GPU, so it is the f32 lowering.

## Where it points

`emit::lower::Lower::med3` (`lower.rs:1469`) computes

```rust
let lo = self.binary(36, a, b);      // min(a, b)
let hi = self.binary(35, a, b);      // max(a, b)
let t = self.binary(36, hi, third);  // min(max(a,b), c)
let median = self.binary(35, lo, t);// max(min(a,b), min(max(a,b), c))
let least = self.binary(36, lo, third);
let nan = or(cmp(UNO, a, b), cmp(UNO, third, third));
select(c, nan, least, median)
```

For `(1.0, 2.0, NaN)`: `lo = 1`, `hi = 2`, `t = min(2, NaN)`,
`median = max(1, t)`, `least = min(1, NaN) = 1`, `nan = true`, so the result
should be `least = 1`.

The value returned, `2.0`, is exactly the **`median`** arm under NaN-skipping
min/max (`min(2, NaN) = 2`, `max(1, 2) = 2`). So on this driver the `median`
arm is what gets selected: either `cmp(UNO, third, third)` is false for a NaN
operand, or the select's arms/materialisation of the `i1` disagree with WARP.
I cannot tell which from the outside; whichever it is, the two hosts disagree
on the same DXIL.

This is the same class of divergence `valu_tests.rs:312` already documents for
signed zero ("DXIL's FMax and FMin compare and select, which can give either
zero") — on this driver it shows on NaN as well.

## Why it matters beyond the test

`med3` is emitted for `v_med3_f32`, and `binary(35/36)` is also what
`v_min3_f32` / `v_max3_f32` use. If a host's NaN behaviour differs from the
console's, a title that feeds NaN into a median (clamped lighting, SSAO,
normal reconstruction) gets a different pixel, not a crash — the kind of
difference that is invisible until it is a visible artefact.

## Suggested directions

1. Confirm on another Intel GPU (Arc A-series or Xe2) whether it is
   Xe-LPG-specific.
2. Make the NaN arm not depend on the host's min: compute the smallest of the
   non-NaN operands with explicit predicate selects (`select(isnan(b), a, b)`
   style) instead of `min`, so no host's NaN-skipping rule can change it.
3. If `cmp(UNO, x, x)` is the culprit, a shader-side `x != x` via
   `cmp(ONE, x, x)` negation would be the cheaper fix, and would need a test
   of its own.

## Note for anyone running the suite on Intel

This was the **only** failure in `cargo test --workspace` on this machine
(120 of 121 `victory-shader` lib tests pass, plus every other target). The
"hardware" half of `run_cases` had, as far as I can tell, never run on an
Intel adapter before, so other host-specific differences may still be hiding
behind the first assertion that fires.

### Comment 1 — @BastienRodz — 2026-11-24T14:48:09Z

A candidate fix is on https://github.com/BastienRodz/VIctory/commits/shader/med3-nan-integer-test (`02c6650`, one commit on `main` `ffe310e`, `lower.rs` +17/-3).

`Lower::med3` chose the NaN arm with `fcmp uno` next to the `FMin`/`FMax` tree. That float test is what a driver's optimiser can fold or reassociate with the min/max around it. The branch tests NaN on the integer bits of each operand instead, `(bitcast(x) & 0x7fff_ffff) >u 0x7f80_0000`, ORed across the three, which no float rule can fold. `v_med3_f16` goes through the same function, with its operands already widened to f32.

On GitHub's `windows-latest` (WARP), both `v_med3_f32_matches_rdna2_with_nan` and `v_med3_f16_matches_rdna2_with_nan` pass, and `victory-shader` has 120 passed: https://github.com/BastienRodz/VIctory/actions/runs/45417688011

We have no Intel GPU. Could you run `cargo test -p victory-shader --lib v_med3` on the branch on your Arc and say whether both pass? If they do, I'll open the PR with your result.
