## Original body

## Setup
- Windows 11, RTX 4070 (NVIDIA; `WaveLaneCountMax` = 32)
- Fork branch `test/integration` (main + #704 + #694 + #1245 + #1280 + a few more), diagnostics build
- Logs, shader dumps and captures available on request

## Symptom
Loading screens and the opening credits render correctly. When the 3D world starts, the device is removed with `DXGI_ERROR_DEVICE_HUNG` (TDR). The frame where it happens varies from run to run (1468 to 2601), so it is not one fixed command.

## Finding 1: 86 compute pipelines refused on NVIDIA (wave64)
The debug layer reports, for every one of them:
`CreateComputeShader: Shader wants wave lane count of 64 but maximum wave lane count for device is 32`

`lower.rs` sets `WaveSize(64)` when a wave64 compute program has console lanes (permute / DPP / mbcnt / readlane / masks read as data) or is a single wave using LDS. NVIDIA cannot run these at all.

Experiment (commit on the fork): `VICTORY_HOST_WAVE32=1` runs console-lane wave64 programs in host waves of 32. Each host wave stands for a console wave whose lanes 32..63 are inactive. Masks, ballots and mbcnt stay consistent within the host wave, and the thread id is relabelled per 32 instead of per 64. Result: refusals dropped from 86 to 36. The remaining 36 are single-wave programs with LDS and no barriers, which I left refused on purpose. Cross-half lane reads would be wrong in this mode.

## Finding 2: the hang is caused by slow shaders, not by an invalid command
With `VICTORY_D3D12_DRED=1 VICTORY_GPU_TIMING=1`, there is no TDR, but these single commands take about a second:

| Shader | Command | Time |
|---|---|---|
| `8bbcbda6008eaa37` | dispatch 128x64x1 | 1.0 to 1.15 s |
| `42683eebec081520` | dispatch 128x64x1 | 0.8 to 1.28 s |
| `b7a81f5b96f4ca93` + `43e24028d4a1faef` | mesh, indirect | 0.2 to 0.5 s |
| `776d835da5ffa646`, `84eafa50504bc9ef` | dispatch | over 0.1 s |

`VICTORY_SHADER_LOOP_LIMIT=16` moves the hang from about 1500-2000 to about 2600 frames (268 s instead of about 70-128 s). So loops with huge trip counts are the cause.
`VICTORY_SKIP_PIPELINES` with these hashes does not help: dependent passes then read unwritten buffers and get slower.

`victory translate --validate --list` on the dumped containers reports all 6 as validated and fully tracked (0 not traced). So the code translation looks right, and the inputs at run time look wrong.

## Finding 3: how `42683eebec081520` gets its trip counts
It is a per-tile min reduction (disassembly excerpt):
```
s_mov_b32 s40, s5 ; s_mov_b32 s41, 0
s_load_dwordx4 s[0:3], s[40:41], null     ; V# held in memory at user-data u5
s_load_dwordx4 s[36:39], s[4:5], null     ; V# at u4
s_buffer_load_dwordx4 s[0:3], s[0:3], null
s_buffer_load_dwordx2 s[4:5], s[36:39], null
v_cvt_f32_u32 v9, s0 ; v_rcp_iflag_f32 v9, v9   ; also s1..s3
v_mul_legacy_f32 v19, v6, v9                    ; ratio = s4 / s0
... nested loops x in [pixel*ratio, (pixel+1)*ratio], image_load + v_min
```
- The u4 buffer holds sane values: `[128, 72, ...]`. These are the output tile counts.
- If the u5 buffer reads 0 (s0..s3), the rcp is inf, the ratio is inf, v_cvt_u32 gives 0xFFFFFFFF, and the loops do about 4e9 x 4e9 iterations. That matches the timings.
- `u5=0x1cc6e00` is not committed title memory and has no heap slot (`describe_slot` returns None). I could not tell how the host resolves this SGPR-held address. **Question for maintainers:** how is a V# loaded through `s[40:41] = {user-data, 0}` bound on the host, and could it resolve to the wrong or an empty buffer?

## Also fixed on the fork (constant buffer tables, `draw.rs`)
- `View::Constant(0, 0)` (the title's null CBV) was bound as a scratch view with `SizeInBytes = 0`, which is invalid. It is now a null CBV.
- A constant view is rounded up to 256 bytes, but only `size` bytes were filled. The rest of the scratch kept stale data, while the console reads zeros past the buffer size. The padding is now zeroed. This gave a visible FPS increase.

## Logging tweaks used (diagnostics only)
- `VICTORY_DUMP_SHADERS=<dir>` and `VICTORY_DUMP_SHADERS_ONLY=<hashes>` save containers on first sight.
- Placed buffer views and slot descriptions now show their first dwords of title memory.
- The slow-command note limit was raised from 300 to 4000 characters.

Branch: https://github.com/nicogunvis-boop/VIctory/tree/test/integration.

Follow-up: the zero divisors in 42683eebec081520 most likely come from the NVIDIA raw-read bound described in #951 (a raw read through a structured SRV returns zeros past NumElements * 4 bytes), not from a wrong binding of the u5 descriptor. That would explain the ~1 s reduction loops on this card too. The fix is gangg111's 0a4b89f, backported by jamesn-xt (test/rtx4080-raw-table-views, 5640d98). I will test it on the RTX 4070 and report back.

### Comment 2 — @Impre-visible — 2026-11-24T20:38:50Z

The same hang seen from Linux, where nothing declares the device hung, so it looks different: the title's own stop is the first visible symptom.

**Setup:** Arch Linux, kernel 6.18 LTS, GTX 1660 6 GB (Turing, 32-lane waves), NVIDIA 620.73.04 open modules, Wine from GE-Proton11-6 + vkd3d-proton (Proton Experimental), Series X mode, diagnostics build, native `d3dcompiler_47` so indirect execution runs. Tree: #1433 with #1492 merged by hand, plus #1077 #1175 #523 #530 #1040 #1406 #542 #1056 #1392 #1516 #1388 #1189 #1523 (so wave64 programs run and very little work is dropped: at most 79 dropped draws or dispatches per frame, summed over the report lines).

**What happens at world entry (one run, GPU load sampled every 2 s, kernel log, VIctory log):**

| time | event |
|---|---|
| 0 s | first world frame starts (about 1,400 pipelines first bound) |
| +14 s | first world frame is presented: 6.7 s, 1534 draws |
| +15 s to +23 s | GPU at 100 % |
| +23 s | kernel: `NVRM: Xid 109 ... name=title-main ... CTX SWITCH TIMEOUT`; GPU load drops to 0 % and stays there |
| +44 s | the title stops itself (the deliberate write to 0 described in #1323) |

- With `VICTORY_STACKS`, during the 0 % phase the scheduler thread of #1388 (`victory-gpu-wait`) is in `Host::execute` at the unbounded `WaitForSingleObject` on the submission's fence in 4 dumps in a row (18 s), and the title's `present` is waiting for the `submitted` mutex behind it. `GetDeviceRemovedReason` is only looked at after that wait returns, so nothing is logged: under vkd3d-proton the killed channel never signals the fence.
- **Xid 109 comes 16 to 28 s before the title's stop in 9 of 9 runs of this tree that reach the world.** In the trees I ran before (the #1511 stack and #1589, where thousands of dispatches per frame were still dropped) there is no Xid before the stop.
- `VICTORY_SHADER_LOOP_LIMIT=64` does not change it here (stop 34 s after the first world frame started). More pipeline workers do not change it either (8 or 20).
- Video memory is at 5.75 of 6 GB from the loading screen on.

So on this card the sequence is: a GPU job that does not yield for about 8 s, the driver kills the channel, VIctory waits forever, the title's watchdog ends the run. I do not know yet which dispatch it is; I am adding a bounded first wait that names the stuck submission and will report.

A possible hardening on the VIctory side, untested: wait on the fence with a timeout and poll `GetDeviceRemovedReason` (or the fence's completed value) so a dead channel is reported instead of waited on.
