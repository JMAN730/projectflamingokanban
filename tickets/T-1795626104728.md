## Original body

### Summary

I ran `victory translate --validate --pipelines --list` over the 26,503 DXBC containers extracted from my own 1.0.2.1 copy, on main `97c78d1` + the Agility exports from #84 (RTX 4080, driver 621.01). AI-assisted (Claude); I ran the translation and grouped the results myself.

All 26,084 programs translate. DXIL is emitted for 12,272 / 14,001 VS/PS, 1,685 / 2,581 compute and 8,191 / 8,506 mesh. **185 of the emitted modules fail validation** with `dxil.dll` 1.8.2502 (from Windows SDK 10.0.26100):

| Stage | Validator failures |
|---|---:|
| Pixel | 68 |
| Mesh | 62 |
| Vertex | 32 |
| Compute | 23 |

Grouped by reason:

- 53 — `vertex plus primitive output size is greater than 32768` (mesh)
- 49 — interpolation modes disagree between elements packed into the same signature row
- 46 — `Container part 'Program Input/Output Signature' does not match expected for module` (25 output, 21 input)
- 23 — `Entry function performs some operation that is incompatible with the shader stage` (compute)
- 14 — PS input position interpolation must be `linear_noperspective_centroid` / `sample` when writing `oDepthGE` / `oDepthLE`

Notably, the D3D12 runtime still created host pipelines for **all** of the VS/PS and mesh modules: 12,272/12,272 VS/PS and 8,191/8,191 mesh. So these are validator rejections, not driver rejections, and the game may still be fine with them. I haven't checked whether any of the 185 are among the shaders actually bound in my runs. The full per-shader output is too large to post, but I can extract any specific group.

For contrast, the driver's refusals are a separate matter: 321 compute pipelines with `E_INVALIDARG`, cross-tabulated in [my #71 comment](https://github.com/Marvisak/VIctory/issues/71#issuecomment-7119040508).

Follow-up on the proposed declaration cap. I compiled two original 128-thread mesh shaders with 19 vertex signature elements, containing 67 and 76 float components respectively and no per-primitive attributes. Both always call `SetMeshOutputCounts(3, 1)`. Windows SDK DXIL 1.8.2502.11 accepts declared `MaxVertices=96` for both and rejects `97` and `107` with the same 32 KiB error.

### Comment 7 — @iurysf — 2026-11-24T06:04:12Z

Update on the 53 mesh modules (`vertex plus primitive output size is greater than 32768`), measured on main `d2a4bae` with dxil.dll 1.9.2602.17.

- **The other 132 validator failures go away with #306.** Main + #306 leaves exactly these 53 (details on #306). #459 does not change them (details on #459).
- **Why they exceed the limit.** I looked at three of them. Each is a 128-thread mesh program with `MaxVertices = 128`, `MaxPrimitives = 128`, no per-primitive outputs, and **19 packed vertex output rows**: 128 × 19 × 16 B = 38,912 B.
- **Packing can't fix it.** They use 65–67 components per vertex, and 128 × 67 × 4 B = 34,304 B is still over 32,768. Packing only takes it to that floor, so any fix has to lower the vertex count or the outputs.

Options I can see:
1. Declare fewer vertices when the `GS_ALLOC_REQ` count is a known constant ≤ 107 (19 rows) — related to #586, which decodes the request but keeps the declared maxima.
2. Drop vertex outputs the paired pixel shader does not read, when the pipeline is made. Several of these programs feed prepass-type pixel shaders that likely read few attributes. This would also shrink the 19 rows in general.

Not verified: whether NVIDIA or AMD drivers misbehave on these at runtime. Your census says the runtime still created all mesh pipelines.
