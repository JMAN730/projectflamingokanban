### What the threads are doing

With `VICTORY_STACKS=10,14,18` the three dumps are identical (92 threads). Shortly before, the title reserves 3,542,286,336 bytes (54,051 pages of 64 KiB); the `xmem::map` calls that follow are one 64 KiB page each. With a local timer around the two host calls in `xmem::map` (my own instrumentation, not in the tree):

Adding a 150 µs spin to each call makes the title stop with 42,900 calls done instead of 53,000. In three runs the stop comes 13.1 to 13.9 s after call 11,000. That fits a bounded wait on the main thread. I have not shown the deadline directly, nor that the title goes on when the mapping is fast.

### Comment 1 — @pushkarreddyy — 2026-11-24T12:06:58Z

Claiming this issue for investigation and resolution.

### Architectural Analysis & Proposed Optimization
In `crates/victory-hle/src/modules/xmem.rs`, `XMemMapPhysicalPages` processes physical page arrays by issuing an individual `MapViewOfFile3` call for each 64 KiB page. When titles reserve ~3.5 GB (54,051 pages), making 54,051 distinct system calls incurs massive `wineserver` IPC context switching under Proton/Wine (~18 seconds), triggering internal title watchdogs/deadlines.

By scanning the physical page descriptors for contiguous runs of physical pages mapped to contiguous virtual addresses, we can coalesce runs into single multi-page `MapViewOfFile3` calls (or batch adjacent mappings). For typical contiguous allocations, this reduces system calls by orders of magnitude (from 54,000+ to under 100).

Preparing an optimization branch on fork.

### Comment 6 — @pushkarreddyy — 2026-11-24T12:55:26Z

### Updated Fix: Cross-Call Page Coalescing with Demand-Paging VEH

Thank you @ghmfreitas for the sharp diagnosis and call-count telemetry! Your profiling pinpointed the exact bottleneck: the title initializes bulk memory by issuing `XMemMapPhysicalPages(addr, 1, page)` in a sequential loop where 44,660+ calls are contiguous across calls, causing wineserver to allocate and track 50,000+ individual 64 KiB views.

I have updated the branch with commit [`546d9b0`](https://github.com/pushkarreddyy/VIctory/commit/546d9b0) (on branch [`perf/xmem-coalesce-page-maps`](https://github.com/pushkarreddyy/VIctory/tree/perf/xmem-coalesce-page-maps)):

#### Architectural Solution (`crates/victory-hle/src/modules/xmem.rs`):
1. **Cross-Call Run Detection**:
   When subsequent calls on the same thread continue the active run (`addr == pending.base + pending.n * PAGE` within the same section and index run), `XMemMapPhysicalPages` increments `pending.n += n` and returns immediately without issuing `VirtualFree` or `MapViewOfFile3`.
2. **Single Syscall Flushes**:
   When the run ends (non-contiguous address, section change, unmap, query, or other HLE memory calls), `flush_pending` executes a single `VirtualFree` and `MapViewOfFile3` for the entire multi-thousand-page run at once. This collapses the 44,660+ individual views and syscalls down to a single view.
3. **Demand-Paging Vectored Exception Handler (VEH)**:
   Registered `on_map_fault` via `AddVectoredExceptionHandler`. If title CPU code touches memory in the pending placeholder window before another HLE API is invoked, the VEH intercepts the access violation, flushes the mapping, and returns `EXCEPTION_CONTINUE_EXECUTION` for seamless transparent resumption.
4. **Unit Test Verification**:
   Added `physical_pages_coalesce_across_individual_calls` asserting that sequential 1-page invocations coalesce into a single view (`assert_eq!(view, Some(10 * PAGE))`) with verified read/write accessibility.

Tested with `rustfmt --edition 2024 --check` and zero Rule #1 asset violations. @ghmfreitas, please try commit `546d9b0` when you have a chance!
