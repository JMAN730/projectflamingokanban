## Original body

﻿Branch (PRs are collaborator-only): [`anasssssssss1:fix-a16-bias`](https://github.com/anasssssssss1/VIctory/commits/fix-a16-bias), one commit on `main` `ffe310e`.

## What

`image_sample_b` with `a16` stopped the program ("a biased image sample with 16-bit coordinates"). Lowering it needs the address layout the hardware uses with `a16`, which the sample path did not follow for any extra word:

- With `a16`, the extra words (texel offset, bias, z-compare) keep a **whole VGPR each**; only gradients and coordinates are packed two per VGPR, and the coordinates start on a fresh VGPR. Each gradient direction is padded to whole VGPRs. (LLVM's AMDGPU backend packs it this way: `packImage16bitOpsToDwords`, "bias is of type half but occupies full 32-bit".)
- The bias is an f16 in the low half of its VGPR.

`addr_val` indexed every logical address as if all were packed, so an `a16` sample with an offset word read its coordinates from the wrong halves; that path was already allowed (`image_sample_o` with `a16`). The sample path now maps each logical address through `slot()`, and reads extra words whole (`extra()`). Without `a16` every index is unchanged. `image_sample_l`'s level also goes through `slot()` (unchanged today, as `first` and the gradients are 0 there).

## Measured

|---|---|---|

### Comment 4 — @anasssssssss1 — 2026-11-24T13:11:25Z

﻿Correction, and closing this as superseded.

`r4tedx/VIctory:integration/testers` (`92bc27b`) already lowers biased `a16` samples, with the extra words a dword each as here, and with one difference that makes it the better one: on GFX10.3 the derivatives are 16-bit only in the `g16` opcodes, not because `a16` is set (LLVM's `lowerImage` keeps the two apart where the target has G16). My branch packs the derivatives whenever `a16` is set, which is wrong for `image_sample_d*` with `a16` on this GPU. The other cases (offset, bias, coordinates) agree.

Please take the testers tree's version rather than `fix-a16-bias`.
