## Original body

# RTX 4060 Ti (8 GB): #189 clears all 92 refused compute pipelines — the remaining `+0x23cf683` trap is not a pipeline problem

**Title:** VIctory (1.0.2.1 retail Xbox Series build, `game_scarlett_master.exe`)
**Host:** Windows 11 26200 · i7-14700KF · 64 GB · **NVIDIA RTX 4060 Ti 8 GB**, driver 32.0.16.2124 · DXC 1.9.2602.17 (SDK 10.0.26100.0)
**Build:** workspace built with `cargo build --release -p victory --features diagnostics`

Two things that may be useful for the merge queue, both measured on the card the title is hardest to run:

## 1. #189 fixes the wave64 refusals completely

Before #189 (main `ffe310eb`), with the D3D12 debug layer on, the first refused compute pipeline reported:

```
ID3D12Device::CreateComputeShader: Shader wants wave lane count of 64 but
maximum wave lane count for device is 32. To check for support, check
device caps via the CheckFeatureSupport() API    id=622 severity=1
```

That is the reason behind every `host pipeline refused error=参数错误 (0x80070057)` on this card.

With **#189 alone** (`54b333f Shaders: default <64-lane hosts to Emulate instead of Wave32`):

| | main | #189 |
|---|---|---|
| `host pipeline refused` | **92** | **0** |
| `0x80070057` | 92 | 3 |
| frames reached the world | yes | yes (0.6–1.7 fps) |

Zero refusals, first time in this whole exercise. #189 does what it says on a 32-lane host.

## 2. #1076 and #189 do not stack

Both change `crates/victory-shader`, and the two branches have diverged structurally:

- #189: `emit::translate_with(...)` with `TranslateOptions` / `Wave64Mode`
- #1076: `emit::translate_for_wave(container, max_wave)` built on `emit_for_wave(...)`

Merging #1076 then #189 (or the reverse, with `-X theirs`) leaves `lower.rs` calling `emulate_wave64`, `emu_total`, `emu_exchange_pair`, `console_subwave` on a `Lower` that does not define them:

```
error[E0609]: no field `emulate_wave64` on type `&mut lower::Lower<'a>`
error[E0599]: no method named `emu_exchange_pair` found ...
```

Taking only `crates/victory-gpu/src` from #1076 onto #189 gets further but stops at:

```
error[E0425]: cannot find function `translate_for_wave` in module `victory_shader::emit`
```

So the two need a rebase against each other before either lands, or one of them should adopt the other's entry point. **We could not run #1076 and #189 together at all**, which matters because:

- With #189 (wave64 fixed) the dominant remaining drop reason became
  `a draw or dispatch dropped: no dynamic slots for its tables` — i.e. the descriptor heap headroom that #1076 addresses;
- and #1076's per-command-list submission is aimed at the TDR, which is the other half of the world-load failure.

Individually each PR fixes half of this card's problem.

## 3. The `+0x23cf683` trap survives all of it

With zero refused pipelines the title still dies at

```
unhandled exception 0xc0000005 in game_scarlett_master.exe+0x23cf683 (write at address 0x0)
```

exactly as on main, and as reported in #675 (and reproduced on Proton/vkd3d by `am-cob`). Two more data points from this side:

- `XCL_ACTIVITY`-equivalent timing here: the last present is ~30–40 s before the fault; the queue is **empty** (`0 submits`), so it is not the GPU being busy.
- The blocked thread sits at `+0x23cf735`, inside the poll loop at `+0x23cf716` (`call 0x1423cb280` / `test al,al` / `jne` / `Sleep(1)` / loop) — waiting for a producer that never reports ready.
- Forcing that poll to report ready (patch `+0x23cf71d` `75` → `EB`) made the title assert **earlier** (`0x80000003` at `+0x1377e7`, 50 s instead of 111 s), which says the data really is absent, not merely late.

So the trap is a consequence, not the bug — no pipeline fix will remove it.

## What would help most

1. A rebased **#189 + #1076** pair, or a note on which one to take for 8 GB Ada cards. Either alone leaves half the failure in place.
2. Whatever the maintainers conclude from the wait tracing (#1251/#638). On this machine a full `victory_gpu=debug` run produced **213 MB / 1,000,000 log lines in 90 s** and the frame rate fell from 13.6 to 0.5 fps, so the wait tracing needs a narrower target filter to be usable at world load.

Happy to rerun anything on the 4060 Ti and report back.

So mode selection **is** the lever: `native` reproduces the refusal on its own, and either override clears it.

```
ID3D12Device::CreateComputeShader: Shader wants wave lane count of 64 but
maximum wave lane count for device is 32 ... id=622 severity=1
```

So those refusals are native-wave64 bytecode reaching `CreateComputeShader` - not an allocator or root-signature problem. What I cannot tell from logs is whether `wave32` and `emulate` differ in dispatch *results*; #1132 suggests the two integrations differ on a standalone `v_readfirstlane_b32`, and I have no way to check that from the title's logs here.
