## Original body

## Summary

Testing on an NVIDIA RTX 4090 (wave32-only), the title boots, runs the first-boot screens and menus at 30 fps, loads the world and spawns the player, then crashes deterministically while prestreaming the first mission's intro (`fbk_stry000_FBK_STRY000_INTRO`). The title's own crash report says `Unsignaled CrossQueueBarrier`, so it looks like its GPU watchdog firing on a cross-queue sync that never completes.

The crash happens at the same address and stage on two very different GPU setups, so it doesn't look like a speed or memory issue.

## Environment

- Windows 11 (build 26200), 48 GB RAM
- GPU 1: NVIDIA GeForce RTX 4090, driver 32.0.16.2101 (WaveLaneCount 32–32)
- GPU 2: AMD Radeon(TM) Graphics (CPU iGPU), driver 32.0.21042.62 (WaveLaneCount 32–64)
- VIctory: `main` as of 2026-11-24, `cargo build --release -p victory`, toolchain from `rust-toolchain.toml`
- Title: 930.048.020-vb_sub_story, TitleID 7952987A, Series X mode

## Observations

### 1. Wave32 GPU: WaveSize(64) compute pipelines refused

On the RTX 4090, 116–119 compute pipelines fail with `E_INVALIDARG (0x80070057)`:

```
WARN victory_gpu::pipeline::host: host pipeline refused error=... (0x80070057) shaders=[compute ...]
```

As expected from the README ("some compute programs need a GPU with 64-lane waves"). Wave64 emulation on wave32 hosts (two 32-lane halves) would be needed for NVIDIA.

### 2. TDR on entering the world

With default Windows TDR (2 s), entering the world ends in `DXGI_ERROR_DEVICE_HUNG (0x887A0006)` after a 5–6 s submission, on both GPUs. With `TdrDelay=60` / `TdrDdiDelay=60`, there is no device removal on either GPU (longest submission 28 s on the iGPU).

### 3. Deterministic title crash at the first mission intro (both GPUs)

To rule out the wave32 refusals, I added a local `VICTORY_ADAPTER` env var to `host.rs` (picks a DXGI adapter by name or index, `EnumAdapterByGpuPreference`) and ran on the AMD iGPU: 0 pipelines refused, wave lanes 32–64.

| | AMD iGPU (VICTORY_ADAPTER=radeon) | RTX 4090 (default) |
|---|---|---|
| World frame rate | 0.6–1.3 fps | 1.4–3.3 fps |
| Refused compute PSOs | 0 | 119 |
| Device removed | no | no |
| Crash | `+0x23cf683` | `+0x23cf683` |
| Title frame at crash | 791 | 1068 |

VIctory's report (identical on both runs):

```
VIctory: unhandled exception 0xc0000005 at victory-image-<hash>.dll+0x23cf683 (write 0x0: nothing mapped there)
  rax 0x0 rbx 0x0 ...
  #0  victory-image-<hash>.dll+0x23cf683
  #1  victory-image-<hash>.dll+0x2215c35
  #2  victory-image-<hash>.dll+0x2215eca
  #3  KERNEL32.DLL+0x2dda7
  #4  ntdll.dll+0xc9c5c
```

The faulting thread starts directly in the title (`BaseThreadInitThunk` → `+0x2215eca`), and the null write looks deliberate.

The title's own crash context (`T:\victory-*.crash.log`) on the RTX 4090 run:

```
Game State: Game Running
Frame: 1068
Streaming Requests: 144
Game Physical: 2174254528/2305818624
Pool: 591978288/624951280
GFX Queue: fb6d2b63
Unsignaled CrossQueueBarrier: 82d9447
Current SRL Name: fbk_stry000_FBK_STRY000_INTRO
Current SRL State: Prestream
```

(The iGPU run shows the same SRL name and state; that report has no `CrossQueueBarrier` line.)

Around the crash, the log shows untranslated compute shaders (`a structured buffer of unknown stride`, `image_gather4_l`, `a lane mask read as data`), dropped indirect executions (`indirect execution dropped ... counted=false`) and one `a dispatch without a host pipeline dropped`. I also noticed `queue.rs` `wait()` returns `S_OK` without waiting.

My guess is that the GPU work meant to signal the cross-queue barrier is among the dropped or untranslated work, or that a queue-to-queue wait/signal isn't modelled, so the title's GPU watchdog ends the run. Before the title's crash handler runs, two device methods are reported unimplemented once at startup: `slot=0x218` and `slot=0x1c8`.
