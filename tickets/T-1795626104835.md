## Original body

Related: #314, #625, #392 (same symptom on other NVIDIA cards), #578, #189, #192, #734.

**Setup**: Windows 11 Pro 26200, Ryzen 5 3600X, 32 GB, **NVIDIA RTX 3070** (driver 32.0.16.2124, 32-lane waves only). VIctory `8e79c80`, `cargo build --profile diag -p victory --features diagnostics`. Own copy, title 1.0.2.1 (exe BLAKE3 `b99f876b74d4a77f03af5f878223b27bd647b5c35a79d5decd9f716504239e93`).

**Works**: boot, offline profile, intro, first-boot screens, legal/terms, saves, story load. Menus at a steady 30 fps. Network stays closed: the title's Breakpad crash reporter tried to upload a ~28 MB minidump to `submit.backtrace.io:443` after a WARP crash and `victory_hle::modules::net` blocked it (`HTTP connection blocked`).

**Problem**: entering the world always ends in `DXGI_ERROR_DEVICE_HUNG` (TDR), not an invalid command (debug layer message is the TDR one).

What `VICTORY_D3D12_DRED=1` showed, run by run:

| Run | Settings | Where the list stopped |
|---|---|---|
| 1 | defaults (+ debug layer) | command 417 of 602, **op 42 DispatchMesh**, inside a run of DispatchMesh (414..470) between two barriers |
| 2 | `VICTORY_SHADER_LOOP_LIMIT=4096` | GPU time per world frame fell from ~1.1 s to 0.1–0.7 s and the run went further, then: ExecuteIndirect kind 10 (mesh), `mesh d9abe24ad7bfe920, pixel 264ae8d58e78b62d` |
| 3 | + `VICTORY_SKIP_PIPELINES=d9abe24ad7bfe920` | DispatchMesh of **one group**, `mesh f0c7efd2aceb2aaa, pixel 7d85c9cab3c80721` |
| 4 | `VICTORY_SHADER_LOOP_LIMIT=64` + same skip | DispatchMesh 111 groups, `mesh 4adfa13bea1c556a` |
| 5 | `main` + **#578** merged locally (no loop limit, no skip) | **no TDR for 10 minutes in the world** (~1 fps), frames black (all channels 0..2), `no host pipeline: a mesh program written for 64-lane waves, on a host without them` |

So a hang that survives a loop limit of 64 on a single mesh group points at wave64 mesh programs running as two 32-lane waves (lockstep/LDS assumptions), not at long loops alone. #578 turns it into dropped draws on this GPU; the world then renders black.

**Other observations**
- 271 compute shaders "do not translate" on this GPU with `main` (wave64).
- Two 2560×1440 render targets are refused by the driver: DXGI format 86 (B5G5R5A1) with flags 5 and 115 (B4G4R4A4) with flags 1 (`no host texture … 0x80070057`).
- Device methods at vtable offsets `0x1c8` and `0x218` are logged as not implemented.
- `host view heap capped at 1000000` (count 1245184).
- With `VICTORY_D3D12_WARP=1` the title's own watchdog ends the run (`mov dword [0], 0` after ~30 s without progress), so WARP can't reach the world at that speed.

### Comment 2 — @EduBertozzi — 2026-11-24T11:40:32Z

A possible way to keep mesh geometry on 32-lane hosts, and one number I need from someone with the title first.

All of the title's mesh programs are wave64 (per @ChruutvoLuzi's count on #578), and mesh shaders cannot declare a wave size. On NVIDIA each console wave runs as two 32-lane host waves that branch per lane. A half with no active lane on a path can skip an `s_barrier` that its console wave reaches, and then the other half waits forever. That would fit the hang above even with one group and a low loop limit, though I haven't confirmed it on the title.

I've been prototyping a compute fallback for mesh pipelines on GPUs without mesh shaders (#3). It runs the mesh program as a compute shader that writes vertices and triangles to buffers, then draws them with a generated vertex shader and the title's pixel shader. A compute shader can do what a mesh shader can't: run in #439's console flow, where both halves take every branch together and exchange lanes through group-shared memory. So the same fallback could serve as the mesh path on NVIDIA. The catch is that #439's console flow only takes groups of **at most 64 threads**, and I don't know the title's mesh group sizes.

So I added `victory mesh-census` on [`pr/mesh-compute-fallback`](https://github.com/EduBertozzi/VIctory/tree/pr/mesh-compute-fallback) (today's `main` plus the fallback). It prints a table by group size: programs, wave64, LDS, `s_barrier`, lane reads, `v_mbcnt`, EXEC branches, and how many translate as mesh and as compute. Then it lists the refusal reasons. **Counts only, nothing of the programs.**

```powershell
git fetch https://github.com/EduBertozzi/VIctory pr/mesh-compute-fallback
git switch --detach FETCH_HEAD
cargo run --release -p victory -- mesh-census <your game dir>
```

It translates every mesh program twice, so expect a few minutes. If you can, please paste the output here.

### Comment 3 — @KenzoPortela — 2026-11-24T12:10:18Z

More measurements on the same RTX 3070 — the world now renders its geometry on a 32-lane GPU.

**1. **2. Letting them run as 32-lane halves** (a local diagnostics switch that bypasses #578's mesh refusal) with `VICTORY_SHADER_LOOP_LIMIT=1024`:

A per-lane guard of 2^20 per loop on nested loops can mean ~2^40 iterations per pixel when the inputs that should end the loop were never written (their producers dropped). That draw still hung once with loop limit 1024. A fix could route `v_readfirstlane` in wave64 mesh programs on narrow hosts through a groupshared slot written by the console wave's first active lane.

### Comment 25 — @c4k3ss — 2026-11-24T14:49:43Z

**A way to run the wave64 programs on 32-lane hosts instead of refusing them: Leonida's emulation scheme (pointers, no game data)**

The finding here, and #578's, is that the world hang on NVIDIA comes from wave64 mesh and compute programs running as two 32-lane waves. #578 turns that into dropped draws, and the world then renders black. Leonida's translator has a mode for exactly this hardware limit, and it is documented, so it may save a design round. Pinned at `d0da7dad` of the continuation:

- **The scheme** ([design.md L401](https://github.com/ubiquitarianism/leonida/blob/d0da7dade8b688f2e0f7f23f4155d6cbb438809e/docs/design.md#L401)): wave64 compute and mesh programs run exactly on any host wave size, with no host wave operation at all. One invocation is still one lane. Everything a lane needs from the rest of its wave goes through a group-shared buffer: votes (`s_cbranch_vccz/execz` and friends), whole-mask words (`s_bcnt1`, `s_ff1`, `v_mbcnt`), `v_readlane`, `v_readfirstlane`, `ds_bpermute`, `ds_swizzle`, `v_permlane16`. The program runs in rounds: each wave runs one segment (a basic block, cut at each cross-lane op), then the whole group meets at one barrier in uniform control flow. A cross-lane op ends its segment after the lane has stored its value or ORed its bit; the code after it runs one round later, when all 64 lanes have written. `s_barrier` becomes a scheduler state. A memory access that conflicts with an earlier one in the same segment starts a new round, so the two halves touch memory in instruction order, as one hardware wave does.
- **Why two free-running halves hang or go wrong** follows from that: a vote or a mask word read in one half never sees the other half's lanes, so a loop that waits on a whole-wave condition can spin. That matches a hang that survives a loop limit of 64 on a single mesh group.
- **Vertex and pixel programs** don't need it. For those the rule is partition invariance ([design.md L498](https://github.com/ubiquitarianism/leonida/blob/d0da7dade8b688f2e0f7f23f4155d6cbb438809e/docs/design.md#L498)), which agrees with #578 keeping them.
- **Implementation and tests there**: [`tools/wave64_emulate_opt.py`](https://github.com/ubiquitarianism/leonida/blob/d0da7dade8b688f2e0f7f23f4155d6cbb438809e/tools/wave64_emulate_opt.py), and 21 hand-written `*_w64x_*` GPU fixtures under `runtime/test/shaders/` (ballots, `ds_bpermute`, `s_barrier` chains, LDS read-after-write, partial waves, a 128-thread group, one mesh program).
- **Measured today on an RTX 5070 Ti** (driver 621.24, 32-lane waves, Leonida Continued `main` `d0da7dad`): that GPU suite passes 198 of 249 natively, with every wave64 compute and mesh fixture skipped for lack of 64-lane waves, and **230 of 249 with the emulation on**. The 32 that flip are exactly those fixtures. The 2 failures are the same on both runs and unrelated.
