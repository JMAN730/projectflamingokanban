## Original body

finding: some pipelines are stored in the pipeline library under a name whose description differs on the next run, so they are compiled again instead of loaded.

**Seen.** With `VICTORY_D3D12_DEBUG=1` and a pipeline cache warmed by an earlier run of the same build, the debug layer reports pairs of warnings while graphics pipelines are made:

- `ID3D12PipelineLibrary::Load*Pipeline: The pipeline state desc provided does not match the one used to create the PSO stored with name "<name>"`
- then `ID3D12PipelineLibrary::StorePipeline: A pipeline with name "<name>" already exists in the library`

47 such warnings in one run, against about 770 pipelines made or loaded. The effect is that those pipelines are compiled again on every run (the library keeps its older entry); nothing is drawn wrongly as far as I can tell.

**Where.** `crates/victory-gpu/src/pipeline/library.rs:100` (`name`) hashes the kind, the root signature blob, the shader code and `GraphicsState::describe()` (`pipeline/host.rs:174`); the graphics description is built at `pipeline/host.rs:489`, the mesh stream in `mesh_pipeline`.

**Ruled out by reading the code (not by a run).** Every field of the graphics description and of the mesh stream is in `describe()`, and the root signature blob in the name is the one the root signature object is created from (`root_signature` returns both from one serialization). So I have not found what differs. Finding it needs a run that logs the name and the full description at each store and at each mismatch, two runs, and a diff.

**Related, minor.** `describe()` records the title's topology, while the description maps `RECTANGLES`/`QUADS` to `TRIANGLE`. That only gives one description two names, not a mismatch.

**Setup and limits.** RTX 3070, driver 621.14, Windows 11. Tree: main `8e79c80` plus several open PRs (listed in my comment on #439), so it may come from one of them; not checked on plain `main`. Reproducing needs the game files (a warm pipeline cache, then a second run with the debug layer).

### Comment 1 — @BastienRodz — 2026-11-24T11:04:11Z

Possibly a known cause, if the 47 pairs are mesh pipelines: #352 found that a mesh pipeline never loads from the library. `LoadPipeline` refuses it with the same "does not match the one used to create the PSO" (972), even with the very stream it was made from, unless the stream has a `PRIMITIVE_TOPOLOGY` subobject that isn't `UNDEFINED`; the store is then refused with "already exists" (970). That's the pair you see, every run. #352 adds the topology (triangles, which is all `mesh_prologue` makes) and gives mesh entries a new library name.

A quick way to tell, on your next warm run: if the names in the warnings are those of mesh pipelines (`mesh_pipeline`), #352 should remove them. If some are VS/PS graphics pipelines, there is a second cause, and the name/description log you describe is the way to find it.

AI-assisted (Claude Code); from reading the code and #352, not run.

### Comment 2 — @Kegwed — 2026-11-24T11:27:49Z

Found it: the mesh pipeline stream leaves the primitive topology out, and the pipeline library cannot load back a mesh pipeline whose topology is undefined.

**Standalone repro (no game files).** A trivial mesh + pixel shader compiled with DXC 1.9 (`ms_6_6` / `ps_6_6`), a stream laid out like `mesh_pipeline`'s, one `ID3D12PipelineLibrary1`: `CreatePipelineState` → `StorePipeline` → `LoadPipeline` with the *same* stream returns `E_INVALIDARG` ("desc provided does not match"). Variations, each from a fresh library:

| stream | `LoadPipeline` |
|---|---|
| root, MS, PS, RT formats (+ VIctory's blend / raster / depth / DSV / samples) | fails |
| + node mask, + flags, + sample desc/mask, + DSV format | fails |
| + topology `UNDEFINED` given explicitly | fails |
| + topology `TRIANGLE` | loads |
| + topology `LINE` (shader outputs triangles) | loads |

Reusing the same root signature object or a copy of the code changes nothing, and a serialised-then-reopened library behaves the same. Any defined topology makes it load. Translated mesh shaders always output triangles (`mesh_prologue` refuses others), so the fix adds a `PRIMITIVE_TOPOLOGY = TRIANGLE` subobject.

This means every mesh pipeline was compiled again on every run, not only the names you saw twice: the warning pairs only show for names requested more than once within one run.

**In the title** (RTX 3060 Laptop, driver 621.01, Windows 11, `main` at `ffe310e`, diag build, `VICTORY_D3D12_DEBUG=1`, scripted keys into the world, each run stopped 4 min after loading the world):

| run | library at start | "desc does not match" | "already exists" | pipelines made / loaded |
|---|---|---:|---:|---:|
| before the fix | empty | 139 (all 41 names mesh) | 167 | 1478 / 4 |
| with the fix | empty | 0 | 11 | 1283 / 157 |
| with the fix | the run above's | 0 | 2 | 45 / 1353 |

The few remaining "already exists" are two workers creating the same new pipeline at once (both loads miss before either stores), a separate and harmless race.

**Branch:** https://github.com/Kegwed/VIctory/tree/gpu/mesh-pipeline-topology (commit `38ea605` on `ffe310e`; PR creation is limited to collaborators) — one file (`crates/victory-gpu/src/pipeline/host.rs`): the stream becomes a module-level `MeshStream` with the topology subobject, plus a unit test that the stream names a triangle topology. `cargo test -p victory-gpu --features diagnostics` passes (54 passed, 1 ignored), `cargo clippy -p victory-gpu --features diagnostics --all-targets -- -D warnings` is clean, `cargo xtask policy` ok.

I first suspected uninitialised padding in the stream (it has some); zeroing it changed nothing (135 mismatches), so it is not part of the fix.

AI-assisted (Claude Code); runs on my machine, no game data in the branch or here.


### Comment 3 — @LAKSHYA-cmd-tech — 2026-11-24T11:30:29Z

The 972/970 mismatch is caused by mesh pipeline state streams lacking an explicit PRIMITIVE_TOPOLOGY_TYPE_TRIANGLE subobject, which D3D12 LoadPipeline requires to match stored PSOs (as documented by @rhuantac in #352 and #264), combined with uninitialized RTFormats past NumRenderTargets. Resolved and verified in https://github.com/LAKSHYA-cmd-tech/VIctory/pull/17.
