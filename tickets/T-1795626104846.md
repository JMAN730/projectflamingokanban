## Original body

## What happens

At startup, Grand Theft Auto VI asks `XMemVirtualAlloc` for a **185 MB placeholder with the 32-bit address flag** (`size=193986560 kind=0x42000 flags=0x7`; `ADDRESS_32BIT` = 4, so `address_range` gives `0..4 GiB`). If the host's own memory has already filled the space below 4 GiB, `VirtualAlloc2` fails with `ERROR_NOT_ENOUGH_MEMORY`. The title then stops at its own assertion, `0x80000003` at `+0x19f4f58` (a check right after window setup), about 3 s after the D3D12 device is made.

Windows allocates bottom up, so the host's early memory lands below 4 GiB first. That includes driver allocations, heap segments, the executable read in `run`, and cache data. `main` doesn't log the refusal (only the title's assertion shows), which makes this hard to spot.

## Evidence (RTX 2080, Windows 11, 32 GB)

A temporary probe in the refusal path walked `0..4 GiB` at the moment of failure:

```
XMemVirtualAlloc refused size=193986560 kind=0x42000 flags=0x7 error=... (os error 8)
range below the limit: want=193986560 free_total=22515712 largest_free=14213120 regions=167
  0x2f230000 1024 MB private committed
  0x7fff0000 1024 MB private committed
  0xbfff0000  256 MB mapped
  2 x 114 MB private reserved, dozens of 32 MB private committed blocks ...
```

That leaves 22 MB free below 4 GiB, with a largest hole of 14 MB. How often it happens depends on how much the host allocates early:
- **With a large pipeline cache** it failed 2 of 3 startups (a build of main plus open PRs).
- **With an empty cache directory** it started every time.
- **With the D3D12 debug layer** (`VICTORY_D3D12_DEBUG=1`) it failed every time on this machine, through the same assertion. That's probably why GPU-based validation was unusable here.

## Fix

Branch: [NuraadGit:xmem/guard-32bit-window](https://github.com/NuraadGit/VIctory/tree/xmem/guard-32bit-window), commit `ab749fd` on `main` `ffe310e`, +181 lines in two files.

- **Install at startup:** `xmem::low_guards::install()` runs at the start of `run` when executing, before the image read, the device and the caches. It reserves the free space below 4 GiB except the lowest 256 MB, which is left to the host.
- **Make room on refusal:** a 32-bit `XMemVirtualAlloc` that finds no room releases the smallest guard that fits it (else the largest) and retries the same call. It then guards whatever is still free of that hole.
- **The normal path is unchanged.** It's only a retry on refusal, so write-watch and placeholder semantics stay exactly as they are.
- **Test:** `low_guards::tests::a_released_guard_is_guarded_again_around_what_took_it`.

Result on the same machine and build: 5 of 5 startups passed, with 3.7 GB below 4 GiB kept for the title. Before the fix it failed 2 of 3.

*AI-assisted (Claude Code): the probe, fix, test and runs were automated. The hardware, title copy and runs are the user's.*
