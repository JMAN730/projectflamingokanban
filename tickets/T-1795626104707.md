### 2. The earlier `0x27ab000` fault looks like a missing heap base after the indirect clamp

`0x27ab000` is the byte offset of view-heap dynamic slot 54,656 (title slots 1,245,184 + 54,656, 32 bytes each), with no heap base added. The host view heap itself is at `0x104f30000+0x2800000`. The work in flight was only `ExecuteIndirect` mesh dispatches (kind 10) and kind-2 dispatches.

In `State::execute_indirect`, `indirect::bound` binds its own compute root signature and pipeline. Afterwards only `host_pipeline` and `host_roots[1]` are reset. So kind-2 dispatches re-set their compute root signature, but kind-10 mesh dispatches reuse the graphics root signature and heaps from before the clamp.

Results on `35b054e` + #57/#40/#67:
- **`VICTORY_NO_INDIRECT_MESH`** (dropping kind 10): no page fault, frame 1144 vs 969.
- **Resetting `host_heaps = [0; 2]` after `bound`** (heaps and both root signatures set again before the indirect command): kind 10 ran ~2,000 times with no heap-offset fault on `9aef3d9`.

The section 1 fault now comes first, at 58 s, with or without the reset. So I can't call the reset a proven fix, only that it removed one fault signature and costs one `SetDescriptorHeaps` per indirect command:

```rust
// draw.rs, State::execute_indirect, after indirect::bound(...)
self.host_pipeline = 0;
self.host_roots[1] = 0;
self.host_heaps = [0; 2]; // heaps and both root signatures again
```

A heap/root-order probe on WARP found no draw or dispatch with the view heap unset, or with the root signature set before the heaps, in about 1,050 frames. So the heap tracking itself looks right, which points at the driver needing them re-set after the clamp's pipeline.

Logs, DRED text and the probes are available if useful. I'd rather not run many more real-GPU tests here: one driver reset took the whole PC down.
