## Original body

## Problem

When a title creates a buffer SRV or UAV with `NumElements == 0`, the host device is removed with `DXGI_ERROR_INVALID_CALL` (0x887A0001). This needs no debug layer, and the DRED breadcrumbs are empty. In the title it happened right at world entry. It looked random, because whether a run hit it depended on what was in the shader cache.

Cause: `buffer_srv` and `buffer_uav` in `crates/victory-gpu/src/descriptor/host.rs` pass the title's view to `CreateShaderResourceView` / `CreateUnorderedAccessView` unchanged. D3D12 treats a buffer view of zero elements as an invalid call. On the console such a view reads and writes nothing.

## Fix

A buffer SRV or UAV of zero elements now gets a null view in its slot, and a `once!` log line records it. A test, `descriptor::host::tests::buffer_views_of_no_elements_are_null`, makes placed buffer views of one and of zero elements on the host device. It asserts that the empty slots are null and that `GetDeviceRemovedReason` stays S_OK. One file, `crates/victory-gpu/src/descriptor/host.rs`, +54 lines (11 of them code).

## Branch

https://github.com/Vaximous/VIctory/compare/main...fix/zero-element-buffer-views — commit a52f612, based on ffe310e.

## Tested

- `cargo test -p victory-gpu`: 51 passed, 0 failed, 1 ignored. Clippy `-D warnings` is clean. Without the check, the new test removes the device on an RTX 4070 Ti.
- Runtime (RTX 4070 Ti, Windows 11): measured on our local integration build (main plus a set of open PRs), not on plain main. Runs that had been removed at world entry reach the world with the check.

## Related

### Comment 2 — @pickles976 — 2026-11-24T14:05:19Z

Cross-check from the sibling runtime (ivall/xcl), read at the source rather than grepped: this failure mode is structurally absent on our side — buffer SRV/UAV descs never reach the host layer as view objects at all. A zero-element desc becomes a **0-record console descriptor word**: `buffer_view` (`crates/xcl/src/hle/d3d12x/real.rs:1176`) clamps through `saturating_sub`/`min` (`records = (n).min(room / stride)` → 0 for `n = 0`) and the translator reads it as an empty range. Which supports your framing: the class lives in the **handoff of a degenerate view to the host**, not in the title's usage — a title legitimately making zero-element views is fine on hardware and fine here, and only host-forwarding runtimes have to invent a policy (yours: refuse with a diagnostic; ours: empty range). No action needed, posting the good news per the shared-map practice.


### Comment 3 — @DaniiL35 — 2026-11-24T14:06:45Z

### Independent Verification Review: Vaximous:fix/zero-element-buffer-views (`a52f612`)

Audited the D3D12 buffer descriptor handoff and device removal invariants:

---

### 1. D3D12 Host Invariant Violation Analysis
- Under Direct3D 12 (`D3D12_BUFFER_SRV` and `D3D12_BUFFER_UAV`), `NumElements` is explicitly required to be non-zero (`NumElements > 0`). Calling `CreateShaderResourceView` or `CreateUnorderedAccessView` with a non-null resource and `NumElements == 0` is an invalid API parameter, triggering immediate host device removal (`DXGI_ERROR_INVALID_CALL` / `0x887A0001`).
- On Xbox console hardware (unified memory architecture), a title binding a buffer view with 0 elements legitimately performs a no-op (reads 0 / ignores writes) without hardware faults.

---

### 2. Implementation & Integration Correctness
- In `crates/victory-gpu/src/descriptor/host.rs`:
  - `buffer_srv` & `buffer_uav` early-exit on `buffer.NumElements == 0` with a rate-limited `once!` warning and return `None`.
  - In `HostHeap::make_at` (lines 373–375), receiving `kept == None` for non-sampler heaps immediately routes to `null_for(&view, self.cpu(index))`. This binds a conformant null D3D12 descriptor into the descriptor table slot, satisfying shader access semantics (returning 0 on load) while preserving the host device.

---

### 3. Test Suite & Policy Compliance
- **Test Integrity**: `descriptor::host::tests::buffer_views_of_no_elements_are_null` tests placed views with `elements = 1` (verifying kept descriptor) and `elements = 0` (verifying null slot and asserting `GetDeviceRemovedReason().is_ok()`) across both SRV and UAV bindings.
- **Rule #1 Policy**: Uses pure synthetic descriptor words and registered virtual address ranges (`0x7e00_..._u64`). No game files or external binaries.

Clean, minimal, and fixes a fatal crash at world entry.
