*From a tester working with Claude (AI-assisted); measured on my own machine.*

Pull requests here are limited to collaborators, so I'm offering this as a branch. If it's useful, a collaborator is welcome to open a PR from it:

https://github.com/schmiticle/VIctory/tree/gpu/write-watch-once-per-submission (one commit on `main` ffe310e, `watch.rs` and `host.rs`, merges cleanly)

## The problem

In the world, nested buffers (several views into one 174 MB block at `0x35030000`, among others) each ask `GetWriteWatch` about largely the same pages. In the opening cutscene on an RX 9070 XT, the `copystat` line showed 816-1,811 askings a frame taking 119-179 ms, with over 99% of the bytes checked unchanged. That one block was asked about ~23 times a frame.

## The change

While `Host::execute` prepares a submission, the title's writes that submission must see are already made. So the preparing thread asks the kernel only about pages it has not asked about in that submission (`watch::Sweep`). It still answers from the journal, so a nested buffer sees what the outer asking found. A step that writes title memory during the preparation (`Batch::title_written`) clears what was asked, so later askings see that write. Other threads, and askings outside a submission, are unchanged.

With it, the askings took 31-47 ms a frame. These were local builds with other open PRs stacked, so the numbers are indicative rather than a clean A/B on `main`.

Tests: three new ones in `watch.rs` (interval helpers; a nested range sharing the outer answer; a write by the sweeping thread seen after `title_written`). `cargo test -p victory-gpu --lib`, both clippy configurations from CI, and `cargo xtask policy` pass.

No game data used.

### Comment 8 — @EduAzevedo — 2026-11-24T13:37:22Z

A correction to the last point of my A/B above: after reading `watch.rs`, I don't think the per-frame sweep can be made correct for write-watched memory, so I would not recommend it and I'm not going to write it.

The per-submission sweep is safe because, while a submission is prepared, every title write it must see has already happened (the comment on `Sweep` says so), apart from the preparing thread's own steps, which `title_written` covers. Across submissions that no longer holds: the title's threads keep writing between two `ExecuteCommandLists`, and for write-watched memory the only way to see those writes is to ask the kernel again. A sweep kept for the whole frame would skip that asking and could give the GPU a page the title rewrote after the previous submission, with no error anywhere. Only guarded view memory has its own write signal, and the 174 MB block is not guarded memory.

So the safe room left looks like fewer or cheaper askings inside one submission. On this machine I can measure where the ~2,300 askings a frame come from (range sizes and time per size) if that helps whoever picks it up.
