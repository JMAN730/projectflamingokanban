### Comment 3 — @ljm-233 — 2026-11-24T09:48:33Z

We went at this from the "make the host run it at 1080p" side and ended up with a working 1920x1080 setup — menus at 30 fps, sharp picture, no OOM on an 8 GB card. Sharing the lever and the trap, because @kykifox1337-source's finding is exactly right ("the mode list is not the lever; the title still creates a 3840x2160 window and swap chain") and the "somewhere else" is findable.

**1. The output size is a resolution ladder in the image.**

In our dump (`game_scarlett_master.exe` from the `GTA6.Xbox.v1.0.2.1-CYBERLEEK` files; prepared image hashes to `b99f876b…`) it sits at `.rdata` RVA `0x615c0c0` and is five entries of 16 bytes, `width, height, 60, 1`:

```
1280x720, 1664x936, 1920x1080, 2560x1440, 3840x2160
```

The title takes its window size, swap chain size *and* render-target sizes from this table. Capping every entry above 1920x1080 at 1920x1080 (two entries in our build) makes it create a 1920x1080 window and 1920x1080 render targets, with no `--console series-s`. We locate the table by those five entries rather than by the RVA, so no bytes of the title live in the tree.

**2. Then an assert fires that has nothing to do with resolution.**

Right after the cap, the title hits an `int3` at `+0x247af2d`:

```
mov rax,[rsp+0x78]
sub rax,[rsp+0x70]
add rax,[rva 0x75e6ff0]
cmp rax,0x1fffff
jbe ok
int3
```

It compares a pool ring-buffer offset (`0x2200000` in our run), not a size. Stepping over that one `int3` from a vectored exception handler (`Rip += 1`, `EXCEPTION_CONTINUE_EXECUTION`) is enough to continue. Worth knowing before concluding that a capped ladder "makes the title crash".

**3. The cap alone gives a blurry quarter, not a picture.**

The title lays its picture out for a 2160-tall console: it draws into `frame * (frame height / 2160)`, anchored top-left, and leaves the rest black. At 1920x1080 that picture is the top-left 960x540.

- `CopyResource` of the whole frame (what we did at first) shows it in the corner.
- Letting DXGI scale the whole frame into a smaller window only makes it smaller and blurrier.

What works: make the swap chain the size of the window's **client area** and `CopyTextureRegion` only that top-left corner into it, 1:1. The other three quarters of the presented frame are black, so the crop loses nothing. Two details matter for 1:1:

- create the window at the content size (960x540 client) **at `CreateWindowExW` time** — resizing it afterwards makes the title run its own crash handler and upload a minidump (we have those);
- on a scaled display, make the process per-monitor DPI aware first, or a 960x540 window becomes 1440x810 physical at 150% and the frame is stretched again.

**4. Numbers** (RTX 5060 Laptop 8 GB, 2560x1600 @150%, 32 GB RAM):

| | 4K, uncapped | 1080p capped + cropped |
|---|---|---|
| menus | OOM, TDR; host textures ~8.8 GB | 30.0 fps, ~2.0 GB host textures |
| window | 3840x2160 | 982x596 (960x540 client), swap chain 960x540 |
| world | not reached | 0.1 fps, 280–540 draws/frame, ~6.4–7.0 GB host textures, 172 s up |

The 172 s world run stayed up with no device loss, but its frames were still black and streaming at that point, so that is not evidence about the NVIDIA hang in #71 — only that the 1080p layout itself was stable on 8 GB.

The world remains the expensive part either way: this only makes the host survive the menus and the loading, and gives a sharp picture instead of a stretched one.

One interaction to keep in mind with #211: it reports the title presenting a separate 3840x2160 UI plane. We present only the first plane, so the crop above preserves what the title draws into *that* plane — in our menus the UI was inside it. If a configuration presents the UI in a second plane, compose the planes first and crop the composed frame; the crop is not a substitute for #211.

If a PR is welcome I can send the patching (both patches are byte-pattern searches; nothing is stored by offset). Our patch code lives in a fork's `crates/victory-game`, which upstream currently has as `lib.rs` + `sgd5.rs`, so tell me where such a patch belongs — a `victory run --resolution`/automatic cap, or under `victory-game`.

### Comment 4 — @ljm-233 — 2026-11-24T10:26:03Z

An update: the change behind the comment above is on a branch, ready to become a PR.

- branch: <https://github.com/ljm-233/VIctory/tree/feat/1080p-window> (one commit on top of `main` at `ffe310e`)
- compare / one-click PR: <https://github.com/Marvisak/VIctory/compare/main...ljm-233:feat/1080p-window?expand=1>
- 10 files: opt-in `VICTORY_RESOLUTION=1920x1080`, default behaviour unchanged.

What it does, in one line each:

- caps the five-entry resolution ladder (`crates/victory-game/src/output.rs`, found by byte pattern, no offsets stored);
- steps over the one `int3` of the pool-offset self-check the capped ladder reaches (pattern-found address, `Rip += 1` from the existing vector handler);
- makes the process per-monitor DPI aware, creates the window at the picture's size (`frame height / 2160`, 960x540 at 1080p) and presents only that corner into a swap chain the size of the client, 1:1.

Measured on an 8 GB RTX 5060 Laptop (2560x1600 @150%): menus 30.0 fps and ~2.0 GB of host textures, window 982x596 with a 960x540 client; the world loads and runs 0.1-0.8 fps, and its device removal after 1-2 min is the hang in #71 (the crop is already off by then — the title maximizes its own window for the world).

Checks: `cargo clippy --workspace --all-targets -- -D warnings` and `--all-features` pass; `cargo test --workspace` passes except `load_probe`, which needs the MSVC linker CI has.

Where it should live is still the open question: an environment switch is a first cut, and the mechanical part is ready for `victory run --resolution 1920x1080` or an automatic cap based on available memory. Also, for a configuration that presents the UI in a second plane (#211), the planes have to be composed before cropping.

### Comment 5 — @ljm-233 — 2026-11-24T10:33:21Z

To set expectations about the branch above: **this is an experimental exploration, for reference only — it has many problems and is not something to merge as it is.**

Known problems:

1. **One build, one machine.** Everything is found by byte pattern, but a build without the ladder or without that self-check does nothing useful, and nothing has been verified across builds. The numbers come from a single setup (the `GTA6.Xbox.v1.0.2.1-CYBERLEEK` files; 8 GB RTX 5060 Laptop; 2560x1600 at 150%).
2. **The `int3` step-over is a workaround, not a fix.** It skips a self-check we believe compares a pool ring-buffer offset rather than a size. If that reading is wrong on another build, the skip hides a real assertion.
3. **It does not fix the world.** The GPU device is still removed one to two minutes in (the hang in #71), and in our runs the world frames were black before that. The world's cost is unchanged.
4. **1:1 only lasts while the window is the picture's size.** The title maximizes its own window when the world starts; after that the crop is off and the frame is stretched to the window again.
5. **The sharpness ceiling is 960x540 at this setting.** The title draws only that region of the frame; the rest is black, so a larger window would only magnify it.
6. **Hard-coded console knowledge** (the 2160 frame height, the five ladder entries), and only the first presented plane is cropped — the second UI plane from #211 still has to be composed first.
7. **An environment switch, not a supported option**: process-wide DPI awareness, host-texture totals rather than measured VRAM, and only the GNU toolchain was exercised locally (the `load_probe` test needs the MSVC linker CI has).
8. **The world cannot be checked on WARP either**: that device is removed too, while creating mesh pipelines.

So please take it as notes and code to look at — not as a feature.
