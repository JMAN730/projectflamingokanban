## Original body

# After the start screen: 1841 draws/frame but a frozen frame — captured frames show it is the title's own dark background, not a black screen

**AI-assisted:** yes
**Kind:** frame-capture evidence + the state sequence. No game data.

## Environment

Windows 10 22H2 UBR 3393 (KB5029331) · RTX 4070 SUPER 12 GB · Ryzen 7 7800X3D · VIctory `main`
@ `8e79c80` + #729's two commits (Agility exports, keyboard stand-in) · diag build
(`--profile diag --features diagnostics`) · Agility core 1.620.2 in `diag\D3D12\`.

## The sequence measured

```
account / language screen   ~21-24 draws/frame, UI text renders (verified by eye)
press Enter                 → the title advances
scene load                  ~1155-1841 draws/frame, 1 fps (1366 ms/frame)
after load                  frame content frozen, background music plays
```

## What the captured frames prove

`VICTORY_CAPTURE` + `VICTORY_CAPTURE_FRAMES=600,900,1200`, 1920x1080 PNGs, sampled grid
(80x45 points), top colors:

```
frame-1      100.0% 0xff000000                       initialised frame, genuinely black
frame-256     99.8% 0xff20202C + 4 px 0xffF9F9F9      dark blue-grey + a few white pixels
frame-1200    99.8% 0xff20202C + 4 px 0xffF9F9F9      identical to frame-256
```

Three things follow:

1. It is **not** a black screen. `0x2C2020`-family dark backgrounds are the title's own UI colour;
   this one (`0x20202C`) matches the account screen exactly.
2. The frame is **static from frame 256 to frame 1200** — the picture does not advance while the
   title keeps presenting at 30 fps.
3. Audio is fine (background music plays throughout), so the title's logic is running; it is the
   presented content that stops changing.

## Likely cause on this host

During the same load, 27 pipelines are refused, split as:

```
mesh shader does not translate          → its pipelines' draws dropped
vertex shader does not translate        → its pipelines' draws dropped
compute PSO refused (0x80070057)        → compute pipeline missing
```

A loading screen whose progress text/bar is drawn by one of the dropped shaders would render exactly
this: the clear colour, a couple of surviving UI glyphs, and nothing moving — while the title keeps
presenting and the music keeps playing.

Request: if the loading UI is what stalls, the mesh/vertex translation failures are the thing to
chase (#156, #468 track the same classes), not the presentation path.

## Translation-failure breakdown from the same run (for prioritisation)

Every `shader does not translate` in this run, grouped by the converter's own message:

```
32x  GFX10 code at 0x..: an address in an SGPR that is no root parameter is not supported
 3x  GFX10 code at 0x..: a descriptor read only as data is not supported
 3x  GFX10 code at 0x..: a lane mask read as data is not supported
 3x  GFX10 code at 0x..: a structured buffer of unknown stride is not supported
 3x  GFX10 code at 0x..: a 64-bit image atomic is not supported
 3x  GFX10 code at 0x..: a structured buffer of unknown stride is not supported (other offsets)
 2x  GFX10 code at 0x..: image_gather4_l is not supported
 1x  GFX10 code at 0x..: image_gather4_l is not supported (other offsets)
```

Notes on what each would unlock, from the shader hashes they come from:

- **SGPR indirect address (32x)** — by far the dominant class. These are the shaders whose
  descriptor base is computed into an SGPR instead of arriving as a root parameter. Supporting
  one level of SGPR-indirect descriptor base would clear the largest group at once.
- **descriptor read only as data / lane mask read as data (6x)** — reads a descriptor or EXEC
  value as plain data. Likely a single lowering rule each.
- **structured buffer of unknown stride (6x)** — the stride comes from a register at runtime.
  Needs the DXIL side to carry a dynamic stride (or clamp to a documented set).
- **64-bit image atomic (3x)** — `image_atomic_*` on 64-bit types.
- **image_gather4_l (3x)** — gather with an explicit lod.

Comma-separated hashes are available in the log if useful; nothing game-specific is quoted here.


### Comment 2 — @bittertea0323 — 2026-11-24T11:22:56Z

# Series S mode is the safe way to run this title on a 32 GB machine (memory comparison)

Practical follow-up to #784: on this host, Series X mode drives `victory.exe` to **13.2 GB RSS** and
the machine becomes unusable (a watchdog had to kill it at 13.2 GB; a full system wedge followed).
Series S mode is four times lighter and stays well clear of trouble.

## Measured, same binary (latest `main` + #729 exports), same title

```
                    Series X          Series S
process RSS          13.2 GB           3.4 GB       (~1/4)
system free RAM      near zero         16.9-17.0 GB
fps                  1.5              30.0
draws/frame          up to 2334       8
wedge risk           high             none observed
```

Series S also reaches the video cutscene with the same two texture allocation failures, at 1280-wide
instead of 2560-wide, so it does not sidestep the format problem (#797) — it only removes the memory
hazard.

## Two notes for the record

1. **13.2 GB is the failure threshold on a 31.2 GB box.** With Windows itself plus the browser this
   session used, there is only ~17 GB of headroom, so a title process at 13 GB is one allocation
   spike away from freezing the desktop. Anyone testing the world on 32 GB should use
   `--console series-s` unless they want to lose the machine.
2. **Closing the window while wedged ends the title with "did not finish suspending in time"**, which
   looks like a crash in the log but is the title-routine suspend timing out. Worth wording
   distinctly in the log so testers do not report it as a 0xC0000005.

Host: Windows 10 22H2 UBR 3393, RTX 4070 SUPER 12 GB, Ryzen 7 7800X3D, 31.2 GB RAM.


### Comment 3 — @bittertea0323 — 2026-11-24T11:29:33Z

# Copy-cost diagnosis: write-watch works (0 fallbacks), the cost is page faults, not bulk copying

Follow-up to #784's perf note. I suspected the 130-250 MB/frame copies were a write-watch failure
falling back to whole-buffer copies. **That is not what happens.** Measured with the diagnostics build
(`copies per frame` in the log):

```
copies per frame: 3.0 submissions; 11 title copies 0.0 MB; 12 refreshes 9.4 MB;
                  0 skipped 0.0 MB; 2 runs 0.0 ms; 0 queries 0.00 ms, moves 0.02 ms,
                  0.00 MB unmapped; 8748 page faults;
                  2 watches 0.04 ms, 2.6 MB checked, 2.5 MB unchanged;
                  0.0 fallbacks; 1 guard faults
```

## What this says

1. **`0.0 fallbacks`** — the write-watch/guard path is doing its job; nothing degrades to a whole-copy.
2. **`2.6 MB checked, 2.5 MB unchanged`** — 96% of the watched pages are correctly skipped. The
   mechanism is efficient at the page level.
3. **`8748 page faults`** in one frame (356 in a lighter one) — this is the actual expense. Each fault
   flips page permissions and re-checks; at ~5 us each, 8748 faults ≈ 40 ms before any copying
   happens. In the scene the frame showed `copies 342 ms / 253.6 MB`, which is consistent with the
   fault cost plus genuinely-dirty pages.

## So the optimisation target is not the watcher

The scene's 253.6 MB/frame is **real dirty data** (the title writes that much), and the overhead on
top is the fault storm. Two directions worth measuring, both cheaper than the alternatives:

- **Coalesce faults per submission** — the copy already collects ranges per submission; if the guard
  is flipped page by page, batching the permission changes (or using `VirtualProtect` on the whole
  span once, then hashing the pages) should remove most of the 8748.
- **Per-page dirty bitmap on the host instead of faults** — `shadow.rs` already notes this
  ("a GPU-side dirty mask would save that if big ranges make it slow"). For the scene the ranges are
  big; a single 64 KiB-granular dirty map filled by an upload-side hash may beat 8 k faults.

## Honest limitation

These numbers are the **menu stage** (9.4 MB/frame, ~2-8 k faults). I did not manage to capture
`copies per frame` for the 1841-draw scene in the same run — the scene reaches 253 MB/frame and the
process was stopped for memory safety (13.2 GB RSS, see my #784 note). Anyone with more headroom
should capture the same line during world load; that number decides which of the two directions above
is the right one.

Host: Windows 10 22H2 UBR 3393, RTX 4070 SUPER 12 GB, diag build, Agility 1.620.2.


### Comment 4 — @bittertea0323 — 2026-11-24T11:40:05Z

﻿Correcting my earlier reading with the engine-breakdown numbers. `nvidia-smi` separates "any engine busy"
from the memory controller, and the app's own GPU time tells the same story:

```
t+12s  GPU 11%  memctrl 8%   VRAM  6404 MiB
t+36s  GPU 38%  memctrl 7%   VRAM  6483 MiB
t+72s  GPU 23%  memctrl 2%   VRAM 11262 MiB
```

and per frame at the menu: `30.0 fps, 33.3 ms/frame (... 2.2 on the GPU ...), 12 draws/frame`.

So at the menu the GPU spends **2.2 ms of a 33.3 ms frame (6%)** — it is nearly idle, which is what a
task-manager style view shows as "GPU not working". That is not the problem at this stage.

The problem is the other number: **VRAM reaches 11262 MiB of 12282 MiB (92-95%) while the menu is
still up.** Once it is that full the driver starts evicting, GPU utilisation drops and the frame rate
collapses — which is what makes it look like the GPU stopped.

For contrast, the scene-stage figure measured earlier on this host was `198.4 on the GPU` per frame,
so the GPU is not under-utilised in the world either; it simply cannot keep enough resident.

## What this changes

The ceiling to attack is **residency**, not shading throughput:

- the title asks for more VRAM than a 12 GB card has, before the world is even visible;
- a memory-budget knob (or reporting the budget from `MicrosoftGame.Config`, which the console build
  does have) would let the title trim instead of thrashing;
- until then, on a 12 GB card, missing shaders cost draws and the VRAM ceiling costs frames — two
  separate limits hit at once.
