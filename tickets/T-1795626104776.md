## Original body

**Context / no game data here.** Cross-project note from the `ivall/xcl` side (via the awesome-PC-ports list). Both projects run the **same retail exe** — SHA-256 `e95020b2fa4a721db3df59fdecf75621730ac559d8835252f6c3b658d5a08993`, 120,181,760 bytes — so `game_scarlett_master.exe+0x…` offsets are shared ground truth. Below is what static analysis over there has established; citing sites instead of symptoms will save this repo days.

## 1. The title kills itself, on purpose, in two places
- `+0x23cf683`: `mov dword ptr [0], 0x4d8bd421` — unconditional null store with a **tag value**, on the stall-watchdog's give-up path. When frame presents stop advancing past the escalation window (tens of seconds), the title ends its own process. The tag matches the report routine xref'd at `+0x221396e`.
- `+0x2215c35`: `mov qword ptr [0], 0` — sibling exit, reached via a null-checked callback through the global at `exe+0x71b6348` (bring-up reporter family).

Consequence: any "crash at address 0" report here should first be checked against these two sites. They are **not** corruption — they mean progress stopped. Chase what stopped; don't chase the AV.

## 2. Watchdog timing model (from dumps correlated on the other project)
Stall → reports escalate → kill lands 40–105 s after presents stop, 100% reproducibly, GPU-independent. Builds that keep *trickling* presents stay alive but then consume half-initialized state — the real fix is throughput of pipeline creation (NVIDIA DXC: ~6–9 s per big compute shader was measured on an RTX 5080; warm-cache runs only move the wall, not remove it).

## 3. Crash sites to classify before debugging (day-1 map)
- `+0xb5a5f8` read: zero object from a success-returning factory (callee `+0xb5a5d0`, factory `+0x1819530`) — auth-subsystem uninitialized chain.
- `+0x193e00f` `int3`: the title treats a **failed GPU allocation as fatal** (`test esi,esi; jns; int3`) — this is what kills 8 GB VRAM cards; `E_OUTOFMEMORY` precedes it in logs.
- Cold-run sentinel family (creation paths only): reads at `0x20` / `0x10` / `0xffffffffffffffff` at `+0x5417661`, `+0x4eeaa29`, `+0x53664a8`, `+0x4e32bc5` — consumers that filter only `null` while failure paths write `0`/`-1` sentinels into handle/index tables.
- The exe uses a **custom import call-table** (no RIP-relative refs to the static IAT; 275 `FF 25` thunks into `.rdata` ~`0x6794xxx`) — "symbol X isn't imported" theories read the wrong table; enumerate the table, don't read the IAT.

## 4. On this repo's #619/#625 (device hangs on 8 GB NVIDIA)
Those numbers (`0x887A0006` after entering world, 8 GB cards) match the class behind the `+0x193e00f` mechanism on the other project: allocation failures + TDR, not a translation hang — DRED page data will show the allocation that failed, and the title's response is the `int3`, not a graceful degrade. A spillover/backfill strategy for failed heap allocations is the fix that unblocked the 16 GB cohort there.

Happy to decode specific sites from your side — the exe copy used for analysis is hash-pinned above; no package bytes are hosted or distributed from this issue, per both repos' rules.

Read for the cohort: this is the title screaming that **its static capacity plan was exceeded by the input it was handed** — the trap cannot fire from corruption of the counters alone (it fires from *quantity > free*), so on #175 the frame-82 event means whatever filled that container produced **more records than the container was sized for**.
